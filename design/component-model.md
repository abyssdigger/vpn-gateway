# Компонентно-событийная модель

**Статус:** нормативный переносимый проектный документ  
**Область:** проектирование, декомпозиция и ревью событийных управляющих систем  
**Привязка к VPN-GATE:** отсутствует; конкретные архитектуры проекта могут ссылаться на этот документ

Документ задает небольшой набор архитектурных ролей и правил взаимодействия. Он намеренно
не описывает конкретный продукт, протокол, операционную систему или способ реализации
доставки сообщений.

Основная цель модели — проводить границы ответственности так, чтобы:

- предметные компоненты были слабо связаны;
- управляющая политика не протекала в технические границы;
- синхронные зависимости оставались явными и ацикличными;
- циклы обратной связи замыкались через события;
- внутреннее устройство управляемой подсистемы не становилось частью контракта верхнего
  уровня без необходимости.

## 1. Базовые понятия

### 1.1. Предметная среда

**Предметная среда** — часть внешней по отношению к компоненту реальности, состояние которой
компонент наблюдает или которой управляет.

Граница предметной среды определяется уровнем декомпозиции. Подсистема, являющаяся
самостоятельной событийной системой на нижнем уровне, может выглядеть как единый внешний
ресурс для компонента верхнего уровня.

### 1.2. Event

**Event** — асинхронно распространяемое сообщение между участниками событийной системы.

Event не является синхронным вызовом процедуры и сам по себе не создает канала ответа.
Publisher не вызывает subscriber напрямую и не должен зависеть от времени или способа
обработки сообщения subscriber'ом.

Event имеет одну из двух семантик:

- **InfoEvent** — публикация знания publisher'а о состоянии, результате или наблюдаемом
  факте;
- **RequestEvent** — публикация управляющего намерения: publisher ожидает, что реакция
  заинтересованных участников приведет к изменению внешней среды.

Обе семантики используют один механизм доставки. Различие является смысловым и должно быть
видно в контракте сообщения.

### 1.3. InfoEvent

**InfoEvent** означает:

> Я обязан сообщить, что наблюдаемая мной реальность или мой опубликованный результат
> сейчас имеет такое значение. Мне не требуется знать, кто и как на это отреагирует.

InfoEvent не предполагает обязательного ответа.

Публикация может передавать:

- полный snapshot проекции состояния;
- delta к ранее опубликованной проекции;
- очередное наблюдение в потоке.

Выбранная форма является частью контракта конкретного event type.

### 1.4. RequestEvent

**RequestEvent** означает:

> Я публикую управляющее намерение и ожидаю, что в результате обработки сообщения
> изменится внешняя среда.

RequestEvent не является RPC и не требует непосредственного response.

Subscriber может:

- изменить свою управляемую среду;
- инициировать дальнейшие RequestEvent;
- опубликовать InfoEvent, логически связанный с исходным request;
- не публиковать непосредственного ответа вообще.

Publisher может подтвердить исполнение request не по ответу конкретного subscriber'а, а по
последующим наблюдаемым изменениям интересующей его среды.

Для трассировки и случаев, где это требуется контрактом, сообщения могут содержать
correlation/request identifier. Такая корреляция не должна становиться обязательным
механизмом подтверждения корректности там, где корректность определяется наблюдением
фактической среды.

### 1.5. Publisher и Subscriber

**Publisher** — capability участника публиковать Events.

**Subscriber** — capability участника объявлять интерес к определенным типам или scopes
Events и получать соответствующие публикации от среды доставки.

Publisher и Subscriber не являются самостоятельными типами компонентов. Один компонент
может одновременно обладать обеими capability.

## 2. Event Delivery Environment

**Event Delivery Environment** — абстрактная среда доставки Events от publishers всем
заинтересованным subscribers.

Она отвечает за маршрутизацию согласно заданным subscriptions, но не:

- интерпретирует предметный смысл сообщения;
- принимает policy-решения;
- владеет предметным состоянием;
- определяет реакцию subscriber'а;
- превращает RequestEvent в RPC.

Конкретная реализация может использовать callback, dispatcher, queue, broker, socket,
process-local bus или другой механизм.

Архитектурная семантика событийного канала требует, чтобы publisher не зависел от
непосредственного результата обработки subscriber'ом. Если реализация вызывает handler
inline, она все равно не должна вводить семантическую зависимость от return value,
reentrancy или порядка вложенных вызовов.

Если event edge используется именно для разрыва синхронного dependency cycle, эта граница
должна быть фактически асинхронной: публикация должна завершаться независимо от обработки
subscriber'ом.

## 3. Manager

**Manager** — семантическая оболочка над управляемой предметной средой.

Manager:

1. принимает входные Events, включая управляющие RequestEvent;
2. самостоятельно наблюдает состояние подответственной среды;
3. при необходимости воздействует на нее согласно своей локальной policy;
4. публикует системно значимую проекцию текущего состояния как InfoEvent;
5. скрывает от верхнего уровня внутреннюю механику управления средой.

С точки зрения системы верхнего уровня Manager представляет свою предметную область как
единый ресурс:

```text
input Events
    |
    v
+-----------+
|  Manager  |
+-----------+
    |
    v
InfoEvents describing current managed state
```

Внутри Manager могут существовать polling, retry, hysteresis, state machines, optimization,
control loops, transactional phases и любая иная техника управления. Это является
внутренней реализацией, пока соответствующее историческое состояние не входит в внешний
семантический контракт Manager.

В частности, применение stateful или differential control algorithm внутри Manager не
делает прошлые внутренние состояния частью состояния системы верхнего уровня, если
публикуемая проекция определяется текущим состоянием управляемой среды.

Manager не обязан публиковать отдельный ответ на каждый RequestEvent. Он может наблюдать
реакцию своей среды, в том числе изменения, вызванные другими участниками, и публиковать
только результирующее актуальное состояние.

## 4. Agent

**Agent** — наблюдающий частный случай Manager, не имеющий механизмов управляющего
воздействия на наблюдаемую предметную среду.

Agent:

1. получает внешние triggers или Events;
2. наблюдает свою предметную среду;
3. при необходимости использует Adapters для чтения внешних механизмов;
4. публикует результаты как Events;
5. не изменяет наблюдаемую им предметную среду.

Agent может быть долгоживущим, периодическим или запускаться по RequestEvent. Наличие
таймеров, retry, debounce, hysteresis или иной внутренней stateful логики само по себе не
превращает Agent в другой архитектурный тип.

Различие Manager и Agent определяется не statefulness, а наличием управляющего воздействия
на представленную предметную среду:

```text
Agent   = observe
Manager = observe + actuate
```

Agent может публиковать как InfoEvent, так и RequestEvent. Например, наблюдаемое внешнее
состояние может потребовать от системы начать некоторую управляющую реакцию.

## 5. Adapter

**Adapter** — синхронная техническая граница к конкретному внешнему API, протоколу,
механизму или нижележащей интегрированной подсистеме.

Adapter имеет семантику:

```text
caller -> Adapter -> external mechanism
       <- result  <-
```

Adapter:

- вызывается синхронно;
- возвращает результат вызывающему компоненту;
- не публикует Events самостоятельно;
- не подписывается на Events;
- не принимает предметных policy-решений;
- не представляет собой самостоятельного участника event graph.

Manager и Agent могут использовать Adapters как внутреннюю механику доступа к внешнему
миру.

### 5.1. Adapter как граница декомпозиции

Adapter может скрывать целую нижележащую подсистему. В таком случае эта подсистема может
внутри содержать собственные Managers, Agents, Event Delivery Environment и Adapters, но
для верхнего уровня считается одним интегрированным внешним ресурсом.

Следовательно, конструкция:

```text
Manager A -> BAdapter -> subsystem B
```

допустима только если B действительно рассматривается на этом уровне как нижележащая
подсистема, а не как peer participant.

## 6. Calculator

**Calculator** — чистое преобразование явно переданных данных.

```text
output = f(input)
```

Calculator:

- не является Subscriber;
- не публикует Events;
- не выполняет внешнего I/O;
- не скрывает неявное предметное состояние.

Если вычислению требуется история, она должна быть передана как явный input. Иначе
компонент перестает быть Calculator и его statefulness должна быть рассмотрена на уровне
владельца этой истории.

Calculator обычно является внутренней реализацией Manager или Agent и используется для
отделения policy calculation от наблюдения и воздействия.

## 7. Stateful и stateless processing — свойства, а не роли

Statefulness не задает отдельный тип архитектурного компонента.

Как Agent, так и Manager могут использовать:

```text
memoryless processing:
    y = f(u)

stateful processing:
    x[n+1] = F(x[n], u[n])
    y[n]   = G(x[n], u[n])
```

Вопрос о значимости состояния рассматривается относительно внешнего контракта компонента.

Если внутреннее состояние используется только для управления скрытой предметной средой, а
наружу публикуется достаточная текущая проекция среды, это implementation detail.

Поэтому термин **Engine** не используется в этой модели как отдельная архитектурная роль.
Он не добавляет независимой оси классификации: stateful processing может находиться внутри
Agent или Manager.

## 8. Current state и технологический cache

Хранение последних полученных публикаций не означает наличие семантически значимой памяти
о прошлом.

Компонент может поддерживать:

```text
latest value of projection A
latest value of projection B
latest value of projection C
```

чтобы собрать актуальный snapshot без повторного опроса всей внешней среды.

Такой cache представляет текущий мир и может быть полностью восстановлен свежими
публикациями. Он не является историческим state только потому, что физически хранится между
обработками Events.

Полезный тест:

> Если после перезапуска компоненту достаточно актуальных входных проекций и текущей policy,
> чтобы получить тот же системно значимый результат, потерянный cache не является
> семантической историей.

## 9. Синхронные зависимости и циклы

Event graph может содержать циклы: feedback является нормальной частью управляющей системы.

Синхронный Adapter dependency graph должен быть ацикличным.

Допустимо:

```text
A -> AdapterB -> B -> AdapterC -> C
```

Недопустимо:

```text
A -> AdapterB -> B -> AdapterA -> A
```

Такой цикл означает, что границы владения и уровни декомпозиции определены противоречиво.
Даже если конкретная реализация работает за счет reentrancy, timeout, lock ordering или
случайного порядка вызовов, архитектурная модель не должна на это опираться.

Один из способов развязки — вставить фактически асинхронную event boundary в любое место
цикла:

```text
A -> AdapterB -> B
B -> Event -> A
```

или:

```text
A -> Event -> B
B -> AdapterA -> A
```

Нормативное правило:

> Цикл допустим как цикл причинности, но не как цикл синхронного владения.

В терминах графов:

```text
synchronous Adapter graph -> DAG
event graph               -> cycles allowed
combined graph            -> cycle allowed only when it contains
                             at least one genuinely asynchronous event edge
```

## 10. Правила ответственности

При проектировании и code review следует проверять следующие признаки.

### 10.1. Manager boundary

Признаки утечки ответственности:

- верхний уровень начинает знать внутренние retry/state-machine детали Manager;
- Manager публикует технические операции вместо системно значимого состояния среды;
- peer Manager синхронно вызывается без явного понижения его до интегрированной подсистемы;
- локальная policy Manager начинает принимать решения, относящиеся к другой предметной
  области.

### 10.2. Agent boundary

Признак неправильной классификации Agent — появление управляющего воздействия на ту же
предметную среду, которую он представляет как наблюдатель. В этом случае компонент является
Manager.

### 10.3. Adapter boundary

Признаки неправильного Adapter:

- самопроизвольная публикация Event;
- subscription на Event;
- предметная policy;
- собственный долгоживущий control loop;
- зависимость caller'а от callback/event из той же нижележащей подсистемы, создающая
  синхронный цикл.

### 10.4. Event semantics

InfoEvent не должен маскировать управляющее намерение.

Если publisher ожидает изменения внешней среды как реакции на сообщение, контракт должен
быть RequestEvent, даже если конкретная реализация сообщения выглядит как декларативное
описание desired state.

RequestEvent не должен превращаться в скрытый synchronous request-reply. Подтверждением
результата предпочтительно является наблюдаемое состояние среды, а не факт успешного
выполнения промежуточной операции.

## 11. Иерархическая композиция

Модель применима рекурсивно.

Подсистема может быть событийной системой на одном уровне и единым управляемым ресурсом за
Adapter на другом. При смене уровня декомпозиции необходимо заново определить:

- какие участники являются peers;
- какая предметная среда скрыта за Manager;
- какие зависимости являются synchronous Adapter edges;
- какие взаимодействия остаются Events.

Граница считается корректной, если верхнему уровню не требуется знать внутреннюю топологию
нижней подсистемы для принятия собственных решений.

## 12. Краткая классификация

```text
Manager
    semantic boundary over a managed domain
    observe + actuate
    Events in, Events out
    Adapters inside

Agent
    semantic boundary over an observed domain
    observe only
    Events in/out
    Adapters inside

Adapter
    synchronous technical boundary
    call -> result
    no Events of its own

Calculator
    explicit data -> explicit data
    no I/O, no subscriptions

Event Delivery Environment
    delivery only
    no domain policy

InfoEvent
    "this is what I know/observe"

RequestEvent
    "I expect the environment to change as a consequence"
```
