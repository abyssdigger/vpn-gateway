# VPN Gateway — архитектурные решения и инварианты

**Статус:** принят к реализации
**Версия:** RC3
**Дата:** 2026-11-10

Документ фиксирует принятые архитектурные решения проекта VPN Gateway. Он описывает обязательные инварианты, жизненный цикл сервиса, модель владения состоянием ядра и правила конфигурации. Нереализованные детали, которые еще требуют отдельного решения, вынесены в раздел **«Открытые решения»**.

Нормативная терминология проекта определена в [«Терминах и определениях»](terms-and-definitions.md).

## 1. Назначение

VPN Gateway — локальный IPv4-шлюз, который:

- направляет заданные сети через один или несколько VPN-профилей;
- не зависит от конкретной VPN-реализации;
- применяет собственную фильтрацию `INPUT`/`FORWARD`;
- применяет NAT;
- использует защитные blackhole-маршруты для отказа с запретом;
- отслеживает появление и исчезновение VPN-интерфейсов через Netlink.

Конфигурация может содержать произвольный каталог описанных VPN-профилей. Во время исполнения
daemon отслеживает и обслуживает только профили, перечисленные в поле верхнего уровня
`managed_vpns`. Автоматического failover между профилями нет.

IPv6-маршрутизация проектом не поддерживается.

## 2. Общие принципы

### 2.1. Жесткий отказ

При ошибке очистки, проверки или применения конфигурации сервис не переходит в частично
рабочее состояние.

Ошибка при запуске означает:

- `ip_forward` не включается;
- новая конфигурация не считается примененной;
- процесс завершается с ненулевым кодом;
- systemd переводит сервис в `failed`.

Startup error никогда не маскируется переходом в `DEGRADED`: ошибка очистки,
конфигурации, обязательной проверки или применения приводит к жесткому отказу.

Недоступность VPN path при однозначном binding state не является startup error. Если
fail-closed desired state полностью применено и проверено, daemon может успешно завершить
startup и впервые войти в `RUN` как `DEGRADED`. Таким образом, после успешного startup
первым рабочим состоянием может быть `ACTIVE` или `DEGRADED`; `failed` означает
именно неуспешный startup.

### 2.2. Отказ с запретом

Защищаемый трафик не должен при отказе VPN или ошибке конфигурации уходить через обычный
маршрут по умолчанию.

Blackhole-маршруты являются одним из защитных механизмов и устанавливаются до разрешения
пересылки.

Blackhole обеспечивает отказ с запретом на уровне выбора маршрута для соответствующего
префикса. Он не является универсальной гарантией доставки и не заменяет независимую
фильтрацию `FORWARD`.

### 2.3. Один владелец сетевого состояния

Один долгоживущий процесс `vpn-gatewayd` является единственным владельцем ресурсов
проекта:

- daemon-owned firewall;
- blackhole-маршрутов;
- VPN-маршрутов;
- NAT;
- `net.ipv4.ip_forward`.

IPv6-пересылка не относится к управляемым ресурсам daemon: для него действует отдельное
обязательное условие среды (§2.6).

Внешние скрипты и административные клиенты не должны самостоятельно изменять эти ресурсы.

`vpn-gatewayd` предназначен для выделенного хоста VPN-шлюза. Совмещение с Docker,
Kubernetes, другими сервисами-шлюзами или компонентами, которым требуется
`net.ipv4.ip_forward=1`, не поддерживается.

Эксклюзивное владение глобальным `net.ipv4.ip_forward` и эксклюзивная ответственность за
окончательное решение для всего IPv4-трафика `FORWARD` являются двумя связанными
архитектурными обязательствами daemon. Пока `ip_forward=1`, в **проверенном требуемом
состоянии** каждый пересылаемый IPv4-пакет обязан получить окончательное решение внутри
daemon-owned префикса правил; пакет не должен доходить до сторонних правил или встроенной
политики `FORWARD ACCEPT`.

В проверенном состоянии daemon-owned префикс физически начинается с позиции 1, а сторонние
правила `FORWARD` сохраняются после `VPNG-FORWARD-DENY` и поэтому недостижимы при
включенной пересылке.

Рассогласование daemon-owned firewall/NAT классифицируется по области влияния.

Если подтвержденное рассогласование ограничено только `INPUT`-частью таблицы `filter`,
оно не влияет на транзитный путь `FORWARD` и восстанавливается точечно: daemon одной
транзакцией возвращает свою `INPUT`-политику в требуемое состояние и проверяет результат,
не изменяя `ip_forward`, `FORWARD`, NAT или маршруты.

Рассогласование `FORWARD` или NAT, переход, меняющий политику, а также случай, когда
область рассогласования нельзя достоверно ограничить только `INPUT`, используют
восстановление с первоначальным запретом (§8.6).

До следующего цикла согласования после внешнего изменения существует окно реакции.
Постоянное конкурентное переписывание daemon-owned ресурсов внешним менеджером остается
неподдерживаемой конфигурацией.

После `cleanup()` daemon-owned переходы и цепочки исчезают, а `ip_forward=0`; базовая
фильтрация хоста снова полностью принадлежит администратору.

`net.ipv4.ip_forward` находится под исключительным управлением daemon. Ручное изменение
sysctl не является постоянной административной паузой или переопределением и будет
приведено daemon к требуемому значению на следующем завершенном цикле согласования.

### 2.4. Никакого скрытого fallback на старую конфигурацию

Конфигурация читается только при запуске процесса.

Изменения применяются только через:

```bash
systemctl restart vpn-gateway.service
```

`reload-config` отсутствует.

После изменения файла допустимы только два состояния:

1. сервис успешно запустился с новой конфигурацией;
2. сервис не запустился и находится в `failed`.

Работа на старой конфигурации при уже измененном файле не допускается.

### 2.5. Никаких сторонних Python-зависимостей

Python-реализация использует только:

- стандартную библиотеку Python;
- штатные системные утилиты Debian 13.

Запрещены:

- `pip`;
- PyPI;
- `apt install python3-*` ради дополнительных библиотек.

Python рассматривается как промежуточная реализация; архитектура должна оставаться
пригодной для последующего переноса на Rust.

### 2.6. IPv6-пересылка и IPv6 на управляемых VPN-интерфейсах

VPN Gateway управляет только IPv4 и не строит политику фильтрации или маршрутизации для
IPv6. Поэтому фактическая IPv6-пересылка на хосте должна быть отключена, а IPv6 на
управляемых VPN-интерфейсах — выключен.

Для целевой системы Debian 13 / Linux 6.12 до чтения snapshot интерфейсов daemon обязан
проверить глобальные обязательные условия хоста:

```text
net.ipv6.conf.all.forwarding       = 0
net.ipv6.conf.default.forwarding   = 0
net.ipv6.conf.default.disable_ipv6 = 1
```

Эти значения читаются непосредственно как sysctl и не требуют знания имен интерфейсов.

В Linux 6.12 `net.ipv6.conf.<interface>.forwarding` задает режим
хоста/маршрутизатора интерфейса, но не является независимым разрешением фактической
IPv6-пересылки при `net.ipv6.conf.all.forwarding=0`. Поэтому для целевой системы не
требуется проверять `forwarding` каждого существующего интерфейса.

После чтения snapshot интерфейсов и адресов daemon обязан проверить
`disable_ipv6=1` для **каждого** уже существующего интерфейса, попадающего в защитное
пространство имен хотя бы одного управляемого селектора:

```text
net.ipv6.conf.<interface>.disable_ipv6 = 1
```

Проверяется именно защитное пространство имен, а не только множество active bindings.
Для префиксного селектора проверка охватывает весь textual prefix, закрываемый deny-only
правилом `-i prefix+`; для explicit list — каждое перечисленное exact name. Только после
этой проверки строятся candidates, active bindings и policy.

Значение `default.disable_ipv6=1` обеспечивает выключенный IPv6 для создаваемых позднее
интерфейсов по умолчанию.

Если будущее поддерживаемое ядро предоставляет отдельный механизм для конкретного
интерфейса, который может разрешить фактическую IPv6-пересылку при
`all.forwarding=0` (например, `force_forwarding` или эквивалент), daemon после чтения
snapshot обязан подтвердить, что такие переопределения выключены для всех существующих
совпадающих интерфейсов, а до snapshot — что выключено соответствующее значение по
умолчанию для новых интерфейсов, если ядро его предоставляет.

Daemon не изменяет перечисленные IPv6 sysctl: они являются обязательными условиями
конфигурации выделенного доверенного хоста. Несоответствие при запуске является фатальной
ошибкой до любых действий, которые могут разрешить IPv4-пересылку.

Все перечисленные IPv6-условия должны сохраняться и во время `RUN`. Каждый полный
reconciliation pass после свежей interface inventory и **до построения allowing policy**
повторно проверяет глобальные IPv6 prerequisites и `disable_ipv6=1` для всех текущих
interfaces guard namespaces.

Нарушение во время `RUN` является host-prerequisite breach: daemon не исправляет IPv6
sysctl, не продолжает ordinary materialization, best-effort выключает IPv4 forwarding и
применяет config-derived isolation filter, если состояние filter читаемо, после чего
остается `ISOLATED` с high-severity diagnostic до исправления хоста и restart.

`ISOLATED` при этом описывает только управляемое daemon IPv4-состояние и **не является
гарантией IPv6 protection**, потому что daemon не владеет IPv6 firewall/forwarding.
Оператор обязан устранить prerequisite violation; автоматическое возвращение в
`ACTIVE` после такого нарушения без restart не поддерживается.

## 3. Процессная модель

Основной компонент:

```text
vpn-gatewayd
```

Это постоянно работающий процесс под управлением systemd.

Он:

- читает и проверяет конфигурацию;
- хранит разобранную конфигурацию в памяти;
- отслеживает состояние VPN-интерфейсов управляемых профилей;
- применяет фильтрацию;
- применяет blackhole-маршруты;
- применяет VPN-маршруты;
- применяет NAT;
- управляет пересылкой IPv4;
- выполняет полную очистку своих ресурсов при запуске и штатном завершении.

Отдельный событийный `vpn-monitor` после перехода на эту архитектуру не требуется.

Daemon пишет обычные текстовые сообщения в `stderr`; при запуске под systemd они попадают
в journal. Структурированное логирование/JSON не требуется.


## 4. Мониторинг VPN-интерфейсов и привязки во время исполнения

Для мониторинга используется Linux Netlink через стандартный Python `socket`:

```text
AF_NETLINK
NETLINK_ROUTE
```

Сервис реагирует как минимум на `RTM_NEWLINK`, `RTM_DELLINK`, `RTM_NEWADDR` и
`RTM_DELADDR`. При запуске daemon выполняет полный snapshot интерфейсов и адресов.
Netlink-событие является только сигналом к reconciliation; решение всегда выводится из
заново прочитанного полного snapshot. При `ENOBUFS` и периодически по
`reconcile_interval` выполняется полная пересверка.

### 4.1. Формы селектора и защитное пространство имен

Поле `interface` задает selector union из трех форм:

```text
"wg0"                    -> точный селектор
"vpns+"                  -> префиксный множественный селектор
["vpnA","vpnB","vpnC"]   -> явный упорядоченный список точных имен
```

Селектор определяет:

1. множество candidate runtime-интерфейсов;
2. защитное пространство имен для deny-only firewall guard;
3. форму назначения метрик UNICAST-маршрутам.

Нормативная семантика:

| Форма | Candidates | Защитный guard | Семантика метрик |
|---|---|---|---|
| exact `name` | только `name` | exact `name` | единственный active interface получает metric 10 |
| `prefix+` | все имена с началом `prefix`, включая exact `prefix` | `-i prefix+` | уникальные технические metrics выделяются динамически; приоритет между interfaces не гарантируется |
| explicit list | перечисленные exact names | exact guard каждого имени | порядок элементов конфигурации задает стабильный route preference |

Завершающий `+` использует подтвержденную EXP-005 textual-prefix семантику iptables.
Оператор `%` больше не является частью конфигурационной грамматики RC3.

Ни строка селектора, ни массив имен не используются как разрешающее условие
`ACCEPT`, NAT или route. Разрешающие ресурсы всегда содержат только exact interface
name текущей active concrete binding.

### 4.2. Инвентаризация интерфейсов

Один snapshot интерфейсов сохраняет как минимум:

```text
name
ifindex
IPv4 local addresses
```

Point-to-point remote endpoint может присутствовать в данных iproute2 и сохраняться для
диагностики, но **не участвует** в selector resolution, route derivation или
transport-peer association. EXP-009 показал, что transport peer не является
универсальной route-next-hop abstraction для VPN-GATE.

Идентичность concrete binding:

```text
ConcreteBinding = exact name + ifindex
```

Повторное создание того же имени с новым ifindex является новой binding.

Если один inventory содержит одно exact name с несовместимыми ifindex, inventory
некорректна и весь reconciliation pass не выбирает одну запись произвольно.

### 4.3. Candidates и active concrete bindings

Candidate определяется только формой селектора:

- exact — существующий interface с указанным именем;
- `prefix+` — все существующие interfaces с textual prefix;
- explicit list — существующие interfaces, чьи exact names перечислены в списке.

Candidate становится **active concrete binding**, только если на нем присутствует хотя бы
один local IPv4 address, принадлежащий `profile.network`.

Несколько candidates/active bindings для `prefix+` и explicit list являются штатным
состоянием. Понятие selector `AMBIGUOUS` для этого больше не требуется.

Candidate без local IPv4 address из `profile.network`:

- остается видимым в status;
- не получает exact `ACCEPT`, NAT или `proto 202` route;
- остается закрыт guard-правилом селектора.

Точный селектор естественно дает 0 или 1 candidate. Для explicit list route preference
определяется позицией exact name в конфигурации. Для `prefix+` приоритет между active
interfaces архитектура не задает.

`operstate`, `LOWER_UP`, ping, handshake и transport-specific peer state не являются
источником binding truth.

Для детерминированного построения и сравнения binding-specific policy используется
нормативный `active_order`:

- exact — единственный active interface;
- `prefix+` — process-local порядок первого принятия active binding текущим daemon;
- explicit list — config order, отфильтрованный до currently active elements.

Для `prefix+` непрерывно active binding сохраняет свою позицию. Новая binding
добавляется в конец, исчезнувшая удаляется без перестановки остальных. Если несколько
новых bindings впервые обнаружены в одном snapshot и их взаимный порядок наблюдать уже
невозможно, только эта новая группа упорядочивается case-sensitive bytewise ASCII перед
добавлением.

`active_order` используется для INPUT/FORWARD exact blocks, `VPNG-INGRESS`, NAT,
status output и обхода новых prefix-bindings при выделении метрик. Поэтому появление
нового prefix-interface не меняет относительный порядок существующих exact blocks/rules
в требуемой policy. Protective-barrier restore при этом по-прежнему может транзакционно
пересобрать daemon-owned chain целиком.

Для `prefix+` этот порядок не является гарантией route preference. Он также не является
персистентной историей создания interfaces: после restart daemon строит новый process-local
order из первого доступного snapshot. Во время непрерывной работы порядок полезен
диагностически как порядок первого принятия bindings daemon'ом.

### 4.4. Materialization маршрутов по active binding set

Для каждого protected destination всегда существует config-derived `BLACKHOLE`.

Для каждого active concrete binding также materialize direct UNICAST route **без
transport next-hop**:

```text
destination = profile.route
via         = None
interface   = active_binding.name
proto       = 202
onlink      = false
```

Для всех daemon-owned UNICAST действует общий инвариант:

```text
0 < metric < BLACKHOLE_METRIC
BLACKHOLE_METRIC = 65536
ROUTE_METRIC_STEP = 10
FIRST_UNICAST_METRIC = 10
```

Тем самым любой требуемый UNICAST-маршрут имеет меньшую metric, чем защитный BLACKHOLE.

Exact:

```text
единственный active interface -> metric 10
```

Explicit list:

```text
interface[0] -> FIRST_UNICAST_METRIC
interface[N] -> FIRST_UNICAST_METRIC + N * ROUTE_METRIC_STEP
при текущих constants: 10,20,30...

```

Отсутствующий элемент списка не сдвигает metric следующих элементов. Конфигурация
недопустима, если metric любого slot будет `>= BLACKHOLE_METRIC`.

Для `prefix+` metric является техническим уникальным идентификатором одновременного
UNICAST-маршрута, а не гарантированным приоритетом interface.

Daemon хранит только во время жизни процесса подтвержденное распределение:

```text
ConcreteBinding(name, ifindex) -> metric
next_metric_cursor
```

Правила allocator:

1. непрерывно active binding сохраняет выделенную metric;
2. исчезнувшая binding освобождает metric после успешной фиксации нового состояния;
3. новая binding получает следующее свободное значение начиная с `next_metric_cursor`;
4. рассматриваются только значения `FIRST_UNICAST_METRIC + N * ROUTE_METRIC_STEP`,
   строго меньшие `BLACKHOLE_METRIC`;
5. при достижении верхней границы поиск циклически продолжается с
   `FIRST_UNICAST_METRIC`;
6. уже занятая metric пропускается; немедленное заполнение более ранней «дырки» не
   требуется;
7. если полный цикл не нашел свободного значения, распределение метрик завершается
   ошибкой;
8. новая binding с тем же именем, но новым `ifindex`, не имеет гарантии наследования
   прежней metric и проходит обычное allocation; случайное получение того же свободного
   численного значения допустимо;
9. после restart распределение начинается заново и прежние metrics не гарантируются.

Порядок перечисления `RouteSpec` не является частью desired route semantics. Route
reconciliation сравнивает маршруты по их полной идентичности/множеству; изменение
порядка сериализации или обхода само по себе не является drift и не должно вызывать
удаление, повторное добавление или переназначение metric существующего desired route.

Если в одном snapshot одновременно появились несколько новых prefix-bindings, только
эта новая группа сортируется case-sensitive bytewise ASCII перед добавлением в конец
текущего prefix active_order и распределением metrics. Уже принятые bindings не
переставляются. Это не превращает ASCII-порядок имен в обещанный route preference.

Предварительно рассчитанное распределение и новый cursor входят в snapshot согласования,
но process-local allocator state фиксируется только после успешной проверки полного
требуемого состояния. При неуспешном применении/verification прежнее подтвержденное
распределение и cursor не изменяются.

EXP-009 подтвердил:

- исчезновение concrete interface автоматически удаляет зависимый route;
- возвращение interface само route не восстанавливает;
- reconciliation обязан rematerialize current desired direct route;
- Linux metric участвует в выборе предпочтительного существующего route, но не является
  end-to-end health-check; для explicit list VPN-GATE гарантирует configured priority, а
  для `prefix+` относительный preference interfaces не является контрактом;
- OpenConnect path работает с direct `dev vpns00 proto 202 metric 10` без `via`;
- WireGuard peer selection внутри `wg0` принадлежит самому transport и не должна
  моделироваться Linux next-hop внутри VPN-GATE.

### 4.5. Смена привязок и остаточное окно реакции

Изменение candidate set всегда будит reconciliation и отражается в status.

**Переходом, меняющим политику**, является как минимум:

- появление или исчезновение active concrete binding;
- замена `name + ifindex` active binding;
- добавление/удаление local IPv4, меняющее принадлежность candidate к `profile.network`
  и тем самым active set;
- изменение metric, назначенной существующей active binding, если такое изменение
  вообще требуется корректирующим согласованием.

При таком переходе daemon по возможности сначала приводит `ip_forward=0`, затем
применяет и проверяет firewall/NAT, routes и только после завершенной проверки возвращает
forwarding.

Появление matching candidate без local IPv4 из `profile.network` само по себе не
открывает разрешающий path: guard уже существует из config, а binding-specific resources
для candidate отсутствуют.

Для `prefix+` guard использует `-i prefix+`. Для explicit list guard содержит
отдельное exact deny-правило каждого имени. Exact active blocks выполняются раньше guard.
Prefix matching разрешен только в deny-only guard rules и никогда не используется для
`ACCEPT`, NAT или route.

Между kernel event и reconciliation существует остаточное окно реакции. Если событие
потеряно, периодический цикл остается резервным механизмом.

Граница модели угроз остается прежней: недоверенные локальные процессы не имеют
`CAP_NET_ADMIN`; жизненным циклом interfaces управляют доверенное VPN-ПО, ядро и
администратор. ifindex позволяет обнаружить повторное создание имени, но iptables rule по
имени не может быть задним числом привязано к историческому ifindex.

## 5. Жизненный цикл сервиса

### 5.1. Запуск

Базовая модель:

```text
START
  ↓
LOCK
  ↓
CLEANUP
  ↓
LOAD + VALIDATE CONFIG
  ↓
APPLY
  ↓
RUN
```

Любая ошибка до перехода в `RUN` является фатальной.

### 5.2. Runtime-каталог и блокировка экземпляра

Runtime-каталог по умолчанию:

```text
/run/vpn-gateway
```

Файл блокировки, удерживаемой в течение всего времени жизни процесса, по умолчанию:

```text
/run/vpn-gateway/vpn-gatewayd.lock
```

Перед открытием файла блокировки daemon безопасно создает при необходимости и проверяет
runtime-каталог:

- последний компонент пути не должен быть символической ссылкой;
- существующий объект обязан быть каталогом;
- режим доступа обязан быть `0700`;
- владелец обязан совпадать с ожидаемой учетной записью сервиса для текущего способа
  развертывания;
- если каталог отсутствует и процесс имеет право его создать, он создается с режимом
  `0700`;
- неправильные владелец или режим существующего каталога не исправляются молча через
  `chmod`/`chown`, а считаются фатальной ошибкой.

При текущем запуске от root ожидаемый владелец — UID 0. При будущем запуске systemd от
отдельного служебного пользователя ожидается владелец, соответствующий этой учетной записи.

Файл блокировки открывается с `O_NOFOLLOW`, режимом `0600`; daemon удерживает эксклюзивную
блокировку `flock` в течение всего времени жизни процесса, а попытка ее получения выполняется
без ожидания. Занятая блокировка
диагностируется отдельной ошибкой о том, что другой экземпляр уже запущен.

Отдельный настраиваемый общий путь блокировки не вводится без реального сценария
одновременного запуска нескольких экземпляров.

### 5.3. Штатное завершение и сигналы

Обработчики сигналов `SIGTERM`/`SIGINT` устанавливаются **до первой фазы запуска**.
Обработчик не выполняет операций с ядром и только устанавливает признак завершения.

Во время `STARTING` этот признак проверяется на границах фаз:

```text
установить обработчики сигналов
  ↓
LOCK
  ↓ контрольная точка
CLEANUP
  ↓ контрольная точка
LOAD + VALIDATE CONFIG
  ↓ контрольная точка
APPLY
  ↓ контрольная точка
RUN
```

Если сигнал пришел до получения блокировки экземпляра, процесс выходит без очистки: он
еще не владеет ресурсами шлюза.

Если сигнал пришел после получения блокировки:

- завершить текущую ограниченную по времени фазу;
- на ближайшей границе не начинать следующую;
- если завершенная фаза могла создать состояние в ядре (`APPLY`), выполнить
  универсальную `cleanup()`;
- если после уже успешной начальной `cleanup()` запуск еще не создавал состояние в ядре,
  дополнительная очистка не обязательна;
- выйти без перехода в `RUN`.

Критическая контрольная точка существует после успешного `APPLY` и **до перехода в `RUN`**.
Если используется `Type=notify`, она также находится до отправки `READY=1`: сигнал в окне
после `ip_forward=1` не должен оставлять управляемую daemon'ом пересылку без очистки.

После входа в `RUN`:

```text
SIGTERM/SIGINT
 ↓
признак завершения + пробуждение сериализованного цикла обработки событий
 ↓
CLEANUP
 ↓
EXIT
```

Для пробуждения блокирующего цикла обработки событий обработчик сигнала использует
`signal.set_wakeup_fd()` или эквивалент self-pipe, чтобы штатное завершение не ожидало
периодического тайм-аута.

`SIGHUP` игнорируется: перезагрузка конфигурации архитектурой не предусмотрена, журнал
пишется в `stderr`/systemd journal, а повторное открытие файлов по HUP не требуется.

Если финальная `cleanup()` не смогла подтвердить полную очистку, процесс завершается с
ошибкой.

Для развертывания под systemd предпочтителен `Type=notify` с `WatchdogSec`, если
реализация поддерживает `sd_notify`. Это не меняет семантику жизненного цикла: `READY=1`
может отправляться только после успешного `APPLY` и прохождения последней контрольной точки,
а сторожевой таймер подтверждает живость сериализованного цикла обработки событий.

### 5.4. Рекомендации по развертыванию

Рекомендуемая конфигурация systemd:

```text
RuntimeDirectory=vpn-gateway
RuntimeDirectoryMode=0700
Restart=on-failure
RestartSec=<bounded delay>
StartLimitIntervalSec=<bounded window>
StartLimitBurst=<bounded count>
ExecStopPost=<страховочное отключение ip_forward>
```

`RuntimeDirectory` остается предпочтительным способом развертывания и особенно важен при
будущей работе не от root. Но корректность автономного daemon не зависит от systemd: если
процесс имеет право создать runtime-каталог, он делает это сам и затем применяет ту же
проверку безопасности.

`ExecStopPost` является вторичным механизмом отказа с запретом на случай `SIGKILL`,
тайм-аута сторожевого таймера или аварии процесса, когда Python-очистка физически не выполнилась.
Ошибка этого страховочного механизма не заменяет очистку daemon и не маскируется как
успешная очистка.

Развертывание не должно постоянно задавать `net.ipv4.ip_forward=1` через `sysctl.d`.
Во время исполнения этим sysctl управляет `vpn-gatewayd`.

Другие средства управления фильтрацией могут иметь собственные правила `INPUT`/`OUTPUT`
и физически сохраняемые правила `FORWARD`, но пока daemon включает пересылку, его
окончательный префикс `FORWARD` имеет приоритет. Конфигурация, в которой внешний сервис
постоянно переписывает пространство имен `VPNG-*` или переходы daemon-owned префикса,
не поддерживается.

Архитектура не требует `geteuid()==0`. Предпочтительно сохранить возможность работы от
отдельного служебного пользователя с минимальным набором Linux capabilities и файловых разрешений, если
практическое развертывание подтвердит их достаточность. Контракт безопасности конфигурации
и путей остается под контролем root.

## 6. Универсальная очистка

`cleanup()` не зависит от текущей конфигурации и от состояния daemon, сохраняемого между запусками. Она используется
перед загрузкой конфигурации при запуске, после аварийного предыдущего запуска и при
штатном завершении.

Успешная очистка означает отсутствие всех ресурсов VPN Gateway, определяемых по маркерам
владения, и `ip_forward=0`.

### 6.1. Маркеры владения

Принятые маркеры:

```text
blackhole routes -> proto 201 + type BLACKHOLE + metric 65536
VPN routes       -> proto 202
iptables chains  -> reserved namespace VPNG-*
owned jumps      -> jumps с target VPNG-*
```

Префикс `VPNG-` целиком зарезервирован daemon'ом в используемых таблицах iptables.

### 6.2. Инвентаризация маршрутов для очистки

Не зависящая от конфигурации очистка **не читает полный snapshot основной таблицы
маршрутизации**.

Для поиска маршрутов по маркерам владения используются выборочные запросы:

```text
ip -j -N -4 route show table main proto 202
ip -j -N -4 route show table main proto 201
```

EXP-004.5 подтвердил, что такие запросы не затрагивают несвязанные сторонние
multipath-маршруты.

При запросе с фильтром по протоколу iproute2 может не печатать поле `protocol`; адаптер
назначает известный протокол из контекста запроса. Для `proto 201` очистка дополнительно
требует `type=BLACKHOLE` и `metric=65536`.

Строгая полная `list_routes()` сохраняется для обычного согласования и по-прежнему
считает ошибкой непредставимые формы multipath/nhid, а не пропускает их молча.

### 6.3. Порядок очистки

1. по схеме «прочитать перед записью» привести `ip_forward` к 0 и **подтвердить**
   результат;
2. только после подтвержденного `ip_forward=0` выполнить выборочную инвентаризацию и
   удалить `proto 202`;
3. прочитать состояние firewall/NAT и удалить daemon-owned переходы/цепочки точным
   набором правил очистки;
4. только после успешной очистки firewall/NAT снова выполнить выборочную инвентаризацию и
   удалить daemon-owned маршруты `proto 201 type BLACKHOLE metric 65536`;
5. новая выборочная инвентаризация маршрутов и фильтрации должна подтвердить полную чистоту.

Подтвержденное `ip_forward=0` является защитным барьером очистки. Если daemon не смог
привести значение к 0 или подтвердить его чтением, очистка немедленно завершается ошибкой и
**не переходит к разрушительным операциям** над фильтрацией, NAT или маршрутами. Сохранение
старой запрещающей политики и blackhole в этом случае безопаснее частичного демонтажа при
возможно продолжающейся пересылке.

EXP-004.4 подтвердил используемую транзакцию очистки отдельно для каждой таблицы на
Debian 13 / iptables-nft 1.8.11: повторяющиеся `-D`, затем `-F/-X`, один `COMMIT`.
Ошибка удаления цепочки не оставляет частично примененную транзакцию таблицы на
проверенной реализации.

### 6.4. Результаты очистки

**Успех**

- `ip_forward=0`;
- нет `proto 202`;
- нет daemon-owned `proto 201 BLACKHOLE metric 65536`;
- нет цепочек/переходов `VPNG-*`.

**Ошибка**

Полная очистка не подтверждена. Запуск не продолжается. Если не подтверждено
`ip_forward=0`, дальнейший демонтаж ресурсов вообще не выполняется. Blackhole-маршруты не
снимаются, если очистка остальных daemon-owned ресурсов не подтверждена.

### 6.5. Никаких слепых полных очисток

Запрещено:

- очищать целиком таблицу маршрутизации;
- очищать целиком таблицу `filter` или `nat`;
- удалять сторонние маршруты вне области точных защищаемых префиксов, за которые отвечает
  daemon;
- удалять сторонние правила фильтрации, не являющиеся daemon-owned переходом в
  `VPNG-*`.

Точные защищаемые префиксы остаются отдельной областью ответственности daemon при обычном
согласовании; универсальная очистка этим исключением не пользуется.

## 7. Загрузка и проверка конфигурации

### 7.1. Проекция конфигурации для исполнения

После успешной `cleanup()` daemon разбирает TOML-документ и строит проекцию конфигурации для исполнения,
содержащую только профили из `managed_vpns`.

На обычный запуск влияют:

1. синтаксическая корректность TOML;
2. схема верхнего уровня конфигурации для исполнения
   (`managed_vpns`, `common_allowed_sources`, `reconcile_interval`);
3. возможность однозначно разрешить каждую ссылку из `managed_vpns` к
   `[vpn.<profile>]`;
4. полная проверка схемы, значений и семантики только выбранных управляемых описаний
   профилей;
5. конфликты, зависящие от выбора, только внутри набора управляемых профилей.

Тела неуправляемых `[vpn.*]` не создают состояния во время исполнения и **не проходят проверку значений
и схемы при обычном запуске**. Ошибочный IP, отсутствующее поле, неизвестный ключ профиля
или иной дефект неуправляемого описания не должен останавливать работающий шлюз.

Это сознательно разделяет:

```text
TOML-документ + выбор управляемых профилей
        ↓
проверенная проекция конфигурации управляемых профилей для исполнения
```

`VpnGatewayDaemon` получает только проверенную проекцию конфигурации управляемых профилей для исполнения.

### 7.2. Проверка вне запуска: `--check-config`

`--check-config` дополнительно анализирует весь каталог описаний профилей.

Для набора управляемых профилей он выдает те же `ERROR`, которые сделали бы обычный
запуск невалидным.

Для неуправляемых описаний и конфликтов, возникающих только при их возможной будущей
совместной активации, он выдает `WARNING`, например:

- некорректное значение поля;
- отсутствующее или неизвестное поле профиля;
- некорректный идентификатор профиля;
- конфликт интерфейсов;
- пересечение маршрутов;
- пересечение `routes` с `vpn.network`;
- неоднозначные без учета регистра описания профилей;
- безвредные точные дубликаты в списках с семантикой множества.

Наличие только `WARNING` не меняет код завершения 0.

`NOTE` используется для валидных, но операционно значимых состояний конфигурации,
которые полезно явно показать оператору. `NOTE` не меняет код завершения 0. Текущая
RC3 schema не имеет обязательного NOTE, завязанного на transport peer list.

### 7.3. Критерии введения ограничений конфигурации

Новое правило проверки конфигурации во время исполнения должно иметь явную цель:

1. проекцию конфигурации для исполнения невозможно однозначно построить;
2. состояние управляемых ресурсов во время исполнения становится неоднозначным или небезопасным.

Потенциальная проблема только неуправляемого описания профиля относится к проверке вне
запуска, а не к ошибке запуска.

Безвредная избыточность входных данных с семантикой множества не является фатальной
ошибкой и нормализуется: например, дубликаты в `managed_vpns`, точные дубликаты
`routes` одного управляемого профиля и дубликаты ACL.

Explicit interface list является упорядоченным списком, а не множеством: duplicate exact
name запрещен, потому что одна concrete interface не может занимать два route-priority
slot.

Отдельной фазы `preflight()` нет. Проверки безопасности, зависящие от состояния ядра,
входят в построение и проверку начального плана согласования. В частности,
`_validate_plan()` запрещает удаление `proto kernel`; точный защищаемый префикс,
совпадающий с подключенным маршрутом `proto kernel` хоста, приводит к ошибке, блокирующей
запуск до любых побочных изменений маршрутов.

## 8. Применение и согласование во время исполнения

Запуск и исполнение используют одну модель политики и привязки, но различаются обработкой
ошибок: при запуске действует жесткий отказ, а в `RUN` daemon может переходить в
`DEGRADED` или `ISOLATED`.


### 8.1. Неизменяемый snapshot согласования

Каждый завершенный цикл использует одну неизменяемую интерпретацию одной свежей
инвентаризации:

```text
ReconciliationSnapshot
    interfaces
    selector_candidates_by_profile
    active_bindings_by_profile
    prefix_metric_allocations_by_profile
    prefix_metric_cursor_by_profile
    desired_routes_by_profile
    desired_full_policy
```

Point-to-point remote endpoints и transport peer state не являются входом route
derivation.

Из snapshot daemon один раз строит full desired firewall/NAT policy и routes. Candidates,
active bindings, предварительное распределение prefix metrics и desired state не
пересчитываются между построением, применением и проверкой одного цикла. Snapshot не означает атомарность kernel operations; он
гарантирует внутреннюю согласованность оркестрации.

### 8.2. Применение при запуске

После успешной очистки и проверки конфигурации:

1. проверить глобальные IPv6 prerequisites §2.6;
2. прочитать один interface/address snapshot;
3. проверить `disable_ipv6=1` на всех существующих interfaces защитных пространств
   имен управляемых селекторов;
4. построить candidates и active concrete bindings по membership local IPv4 в
   `profile.network`, а для `prefix+` также provisional metric allocation/cursor;
5. построить full desired firewall/NAT policy;
6. применить и проверить `filter`, затем `nat`;
7. прочитать строгий route snapshot, построить и проверить route plan;
8. materialize BLACKHOLE и direct `proto 202 dev <exact-interface>` routes;
9. повторно проверить exact protected-prefix route state;
10. подтвердить verification result для desired fail-closed state;
11. сформировать functional `ProfileResult` поверх verified state;
12. зафиксировать OWNED routes, active binding state и prefix allocator mapping/cursor
    после verification независимо от availability SUCCESS/FAIL;
13. установить и повторно подтвердить `ip_forward=1`;
14. перейти в `RUN`.

Отсутствие active concrete binding не является startup error само по себе. Если
fail-closed desired policy и route state полностью применены и проверены, профиль получает
`FAIL` по availability, daemon успешно завершает startup и входит в `RUN/DEGRADED`.

Ошибка inventory, config, firewall/NAT apply/verification, route apply/verification либо
невозможность финально подтвердить `ip_forward=1` остается hard startup failure.
Zero-path `ProfileResult=FAIL` после successful BLACKHOLE-only/direct-route verification
**не является route verification failure** и не превращается в startup error.

На обычном startup forwarding изначально выключен, поэтому первоначальное применение
`filter -> nat -> routes` безопасно без дополнительного runtime barrier.

### 8.3. Требуемые маршруты

Для каждого `profile.route` требуется BLACKHOLE:

```text
destination = profile.route
type        = BLACKHOLE
via         = None
interface   = None
proto       = 201
metric      = 65536
onlink      = false
```

Для каждого active concrete binding требуется direct UNICAST:

```text
destination = profile.route
type        = UNICAST
via         = None
interface   = exact active interface
proto       = 202
metric      = selector/list-derived or allocated prefix metric
onlink      = false
```

Metric rules определены в §4.4 и §18.

BLACKHOLE выводится только из config и существует независимо от availability. UNICAST
выводится только из active binding set текущего snapshot. Transport peer address,
point-to-point remote endpoint, handshake и route next-hop в desired model не входят.

Ни одна форма селектора не попадает в `RouteSpec.interface`; там разрешено только exact
runtime interface name.

### 8.4. Согласование во время исполнения

Каждый цикл согласования сериализован единым event loop и запускается Netlink wakeup,
периодическим таймером, полной пересверкой либо административной командой.

#### Ошибка инвентаризации интерфейсов

Без достоверной inventory daemon не может вычислить binding-specific policy/routes.
Ошибка чтения или разбора interface inventory переводит pass в `ISOLATED`: daemon
пытается выключить forwarding и может применить config-derived isolation filter, но не
угадывает active interfaces.

#### Ошибка построения snapshot / предметной проекции

Если после успешной inventory невозможно построить полный `ReconciliationSnapshot`,
частичное desired state не используется. Это относится в том числе к исчерпанию всех
допустимых prefix metric slots.

Во время `RUN` daemon best-effort выключает forwarding, может применить выводимый только
из config isolation filter и переходит в `ISOLATED`. Provisional allocator mapping/cursor
не commit-ятся. При startup такая ошибка является hard startup failure до открытия
разрешающего пути.

#### Обычный цикл

После успешной inventory:

1. повторно проверить global/per-interface IPv6 prerequisites §2.6 для current guard
   namespaces; violation -> host-prerequisite isolation path без allowing apply;
2. построить один immutable `ReconciliationSnapshot`, включая provisional prefix
   metric allocation/cursor;
3. сравнить candidates и active concrete binding identities с последним verified state;
4. при policy-changing transition по возможности привести `ip_forward=0`;
5. прочитать firewall/NAT и классифицировать `SAFE/UNSAFE/UNKNOWN`;
6. `UNKNOWN` либо неопределимая область drift -> `ISOLATED`;
7. INPUT-only `UNSAFE` без policy transition -> narrow INPUT repair;
8. FORWARD/NAT `UNSAFE` либо policy transition -> protective barrier §8.6;
9. после `SAFE` полной policy прочитать strict route snapshot;
10. построить, проверить, применить и повторно проверить route plan из того же snapshot;
11. materialize отсутствующие direct routes для всех active bindings;
12. зафиксировать OWNED, active binding state и prefix allocator mapping/cursor только
    после successful verification;
13. в завершенном non-ISOLATED `RUN` привести `ip_forward` к 1 и reread;
14. confirmed `ip_forward=0` после failed enable -> `DEGRADED`; unreadable
    `ip_forward` -> `ISOLATED`.

Candidate-only change без изменения active set не требует тяжелого IPv4 barrier **только
после successful IPv6 prerequisite verification текущего guard namespace**. После этой
проверки allowing IPv4 policy действительно не меняется; status обновляется из нового
snapshot.

### 8.5. Частичная доступность множественного селектора

Для `prefix+` и explicit list несколько active concrete bindings являются нормальным
состоянием. Daemon не требует наличия всех потенциальных или перечисленных paths, чтобы
профиль был `SUCCESS`.

Если active bindings остались хотя бы в количестве одного и required routes/policy
успешно применены и verified, profile остается `SUCCESS`.

Если active binding отсутствует полностью:

- binding-specific exact `ACCEPT`/NAT отсутствуют;
- direct `proto 202` routes отсутствуют;
- selector guards, protected-destination `REJECT` и BLACKHOLE сохраняются;
- после успешной verification profile = `FAIL`;
- при global `SAFE` policy daemon = `DEGRADED`, а не `ISOLATED`.

Понятие runtime selector ambiguity в новой модели не используется: multiplicity является
свойством supported selector forms, а exact interface name в Linux уникально. Конфликт
между managed selector namespaces является config error, а некорректная inventory с одним
именем и разными ifindex — error уровня reconciliation pass.

### 8.6. Состояние безопасности firewall и восстановление с первоначальным запретом

Состояние firewall/NAT использует именованные значения:

```text
SAFE     -> безопасно
UNSAFE   -> небезопасно
UNKNOWN  -> состояние неизвестно
```

Полное ожидаемое состояние зависит от неизменяемого `ReconciliationSnapshot`.

Отдельно слой политики обязан уметь построить **изолирующий фильтр**, выводимый только из
конфигурации:

```text
desired_isolation_filter(config)
```

Он не содержит правил `ACCEPT`, зависящих от привязки, и не требует инвентаризации
интерфейсов. Он сохраняет только структурную политику фильтрации с отказом с запретом:

- запрещающие правила `INPUT` управляемых селекторов;
- запрещающие правила входящего `FORWARD`-трафика управляемых селекторов;
- `REJECT` транспортных сетей VPN;
- безусловные `REJECT` защищаемых назначений;
- окончательный `VPNG-FORWARD-DENY`;
- необходимые структурные цепочки и переходы.

Состояние `UNKNOWN` никогда не восстанавливается вслепую. Daemon по возможности выключает
пересылку и остается в `ISOLATED`.

Подтвержденное рассогласование, ограниченное только `INPUT`, имеет отдельный узкий путь
восстановления. Daemon одной транзакцией таблицы `filter`:

1. восстанавливает содержимое daemon-owned профильных `INPUT`-цепочек и
   `VPNG-INPUT-GUARD`, если они изменены;
2. удаляет и заново вставляет только принадлежащие daemon переходы из встроенной
   `INPUT`, возвращая daemon-owned префикс на позицию 1;
3. сохраняет сторонние правила и цепочки;
4. повторно читает таблицу и проверяет требуемую `INPUT`-политику.

Payload этой транзакции намеренно ограничен daemon-owned `INPUT`-цепочками и операциями
с переходами из встроенной `INPUT`. Он **не содержит** объявлений, правил или операций с
daemon-owned `FORWARD`-цепочками и переходами из встроенной `FORWARD`.

На этом пути `ip_forward` не изменяется, изолирующий фильтр не применяется,
`FORWARD`, NAT и маршруты не перестраиваются. Причина: `INPUT` определяет доступ к
локальным сервисам самого хоста и не участвует в транзитном пути. Выключение пересылки не
устраняет угрозу от раннего стороннего `INPUT ACCEPT`, а только без необходимости
прерывает транзит.

Если точечное восстановление `INPUT` не удалось применить или проверить, daemon больше
не имеет подтвержденного безопасного полного состояния firewall и переходит к обычному
fail-closed пути `ISOLATED`; неуспешное точечное восстановление не считается успешной
оптимизацией.

Для `UNSAFE`, затрагивающего `FORWARD` или NAT, для неопределенной области
рассогласования либо для перехода, меняющего политику, применяется последовательность с
первоначальным запретом:

```text
1. по возможности ip_forward=0

2. применить изолирующий фильтр как полное требуемое daemon-owned состояние таблицы `filter`
   для этой промежуточной стадии; все устаревшие ACCEPT, зависящие от привязки,
   для всех профилей должны быть удалены
3. проверить изолирующий фильтр
   - эта проверка подтверждает только защитный барьер
   - она НЕ означает SAFE полной политики

4. применить требуемый NAT для текущего неизменяемого snapshot
5. проверить требуемый NAT

6. применить полный требуемый filter с точными ACCEPT, зависящими от привязки
7. проверить полный требуемый filter
   - только после проверки NAT + полного `filter` состояние firewall/NAT может быть `SAFE`

8. согласовать и проверить маршруты

9. только после полной успешной проверки:
       включить/подтвердить пересылку согласно требуемому состоянию
```

Изолирующий фильтр применяется как **полное** принадлежащее daemon состояние таблицы `filter` на
промежуточной стадии. Поэтому на время защитного барьера разрешающие правила всех
управляемых профилей временно отсутствуют и вся управляемая пересылка запрещена, включая
профили, чья привязка не менялась. Сохранение разрешающих правил «незатронутых» профилей
не является допустимой оптимизацией этого протокола восстановления.

Это относится также к `ESTABLISHED,RELATED`-трафику, входящему с управляемых
VPN-интерфейсов: на стадии изоляции точные разрешающие блоки отсутствуют, а защитные правила селекторов
выдают запрет. Поэтому административная сессия к самому шлюзу, проходящая через
управляемый VPN-интерфейс, на время защитного барьера теряет прохождение пакетов и может
оборваться либо восстановиться после барьера в зависимости от длительности и поведения
транспортного протокола. Непрерывный административный доступ во время восстановления не
должен зависеть только от управляемого VPN-пути.

Применение изолирующего фильтра не изменяет таблицу `nat`. Ранее примененные правила NAT
могут временно оставаться в ядре за уже проверенным запрещающим барьером до шага 4, где
требуемый NAT для текущего snapshot применяется и проверяется. Наличие старого NAT за
проверенным фильтрующим барьером само по себе не открывает путь пересылки.

Этот порядок обязателен даже если `set_ip_forward(False)` завершился ошибкой. Благодаря
этому полный `ACCEPT` для `FORWARD` не появляется раньше проверенного NAT.

Если изолирующий фильтр не удалось применить или проверить, daemon остается в `ISOLATED`
и не переходит к NAT, полному фильтру и маршрутам.

Простая глобальная перестановка `nat -> filter` запрещена: при уже небезопасном или
разрешающем фильтре она оставила бы разрешенную пересылку активной дольше. Защитным
барьером является именно фильтр с первоначальным запретом.

Если пересылка подтверждена выключенной, реализация может оптимизировать технические детали
транзакций только при сохранении той же наблюдаемой семантики безопасности.

### 8.7. Исполнитель маршрутов

Порядок изменений маршрутов сохраняется:

```text
1. добавить отсутствующие BLACKHOLE
2. удалить конкурирующие точные маршруты
3. выполнить определяющие замены
4. добавить оставшиеся маршруты
```

Проверка плана маршрутов сохраняет определяющую семантику точного префикса и запрет
изменения `proto kernel`.


### 8.8. OWNED и фиксация binding state

Process-local OWNED routes, последнее подтвержденное состояние active concrete bindings
и prefix allocator mapping/cursor изменяются только после завершенной успешной проверки
соответствующего цикла.

**Verification success и `ProfileResult` — разные оси.** Если fail-closed desired state
полностью verified, active binding state текущего snapshot фиксируется даже когда functional availability
дает `ProfileResult=FAIL` из-за zero UNICAST paths. Иначе
валидный `RUN/DEGRADED` создавал бы ложный policy transition на каждом periodic pass.

Порядок запуска и policy-changing reconciliation:

```text
проверить routes/policy
-> зафиксировать OWNED + active binding state + prefix allocator state
-> включить и подтвердить ip_forward
```

Фиксация после включения forwarding запрещена.

### 8.9. Состояние жизненного цикла

```text
недостаточная наблюдаемость interfaces/policy/ip_forward -> ISOLATED
firewall/NAT != SAFE                                     -> ISOLATED

firewall/NAT == SAFE
  И все managed profiles SUCCESS
  И ip_forward == 1                                      -> ACTIVE

firewall/NAT == SAFE
  И остальные проверки завершены
  И (
       хотя бы один profile FAIL
       ИЛИ confirmed ip_forward == 0
    )                                                    -> DEGRADED
```

Profile result формируется после проверки full desired firewall/NAT policy и route state.

`SUCCESS` требует:

1. binding-specific contribution full policy применен и verified;
2. exact protected-prefix route state полностью совпадает с desired;
3. для каждого `profile.route` существует как минимум один verified desired UNICAST
   path через active concrete interface;
4. BLACKHOLE и остальные required resources соответствуют desired state.

У множественного selector не требуется присутствие всех paths. Один verified active
interface для каждого protected destination достаточен для `SUCCESS`.

`FAIL` означает либо verified availability loss (нет ни одного desired UNICAST path
хотя бы для одного protected destination), либо profile-level route/policy mismatch,
который удалось достоверно классифицировать при сохраненном fail-closed state.

Ошибка наблюдаемости уровня всего pass не превращается в набор `FAIL`; она приводит к
`ISOLATED`.

`ACTIVE` и `ProfileResult=SUCCESS` подтверждают desired kernel configuration, но не
end-to-end transport reachability. Ping, handshake и transport peer health не входят в
этот статус.

Операционный status профиля сообщает как минимум:

- `ProfileResult=SUCCESS|FAIL` и стабильную reason code при `FAIL`;
- selector form;
- candidates;
- active concrete bindings;
- desired/verified direct `UNICAST RouteSpec` с interface/metric;
- для explicit list — configured order;
- для prefix — process-local active_order и текущие binding -> metric allocations;
  порядок route priority не обещается; active_order может использоваться как
  диагностический порядок первого принятия bindings текущим daemon.

Ручной `sysctl -w net.ipv4.ip_forward=0` не является административной паузой; чистый
reconciliation возвращает daemon-owned desired value.

## 9. Фильтрация и blackhole

Политика сетевых правил (firewall и NAT) daemon-owned ресурсов состоит из структурной части и части, зависящей
от привязки.

Структурная часть существует для всех управляемых профилей независимо от текущего binding state:

- зарезервированные цепочки `VPNG-*`;
- детерминированный префикс переходов из встроенных цепочек;
- `VPNG-RESERVED`;
- окончательные запреты защищаемых назначений в цепочках профилей;
- `VPNG-INPUT-GUARD`;
- `VPNG-FORWARD-DENY`.

Часть, зависящая от привязок, строится только для active concrete interfaces и
однозначных active bindings текущего snapshot.

### 9.1. Порядок переходов из встроенных цепочек

Профили во всех daemon-owned префиксах сортируются лексикографически по нормализованному
идентификатору профиля в верхнем регистре, по ASCII-коду символов. Порядок не зависит от
локали и должен совпадать в Python- и Rust-реализациях.

`INPUT`:

```text
1..N   -> VPNG-<PROFILE>-INPUT, в порядке профилей
N+1    -> VPNG-INPUT-GUARD
далее  -> сторонние правила INPUT
```

`FORWARD` в проверенном требуемом состоянии:

```text
1      -> VPNG-INGRESS
2      -> VPNG-RESERVED
3..    -> VPNG-<PROFILE>-FORWARD, в порядке профилей
last   -> VPNG-FORWARD-DENY
далее  -> сторонние правила FORWARD
```

`POSTROUTING`:

```text
1..N   -> VPNG-<PROFILE>-NAT, в порядке профилей
далее  -> сторонние правила
```

В проверенном требуемом состоянии daemon-owned префикс физически начинается с позиции 1
во всех трех встроенных цепочках.

Стороннее правило перед daemon-owned префиксом `INPUT` является подтвержденным
`INPUT`-рассогласованием и восстанавливается точечно по §8.6: правило не удаляется, а
после перестановки оказывается после `VPNG-INPUT-GUARD`.

Стороннее правило перед daemon-owned префиксом `FORWARD` или `POSTROUTING` является
транзитным рассогласованием `UNSAFE` и использует восстановление с первоначальным
запретом. Для `FORWARD` строгий префикс сохраняет полное владение решением через
`VPNG-FORWARD-DENY`; для `POSTROUTING` гарантирует обработку daemon-owned NAT раньше
сторонних преобразований.

Каждая NAT-цепочка профиля при несовпадении возвращает управление через `RETURN`.
Поэтому сторонние правила `POSTROUTING` после daemon-owned префикса сохраняются и
остаются достижимыми для неуправляемого исходящего трафика.

`OUTPUT` не входит в область управления VPN Gateway: daemon не создает, не изменяет, не
переставляет и не удаляет правила этой цепочки. Политика `OUTPUT` принадлежит
администратору хоста.

Следствие: локально созданный на самом шлюзе трафик не проходит ACL источников
`FORWARD` и может использовать установленные защищаемые маршруты. Это сознательная часть
модели доверенного выделенного хоста; ограничение локального `OUTPUT` остается
ответственностью администратора.

Каждый daemon-переход существует ровно один раз и использует обычный `-j`.


### 9.2. Семантика INPUT

Цепочка `INPUT` профиля содержит точный блок для каждого уникального active concrete
interface:

```text
-i <точный-интерфейс>
ctstate INVALID
    DROP

-i <точный-интерфейс>
ctstate ESTABLISHED,RELATED
    ACCEPT

-i <точный-интерфейс>
    REJECT --reject-with icmp-host-prohibited
```

Exact blocks идут в нормативном `active_order` §4.3. Для `prefix+` в требуемой policy
block новой binding располагается после уже принятых bindings и не меняет относительный
порядок существующих blocks. Транзакционное применение полной цепочки не считается
изменением этого логического порядка. После всех exact blocks цепочка возвращает
управление через `RETURN`.

Таким образом, удаленная сторона VPN не может инициировать новое соединение с самим
шлюзом через active managed interface. Разрешен только ответный
`ESTABLISHED,RELATED` traffic на соединения, инициированные локально самим хостом.

После цепочек профилей `VPNG-INPUT-GUARD` блокирует входящий traffic защитных пространств
имен, который не был завершен более ранним exact block:

- exact selector — exact interface rule;
- `prefix+` — `-i prefix+`;
- explicit exact list — exact deny rule для каждого элемента.

Prefix matching никогда не используется для `ACCEPT` или NAT.

Traffic вне защитных пространств имен после daemon-owned INPUT prefix продолжает
обрабатываться обычной host firewall policy.

### 9.3. Семантика FORWARD

`VPNG-INGRESS` сначала содержит exact block для каждого уникального active concrete
interface в нормативном `active_order` §4.3. Для `prefix+` добавление новой binding не
меняет относительный порядок уже существующих blocks:

```text
-i <точный-интерфейс>
ctstate INVALID
    DROP

-i <точный-интерфейс>
ctstate ESTABLISHED,RELATED
    ACCEPT

-i <точный-интерфейс>
    REJECT --reject-with icmp-host-prohibited
```

После exact blocks идут deny guards всех managed selectors в детерминированном порядке
профилей. Для `prefix+` guard использует `-i prefix+`; explicit exact list
materialize как набор exact guards. Затем следует `RETURN`.

`VPNG-RESERVED` всегда выполняет `REJECT` для назначения в любую managed
`vpn.network`.

Цепочка `FORWARD` профиля для каждого protected destination обходит active egress
interfaces в нормативном `active_order` §4.3 и для каждого содержит:

```text
-d route -o <точный-интерфейс> ctstate INVALID
    DROP

для каждого effective_source:
    -s source -d route -o <точный-интерфейс>
        ACCEPT
```

После всех active egress interfaces для данного protected destination всегда идет:

```text
-d route
    REJECT --reject-with icmp-host-prohibited
```

Отсутствие `-i` в разрешающем правиле профиля не предоставляет обратный доступ через
managed VPN interfaces: incoming traffic уже обязан завершиться внутри `VPNG-INGRESS`.

После всех профильных chains `VPNG-FORWARD-DENY` сохраняет полное владение решением
`FORWARD`:

```text
ctstate INVALID
    DROP

все остальное
    REJECT --reject-with icmp-host-prohibited
```

В проверенном состоянии ни один пересылаемый IPv4 packet при daemon-owned
`ip_forward=1` не достигает сторонних FORWARD rules или builtin policy.

### 9.4. Fail2ban

Поддерживаемая интеграция Fail2ban относится только к обычной политике хоста в `INPUT`
после daemon-owned префикса.

Daemon не распознает Fail2ban по именам цепочек и не анализирует рекурсивно семантику
сторонних правил. Если Fail2ban или другой firewall хоста вставляет правило перед
daemon-owned `INPUT`-префиксом, следующий цикл согласования точечно возвращает префикс
на позицию 1 без изменения `ip_forward` и транзитной политики. Стороннее правило
сохраняется после `VPNG-INPUT-GUARD`.

Для трафика вне управляемых VPN-интерфейсов профильные `VPNG-*` цепочки возвращают
управление, поэтому последующие правила Fail2ban продолжают работать как обычная политика
хоста.

Fail2ban для входящего трафика управляемых VPN-интерфейсов сознательно не поддерживается;
это ничего не стоит текущей однонаправленной модели, в которой новый `INPUT` с
управляемой VPN-стороны все равно запрещен. Если будущая двунаправленная модель потребует
фильтрации разрешенного `NEW` трафика с управляемых VPN-интерфейсов, для нее должна быть
спроектирована явная точка интеграции и при необходимости специализированный action, а не
анализ произвольного стороннего firewall.

Произвольные actions, изменяющие `FORWARD`, `POSTROUTING` или daemon-owned
`VPNG-*`, не получают специальной совместимости с Fail2ban и оцениваются по общим
инвариантам соответствующей области.

### 9.5. Blackhole

Blackhole-маршруты устанавливаются для всех защищаемых маршрутов управляемых профилей:

```text
proto 201
metric 65536
type blackhole
```

Blackhole не зависит от текущего binding state и наличия UNICAST path.

EXP-004.2 подтвердил: при исчезновении зависящего от интерфейса `proto 202` UNICAST
blackhole остается и не дает защищаемому назначению уйти через маршрут по умолчанию.

Blackhole не заменяет фильтрацию: полная политика `FORWARD` остается независимым слоем
отказа с запретом.

## 10. VPN-маршруты

Все VPN-маршруты daemon имеют:

```text
proto 202
```

Это обязательный ownership marker для cleanup после crash/restart/config change.

VPN UNICAST route является **direct interface route**:

```text
destination <prefix>
dev <exact-active-interface>
metric <selector-derived>
proto 202
```

`via` и `onlink` для daemon-owned UNICAST не используются. Transport peer selection
находится за границей VPN-GATE.

Очистка удаляет только принадлежащие сервису routes `proto 202`.

## 11. NAT

Для каждого управляемого профиля существует структурная цепочка:

```text
VPNG-<PROFILE>-NAT
```

и детерминированный переход из `POSTROUTING`.

Для каждого уникального active egress interface профиля в нормативном `active_order`
§4.3 создается:

```text
-o <точный-интерфейс>
-m addrtype ! --src-type LOCAL
-j MASQUERADE
```

После всех таких правил цепочка содержит `RETURN`.

Если active egress interfaces отсутствуют, цепочка содержит только `RETURN`.

Ни explicit-list selector, ни строка `prefix+` никогда не используются как условие
интерфейса в NAT.

При переходе, меняющем политику, daemon отключает пересылку до повторного применения и
проверки binding-specific firewall/NAT. NAT должен быть проверен до добавления или
восстановления `proto 202` routes через новые exact interface names.

Сторонние правила `POSTROUTING` не удаляются. Если профильная NAT-chain не совпала с
traffic, ее `RETURN` передает обработку последующим сторонним правилам.

Сохраняется зависимость безопасности:

```text
active bindings определены
-> точная filter/NAT policy применена и проверена
-> routes применены
-> forwarding включен/восстановлен
```

Сторонний route через managed exact interface не обходит daemon policy, потому что полное
владение `FORWARD` разрешает outgoing traffic только явным профильным `ACCEPT`.

### 11.1. Окно реакции на событие

Разрешающий NAT нельзя materialize из selector template: он создается только для active
exact interfaces текущего snapshot.

Между kernel event и reconciliation остается ограниченное окно реакции (§4.5). До
reconciliation новый candidate interface не получает `proto 202` route или exact
разрешающее правило `FORWARD`; blackhole, selector guard и окончательный FORWARD deny
сохраняют отказ с запретом.

Быстрое повторное использование прежнего exact name остается гонкой в границах модели
доверенного хоста и обнаруживается по изменению ifindex на ближайшем Netlink event или
полной пересверке.

## 12. Конфигурация

Конфигурационный файл по умолчанию:

```text
/etc/vpn-gateway/vpn-gateway.toml
```

Формат — TOML. Файл и его родительский каталог принадлежат `root`, не writable для
group/other; последний компонент файла не symlink. Эти security requirements проверяются
как startup, так и `--check-config`.

Пример:

```toml
reconcile_interval = 10.0

managed_vpns = ["primary", "backup"]

common_allowed_sources = [
    "10.200.200.8",
    "10.200.200.9",
]

[vpn.primary]
interface = "vpns+"
network = "172.20.130.0/29"
routes = ["10.0.0.0/8"]
allowed_sources = ["10.200.201.0/24"]

[vpn.backup]
interface = "wg0"
network = "172.20.126.0/29"
routes = [
    "100.64.0.0/10",
    "192.168.0.0/16",
]
allowed_sources = []
```

Explicit ordered multi-interface profile:

```toml
[vpn.explicit]
interface = ["vpnA", "vpnB", "vpnC"]
network = "172.20.140.0/29"
routes = ["172.21.0.0/16"]
allowed_sources = []
```

Каждая `[vpn.<profile>]` является описанием профиля. Только `managed_vpns` выбирает
profiles, которыми daemon управляет. Порядок `managed_vpns` приоритета не задает.

Transport-specific peer configuration в VPN-GATE отсутствует. WireGuard `AllowedIPs`,
OpenConnect session identity и аналогичные transport details принадлежат самому VPN
transport и настраиваются вне `vpn-gatewayd`.

## 13. Закрытая схема конфигурации

Неизвестные top-level keys являются fatal startup error. Ошибки profile schema/value
фатальны только для managed profile; для unmanaged описаний они выдаются как `WARNING`
в `--check-config`.

```text
reconcile_interval          float, optional, default 10.0, range [1.0, 60.0]
managed_vpns                array[string], required, non-empty
common_allowed_sources      array[string], required

[vpn.<profile>]
interface                   string | array[string], required; exact / prefix+ / ordered exact list
network                     string, required
routes                      array[string], required
allowed_sources             array[string], required
```

Ключи `peers` и `local_address` больше не входят в RC3 schema и являются unknown
profile keys. Селектор `prefix%` больше не поддерживается и является invalid interface
selector.

Profile id:

```text
[A-Za-z][A-Za-z0-9_-]{0,14}
```

Имена profiles уникальны case-insensitively. `managed_vpns` должен после нормализации
быть непустым; его exact/case-insensitive duplicates нормализуются как set-like input, а
`--check-config` сообщает warning.

Daemon-owned chain names:

```text
VPNG-<PROFILE>-INPUT
VPNG-<PROFILE>-FORWARD
VPNG-<PROFILE>-NAT
```

Profile-name length 15 сохраняет longest chain name короче iptables-nft limit.

Unknown key внутри managed profile фатален. Неожиданная nested TOML structure обрабатывается
по тем же managed/unmanaged projection rules §7.

## 14. Пустые списки и количество профилей

Для managed configuration:

```text
managed_vpns = []               -> запрещено
profile.routes = []             -> запрещено
common_allowed_sources = []     -> разрешено
profile.allowed_sources = []    -> разрешено
interface = []                  -> запрещено
```

Отдельный лимит общего количества profiles не требуется. Для explicit interface list
число элементов ограничивается валидностью имен и тем, что каждая вычисляемая
`FIRST_UNICAST_METRIC + index*ROUTE_METRIC_STEP` UNICAST metric строго меньше `BLACKHOLE_METRIC`;
это проверяется config validator.
Для prefix selector runtime active count проверяется отдельно при desired-route derivation.

## 15. Селекторы интерфейсов

`interface` имеет тип:

```text
string | array[string]
```

Поддерживаются только exact string, trailing-`+` prefix и непустой ordered exact list.

### 15.1. Точный селектор

Exact name:

```text
[A-Za-z][A-Za-z0-9_.-]{0,14}
```

Case-insensitive forbidden names:

```text
lo
any
default
all
```

Exact selector имеет не более одного candidate. При наличии хотя бы одного local IPv4 из
`profile.network` candidate становится active и получает metric 10.

### 15.2. Префиксный селектор `+`

Форма:

```text
<prefix>+
```

Prefix начинается с ASCII letter, использует exact-name grammar и имеет длину 1..14.
`+` допустим только последним символом.

Candidates — все interface names, начинающиеся с prefix, включая exact `prefix`.
Несколько candidates/active bindings являются штатным состоянием.

Deny-only guard использует проверенную EXP-005 форму:

```text
-i prefix+
```

Active exact names идут в нормативном `active_order` §4.3. Для `prefix+`
непрерывно active bindings сохраняют относительный порядок первого принятия текущим
daemon, новые bindings добавляются в конец, а case-sensitive bytewise ASCII используется
только как tie-break внутри группы новых bindings, впервые обнаруженных в одном snapshot.
Этот порядок используется при построении policy/status и при обходе новых bindings
allocator'ом, но не задает гарантированный route preference. Уже существующие
firewall/NAT rules и UNICAST routes не переставляются, не пересоздаются и не получают
новые metrics только ради канонизации порядка; metrics prefix-bindings выделяются по
правилам §4.4.

### 15.3. Явный упорядоченный список точных имен

Пример:

```toml
interface = ["vpnA", "vpnB", "vpnC"]
```

Список непустой, каждый элемент валиден как exact name, duplicates запрещены.

Порядок **имеет нормативную семантику route preference**:

```text
vpnA -> metric 10
vpnB -> metric 20
vpnC -> metric 30
```

Если `vpnB` отсутствует, `vpnC` сохраняет metric 30. Для каждого элемента
существует exact deny guard.

### 15.4. Конфликты защитных пространств имен

Managed selectors попарно не пересекаются по guard namespace.

Fatal examples:

```text
vpns+                  + vpns0
vpns+                  + ["vpns9","tun0"]
["tun-a","tun-b"]     + tun-a
["vpnA","vpnB"]       + ["vpnB","vpnC"]
```

Non-overlap examples:

```text
vpnsA+ + vpnsB+
wg0    + ["tun-a","tun-b"]
```

Если два managed selectors могут охватить одно exact interface name, runtime projection
invalid. Conflict только с unmanaged description не блокирует startup и диагностируется
`--check-config`.

Оператор `%` запрещен; wildcard/glob/regex кроме завершающего `+` не поддерживаются.

## 16. VPN-сети и адреса

Для каждого profile:

- `network` — canonical IPv4 CIDR transport address space;
- `/32` запрещен, минимально допустима `/31`;
- selector namespaces managed profiles не пересекаются;
- protected `routes` не пересекаются с managed `network`.

`network` имеет две связанные функции:

1. structural fail-closed protection, включая `VPNG-RESERVED`;
2. transport-agnostic interface applicability predicate.

Matching candidate считается active concrete binding, если в его kernel inventory есть
хотя бы один local IPv4 address, принадлежащий `profile.network`.

Проверяется **host IPv4 membership**, а не фактическая prefix length адреса на interface.
P2P/tunnel transport может представить local endpoint как /32 даже при более широкой
логической `profile.network`; это не делает candidate inactive.

Конкретный host address внутри transport network является ответственностью transport
configuration и отдельно в VPN-GATE не задается.

Remote point-to-point address, peer address и handshake в config отсутствуют и не
участвуют в active binding resolution.

Адрес сети и broadcast address не объявляются отдельно запрещенными для tunnel semantics;
валидность конкретного transport addressing остается ответственностью transport config.

## 17. ACL источников

ACL имеет два уровня:

```text
common_allowed_sources
vpn.<profile>.allowed_sources
```

Оба списка разрешают:

- одиночный IPv4;
- IPv4 CIDR.

Одиночный адрес внутри модели нормализуется в `/32`.

CIDR должен быть каноническим сетевым префиксом. Неканонический CIDR, например
`10.200.200.8/24`, является ошибкой и не нормализуется молча в более широкую сеть.

Списки ACL имеют семантику множества: точные дубликаты после нормализации удаляются.
`--check-config` сообщает их как предупреждение; ошибка во время исполнения не требуется, потому что
политика от дубликата не меняется.

Пересечения разрешены. Например, допустимо одновременно иметь:

```text
10.200.200.8/32
10.200.200.9/32
10.200.200.0/24
```

Эффективный ACL конкретного VPN-профиля:

```text
effective_allowed_sources(profile)
    = common_allowed_sources
      ∪ profile.allowed_sources
```

Профильный ACL только расширяет общий. Отрицательных правил, исключений и семантики
запрета нет.

Эта семантика намеренно отличается от `routes`: ACL является набором разрешающих
предикатов, а не описанием маршрутного пространства.


## 18. Маршруты защищаемых сетей

Managed protected routes:

- только canonical IPv4 CIDR;
- `0.0.0.0/0` запрещен;
- `routes=[]` запрещен;
- exact duplicates внутри profile нормализуются;
- нетождественные overlaps/nesting внутри и между managed profiles запрещены;
- один exact protected prefix принадлежит одному managed profile;
- overlap с любой managed `vpn.network` запрещен.

Для каждого protected destination daemon всегда требует BLACKHOLE proto 201 metric 65536.

UNICAST proto 202 создается как direct route на каждый active concrete interface.

Metric contract:

```text
для всех UNICAST:
    0 < metric < BLACKHOLE_METRIC

exact:
    active interface -> 10

prefix+:
    unique metric from cyclic process-local allocator
    continuous binding keeps its metric
    route preference between interfaces is not guaranteed

explicit ordered list:
    config index N
    -> FIRST_UNICAST_METRIC + N * ROUTE_METRIC_STEP
    при текущих constants -> 10,20,30...
    absent list element не сдвигает следующие metrics
```

Для exact и explicit list диапазон проверяется при config validation; любой вычисляемый
UNICAST metric обязан быть строго меньше `BLACKHOLE_METRIC`.

Для `prefix+` capacity определяется текущими `BLACKHOLE_METRIC`,
`FIRST_UNICAST_METRIC` и `ROUTE_METRIC_STEP`. При значениях 65536/10/10 доступны
6553 одновременных metric slots. Это не архитектурный предел: изменение констант может
расширить пространство без изменения модели allocator.

Allocator не перенумеровывает непрерывно active bindings при появлении/исчезновении
соседних interfaces. Освобожденные slots могут быть использованы после циклического
возврата cursor. Исчерпание всех допустимых slots является ошибкой построения требуемого
маршрутного состояния: на startup это hard failure, во время исполнения daemon не
открывает новый путь и использует обычный fail-closed/isolation path.

Metric сама по себе не является health-check и для `prefix+` не является обещанием
семантического приоритета между interfaces.

EXP-009 подтвердил interface lifecycle, direct OpenConnect route без `via` и отсутствие
health-aware failover только по metric. Transport-specific peer health не входит в route
truth.

## 19. Состояние VPN и сетевых правил

Structural guards и BLACKHOLE не зависят от transport connectivity.

Binding-specific resources строятся только из active concrete interfaces текущего
snapshot:

- exact `INPUT`/`FORWARD` rules;
- exact `MASQUERADE`;
- direct `UNICAST proto 202 dev <exact-interface>`.

Для multiple selector временная потеря части active interfaces удаляет только их
contribution. Остальные paths продолжают быть desired и после safe reconciliation
профиль может оставаться `SUCCESS`.

Изменение candidate set отражается в status. Изменение active binding identity/set либо
изменение metric уже существующей active binding является policy-changing transition.
Обычное добавление новой prefix-binding получает новую свободную metric без
перенумерации существующих bindings.

Transport peer inventory, handshake, remote endpoint reachability и internal transport
routing не входят в VPN-GATE state model.

## 20. Проверка конфигурации без запуска

Сервис обязан поддерживать режим:

```bash
vpn-gatewayd --check-config
```

Он:

- читает TOML;
- проверяет права и владельца конфигурационного файла;
- проверяет закрытую схему;
- выполняет ту же проверку конфигурации для исполнения для `managed_vpns`;
- отдельно проверяет схему, значения и семантику неуправляемых описаний, а также их
  потенциальные перекрестные конфликты;
- агрегирует доступные `ERROR`, `WARNING` и `NOTE` за один прогон;
- не получает блокировку экземпляра;
- не изменяет маршруты;
- не изменяет iptables;
- не изменяет `ip_forward`;
- не выполняет `cleanup()`;
- завершается с кодом 0, если нет `ERROR`; наличие только `WARNING` код не меняет.
  При `ERROR` код ненулевой.

`--check-config` читает файл без синхронизации с работающим сервисом. Для согласованного
административного обновления конфигурация должна публиковаться атомарной заменой готового
файла (`rename`/`mv` из временного файла).

Рекомендуемый административный порядок:

```bash
vpn-gatewayd --check-config &&
systemctl restart vpn-gateway.service
```

Настоящий запуск сервиса все равно повторно проверяет конфигурацию.

CLI поддерживает:

```text
--config PATH
```

По умолчанию используется `/etc/vpn-gateway/vpn-gateway.toml`.

`--check-config` проверяет выбранный путь конфигурации и не затрагивает состояние ядра.

## 21. Административный интерфейс

Отдельный IPC может использоваться для простых локальных административных команд, например:

```text
status
shutdown
```

`reload-config` отсутствует по архитектурному решению.

IPC не должен позволять клиенту напрямую изменять состояние ядра; команды исполняет сам `vpn-gatewayd`.

## 22. Что сознательно исключено

На текущем этапе не реализуются:

- автоматическое переключение между VPN-профилями;
- изменение конфигурации без перезапуска;
- откат на старую конфигурацию;
- snapshot конфигурации, сохраняемый между запусками;
- состояние исполнения, сохраняемое между запусками, как источник истины;
- проверка доступности удаленной стороны VPN (ping);
- проверка WireGuard handshake;
- пересылка IPv6;
- сторонние Python-библиотеки.

Неперсистентная инвентаризация `OWNED` во время исполнения не относится ни к состоянию daemon,
сохраняемому между запусками, ни к snapshot конфигурации, сохраняемому между запусками.

## 23. Внутренняя модель реализации

Python-реализация больше не обязана помещаться в один исходный файл.

Допустим и предпочтителен небольшой пакет/каталог, если это улучшает аудит и снижает
связанность кода. При развертывании сохраняется одна точка входа daemon, например:

```text
vpn-gatewayd
vpn_gateway/
    config.py
    model.py
    kernel.py
    policy.py
    daemon.py
```

Точные имена и разбиение не являются архитектурным API. Не следует дробить код на
микромодули без смысловой границы.

Будущая реализация на Rust по-прежнему ориентируется на один исполняемый файл. Поэтому
границы предметных областей должны естественно переноситься в Rust `struct`/`enum` и модули
и не зависеть от динамической подмены методов (monkey-patching) или специфичной для Python
метапрограммной техники.


### 23.1. Модель конфигурации и предметной области

Runtime config содержит только typed managed profiles.

`interface` разбирается в:

```text
InterfaceSelector:
    EXACT(name)
    PREFIX(prefix)              # prefix+
    EXACT_LIST(tuple[name,...]) # ordered
```

Selector value не распространяется в allowing rule как wildcard.

```text
InterfaceRecord:
    name: str
    ifindex: int
    ipv4_local: frozenset[IPv4Address]

ConcreteBinding:
    name: str
    ifindex: int

ProfileInterfaceState:
    candidates: tuple[InterfaceRecord,...]
    active_bindings: tuple[ConcreteBinding,...]
```

Point-to-point peer evidence может быть сохранено диагностически, но не является
domain input для route derivation.

Exact active set содержит максимум одну binding. Prefix/list допускают несколько.
Active predicate: candidate содержит хотя бы один local IPv4 address внутри configured
`network`.

`VpnProfile` хранит immutable config и process-local verified OWNED/binding state; для
`prefix+` рядом хранится verified metric allocator mapping/cursor. Kernel самостоятельно
эту модель не читает.

`BLACKHOLE` выводится из config. `UNICAST` выводится из protected destination +
active concrete binding + metric semantics соответствующей формы selector. Для
`prefix+` metric зависит также от подтвержденного process-local allocator state.

Один immutable `ReconciliationSnapshot` содержит inventory, candidates, active bindings,
предварительное распределение prefix metrics/cursor, desired routes и full desired policy.

### 23.2. Модель маршрутов

`RouteSpec` остается immutable value object:

```python
@dataclass(slots=True, frozen=True)
class RouteSpec:
    destination: IPv4Network
    route_type: RouteType
    via: IPv4Address | None
    interface: str | None
    metric: int | None
    proto: int | None
    onlink: bool
```

Нормативные значения:

- BLACKHOLE: `via=None`, `interface=None`, `onlink=False`;
- daemon-owned UNICAST: `via=None`, `interface=<exact active name>`,
  `onlink=False`, `proto=202`.

Поля `via` и `onlink` сохраняются в generic kernel boundary, потому что daemon
инвентаризует и сравнивает foreign routes, но **desired VPN-GATE UNICAST никогда не
использует transport next-hop**.

Route plan сохраняет `adds/deletes/replaces` и authoritative exact-prefix semantics.

### 23.3. Состояние OWNED во время исполнения

Process-local state хранит:

- verified OWNED routes;
- active concrete binding identities в normative `active_order`;
- для каждого `prefix+` profile — подтвержденный process-local active_order,
  отображение `ConcreteBinding(name, ifindex) -> metric` и `next_metric_cursor`.

Current candidate set остается частью immutable reconciliation snapshot, но отдельно как
committed process-local state не хранится.

Prefix active_order и allocator state не сохраняются на диск и не являются источником
сетевой истины. После restart cleanup удаляет `proto 202`, process-local order начинается
заново из первого snapshot, а allocator — с пустого отображения и
`FIRST_UNICAST_METRIC`.

Каждый reconciliation заново читает inventory и строит current state. Prefix active_order
строится из последнего verified order и текущих active bindings: surviving bindings
сохраняют относительный порядок, исчезнувшие удаляются, новые добавляются в конец.
Предварительное распределение prefix metrics вычисляется из последнего verified allocator
state и этого нового order. Новый active_order, распределение и cursor фиксируются только
после successful verification полного требуемого состояния.

Commit verified binding/allocator state не зависит от functional `ProfileResult`:
verified zero-path state с `ProfileResult=FAIL` также commit-ится. При actual
verification error прежние verified binding/allocator state сохраняются.

### 23.4. Граница взаимодействия с ядром

`KernelInterface` остается узкой физической границей и не принимает решений политики.

Обычное согласование:

```text
list_routes() -> строгий полный snapshot основной IPv4-таблицы
list_interfaces() -> записи интерфейсов с name/ifindex/IPv4
add_route(RouteSpec)
delete_route(RouteSpec)
replace_route(RouteSpec)
read/write ip_forward
iptables-save / iptables-restore
```

Для очистки дополнительно используются выборочные по маркеру запросы маршрутов:

```text
list_routes_by_proto(201)
list_routes_by_proto(202)
```

Точное имя метода относится к деталям реализации. Семантический контракт: запрос с
фильтром не разбирает несвязанные сторонние маршруты.

Адаптер дочерних процессов для Debian использует:

```text
ip -j -N -4 route show table main
ip -j addr show
ip -j -N -4 route show table main proto <N>
```

Полная инвентаризация маршрутов по-прежнему считает ошибкой непредставимые формы
multipath/nexthop/nhid.

Выборочная инвентаризация при очистке получает идентичность протокола из контекста запроса,
потому что iproute2 может не печатать `protocol` в отфильтрованном выводе.

Инвентаризация по протоколу остается строгой **внутри зарезервированного пространства
маркеров**: непредставимый маршрут `proto 201/202` с multipath/nhid в структурированной форме не
пропускается молча и считается ошибкой очистки. Для `proto 201` ресурс очистки дополнительно
обязан соответствовать `type=BLACKHOLE metric=65536`; другая форма с зарезервированным
`proto 201` является конфликтом маркера, а не кандидатом на молчаливое удаление.

Разборщик адресов/интерфейсов учитывает только `addr_info[].family == "inet"` и поле
`local`; ifindex сохраняется в `InterfaceRecord`. Remote point-to-point `address`
может сохраняться как diagnostic evidence, но route/binding model от него не зависит.
Дублирующиеся записи одного имени могут объединяться только при одинаковом `ifindex`.

### 23.5. Модель политики firewall/NAT

Слой политики строит из неизменяемой конфигурации и snapshot текущего цикла две явные
формы:

```text
desired_full_policy(snapshot)
desired_isolation_filter(config)
```

Точные имена функций и классов относятся к деталям реализации.

Полная политика содержит структурные ресурсы и точные правила, зависящие от привязки.

Изолирующий фильтр:

- не зависит от инвентаризации интерфейсов;
- не содержит `ACCEPT`, зависящих от привязки;
- не содержит разрешающего сопоставления по префиксу;
- сохраняет защитные правила селекторов `INPUT`;
- сохраняет запрещающие правила входящего `FORWARD`-трафика селекторов;
- сохраняет `REJECT` транспортных сетей VPN, защищаемых назначений и окончательный
  `VPNG-FORWARD-DENY`.

Его профильные цепочки имеют однозначную структуру.

`VPNG-<PROFILE>-INPUT` в изолирующем фильтре:

```text
RETURN
```

`VPNG-<PROFILE>-FORWARD`:

```text
для каждого защищаемого назначения:
    -d route
        REJECT --reject-with icmp-host-prohibited

RETURN
```

`VPNG-INGRESS` не содержит точных блоков active concrete bindings. Он содержит только
запрещающие guard-правила всех управляемых селекторов и завершающий `RETURN`.

При применении изолирующий фильтр является **полным требуемым состоянием под управлением daemon
таблицы `filter`** для этой промежуточной стадии. Он не добавляется поверх текущего фильтра:
устаревшие daemon-owned правила `ACCEPT`, которых нет в требуемом состоянии изолирующей
стадии, должны быть удалены или заменены в той же операции применения.

Применение изолирующего фильтра не изменяет таблицу `nat`. Ранее примененный NAT может
временно оставаться за проверенным запрещающим барьером. Затем оркестрация применяет и
проверяет требуемый NAT текущего snapshot и только после этого применяет полную разрешающую
политику фильтрации.

Успешная проверка изолирующего фильтра означает только подтверждение защитного барьера и
никогда не эквивалентна состоянию `SAFE` полной требуемой политики firewall/NAT.

Только состояние `SAFE` полной требуемой политики firewall/NAT после проверки требуемого
NAT и полного фильтра может открыть путь к завершению согласования маршрутов и последующему
включению пересылки.

Обе формы выводятся из **одной модели политики**. Сравнение и восстановление не имеют
независимых источников истины; оркестрация не выполняет точечных правок отдельных правил.

Ни префиксный селектор, ни explicit list не применяются непосредственно в allowing
`ACCEPT` или NAT; там используются только exact active interface names. Сопоставление
`-i prefix+` допустимо только в проверенных deny-only guard rules `INPUT`/`FORWARD`.

### 23.6. Политика владения маршрутами

Daemon является определяющим владельцем маршрутов только для точных защищаемых префиксов
управляемых профилей.

Для каждого точного защищаемого префикса:

```text
требуемый OWNED RouteSpec              -> оставить
OWNED, но не требуемый                 -> удалить
сторонний нетребуемый точный маршрут   -> удалить
точный требуемый, но не OWNED          -> заменить/канонизировать, затем проверить
настроенный защитный BLACKHOLE          -> требуется всегда
```

Маршрут `proto kernel` никогда не удаляется и не заменяется. Совпадение точного
защищаемого префикса с маршрутом подключенной сети `proto kernel` является фатальным при запуске.

Если такой конфликт с `proto kernel` появляется во время `RUN`, daemon также не имеет
права изменять этот маршрут. План маршрутизации завершается ошибкой для соответствующего
профиля; при уже проверенной безопасном состоянии firewall жизненный цикл сохраняет отказ
с запретом и переходит в `DEGRADED`, а маршрут ядра не принимается как OWNED.

Пересечения с более или менее специфичными маршрутами автоматически не удаляются и
остаются диагностическими.

Отказ с запретом обеспечивается тремя независимыми слоями:

1. `BLACKHOLE` для защищаемого префикса;
2. безусловный `REJECT` защищаемого назначения внутри профильной цепочки `FORWARD`;
3. глобальный окончательный `VPNG-FORWARD-DENY`.

### 23.7. Цикл обработки событий

Один `VpnGatewayDaemon` владеет:

- одним слушателем Netlink;
- периодическим таймером согласования;
- механизмом пробуждения по сигналу;
- событиями IPC и административными командами.

Все события сериализованы. Одновременно выполняется не более одного цикла согласования.

Netlink-событие используется как сигнал пробуждения и признак необходимости пересверки,
а не как достоверное описание изменения состояния. Согласование читает заново полный
snapshot интерфейсов.

Событие interface можно игнорировать только если exact name не может попасть ни в одно
guard namespace managed selectors. Любое имя, совпадающее с exact/list element либо
prefix namespace, будит full reconciliation. Сам event остается wakeup hint; resources
выводятся из заново построенного snapshot.

### 23.8. Диагностическая модель

Ожидаемые эксплуатационные ошибки имеют стабильную машинную идентичность причины,
независимую от человекочитаемого текста. Концептуальный контракт:

```text
DiagnosticFact:
    code   -> стабильный код причины
    detail -> необязательный человекочитаемый контекст
```

Точные имена Python-классов относятся к реализации. Архитектурным контрактом является
стабильная машинная идентичность причины; полный каталог конкретных кодов определяется
реализацией и тестами, а не выводится из свободного текста исключения.

После того как код причины опубликован через CLI/IPC/status или закреплен регрессионным тестом,
его изменение считается изменением совместимости и должно быть явным.

Поле `detail` предназначено только для диагностики человеком и не должно определять
идентичность или дедупликацию события.

Ожидаемые ошибки на границе взаимодействия ядра и пользовательского пространства
переводятся в известные диагностические причины на соответствующей границе оркестрации.
Исключения из-за ошибок программирования, нарушенные внутренние инварианты и иные
неожиданные ошибки не маскируются как штатные `UNKNOWN`/`DEGRADED`.



### 23.9. Результат профиля

Завершенный reconciliation формирует для каждого managed profile:

```text
SUCCESS
FAIL
```

`SUCCESS` требует одновременно:

- profile contribution к full desired firewall/NAT policy применен и verified;
- exact protected-prefix route state совпадает с desired;
- для каждого protected destination есть хотя бы один verified desired direct UNICAST
  path через active concrete interface;
- BLACKHOLE и остальные required resources соответствуют desired.

Для prefix/list selector присутствие всех потенциальных paths не требуется. Partial
availability остается `SUCCESS`, если хотя бы один active path существует для каждого
protected destination.

`FAIL` возникает, если после completed verification хотя бы один protected destination
не имеет desired UNICAST path либо profile route/policy state не соответствует desired.

Availability `FAIL` при global `SAFE` policy является `DEGRADED`, не `ISOLATED`.
Полное отсутствие active bindings является валидным fail-closed runtime state и не
является config/startup error само по себе.

Transport handshake/peer health не меняет `ProfileResult`. `SUCCESS` подтверждает
kernel desired state, а не end-to-end reachability.

Ошибка наблюдаемости, не позволяющая достоверно построить profile state, относится к
reconciliation pass целиком и дает `ISOLATED`.

## 24. Замечания по реализации, уже зафиксированные архитектурой

- EXP-001 подтвердил canonical `iptables-save` representation на Debian 13 /
  iptables-nft.
- EXP-002/002A подтвердили interface/address inventory с `ip -j addr show` и
  `addr_info[].local`.
- EXP-004 подтвердил fail-closed blackhole/route ownership и ocserv interface-family
  behavior.
- EXP-005 подтвердил deny-only iptables prefix contract `-i prefix+`.
- EXP-006 подтвердил `iptables-restore --noflush` orchestration и narrow INPUT repair.
- EXP-007/008 подтвердили live daemon lifecycle и runtime drift recovery прежнего
  implementation baseline.
- EXP-009 является основанием interface-centric route model:
  - healthy OpenConnect profile может иметь несколько simultaneous concrete interfaces;
  - direct OpenConnect route `dev vpns00` работает без transport next-hop;
  - disappearing interface removes dependent route, returning interface requires
    rematerialization;
  - metric не является path-health detector;
  - WireGuard peer selection внутри stable `wg0` принадлежит `AllowedIPs`, а duplicate
    prefix не создает primary/secondary Linux routes;
  - peer health не переводит destination ownership между WireGuard peers.
- Allowing rules/NAT/routes используют только exact active interface names.
- Policy-changing active-binding transitions используют protective barrier:
  isolation filter -> verify -> NAT -> verify -> full filter -> verify -> routes -> verify.
- Confirmed INPUT-only drift without policy transition uses narrow repair.
- Interface inventory failure forbids blind binding-specific repair and leads to isolation.
- `ip_forward` remains daemon-owned and read-after-write verified.
- IPv6 prerequisites §2.6 remain mandatory.
- Python implementation may be a package but keeps one daemon entry point.

### 24.1. Несовместимые изменения относительно текущей Python-реализации до EXP-009

Implementation update must include at least:

- `InterfaceSelector = EXACT | PREFIX | EXACT_LIST`; `%` removed;
- explicit list preserves configured order;
- prefix/list may resolve to multiple simultaneous active bindings;
- no `AMBIGUOUS` selector state for normal multiplicity;
- `peers` removed from config/domain model;
- `local_address` removed from config/domain model; interface applicability derives from
  local IPv4 membership in `network`;
- transport peer-association domain object removed;
- point-to-point remote endpoint removed from route association;
- desired UNICAST is direct `dev exact-interface proto 202`, `via=None`,
  `onlink=False`;
- prefix active_order is process-local and append-only for surviving bindings: new
  bindings append, removed bindings disappear, existing firewall/NAT rules are not
  reordered merely because a lexically earlier name appears;
- prefix metrics use a cyclic process-local allocator; continuous bindings retain
  allocated metrics, all UNICAST metrics remain below BLACKHOLE_METRIC, and no prefix
  route-priority order is guaranteed;
- explicit-list metrics derive from stable configured slots and must remain below
  BLACKHOLE_METRIC;
- full policy/NAT derives from all active exact interfaces;
- snapshot stores candidates + active bindings + provisional prefix metric allocations/cursor;
  committed transition state stores verified active bindings together with verified
  prefix allocator mapping/cursor;
- `ProfileResult` checks verified UNICAST path existence, not merely exact desired-set
  equality;
- successful startup may enter `RUN/DEGRADED` when no active path exists but fail-closed
  desired state is verified;
- Netlink remains wakeup-only; snapshot decides.

Generic `RouteSpec.via/onlink` may remain for foreign-route inventory. `ReconciliationPlan`
may retain adds/deletes/replaces.

## 26. Ключевые инварианты

Ниже используется компактная техническая запись. Именованные состояния, поля конфигурации,
имена цепочек, классов, методов и команд сохраняются без перевода; обычные понятия
формулируются по-русски.

```text
1. Один daemon-процесс владеет всеми ресурсами VPN-GATE в ядре.

2. Конфигурация читается один раз за время жизни процесса; изменения применяются только
   перезапуском.

3. Запуск: обработчики сигналов -> runtime-каталог/LOCK -> CLEANUP -> LOAD/VALIDATE -> APPLY -> RUN.

4. Ошибка запуска никогда не переводит сервис в DEGRADED; IPv4-пересылка не должна
   остаться включенной, а обязательные IPv6-условия §2.6 проверяются до перехода в RUN.

5. Очистка не зависит от конфигурации и опирается на маркеры владения.

6. Маркер владения BLACKHOLE: proto 201 + type BLACKHOLE + metric 65536.

7. Маркер владения VPN UNICAST: proto 202.

8. При очистке маршруты читаются выборочными запросами по proto 201/202, а не полной
   инвентаризацией основной таблицы.

9. При обычном согласовании полная инвентаризация маршрутов остается строгой и не
   пропускает молча неподдерживаемые multipath/nhid формы.

10. `ip_forward` находится в исключительном управлении daemon и read-after-write verified. IPv6 daemon не маршрутизирует/не фильтрует: global prerequisites и `disable_ipv6=1` для всех current guard-namespace interfaces проверяются startup и на каждом полном RUN reconciliation до allowing policy. Runtime violation блокирует ordinary apply и оставляет IPv4 state ISOLATED; это не считается IPv6 protection.

11. Эксклюзивное управление `ip_forward` архитектурно связано с эксклюзивной ответственностью
    daemon за окончательное решение для каждого IPv4-пакета FORWARD.

12. В проверенном состоянии сторонние правила `FORWARD` физически находятся после
    daemon-owned префикса и недостижимы из-за VPNG-FORWARD-DENY; правило, вставленное перед
    префиксом, является рассогласованием UNSAFE до следующего цикла согласования.

13. В проверенном состоянии daemon-owned префикс `INPUT` находится с позиции 1, а
    сторонние правила `INPUT` — после `VPNG-INPUT-GUARD`. Подтвержденное рассогласование,
    ограниченное только `INPUT`, восстанавливается точечно без изменения `ip_forward`.
    `OUTPUT` не изменяется daemon и полностью остается политикой администратора хоста;
    локальный OUTPUT не проходит ACL источников FORWARD.

14. Поле `interface` является selector union: exact string, trailing-`+` prefix либо непустой ordered explicit exact list.

15. Exact selector имеет не более одной candidate binding; `prefix+` и explicit list допускают несколько simultaneous candidates/active bindings без состояния ambiguity.

16. `prefix+` discovery охватывает весь textual prefix, включая exact name `prefix`; process-local active_order сохраняет относительный порядок непрерывно active bindings, новые bindings добавляются в конец, исчезнувшие удаляются без перестановки остальных. Если несколько новых bindings впервые обнаружены одним snapshot, только их взаимный порядок определяется case-sensitive bytewise ASCII.

17. Explicit list непустой, содержит уникальные valid exact names и сохраняет config order как route-priority slots; отсутствующий элемент не сдвигает metrics следующих; каждая вычисляемая UNICAST metric обязана быть < BLACKHOLE_METRIC.

18. Managed selectors попарно не пересекаются по guard namespace; overlap является fatal config error.

19. Candidate становится active concrete binding только при наличии хотя бы одного local IPv4 address внутри configured `profile.network`; multiple active bindings у prefix/list являются штатными.

20. Transport peer address, handshake, endpoint reachability и point-to-point remote evidence не являются route/binding truth VPN-GATE.

21. Идентичность concrete binding включает exact name + ifindex; повторное создание имени с новым ifindex является binding transition.

22. Allowing `INPUT`/`FORWARD`, NAT и UNICAST routes используют только exact active interfaces. Для binding-specific policy применяется active_order: exact single; prefix process-local append-only order surviving bindings; explicit list config order filtered to active. Появление нового prefix-interface не меняет relative desired order существующих exact firewall/NAT blocks; full protective restore может технически пересобрать chain целиком. Prefix route metrics от active_order не определяют гарантированный priority.

23. `operstate`/`LOWER_UP`, ping и handshake не определяют active binding; interface applicability определяется local IPv4 membership в `profile.network`.

24. Daemon-owned UNICAST route является direct `dev <exact-interface>` route с `via=None`, `onlink=False`, `proto=202`; transport peer selection находится вне route model.

25. BLACKHOLE и REJECT защищаемого назначения не зависят от текущего binding state или
    наличия UNICAST path.

26. Точный `INPUT` block active concrete interface разрешает только ESTABLISHED,RELATED и
    запрещает остальное; общего NEW ACCEPT с VPN-стороны нет. Незавершенный traffic
    защитного пространства имен закрывает VPNG-INPUT-GUARD.

27. Сопоставление семейства по префиксу допустимо только как проверенное запрещающее
    защитное правило; префиксные ACCEPT/NAT запрещены.

28. Порядок FORWARD: VPNG-INGRESS -> VPNG-RESERVED -> цепочки профилей ->
    VPNG-FORWARD-DENY -> сторонние правила.

29. Динамический ACCEPT в цепочке FORWARD профиля требует source + protected destination
    + exact active egress interface.

30. В каждом отдельном блоке защищаемого назначения после динамических ACCEPT всегда
    существует безусловный REJECT.

31. `VPNG-FORWARD-DENY` выдает окончательный `DROP`/`REJECT` для всего оставшегося IPv4-транзита.

32. `FORWARD` к управляемой транспортной `vpn.network` получает `REJECT` до ACL профиля.

33. VPNG-INGRESS содержит exact block для каждого active concrete interface:
    INVALID -> DROP, ESTABLISHED/RELATED -> ACCEPT, остальное -> REJECT; traffic
    защитного пространства имен, не завершенный exact block, получает REJECT до ACL.

34. NAT-chain существует структурно для каждого managed profile; один MASQUERADE
    materialize для каждого unique active egress interface; foreign POSTROUTING rules
    сохраняются и остаются достижимыми после RETURN для unmanaged outgoing traffic.

35. NAT проверяется раньше восстановления маршрутов proto 202 через новую привязку.

36. Изменение active binding set/identity является policy-changing transition, но для `prefix+` новая binding добавляется в конец process-local active_order и получает свободную metric без перестановки/перенумерации непрерывно active bindings. Изменение metric или относительного order уже существующей binding само является policy-changing transition. Candidate-only change без active-resource change не требует тяжелого IPv4 barrier только после successful current IPv6 prerequisite verification.

37. Остаточное окно «событие ядра -> реакция daemon» существует и документировано;
    запрещающие правила селекторов закрывают входящий трафик нового непривязанного
    интерфейса семейства, но ограничение «то же имя / новый `ifindex`» в iptables остается
    границей модели.

38. Netlink-событие является сигналом пробуждения/необходимости пересверки; достоверное
    состояние заново читается из snapshot.

39. Событие имени, потенциально соответствующего управляемому селектору, инициирует полную
    пересверку.

40. Периодическое согласование обязательно как страховка; `reconcile_interval` имеет диапазон
    [1.0, 60.0] и не может быть отключен значением 0.

41. Один immutable snapshot interfaces/candidates/active bindings/provisional prefix metric allocations повторно используется на всех фазах построения, применения и проверки одного цикла; provisional allocator mapping/cursor не меняется внутри цикла.

42. BLACKHOLE RouteSpec выводится только из config. UNICAST RouteSpec выводится из protected destination + active concrete binding + metric semantics selector form; для `prefix+` используется verified process-local allocator state.

43. `RouteSpec.interface` для desired UNICAST содержит exact active interface name; `via=None`, `onlink=False`; selector value туда не попадает.

44. Отсутствующие BLACKHOLE добавляются раньше любых разрушительных операций с маршрутами.

45. Исполнитель маршрутов: добавить BLACKHOLE -> удалить конкурирующие точные маршруты ->
    выполнить замены -> добавить оставшиеся маршруты.

46. Daemon является определяющим владельцем маршрутов только для точных защищаемых
    префиксов `profile.routes`.

47. Конкурирующие сторонние точные маршруты могут удаляться; `proto kernel` никогда не
    удаляется и не заменяется.

48. Пересечения с более или менее специфичными маршрутами автоматически не удаляются.

49. Маршрут по умолчанию не считается ресурсом диагностики пересечений.

50. OWNED routes, подтвержденный active binding state/order и prefix allocator mapping/cursor process-local, после restart начинаются заново и меняются только после verification. Current candidates заново выводятся из каждого snapshot и отдельно не commit-ятся. Verified state commit не зависит от functional ProfileResult SUCCESS: verified zero-path FAIL также commit-ится.

51. Process-local фиксация OWNED/active binding order/prefix allocator state выполняется одной verified-state commit boundary после verification и до final enable forwarding; failed apply/verification не изменяет verified active_order, allocator mapping/cursor, availability FAIL не блокирует commit verified fail-closed state.

52. Само по себе фактическое состояние ядра не означает принятия ресурса во владение.

53. `desired_full_policy` и `desired_isolation_filter` являются двумя производными формами
    одной модели политики; сравнение и восстановление не имеют независимых источников
    политики.

54. Состояние безопасности firewall/NAT = `SAFE`/`UNSAFE`/`UNKNOWN`; `UNKNOWN` не восстанавливается
    вслепую. Для подтвержденного `UNSAFE` daemon также определяет, ограничено ли
    рассогласование только `INPUT` либо затрагивает транзитную политику.

55. Подтвержденное `INPUT`-only `UNSAFE` без перехода, меняющего политику,
    восстанавливается точечно одной транзакцией `filter` без изменения `ip_forward`,
    `FORWARD`, NAT и маршрутов. `FORWARD`/NAT `UNSAFE`, неопределенная область
    рассогласования либо переход, меняющий политику, используют порядок с первоначальным
    запретом: изолирующий фильтр -> проверка -> требуемый NAT -> проверка -> полный
    требуемый фильтр -> проверка -> маршруты -> проверка.

56. Невозможность подтвердить ip_forward=0 не разрешает полный ACCEPT раньше проверенного
    NAT; защитный барьер с первоначальным запретом все равно применяется.

57. Ошибка interface inventory/parsing либо невозможность построить полный ReconciliationSnapshot, включая exhausted prefix metric allocator, на уровне цикла -> ISOLATED; partial desired state и provisional allocator state не принимаются. Отсутствие active path при достоверном snapshot -> profile FAIL / DEGRADED.

58. При ошибке инвентаризации интерфейсов слепое восстановление политики, зависящей от
    привязки, запрещено; изолирующий фильтр, выводимый только из конфигурации, допустим как
    безопасный барьер при читаемом состоянии фильтрации.

59. После изоляции пересылка возвращается только после SAFE полной политики и завершенной
    новой проверки маршрутов.

60. Desired policy профиля без active bindings не содержит binding-specific ACCEPT/NAT/UNICAST, сохраняя blackhole, selector guards и protected-destination REJECT.

61. Profile `SUCCESS` требует как минимум один verified desired UNICAST RouteSpec для каждого protected destination. Partial prefix/list availability остается `SUCCESS`, если такой path существует; zero paths -> functional `FAIL`, а при SAFE verified fail-closed state -> DEGRADED. Verification success и functional ProfileResult являются разными осями.

62. Multiple candidates/active bindings у prefix/list не являются ошибкой. Конфликт managed selector namespaces является config error; duplicate interface name with conflicting ifindex is inventory error.

63. `ACTIVE` = политика `SAFE` + результаты всех профилей `SUCCESS` + `ip_forward=1`;
    ни `ACTIVE`, ни profile `SUCCESS` не означают доказанную end-to-end связность VPN.

64. В завершенном `RUN` при `SAFE` policy подтвержденный `ip_forward=0` либо хотя бы
    один profile `FAIL` -> `DEGRADED`; `ACTIVE` требует все profiles `SUCCESS` и
    `ip_forward=1`. Не-`SAFE` policy либо недостаточная наблюдаемость policy/ip_forward
    -> `ISOLATED`.

65. Очистка не переходит к разрушительным операциям, пока не подтверждено `ip_forward=0`;
    затем: `proto 202` -> `filter`/NAT -> `proto 201` blackhole -> проверка.

66. Blackhole снимается только после подтвержденной очистки остальных принадлежащих daemon
    ресурсов.

67. Очистка iptables точная; глобальная очистка таблиц запрещена.

68. Пространство имен `VPNG-*` полностью зарезервировано daemon'ом.

69. Атомарность iptables-restore в пределах одной таблицы не считается атомарностью между
    таблицами.

70. Последний компонент runtime-каталога: не символическая ссылка, каталог, режим 0700,
    ожидаемый владелец сервиса.

71. Отсутствующий runtime-каталог daemon может создать сам при достаточных правах.

72. Неправильные владелец/режим существующего runtime-каталога не исправляются молча.

73. Файл блокировки открывается с `O_NOFOLLOW`; эксклюзивная блокировка `flock` удерживается
    все время жизни процесса, а попытка ее получения выполняется без ожидания.

74. Конфигурационный файл: обычный файл, не символическая ссылка, принадлежит `root`;
    родительский каталог защищен от записи группы и остальных пользователей (`group`/`other`).

75. `--check-config` не получает блокировку экземпляра и не меняет состояние ядра.

76. Неизвестные ключи конфигурации фатальны для проекции конфигурации управляемых профилей для исполнения.

77. Некорректные неуправляемые описания профилей не блокируют запуск; `--check-config`
    выдает `WARNING`.

78. Защищаемые маршруты управляемых профилей глобально не пересекаются и не пересекают
    управляемые vpn.network.

79. Metrics: все daemon-owned UNICAST имеют 0 < metric < BLACKHOLE_METRIC. Exact = FIRST_UNICAST_METRIC. Explicit list slot N использует FIRST_UNICAST_METRIC + N*ROUTE_METRIC_STEP без сдвига отсутствующих элементов; config validator запрещает любой slot с metric >= BLACKHOLE_METRIC. Prefix использует то же допустимое пространство метрик и циклический process-local allocator: непрерывно active binding сохраняет metric, занятые значения пропускаются, при верхней границе поиск возвращается к FIRST_UNICAST_METRIC, при полном исчерпании slots построение snapshot завершается ошибкой; гарантированного route preference между prefix-bindings нет.

80. `common_allowed_sources` объединяется с `profile.allowed_sources`; отрицательных правил
    и исключений нет.

81. Обратная доступность со стороны VPN не входит в текущий контракт: новый INPUT с
    управляемого VPN-интерфейса запрещен, а NEW FORWARD закрыт ingress-политикой. Локальный
    OUTPUT самого доверенного шлюза регулируется отдельно администратором.

82. Python-реализация может быть пакетом из нескольких файлов, но имеет одну точку входа
    daemon.

83. Границы предметных областей должны переноситься в будущие Rust-модули, `struct` и `enum`;
    развертывание Rust ориентировано на один исполняемый файл.

84. Один цикл обработки событий сериализует Netlink, таймер, IPC и завершение; параллельное
    согласование запрещено.

85. Обработчики сигналов не выполняют работу с ядром; завершение проходит через
    сериализованную очистку жизненного цикла.

86. SIGHUP не перезагружает конфигурацию.

87. Формы внешних CLI-команд, влияющие на безопасность, проверяются на целевой Debian до
    закрепления в адаптере.

88. Исключения из-за ошибок программирования и нарушения внутренних контрактов не
    маскируются как ожидаемые эксплуатационные `UNKNOWN`/`DEGRADED`.

89. Машинная идентичность диагностической причины задается стабильным кодом; полный каталог
    кодов является контрактом реализации/интерфейса после публикации, а свободный текст
    `detail` не участвует в идентичности/дедупликации.

90. Префиксный селектор резервирует весь textual prefix namespace deny-only guard; matching interface без local IPv4 из `profile.network` остается guard-blocked и не становится active.

91. Остаточное окно «событие -> реакция» является явной границей модели угроз доверенного
    хоста: недоверенные процессы не имеют `CAP_NET_ADMIN` и не управляют жизненным циклом
    сетевых интерфейсов.

92. Замена «то же имя / новый `ifindex`» обнаруживается при согласовании snapshot, но
    существующее сопоставление имени в iptables нельзя задним числом привязать к прежнему
    `ifindex`.

93. Дублирующееся имя интерфейса с конфликтующими ifindex является некорректной
    инвентаризацией ядра и возвращает KernelError; адаптер не выбирает одну запись и не
    объединяет конфликт молча.

94. Выборочная по протоколу очистка остается строгой для зарезервированных `proto 201/202`;
    неподдерживаемые формы выбранных маршрутов фатальны и не пропускаются молча.

95. `desired_isolation_filter` выводится только из конфигурации и не содержит `ACCEPT`,
    зависящих от привязки.

96. Применение изолирующего фильтра заменяет/канонизирует полное требуемое состояние под
    управлением daemon для таблицы `filter` на этой стадии; устаревшие daemon-owned
    `ACCEPT`, зависящие от
    привязки, не должны оставаться достижимыми.

97. Проверка изолирующего фильтра является отдельным результатом защитного барьера и
    никогда не удовлетворяет состоянию `SAFE` полной политики firewall/NAT.

98. `SAFE` полной политики требует проверки требуемого NAT и полного требуемого фильтра для
    одного и того же неизменяемого snapshot согласования.

99. Операционный status сообщает selector form, candidates, active concrete bindings, interface/metric для desired/verified UNICAST и ProfileResult отдельно от lifecycle state ACTIVE; для `prefix+` status также показывает process-local active_order как диагностический порядок первого принятия bindings текущим daemon, но не трактует его как гарантированный route priority.
```
