# VPN Gateway — архитектурные решения и инварианты

**Статус:** кандидат на утверждение и реализацию
**Версия:** RC3
**Дата:** 2026-11-09

Документ фиксирует принятые архитектурные решения проекта VPN Gateway. Он описывает обязательные инварианты, жизненный цикл сервиса, модель владения состоянием ядра и правила конфигурации. Нереализованные детали, которые ещё требуют отдельного решения, вынесены в раздел **«Открытые решения»**.

Нормативная терминология проекта определена в [«Терминах и определениях»](terms-and-definitions.md).

## 1. Назначение

VPN Gateway — локальный IPv4-шлюз, который:

- направляет заданные сети через один или несколько VPN-профилей;
- не зависит от конкретной VPN-реализации;
- применяет собственную фильтрацию `INPUT`/`FORWARD`;
- применяет NAT;
- использует защитные blackhole-маршруты для отказа с запретом;
- отслеживает появление и исчезновение VPN-интерфейсов через Netlink.

Конфигурация может содержать произвольный каталог описанных VPN-профилей. Во время runtime
daemon отслеживает и обслуживает только профили, перечисленные в поле верхнего уровня
`managed_vpns`. Автоматического failover между профилями нет.

IPv6-маршрутизация проектом не поддерживается.

## 2. Общие принципы

### 2.1. Жёсткий отказ

При ошибке очистки, проверки или применения конфигурации сервис не переходит в частично
рабочее состояние.

Ошибка при запуске означает:

- `ip_forward` не включается;
- новая конфигурация не считается применённой;
- процесс завершается с ненулевым кодом;
- systemd переводит сервис в `failed`.

Режим `DEGRADED` при запуске не используется.

### 2.2. Отказ с запретом

Защищаемый трафик не должен при отказе VPN или ошибке конфигурации уходить через обычный
маршрут по умолчанию.

Blackhole-маршруты являются одним из защитных механизмов и устанавливаются до разрешения
пересылки.

Blackhole обеспечивает отказ с запретом на уровне выбора маршрута для соответствующего
префикса. Он не является универсальной гарантией доставки и не заменяет независимую
фильтрацию `FORWARD`.

### 2.3. Один владелец сетевого состояния

Один долгоживущий процесс `vpn-gatewayd` является единственным владельцем ресурсов
проекта:

- daemon-owned политики фильтрации;
- blackhole-маршрутов;
- VPN-маршрутов;
- NAT;
- `net.ipv4.ip_forward`.

IPv6 forwarding не относится к управляемым ресурсам daemon: для него действует отдельное
обязательное условие среды (§2.6).

Внешние скрипты и административные клиенты не должны самостоятельно изменять эти ресурсы.

`vpn-gatewayd` предназначен для выделенного хоста VPN-шлюза. Совмещение с Docker,
Kubernetes, другими сервисами-шлюзами или компонентами, которым требуется
`net.ipv4.ip_forward=1`, не поддерживается.

Эксклюзивное владение глобальным `net.ipv4.ip_forward` и эксклюзивная ответственность за
окончательное решение для всего IPv4-трафика `FORWARD` являются двумя связанными
архитектурными обязательствами daemon. Пока `ip_forward=1`, в **проверенном требуемом
состоянии** каждый пересылаемый IPv4-пакет обязан получить окончательное решение внутри
daemon-owned префикса правил; пакет не должен доходить до сторонних правил или встроенной
политики `FORWARD ACCEPT`.

В проверенном состоянии daemon-owned префикс физически начинается с позиции 1, а сторонние
правила `FORWARD` сохраняются после `VPNG-FORWARD-DENY` и поэтому недостижимы при
включённой пересылке.

Если внешний менеджер во время работы вставил стороннее правило перед daemon-owned
префиксом, это считается рассогласованием `UNSAFE`. До следующего цикла согласования
существует окно реакции, в котором такое правило может получить влияние на решение.
Восстановление с первоначальным запретом заново размещает daemon-owned префикс с позиции 1;
стороннее правило не удаляется, а физически оказывается после `VPNG-FORWARD-DENY`.
Постоянное конкурентное переписывание префикса внешним менеджером остаётся
неподдерживаемой конфигурацией.

После `cleanup()` daemon-owned переходы и цепочки исчезают, а `ip_forward=0`; базовая
фильтрация хоста снова полностью принадлежит администратору.

`net.ipv4.ip_forward` находится под исключительным управлением daemon. Ручное изменение
sysctl не является постоянной административной паузой или переопределением и будет
приведено daemon к требуемому значению на следующем завершённом цикле согласования.

### 2.4. Никакого скрытого fallback на старую конфигурацию

Конфигурация читается только при запуске процесса.

Изменения применяются только через:

```bash
systemctl restart vpn-gateway.service
```

`reload-config` отсутствует.

После изменения файла допустимы только два состояния:

1. сервис успешно запустился с новой конфигурацией;
2. сервис не запустился и находится в `failed`.

Работа на старой конфигурации при уже изменённом файле не допускается.

### 2.5. Никаких сторонних Python-зависимостей

Python-реализация использует только:

- стандартную библиотеку Python;
- штатные системные утилиты Debian 13.

Запрещены:

- `pip`;
- PyPI;
- `apt install python3-*` ради дополнительных библиотек.

Python рассматривается как промежуточная реализация; архитектура должна оставаться
пригодной для последующего переноса на Rust.

### 2.6. IPv6-пересылка должна быть отключена

VPN Gateway управляет только IPv4 и не строит политику фильтрации или маршрутизации для
IPv6. Поэтому включённая IPv6-пересылка на хосте является неподдерживаемым обходным путём
мимо описанной политики безопасности.

Перед применением IPv4-политики и до перехода в `RUN` daemon обязан проверить как минимум:

```text
net.ipv6.conf.all.forwarding     = 0
net.ipv6.conf.default.forwarding = 0
```

Если ядро предоставляет отдельные per-interface механизмы, способные разрешить IPv6
forwarding вопреки глобальному значению, они также должны быть выключены для всех
существующих интерфейсов. Новые интерфейсы должны наследовать выключенную пересылку.

Daemon не изменяет эти IPv6 sysctl: они являются обязательным условием конфигурации
выделенного хоста. Несоответствие при запуске является фатальной ошибкой до любых действий,
которые могут разрешить IPv4-пересылку.

Изменение этих настроек доверенным администратором во время `RUN` находится вне
поддерживаемой модели эксплуатации и требует перезапуска сервиса после исправления.

## 3. Процессная модель

Основной компонент:

```text
vpn-gatewayd
```

Это постоянно работающий процесс под управлением systemd.

Он:

- читает и проверяет конфигурацию;
- хранит разобранную конфигурацию в памяти;
- отслеживает состояние VPN-интерфейсов управляемых профилей;
- применяет фильтрацию;
- применяет blackhole-маршруты;
- применяет VPN-маршруты;
- применяет NAT;
- управляет пересылкой IPv4;
- выполняет полную очистку своих ресурсов при запуске и штатном завершении.

Отдельный событийный `vpn-monitor` после перехода на эту архитектуру не требуется.

Daemon пишет обычные текстовые сообщения в `stderr`; при запуске под systemd они попадают
в journal. Структурированное логирование/JSON не требуется.

## 4. Мониторинг VPN-интерфейса и привязка во время runtime

Для мониторинга используется Linux Netlink через стандартный Python `socket`:

```text
AF_NETLINK
NETLINK_ROUTE
```

Сервис реагирует как минимум на:

- `RTM_NEWLINK`;
- `RTM_DELLINK`;
- `RTM_NEWADDR`;
- `RTM_DELADDR`.

При запуске daemon выполняет полный snapshot интерфейсов и адресов и не полагается только
на будущие события. При потере Netlink-событий, например `ENOBUFS`, выполняется полная
пересверка. Периодическое согласование остаётся страховкой от дрифта ресурсов и потерянных
событий.

### 4.1. Селектор интерфейса

Поле конфигурации `interface` является **селектором**, а не обязательно конкретным
Linux-интерфейсом.

Поддерживаются две формы:

```text
wg0    -> точный селектор
vpns+  -> префиксный селектор
```

Завершающий `+` использует семантику сопоставления по префиксу, подтверждённую EXP-005
для условия по входному интерфейсу `iptables -i prefix+`: `vpns+` означает всё
пространство имён интерфейсов с префиксом `vpns`, включая имя `vpns` без суффикса.

Это не shell-шаблон и не пользовательское регулярное выражение.

Селектор используется только для поиска и классификации runtime-интерфейсов. Строка
префиксного селектора с `+` **никогда** не передаётся в операции маршрутизации,
`ACCEPT` или NAT; после разрешения селектора эти ресурсы используют только точное имя
найденного интерфейса.

Daemon разрешает селектор по одному snapshot интерфейсов:

```text
0 совпадений  -> ABSENT (отсутствует)
1 совпадение  -> BOUND(name, ifindex), жесткая привязка
>1 совпадения -> AMBIGUOUS (неоднозначен)
```

Жесткая привязка содержит как минимум точное имя интерфейса и ifindex из snapshot.
`ifindex` нужен для обнаружения удаления и повторного создания интерфейса под тем же
именем; операции с маршрутами и iptables всё равно используют точное имя интерфейса.

Daemon никогда не выбирает «первый», «минимальный номер», «самый новый» или иной
произвольный интерфейс при неоднозначности.

### 4.2. Конфликты селекторов в конфигурации

Два одновременно управляемых селектора не могут иметь непустое множество общих возможных
runtime-имён интерфейсов.

Это ошибка конфигурации, блокирующая запуск.

Примеры конфликтов:

```text
vpns+ + vpns0
vpns+ + vpns1+
vpns+ + vpns+
```

Точные имена и сопоставление селектора чувствительны к регистру, как и имена
Linux-интерфейсов.

Для префиксного селектора префикс должен содержать хотя бы один допустимый символ имени
Linux-интерфейса; завершающий `+` является оператором селектора и не входит в конкретное
имя.

Неуправляемые описания профилей не блокируют runtime-запуск; соответствующие конфликты с
управляемыми профилями являются `WARNING` в `--check-config`, как и остальные
перекрёстные конфликты неуправляемых описаний.

### 4.3. Критерий готовности VPN

Профиль считается готовым, если одновременно:

1. селектор разрешён ровно в один интерфейс;
2. это та же жесткая привязка `name + ifindex`, которая рассматривается в текущем цикле
   согласования;
3. на интерфейсе присутствует ожидаемый `local_address`.

Не используются как критерий готовности:

- `operstate`;
- `LOWER_UP`;
- доступность удалённой стороны;
- ping;
- рукопожатие VPN-протокола;
- фактическое прохождение трафика.

Если селектор не имеет совпадений либо найденный интерфейс существует без ожидаемого
локального IPv4, профиль не готов. Его защищаемые маршруты остаются под blackhole и
окончательным `REJECT` в `FORWARD`.

Если селектор находится в состоянии `AMBIGUOUS`:

- при запуске это фатальный конфликт runtime-среды; сервис не включает пересылку;
- в `RUN` профиль переходит в `FAIL`/`DEGRADED`;
- разрешающие правила, NAT и UNICAST-маршруты, зависящие от привязки, должны быть удалены
  или не созданы;
- blackhole и запрещающая политика сохраняются.

### 4.4. Смена привязки, смена готовности и остаточное окно реакции

Появление, исчезновение, замена ifindex либо изменение числа совпадений селектора считается
**сменой привязки** и инициирует полное сериализованное согласование.

Появление или исчезновение ожидаемого `local_address` на неизменной жесткой привязке
считается **сменой готовности**. Смена привязки или смена готовности является
**переходом, меняющим политику**, потому что меняет набор разрешающих правил
`INPUT`/`FORWARD`, NAT либо маршрутов `proto 202`.

При подтверждённом переходе, меняющем политику, daemon по возможности сначала отключает
`ip_forward`, затем применяет политику и маршруты для нового неизменяемого snapshot,
проверяет состояние и только после этого может вернуть пересылку.

Существует принципиальное окно реакции между изменением состояния ядра и обработкой
Netlink-события daemon. Особенно это заметно при быстром появлении второго подходящего
интерфейса или при удалении и повторном создании интерфейса под тем же именем: старые
правила по точному имени физически существуют до реакции daemon.

Для префиксного семейства дополнительное запрещающее правило входящего `FORWARD`-трафика
в `VPNG-INGRESS` закрывает сценарий, при котором новый ещё не привязанный интерфейс мог
бы дойти до старой разрешающей цепочки профиля. Неустранимой остаётся граница
сопоставления iptables по имени: уже существующее правило по имени нельзя задним числом
привязать к историческому ifindex при пересоздании интерфейса с тем же именем.

Если своевременный Netlink-сигнал не получен или потерян, периодический цикл согласования
служит резервным механизмом обнаружения изменения. При работающем цикле обработки событий
следующая такая пересверка наступает не позже следующего `reconcile_interval`,
настраиваемого в диапазоне 1–60 секунд. Это не является гарантией при зависшем daemon:
в таком состоянии сам таймер также не исполняется.

Архитектура принимает остаточное окно реакции как неизбежную границу многозадачной ОС на
выделенном доверенном шлюзе. Она уменьшает окно пробуждением по Netlink, запрещающими
правилами селекторов и периодической полной пересверкой, но не изображает набор отдельных
операций ядра как атомарную транзакцию.

Граница модели угроз для этого окна явная:

- недоверенные локальные пользователи и процессы не имеют `CAP_NET_ADMIN` и не могут
  создавать, переименовывать или удалять сетевые интерфейсы;
- жизненным циклом runtime-интерфейсов управляют доверенное VPN-ПО, ядро и администратор;
- ifindex позволяет обнаружить повторное создание интерфейса под тем же именем при
  следующем snapshot, но существующее правило iptables по имени нельзя задним числом
  привязать к старому ifindex.

Новые или ещё не привязанные интерфейсы управляемых селекторов не должны иметь
статических разрешающих правил по шаблону.

Для `INPUT` хоста заранее устанавливается защитное правило селектора только с запретом:
для точного селектора — по точному имени, для префиксного — `-i prefix+`.
`VPNG-INPUT-GUARD` блокирует такой трафик, если его не завершила более ранняя точная
цепочка готового профиля.

Для `FORWARD` тот же принцип реализуется внутри `VPNG-INGRESS`: точные правила готовых
жестких привязок выполняются раньше запрещающих правил всех управляемых селекторов.
Префиксное сопоставление `-i prefix+` разрешено только в таком запрещающем защитном
правиле. Оно никогда не используется для `ACCEPT`, NAT или маршрутов.

## 5. Жизненный цикл сервиса

### 5.1. Запуск

Базовая модель:

```text
START
  ↓
LOCK
  ↓
CLEANUP
  ↓
LOAD + VALIDATE CONFIG
  ↓
APPLY
  ↓
RUN
```

Любая ошибка до перехода в `RUN` является фатальной.

### 5.2. Runtime-каталог и блокировка экземпляра

Runtime-каталог по умолчанию:

```text
/run/vpn-gateway
```

Файл пожизненной блокировки по умолчанию:

```text
/run/vpn-gateway/vpn-gatewayd.lock
```

Перед открытием файла блокировки daemon безопасно создаёт при необходимости и проверяет
runtime-каталог:

- последний компонент пути не должен быть символической ссылкой;
- существующий объект обязан быть каталогом;
- режим доступа обязан быть `0700`;
- владелец обязан совпадать с ожидаемой учётной записью сервиса для текущего способа
  развёртывания;
- если каталог отсутствует и процесс имеет право его создать, он создаётся с режимом
  `0700`;
- неправильные владелец или режим существующего каталога не исправляются молча через
  `chmod`/`chown`, а считаются фатальной ошибкой.

При текущем запуске от root ожидаемый владелец — UID 0. При будущем запуске systemd от
отдельного служебного пользователя ожидается владелец, соответствующий этой учётной записи.

Файл блокировки открывается с `O_NOFOLLOW`, режимом `0600` и удерживает неблокирующую
эксклюзивную `flock` в течение всего времени жизни процесса. Занятая блокировка
диагностируется отдельной ошибкой о том, что другой экземпляр уже запущен.

Отдельный настраиваемый общий путь блокировки не вводится без реального сценария
одновременного запуска нескольких экземпляров.

### 5.3. Штатное завершение и сигналы

Обработчики сигналов `SIGTERM`/`SIGINT` устанавливаются **до первой фазы запуска**.
Обработчик не выполняет операций с ядром и только устанавливает признак завершения.

Во время `STARTING` этот признак проверяется на границах фаз:

```text
install handlers
  ↓
LOCK
  ↓ checkpoint
CLEANUP
  ↓ checkpoint
LOAD + VALIDATE CONFIG
  ↓ checkpoint
APPLY
  ↓ checkpoint
RUN
```

Если сигнал пришёл до получения пожизненной блокировки, процесс выходит без очистки: он
ещё не владеет ресурсами шлюза.

Если сигнал пришёл после получения блокировки:

- завершить текущую ограниченную по времени фазу;
- на ближайшей границе не начинать следующую;
- если завершённая фаза могла создать состояние в ядре (`APPLY`), выполнить
  универсальную `cleanup()`;
- если после уже успешной начальной `cleanup()` запуск ещё не создавал состояние в ядре,
  дополнительная очистка не обязательна;
- выйти без перехода в `RUN`.

Критическая контрольная точка существует после успешного `APPLY` и **до перехода в `RUN`**.
Если используется `Type=notify`, она также находится до отправки `READY=1`: сигнал в окне
после `ip_forward=1` не должен оставлять управляемую daemon'ом пересылку без очистки.

После входа в `RUN`:

```text
SIGTERM/SIGINT
 ↓
shutdown flag + wakeup serialized event loop
 ↓
CLEANUP
 ↓
EXIT
```

Для пробуждения блокирующего цикла обработки событий обработчик сигнала использует
`signal.set_wakeup_fd()` или эквивалент self-pipe, чтобы штатное завершение не ожидало
периодического тайм-аута.

`SIGHUP` игнорируется: перезагрузка конфигурации архитектурой не предусмотрена, журнал
пишется в `stderr`/systemd journal, а повторное открытие файлов по HUP не требуется.

Если финальная `cleanup()` не смогла подтвердить полную очистку, процесс завершается с
ошибкой.

Для развёртывания под systemd предпочтителен `Type=notify` с `WatchdogSec`, если
реализация поддерживает `sd_notify`. Это не меняет семантику жизненного цикла: `READY=1`
может отправляться только после успешного `APPLY` и прохождения последней контрольной точки,
а watchdog подтверждает живость сериализованного цикла обработки событий.

### 5.4. Рекомендации по развёртыванию

Рекомендуемая конфигурация systemd:

```text
RuntimeDirectory=vpn-gateway
RuntimeDirectoryMode=0700
Restart=on-failure
RestartSec=<bounded delay>
StartLimitIntervalSec=<bounded window>
StartLimitBurst=<bounded count>
ExecStopPost=<best-effort ip_forward=0 safety action>
```

`RuntimeDirectory` остаётся предпочтительным способом развёртывания и особенно важен при
будущей работе не от root. Но корректность автономного daemon не зависит от systemd: если
процесс имеет право создать runtime-каталог, он делает это сам и затем применяет ту же
проверку безопасности.

`ExecStopPost` является вторичным механизмом отказа с запретом на случай `SIGKILL`,
тайм-аута watchdog или аварии процесса, когда Python-очистка физически не выполнилась.
Ошибка этого страховочного механизма не заменяет очистку daemon и не маскируется как
успешная очистка.

Развёртывание не должно постоянно задавать `net.ipv4.ip_forward=1` через `sysctl.d`.
Runtime-владелец этого sysctl — `vpn-gatewayd`.

Другие средства управления фильтрацией могут иметь собственные правила `INPUT`/`OUTPUT`
и физически сохраняемые правила `FORWARD`, но пока daemon включает пересылку, его
окончательный префикс `FORWARD` имеет приоритет. Конфигурация, в которой внешний сервис
постоянно переписывает пространство имён `VPNG-*` или переходы daemon-owned префикса,
не поддерживается.

Архитектура не требует `geteuid()==0`. Предпочтительно сохранить возможность работы от
отдельного служебного пользователя с минимальными capabilities/permissions, если
практическое развёртывание подтвердит их достаточность. Контракт безопасности конфигурации
и путей остаётся под контролем root.

## 6. Универсальная очистка

`cleanup()` не зависит от текущей конфигурации и состояния runtime, сохраняемого между запусками. Она используется
перед загрузкой конфигурации при запуске, после аварийного предыдущего запуска и при
штатном завершении.

Успешная очистка означает отсутствие всех ресурсов VPN Gateway, определяемых по маркерам
владения, и `ip_forward=0`.

### 6.1. Маркеры владения

Принятые маркеры:

```text
blackhole routes -> proto 201 + type BLACKHOLE + metric 65536
VPN routes       -> proto 202
iptables chains  -> reserved namespace VPNG-*
owned jumps      -> jumps с target VPNG-*
```

Префикс `VPNG-` целиком зарезервирован daemon'ом в используемых таблицах iptables.

### 6.2. Инвентаризация маршрутов для очистки

Не зависящая от конфигурации очистка **не читает полный snapshot основной таблицы
маршрутизации**.

Для поиска маршрутов по маркерам владения используются выборочные запросы:

```text
ip -j -N -4 route show table main proto 202
ip -j -N -4 route show table main proto 201
```

EXP-004.5 подтвердил, что такие запросы не затрагивают несвязанные сторонние
multipath-маршруты.

При запросе с фильтром по протоколу iproute2 может не печатать поле `protocol`; адаптер
назначает известный протокол из контекста запроса. Для `proto 201` очистка дополнительно
требует `type=BLACKHOLE` и `metric=65536`.

Строгая полная `list_routes()` сохраняется для обычного согласования и по-прежнему
считает ошибкой непредставимые формы multipath/nhid, а не пропускает их молча.

### 6.3. Порядок очистки

1. по схеме «прочитать перед записью» привести `ip_forward` к 0 и **подтвердить**
   результат;
2. только после подтверждённого `ip_forward=0` выполнить выборочную инвентаризацию и
   удалить `proto 202`;
3. прочитать состояние фильтрации/NAT и удалить daemon-owned переходы/цепочки точным
   набором правил очистки;
4. только после успешной очистки фильтрации/NAT снова выполнить выборочную инвентаризацию и
   удалить принадлежащие daemon маршруты `proto 201 type BLACKHOLE metric 65536`;
5. новая выборочная инвентаризация маршрутов и фильтрации должна подтвердить полную чистоту.

Подтверждённое `ip_forward=0` является защитным барьером очистки. Если daemon не смог
привести значение к 0 или подтвердить его чтением, очистка немедленно завершается ошибкой и
**не переходит к разрушительным операциям** над фильтрацией, NAT или маршрутами. Сохранение
старой запрещающей политики и blackhole в этом случае безопаснее частичного демонтажа при
возможно продолжающейся пересылке.

EXP-004.4 подтвердил используемую транзакцию очистки отдельно для каждой таблицы на
Debian 13 / iptables-nft 1.8.11: повторяющиеся `-D`, затем `-F/-X`, один `COMMIT`.
Ошибка удаления цепочки не оставляет частично применённую транзакцию таблицы на
проверенной реализации.

### 6.4. Результаты очистки

**SUCCESS**

- `ip_forward=0`;
- нет `proto 202`;
- нет принадлежащих daemon `proto 201 BLACKHOLE metric 65536`;
- нет цепочек/переходов `VPNG-*`.

**FAILURE**

Полная очистка не подтверждена. Запуск не продолжается. Если не подтверждено
`ip_forward=0`, дальнейший демонтаж ресурсов вообще не выполняется. Blackhole-маршруты не
снимаются, если очистка остальных принадлежащих daemon ресурсов не подтверждена.

### 6.5. Никаких слепых полных очисток

Запрещено:

- очищать целиком таблицу маршрутизации;
- очищать целиком таблицу `filter` или `nat`;
- удалять сторонние маршруты вне области точных защищаемых префиксов, за которые отвечает
  daemon;
- удалять сторонние правила фильтрации, не являющиеся принадлежащим daemon переходом в
  `VPNG-*`.

Точные защищаемые префиксы остаются отдельной областью ответственности daemon при обычном
согласовании; универсальная очистка этим исключением не пользуется.

## 7. Загрузка и проверка конфигурации

### 7.1. Runtime-проекция конфигурации

После успешной `cleanup()` daemon разбирает TOML-документ и строит runtime-проекцию
только для профилей из `managed_vpns`.

На обычный запуск влияют:

1. синтаксическая корректность TOML;
2. схема верхнего уровня runtime-конфигурации
   (`managed_vpns`, `common_allowed_sources`, `reconcile_interval`);
3. возможность однозначно разрешить каждую ссылку из `managed_vpns` к
   `[vpn.<profile>]`;
4. полная проверка схемы, значений и семантики только выбранных управляемых описаний
   профилей;
5. конфликты, зависящие от выбора, только внутри набора управляемых профилей.

Тела неуправляемых `[vpn.*]` не создают runtime-state и **не проходят проверку значений
и схемы при обычном запуске**. Ошибочный IP, отсутствующее поле, неизвестный ключ профиля
или иной дефект неуправляемого описания не должен останавливать работающий шлюз.

Это сознательно разделяет:

```text
TOML document + selection
        ↓
validated managed runtime projection
```

`VpnGatewayDaemon` получает только проверенную runtime-проекцию управляемых профилей.

### 7.2. Проверка вне запуска: `--check-config`

`--check-config` дополнительно анализирует весь каталог описаний профилей.

Для набора управляемых профилей он выдаёт те же `ERROR`, которые сделали бы обычный
запуск невалидным.

Для неуправляемых описаний и конфликтов, возникающих только при их возможной будущей
совместной активации, он выдаёт `WARNING`, например:

- некорректное значение поля;
- отсутствующее или неизвестное поле профиля;
- некорректный идентификатор профиля;
- конфликт интерфейсов;
- пересечение маршрутов;
- пересечение `routes` с `vpn.network`;
- неоднозначные без учёта регистра описания профилей;
- безвредные точные дубликаты в списках с семантикой множества.

Наличие только `WARNING` не меняет код завершения 0.

`NOTE` используется для валидных, но операционно значимых состояний управляемой
конфигурации, которые полезно явно показать оператору. Текущий обязательный `NOTE` —
управляемый профиль с `peers=[]`. `NOTE` также не меняет код завершения.

### 7.3. Область проверки: не накапливать ограничения без причины

Новое правило проверки runtime-конфигурации должно иметь явную цель:

1. runtime-проекцию невозможно однозначно построить;
2. runtime-состояние управляемых ресурсов становится неоднозначным или небезопасным.

Потенциальная проблема только неуправляемого описания профиля относится к проверке вне
запуска, а не к ошибке запуска.

Безвредная избыточность входных данных с семантикой множества не является фатальной
ошибкой и нормализуется: например, дубликаты в `managed_vpns`, точные дубликаты
`routes` одного управляемого профиля и дубликаты ACL.

`peers` — сознательное исключение: порядок элементов задаёт метрики маршрутов, поэтому
дубликат меняет модель приоритета и не является просто избыточностью множества.

Отдельной фазы `preflight()` нет. Проверки безопасности, зависящие от состояния ядра,
входят в построение и проверку начального плана согласования. В частности,
`_validate_plan()` запрещает удаление `proto kernel`; точный защищаемый префикс,
совпадающий с подключённым маршрутом `proto kernel` хоста, приводит к ошибке, блокирующей
запуск до любых побочных изменений маршрутов.

## 8. Применение и согласование во время runtime

Запуск и runtime используют одну модель политики и привязки, но различаются обработкой
ошибок: при запуске действует жёсткий отказ, а в `RUN` daemon может переходить в
`DEGRADED` или `ISOLATED`.

### 8.1. Неизменяемый snapshot согласования

Каждый завершённый цикл согласования использует один неизменяемый snapshot уровня daemon:

```text
ReconciliationSnapshot
    interfaces
    resolutions_by_profile
    readiness_by_profile
    desired_routes_by_profile
    desired_full_policy
```

Точные имя и тип относятся к деталям реализации. Обязательная семантика: snapshot является
одной зафиксированной интерпретацией одной заново прочитанной инвентаризации интерфейсов и
неизменяемой конфигурации.

Селектор каждого управляемого профиля разрешается в одно из состояний:

```text
ABSENT
BOUND(name, ifindex)
AMBIGUOUS(matches...)
```

Готовность вычисляется по тому же snapshot интерфейсов:

```text
ready = BOUND
        AND expected local_address присутствует на bound interface
```

Из конфигурации и этого неизменяемого snapshot привязки/готовности daemon один раз строит
полную требуемую политику фильтрации/NAT и требуемые маршруты. Селекторы, готовность и
требуемое состояние не пересчитываются между фазами построения, применения и проверки
одного цикла.

Это **не** означает атомарную транзакцию ядра между отдельными операциями с маршрутами,
интерфейсами и фильтрацией. Snapshot гарантирует только внутреннюю согласованность одного
цикла оркестрации.

### 8.2. Применение при запуске

После успешной очистки и проверки конфигурации:

1. проверить обязательное условие отключённой IPv6-пересылки (§2.6);
2. прочитать snapshot интерфейсов и адресов;
3. разрешить селекторы и проверить неоднозначность runtime-среды;
4. неоднозначность при запуске является фатальной до `ip_forward=1`;
5. построить требуемую политику фильтрации/NAT:
   - структурные цепочки, переходы и защитные правила;
   - точные разрешающие правила `INPUT`/`FORWARD`, зависящие от привязки, только для
     готовых профилей;
   - точный `MASQUERADE`, зависящий от привязки, только для готовых профилей;
6. применить таблицу `filter`, затем `nat`; каждая таблица применяется атомарно в
   пределах своего `COMMIT`;
7. проверить фильтрацию/NAT относительно того же snapshot привязки;
8. прочитать строгий полный snapshot маршрутов;
9. построить и проверить требуемый план маршрутов:
   - `BLACKHOLE` всегда;
   - `UNICAST` только для готового профиля и только с точным именем привязанного
     интерфейса;
10. применить план маршрутов; отсутствующие `BLACKHOLE` добавляются первой фазой;
11. заново прочитать и проверить маршруты относительно того же требуемого snapshot;
12. зафиксировать локальные для процесса OWNED-маршруты и подтверждённое состояние
    привязки/готовности;
13. по схеме «прочитать перед записью» включить `ip_forward=1` самым последним и
    подтвердить результат.

Если любой этап до последнего подтверждения неуспешен, запуск завершается фатальной
ошибкой, а пересылка не должна оставаться включённой.

### 8.3. Требуемые маршруты

`RouteSpec` типа `BLACKHOLE` выводится только из конфигурации:

```text
destination = profile.route
type        = BLACKHOLE
proto       = 201
metric      = 65536
interface   = None
```

`RouteSpec` типа `UNICAST` выводится из конфигурации **и готовой жесткой привязки**:

```text
destination = profile.route
via         = peer
interface   = binding.name
proto       = 202
metric      = 10,20,30...
onlink      = true
```

Префиксный селектор никогда не попадает в `RouteSpec`.

### 8.4. Согласование во время runtime

Каждый runtime-цикл согласования сериализован единым циклом обработки событий и запускается
по значимому Netlink-событию, периодическому таймеру, полной пересверке либо
административной команде.

#### Ошибка инвентаризации интерфейсов

Заново прочитанная инвентаризация интерфейсов критична для политики: без неё daemon не
может достоверно вычислить состояние `INPUT`/`FORWARD`/NAT, зависящее от привязки.

Если чтение или разбор инвентаризации интерфейсов не завершены либо весь этап разрешения
селекторов нельзя достоверно завершить:

1. по возможности привести `ip_forward=0`;
2. перейти в `ISOLATED`;
3. не выполнять слепое восстановление NAT и разрешающей политики, зависящих от привязки;
4. если состояние фильтрации читаемо, предпочесть безопасный изолирующий фильтр (§8.6),
   выводимый только из конфигурации и не требующий жесткой привязки;
5. повторить попытку на следующем сериализованном цикле согласования.

Обычный результат одного профиля `AMBIGUOUS` не относится к этому классу ошибок
наблюдаемости: он обрабатывается как `FAIL` профиля и состояние `DEGRADED` (§8.5).

#### Обычный цикл

После успешной инвентаризации интерфейсов:

1. построить один неизменяемый `ReconciliationSnapshot`;
2. сравнить текущую идентичность и число совпадений привязки, а также готовность, с последним
   подтверждённым состоянием привязки/готовности;
3. при переходе, меняющем политику, по возможности привести `ip_forward=0`;
4. прочитать текущее состояние фильтрации/NAT;
5. если инвентаризация либо каноническая интерпретация даёт `UNKNOWN`:
   - по возможности выключить пересылку;
   - перейти в `ISOLATED`;
   - не выполнять слепое восстановление;
6. если текущая политика = `UNSAFE` либо переход, меняющий политику, требует повторного
   применения ресурсов, выполнить восстановление с первоначальным запретом (§8.6);
7. только после состояния `SAFE` полной требуемой политики фильтрации/NAT прочитать строгий
   полный snapshot маршрутов;
8. построить, проверить, применить и повторно проверить план маршрутов из того же
   `ReconciliationSnapshot`;
9. зафиксировать OWNED и подтверждённое состояние привязки/готовности только после успешной
   проверки;
10. после успешно завершённых проверок политики и маршрутов привести `ip_forward`, которым
    daemon управляет эксклюзивно, к требуемому значению.

Сменой привязки считаются как минимум:

- `BOUND -> ABSENT`;
- `ABSENT -> BOUND`;
- `BOUND(name/ifindex A) -> BOUND(name/ifindex B)`;
- переход в `AMBIGUOUS` или выход из него.

Сменой готовности считается изменение присутствия ожидаемого `local_address` при
неизменной жесткой привязке. Оба класса изменений являются переходами, меняющими
политику, и используют один порядок восстановления.

### 8.5. Неоднозначность во время runtime

Для профиля в состоянии `AMBIGUOUS` требуемая политика обеспечивает отказ с запретом:

- отсутствует разрешающее правило `INPUT`, зависящее от привязки;
- отсутствует разрешающее правило `FORWARD`, зависящее от привязки;
- отсутствует `MASQUERADE`, зависящий от привязки;
- отсутствуют маршруты `UNICAST proto 202`;
- сохраняются защитные `BLACKHOLE`;
- защищаемые назначения продолжают получать окончательный `REJECT`;
- сохраняются запрещающие правила селектора для `INPUT` и входящего `FORWARD`
  (`VPNG-INPUT-GUARD` и `VPNG-INGRESS`).

После применения и проверки этого состояния daemon может снова включить глобальную
пересылку для остальных профилей, но общее состояние жизненного цикла остаётся
`DEGRADED`, а профиль — `FAIL` до устранения неоднозначности.

### 8.6. Состояние безопасности фильтрации и восстановление с первоначальным запретом

Состояние фильтрации/NAT использует именованные значения:

```text
SAFE     -> безопасно
UNSAFE   -> небезопасно
UNKNOWN  -> состояние неизвестно
```

Полное ожидаемое состояние зависит от неизменяемого `ReconciliationSnapshot`.

Отдельно слой политики обязан уметь построить **изолирующий фильтр**, выводимый только из
конфигурации:

```text
desired_isolation_filter(config)
```

Он не содержит правил `ACCEPT`, зависящих от привязки, и не требует инвентаризации
интерфейсов. Он сохраняет только структурную политику фильтрации с отказом с запретом:

- запрещающие правила `INPUT` управляемых селекторов;
- запрещающие правила входящего `FORWARD`-трафика управляемых селекторов;
- `REJECT` транспортных сетей VPN;
- безусловные `REJECT` защищаемых назначений;
- окончательный `VPNG-FORWARD-DENY`;
- необходимые структурные цепочки и переходы.

Состояние `UNKNOWN` никогда не восстанавливается вслепую. Daemon по возможности выключает
пересылку и остаётся в `ISOLATED`.

Для подтверждённого `UNSAFE` либо перехода, меняющего политику, применяется
последовательность с первоначальным запретом:

```text
1. best-effort ip_forward=0

2. применить изолирующий фильтр как полное требуемое daemon-owned состояние filter
   для этой промежуточной стадии; все устаревшие ACCEPT, зависящие от привязки,
   для всех профилей должны быть удалены
3. проверить изолирующий фильтр
   - эта проверка подтверждает только защитный барьер
   - она НЕ означает SAFE полной политики

4. применить требуемый NAT для текущего неизменяемого snapshot
5. проверить требуемый NAT

6. применить полный требуемый filter с точными ACCEPT, зависящими от привязки
7. проверить полный требуемый filter
   - только после проверки NAT + полного filter состояние firewall/NAT может быть SAFE

8. согласовать и проверить маршруты

9. только после полной успешной проверки:
       включить/подтвердить пересылку согласно требуемому состоянию
```

Изолирующий фильтр применяется как **полное** daemon-owned состояние таблицы `filter` на
промежуточной стадии. Поэтому на время защитного барьера разрешающие правила всех
управляемых профилей временно отсутствуют и вся управляемая пересылка запрещена, включая
профили, чья привязка не менялась. Сохранение разрешающих правил «незатронутых» профилей
не является допустимой оптимизацией этого протокола восстановления.

Применение изолирующего фильтра не изменяет таблицу `nat`. Ранее применённые правила NAT
могут временно оставаться в ядре за уже проверенным запрещающим барьером до шага 4, где
требуемый NAT для текущего snapshot применяется и проверяется. Наличие старого NAT за
проверенным фильтрующим барьером само по себе не открывает путь пересылки.

Этот порядок обязателен даже если `set_ip_forward(False)` завершился ошибкой. Благодаря
этому полный `ACCEPT` для `FORWARD` не появляется раньше проверенного NAT.

Если изолирующий фильтр не удалось применить или проверить, daemon остаётся в `ISOLATED`
и не переходит к NAT, полному фильтру и маршрутам.

Простая глобальная перестановка `nat -> filter` запрещена: при уже небезопасном или
разрешающем фильтре она оставила бы разрешённую пересылку активной дольше. Защитным
барьером является именно фильтр с первоначальным запретом.

Если пересылка подтверждена выключенной, реализация может оптимизировать технические детали
транзакций только при сохранении той же наблюдаемой семантики безопасности.

### 8.7. Исполнитель маршрутов

Порядок изменений маршрутов сохраняется:

```text
1. добавить отсутствующие BLACKHOLE
2. удалить конкурирующие точные маршруты
3. выполнить определяющие замены
4. добавить оставшиеся маршруты
```

Проверка плана маршрутов сохраняет определяющую семантику точного префикса и запрет
изменения `proto kernel`.

### 8.8. OWNED и фиксация привязки/готовности

Локальные для процесса OWNED-маршруты и последнее подтверждённое состояние привязки/готовности
изменяются только после завершённой успешной проверки соответствующего цикла.

Порядок запуска остаётся:

```text
проверить маршруты/политику
-> зафиксировать process-local OWNED + состояние привязки/готовности
-> включить и подтвердить ip_forward
```

Фиксация после включения пересылки запрещена: неожиданная ошибка локальной для процесса фиксации не
должна превращать применение в неуспешное уже после включения пересылки.

### 8.9. Состояние жизненного цикла

```text
недостаточная наблюдаемость интерфейсов/политики -> ISOLATED
firewall != SAFE                              -> ISOLATED
firewall == SAFE
  AND все управляемые профили SUCCESS
  AND ip_forward == 1                         -> ACTIVE
firewall == SAFE, остальные проверки
  профилей/политики завершены                 -> DEGRADED
```

Профиль `ABSENT` или неготовый профиль сам по себе не является ошибкой, если его
требуемое состояние blackhole/запрета успешно применено и проверено. `AMBIGUOUS`
является `FAIL` профиля.

`ACTIVE` означает, что **требуемое состояние политики в ядре полностью реализовано**, а
не то, что доказана связность с удалённой стороной VPN через туннель. Семантика результатов
профиля `SUCCESS`/`FAIL` определена в §23.9. Поэтому операционный статус обязан отдельно
показывать для каждого профиля селектор, привязку, готовность и результат маршрутизации.

Ручной `sysctl -w net.ipv4.ip_forward=0` не является административной паузой; успешно
завершённый чистый цикл согласования восстанавливает требуемое значение `ip_forward`,
которым daemon управляет эксклюзивно.

## 9. Фильтрация и blackhole

Политика фильтрации daemon-owned ресурсов состоит из структурной части и части, зависящей
от привязки.

Структурная часть существует для всех управляемых профилей независимо от готовности:

- зарезервированные цепочки `VPNG-*`;
- детерминированный префикс переходов из встроенных цепочек;
- `VPNG-RESERVED`;
- окончательные запреты защищаемых назначений в цепочках профилей;
- `VPNG-INPUT-GUARD`;
- `VPNG-FORWARD-DENY`.

Часть, зависящая от привязки, строится только для точных интерфейсов готовых жестких
привязок.

### 9.1. Порядок переходов из встроенных цепочек

Профили во всех daemon-owned префиксах сортируются лексикографически по нормализованному
идентификатору профиля в верхнем регистре, по ASCII-коду символов. Порядок не зависит от
locale и должен совпадать в Python- и Rust-реализациях.

`INPUT`:

```text
1..N   -> VPNG-<PROFILE>-INPUT, в порядке профилей
N+1    -> VPNG-INPUT-GUARD
далее  -> сторонние правила INPUT
```

`FORWARD` в проверенном требуемом состоянии:

```text
1      -> VPNG-INGRESS
2      -> VPNG-RESERVED
3..    -> VPNG-<PROFILE>-FORWARD, в порядке профилей
last   -> VPNG-FORWARD-DENY
далее  -> сторонние правила FORWARD
```

`POSTROUTING`:

```text
1..N   -> VPNG-<PROFILE>-NAT, в порядке профилей
далее  -> сторонние правила
```

Положение daemon-owned префикса является частью проверяемой политики во всех трёх
встроенных цепочках. Стороннее правило или переход, вставленные перед ожидаемым префиксом
`INPUT`, `FORWARD` или `POSTROUTING`, считаются рассогласованием `UNSAFE`.
Восстановление возвращает daemon-owned префикс на позицию 1 и физически сдвигает сторонние
правила после него, не удаляя их.

Для `FORWARD` это необходимо для сохранения полного владения решением через
`VPNG-FORWARD-DENY`. Для `INPUT` это не позволяет раннему стороннему `ACCEPT`
обойти защиту управляемых VPN-интерфейсов. Для `POSTROUTING` это гарантирует, что
daemon-owned NAT обрабатывается раньше сторонних преобразований.

Каждая NAT-цепочка профиля при несовпадении возвращает управление через `RETURN`.
Поэтому сторонние правила `POSTROUTING` после daemon-owned префикса сохраняются и
остаются достижимыми для неуправляемого исходящего трафика.

`OUTPUT` не входит в область управления VPN Gateway: daemon не создаёт, не изменяет, не
переставляет и не удаляет правила этой цепочки. Политика `OUTPUT` принадлежит
администратору хоста.

Следствие: локально созданный на самом gateway трафик не проходит ACL источников
`FORWARD` и может использовать установленные защищаемые маршруты. Это сознательная часть
модели доверенного выделенного хоста; ограничение локального `OUTPUT` остаётся
ответственностью администратора.

Каждый daemon-переход существует ровно один раз и использует обычный `-j`.

### 9.2. Семантика INPUT

Цепочка `INPUT` профиля содержит точные правила, зависящие от привязки, только когда
профиль готов:

```text
-i <точный-интерфейс>
ctstate INVALID
    DROP

-i <точный-интерфейс>
ctstate ESTABLISHED,RELATED
    ACCEPT

-i <точный-интерфейс>
    REJECT --reject-with icmp-host-prohibited

RETURN
```

Таким образом, удалённая сторона VPN не может инициировать новое соединение с самим
gateway через управляемый VPN-интерфейс. Разрешён только ответный
`ESTABLISHED,RELATED`-трафик на соединения, инициированные локально самим хостом.
Если в будущем потребуется публиковать локальный сервис на VPN-интерфейсе, это должно быть
отдельным явным расширением политики, а не следствием общей транспортной сети
`profile.network`.

Если профиль не готов или находится в `AMBIGUOUS`, точный блок отсутствует и цепочка
возвращает управление.

После цепочек профилей `VPNG-INPUT-GUARD` с отказом с запретом блокирует входящий трафик
всех настроенных управляемых селекторов, который не был завершён более ранней точной
цепочкой профиля.

Для точного селектора защитное правило использует точное имя интерфейса. Для префиксного
селектора используется проверенное EXP-005 запрещающее сопоставление `-i prefix+`.
Сопоставление по префиксу никогда не используется для `ACCEPT` или NAT.

Трафик, не относящийся ни к одному управляемому селектору, после daemon-owned префикса
`INPUT` продолжает обрабатываться базовой фильтрацией хоста.

### 9.3. Семантика FORWARD

`VPNG-INGRESS` сначала содержит точный блок для каждой **готовой жесткой привязки**:

```text
-i <точный-интерфейс>
ctstate INVALID
    DROP

-i <точный-интерфейс>
ctstate ESTABLISHED,RELATED
    ACCEPT

-i <точный-интерфейс>
    REJECT --reject-with icmp-host-prohibited
```

После всех точных блоков `VPNG-INGRESS` содержит запрещающее правило для каждого
управляемого селектора в детерминированном порядке профилей:

```text
точный селектор:
    -i <точное-имя>
        REJECT --reject-with icmp-host-prohibited

префиксный селектор:
    -i prefix+
        REJECT --reject-with icmp-host-prohibited

RETURN
```

Точный блок готового интерфейса расположен раньше соответствующего запрещающего правила.
Поэтому установленный ответный трафик готовой жесткой привязки может завершиться
`ACCEPT`, а новый, ещё не привязанный интерфейс управляемого префиксного семейства
останавливается в `VPNG-INGRESS` и не достигает разрешающих цепочек профилей.

Префиксное сопоставление используется здесь только для запрета. Оно не применяется в
`ACCEPT`, NAT или маршрутах.

`VPNG-RESERVED` всегда выполняет `REJECT` для назначения в любой управляемой
`vpn.network`.

Цепочка `FORWARD` профиля для каждого защищаемого назначения:

```text
если профиль готов:
    -d route -o <точный-интерфейс> ctstate INVALID
        DROP

    для каждого effective_source:
        -s source -d route -o <точный-интерфейс>
            ACCEPT

всегда:
    -d route
        REJECT --reject-with icmp-host-prohibited

RETURN
```

Отсутствие `-i` в разрешающем правиле профиля не предоставляет обратный доступ через
управляемые VPN-интерфейсы: такой входящий трафик уже обязан завершиться внутри
`VPNG-INGRESS`. Это сохраняет возможность принимать разрешённый LAN-трафик с любого
неуправляемого локального интерфейса.

После всех цепочек профилей `VPNG-FORWARD-DENY` обеспечивает полное владение решением
`FORWARD`:

```text
ctstate INVALID
    DROP

всё остальное
    REJECT --reject-with icmp-host-prohibited
```

В проверенном требуемом состоянии ни один пересылаемый IPv4-пакет при daemon-owned
`ip_forward=1` не достигает сторонних правил `FORWARD` или встроенной политики.

### 9.4. Fail2ban

Fail2ban может существовать как отдельный более ранний перехватчик nftables для `INPUT`. Он не
участвует в политике `FORWARD` и не меняет детерминированный порядок переходов
`VPNG-*` внутри iptables `INPUT`.

### 9.5. Blackhole

Blackhole-маршруты устанавливаются для всех защищаемых маршрутов управляемых профилей:

```text
proto 201
metric 65536
type blackhole
```

Blackhole не зависит от привязки или готовности.

EXP-004.2 подтвердил: при исчезновении зависящего от интерфейса `proto 202` UNICAST
blackhole остаётся и не даёт защищаемому назначению уйти через маршрут по умолчанию.

Blackhole не заменяет фильтрацию: полная политика `FORWARD` остаётся независимым слоем
отказа с запретом.

## 10. VPN-маршруты

Все VPN-маршруты, создаваемые сервисом, должны иметь:

```text
proto 202
```

Это обязательный маркер владения.

Он позволяет `cleanup()` обнаруживать VPN-маршруты после:

- `kill -9`;
- OOM;
- аварийного завершения процесса;
- изменения конфигурации между запусками.

Очистка удаляет только принадлежащие сервису маршруты `proto 202`.

## 11. NAT

Для каждого управляемого профиля существует структурная цепочка:

```text
VPNG-<PROFILE>-NAT
```

и детерминированный переход из `POSTROUTING` к ней.

`MASQUERADE` больше не является статическим правилом, выводимым только из конфигурации.

Если профиль готов и имеет жесткую привязку, требуемая цепочка:

```text
-o <точный-интерфейс>
-m addrtype ! --src-type LOCAL
-j MASQUERADE

RETURN
```

Если профиль отсутствует, не готов или находится в `AMBIGUOUS`:

```text
RETURN
```

Строка префиксного селектора никогда не используется как аргумент интерфейса в NAT.

При переходе, меняющем политику, daemon отключает пересылку до повторного применения и
проверки фильтрации/NAT, зависящих от привязки. NAT должен быть проверен до
добавления или восстановления маршрутов `proto 202` через новое точное имя интерфейса.

Сторонние правила `POSTROUTING` не удаляются. Если NAT-цепочка профиля не совпала с
трафиком, её `RETURN` передаёт обработку последующим сторонним правилам.

Тем самым сохраняется зависимость безопасности:

```text
привязка разрешена
-> точная политика filter/NAT применена и проверена
-> маршруты применены
-> пересылка включена/восстановлена
```

Сторонний маршрут через управляемый точный интерфейс не обходит политику daemon, потому
что полное владение решением `FORWARD` разрешает исходящий трафик только явным
`ACCEPT` соответствующего профиля.

### 11.1. Окно реакции на событие

Старая статическая модель NAT имела удобное свойство: правило уже существовало до
появления интерфейса. Для префиксного селектора это невозможно без разрешающего
сопоставления по префиксу, которое архитектура запрещает.

Поэтому NAT, зависящий от привязки, создаётся только после обнаружения точного интерфейса.

Между событием ядра и согласованием существует ограниченное окно реакции (§4.4). До
согласования новый интерфейс не получает маршрут `proto 202` профиля или точное
разрешающее правило `FORWARD`; blackhole и окончательный запрет `FORWARD` предотвращают
управляемый транзит через него.

Быстрое повторное использование прежнего точного имени интерфейса остаётся гонкой в
границах модели доверенного хоста и обнаруживается по изменению ifindex на ближайшем
Netlink-событии или полной пересверке.

## 12. Конфигурация

Конфигурационный файл по умолчанию:

```text
/etc/vpn-gateway/vpn-gateway.toml
```

Формат конфигурации — TOML.

Конфигурационный файл должен принадлежать `root` и не быть доступен для записи классам
group/other. Нарушение этого требования является фатальной ошибкой и проверяется как при
обычном запуске, так и в `--check-config`.

Последний компонент пути конфигурационного файла должен быть **обычным файлом, а не
символической ссылкой**. Проверка выполняется через `lstat` до чтения. Причина та же, что
у проверки родительского каталога: защищённая символическая ссылка внутри
`/etc/vpn-gateway` могла бы указывать на файл, чей содержащий каталог допускает иную
подмену через `rename` и тем самым обходить принятую модель безопасности пути.

Родительский каталог `/etc/vpn-gateway` также должен принадлежать `root` и не быть
доступен для записи group/other. Проверка каталога обязательна, потому что возможность
записи в него позволила бы подменить защищённый конфигурационный файл атомарным rename.

Причины выбора TOML:

- есть штатный `tomllib` в Python 3.13;
- нет исполняемого shell-конфига;
- есть нормальные массивы и таблицы;
- формат пригоден для будущей Rust-реализации.

Пример:

```toml
reconcile_interval = 10.0

managed_vpns = [
    "primary",
    "backup",
]

common_allowed_sources = [
    "10.200.200.8",
    "10.200.200.9",
]

[vpn.primary]
interface = "vpns+"
network = "172.20.130.0/29"
local_address = "172.20.130.1"
peers = [
    "172.20.130.6",
]
routes = [
    "10.0.0.0/8",
]
allowed_sources = [
    "10.200.201.0/24",
]

[vpn.backup]
interface = "wg0"
network = "172.20.126.0/29"
local_address = "172.20.126.1"
peers = [
    "172.20.126.2",
]
routes = [
    "100.64.0.0/10",
    "192.168.0.0/16",
]
allowed_sources = []
```

Каждая секция `[vpn.<profile>]` является **описанием VPN-профиля**. Само наличие
описания не создаёт runtime-ресурсов.

Поле верхнего уровня `managed_vpns` выбирает описания, которыми daemon управляет в
текущем запуске. Профиль, отсутствующий в `managed_vpns`, является неуправляемым:
daemon не отслеживает его интерфейс и не создаёт для него правил фильтрации, маршруты или blackhole.

`managed_vpns` имеет семантику множества; порядок элементов не задаёт приоритет.
Ссылки разрешаются без учёта регистра к уникальным идентификаторам профилей и
нормализуются к написанию соответствующего описания.

Если одинаковые без учёта регистра `[vpn.*]` существуют только среди неуправляемых
описаний, обычный запуск их не проверяет; `--check-config` выдаёт `WARNING`. Если ссылка
из `managed_vpns` разрешается неоднозначно, runtime-проекцию построить нельзя — это
фатальная ошибка запуска.

## 13. Закрытая схема конфигурации

Неизвестные ключи и секции **верхнего уровня** являются фатальной ошибкой обычного запуска.
Ошибки схемы и значений внутри `[vpn.<profile>]` являются фатальными только для профиля,
выбранного в `managed_vpns`; для неуправляемого описания они диагностируются как `WARNING`
только в `--check-config` (§7).

Базовая схема:

```text
reconcile_interval          float, optional, default 10.0, range [1.0, 60.0]
managed_vpns                 array[string], required, non-empty selection
common_allowed_sources       array[string], required

[vpn.<profile>]              profile definition sections
interface                    string selector, required
network                      string, required
local_address                string, required
peers                        array[string], required
routes                       array[string], required
allowed_sources              array[string], required
```

Схема полей профиля выше является обязательным runtime-контрактом для описаний, выбранных
в `managed_vpns`. Для неуправляемых секций тот же контракт используется только
`--check-config` и не блокирует обычный запуск.

`reconcile_interval` — необязательное поле верхнего уровня. `managed_vpns` и
`common_allowed_sources` обязательны. Полная проверка схемы и значений профиля
применяется только к описаниям из `managed_vpns`; тела неуправляемых профилей являются
входом для проверки вне запуска.

Имя `<profile>` является административным идентификатором VPN-профиля и не имеет
протокольной семантики для `vpn-gatewayd`.

Допустимый формат имени профиля:

```text
[A-Za-z][A-Za-z0-9_-]{0,14}
```

То есть имя:

- имеет длину 1..15 символов;
- начинается с ASCII-буквы;
- далее содержит только ASCII-буквы, цифры, `_` и `-`;
- не содержит пробелов, точек, `/`, `@`, `*` и иной TOML-экзотики.

Количество VPN-профилей произвольно. Сервис не содержит списка известных VPN-протоколов
и не интерпретирует имена профилей как `OpenConnect`, `WireGuard`, `OpenVPN`,
`L2TP` и т. п.

Имена профилей уникальны без учёта регистра: например, `primary` и `PRIMARY`
одновременно запрещены.

`managed_vpns`:

- после нормализации должен содержать хотя бы один идентификатор профиля;
- каждая ссылка обязана разрешаться к существующему `[vpn.<profile>]`;
- порядок не имеет семантики;
- точные и совпадающие без учёта регистра дубликаты не меняют выбор, нормализуются во
  время runtime без ошибки; `--check-config` выдаёт предупреждение.

Имена цепочек ядра строятся детерминированно из имени профиля в верхнем регистре:

```text
VPNG-<PROFILE>-INPUT
VPNG-<PROFILE>-FORWARD
VPNG-<PROFILE>-NAT
```

Ограничение имени профиля в 15 символов выведено из проверенного ограничения
`iptables-nft`: имя цепочки должно быть короче 29 символов. Самая длинная форма
`VPNG-<PROFILE>-FORWARD` при идентификаторе профиля длиной 15 имеет длину 28 символов.

Неизвестный ключ внутри управляемого `[vpn.<profile>]` является фатальной ошибкой обычного
запуска. Тот же дефект внутри неуправляемого описания не блокирует запуск и выдаётся как
`WARNING` в `--check-config`.

При разборе TOML различаются:

- `[vpn."foo.bar"]` — описание с недопустимым именем профиля;
- `[vpn.foo.bar]` — неожиданная вложенная структура.

Если такая структура нужна для построения runtime-проекции управляемого профиля, это
фатальная ошибка обычного запуска. Если дефект относится только к неуправляемому описанию,
обычный запуск его не проверяет, а `--check-config` выдаёт `WARNING`.

## 14. Пустые списки и количество профилей

Для набора управляемых профилей принято:

```text
managed_vpns = []               -> запрещено
managed profile.routes = []     -> запрещено
common_allowed_sources = []     -> разрешено
profile.allowed_sources = []    -> разрешено
peers = []                      -> разрешено
```

Отдельная проверка общего количества профилей не нужна: непустой `managed_vpns` уже
требует существования хотя бы одного описания профиля.

## 15. Селекторы интерфейсов

Поле `interface` проверяется во время runtime только для управляемых описаний;
`--check-config` проверяет также неуправляемые описания.

### 15.1. Точный селектор

Разрешено:

```text
1..15 символов
первый символ: ASCII-буква
остальные: ASCII-буквы, цифры, _, ., -
```

Регулярное выражение:

```text
[A-Za-z][A-Za-z0-9_.-]{0,14}
```

Символ `+` целиком зарезервирован грамматикой селектора для префиксной формы и поэтому
не поддерживается в точном селекторе ни в какой позиции.

Для завершающего `+` есть и прямое техническое основание: `vpn-gateway` использует
iptables, а iptables трактует завершающий `+` в условии по интерфейсу как сопоставление
по префиксу, а не как буквальное точное имя.

Запрещённые точные имена без учёта регистра:

```text
lo
any
default
all
```

### 15.2. Префиксный селектор

Форма:

```text
<prefix>+
```

Префикс соответствует тем же допустимым символам точного имени, начинается с ASCII-буквы
и имеет длину 1..14. Завершающий `+` является оператором селектора и не входит в
конкретное имя интерфейса.

Семантика:

```text
prefix+ -> все имена интерфейсов, начинающиеся с prefix,
           включая имя prefix без суффикса
```

Эта семантика намеренно совпадает с проверенным на целевой системе
`iptables -i prefix+`.

`+` разрешён только один раз и только последним символом селектора.

Буквальное точное имя интерфейса, содержащее `+`, `vpn-gateway` не поддерживает. Это
проектное ограничение следует из выбранной грамматики; для завершающего `+`
дополнительно действует прямое ограничение iptables: такой аргумент означает
сопоставление по префиксу, а не точное совпадение.

Префиксный селектор резервирует на выделенном шлюзе **всё текстовое пространство имён
интерфейсов с данным префиксом** для одного управляемого профиля. Любой посторонний
интерфейс внутри этого пространства участвует в подсчёте совпадений и может намеренно
перевести профиль в `AMBIGUOUS` с отказом с запретом.

### 15.3. Взаимная исключительность управляемых селекторов

Управляемые селекторы должны быть попарно непересекающимися по множеству возможных
конкретных имён.

Проверяется не только строковое равенство.

Примеры фатальных конфликтов:

```text
vpns+ + vpns0
vpns+ + vpns1+
vpns+ + vpns+
```

Для префиксных семейств наложение означает пересечение текстовых пространств имён.
Например:

```text
vpns+   + vpns1+   -> пересечение
vpns1+  + vpns12+  -> пересечение
vpns1+  + vpns2+   -> не пересекаются
```

Если один селектор когда-либо может классифицировать тот же конкретный Linux-интерфейс,
что и другой управляемый селектор, runtime-проекция недопустима.

Администратор обязан использовать разные пространства имён интерфейсов для разных
управляемых экземпляров VPN и не создавать посторонние сетевые интерфейсы внутри зарезервированного
пространства имён префикса.

Ошибка проверки пересечения должна явно называть оба конфликтующих профиля и оба селектора,
чтобы результат `--check-config` был пригоден для непосредственного исправления
конфигурации.

## 16. VPN-сети и адреса

IPv4/CIDR и внутренние контракты локального адреса и адресов удалённых сторон проверяются во время runtime только для
управляемых описаний. `--check-config` проверяет те же контракты для неуправляемых
описаний и выдаёт `WARNING`. Конфликты, зависящие от выбора, фатальны только внутри
набора управляемых профилей.

Для каждого VPN-профиля:

- селекторы `interface` обязаны быть попарно непересекающимися среди управляемых
  профилей; пересечение с неуправляемым описанием не влияет на запуск и является
  предупреждением `--check-config`;
- `network` — канонический IPv4 CIDR;
- `/32` для `network` запрещён: VPN-сеть должна содержать как минимум две точки;
- минимально допустимая сеть — `/31`;
- `local_address` — IPv4 внутри `network`;
- каждый `peer` — IPv4 внутри `network`;
- `peer` не может совпадать с `local_address`;
- значения `peers` внутри управляемого профиля не дублируются: порядок значим и дубликат
  меняет модель приоритета маршрутов; дубликат в неуправляемом описании анализируется
  только `--check-config` и даёт `WARNING`;
- порядок `peers` однозначно задаёт приоритет маршрутов;
- `peers = []` разрешён и означает отсутствие обслуживаемых адресов удалённых сторон в конфигурации.

Для управляемого профиля `--check-config` при `peers=[]` выводит информационный
`NOTE`: маршруты `UNICAST` VPN не будут созданы, защищаемые маршруты останутся под
`BLACKHOLE`. Это не `WARNING` и не ошибка.

Если `peers = []` у управляемого профиля, конфигурация остаётся валидной: маршруты VPN
`UNICAST` не устанавливаются, а защищаемые `routes` остаются под blackhole.
`MASQUERADE`, зависящий от привязки, существует только если профиль готов и имеет
жесткую привязку; само `peers=[]` на готовность NAT не влияет.

Адрес сети и широковещательный адрес не считаются запрещёнными адресами внутри VPN-сети. Для
туннельной семантики «точка-точка» нижний и верхний адрес диапазона могут использоваться
как обычные `local_address` или `peer`.

Поэтому валидатор не должен навязывать Ethernet-семантику сетевого и широковещательного адресов и не должен
применять отдельные запреты к `/31`, кроме общих правил членства в сети и
`peer != local_address`.

`vpn.network` является **транспортной сетью VPN** профиля: она предназначена только для
локального адреса и адресов удалённых сторон туннеля и не входит в удалённое защищаемое адресное пространство.

Для набора управляемых профилей любое пересечение `profile.routes` любого управляемого
профиля с `vpn.network` любого управляемого профиля является фатальной ошибкой
конфигурации. Проверяются точное совпадение, вложение в обе стороны и частичное
пересечение.

Если хотя бы одна сторона конфликта относится к неуправляемому описанию, обычный запуск
его не анализирует; `--check-config` выдаёт предупреждение о том, что соответствующий
набор описаний нельзя одновременно добавить в `managed_vpns`.

Секции `[vpn.<profile>]` являются независимыми описаниями способов добраться до
удалённой стороны, возможно одной и той же.

Поэтому одинаковые адреса удалённых сторон в разных VPN-профилях разрешены и ожидаемы.

## 17. ACL источников

ACL имеет два уровня:

```text
common_allowed_sources
vpn.<profile>.allowed_sources
```

Оба списка разрешают:

- одиночный IPv4;
- IPv4 CIDR.

Одиночный адрес внутри модели нормализуется в `/32`.

CIDR должен быть каноническим сетевым префиксом. Неканонический CIDR, например
`10.200.200.8/24`, является ошибкой и не нормализуется молча в более широкую сеть.

Списки ACL имеют семантику множества: точные дубликаты после нормализации удаляются.
`--check-config` сообщает их как предупреждение; ошибка runtime не требуется, потому что
политика от дубликата не меняется.

Пересечения разрешены. Например, допустимо одновременно иметь:

```text
10.200.200.8/32
10.200.200.9/32
10.200.200.0/24
```

Эффективный ACL конкретного VPN-профиля:

```text
effective_allowed_sources(profile)
    = common_allowed_sources
      ∪ profile.allowed_sources
```

Профильный ACL только расширяет общий. Отрицательных правил, исключений и семантики
запрета нет.

Эта семантика намеренно отличается от `routes`: ACL является набором разрешающих
предикатов, а не описанием маршрутного пространства.

## 18. Маршруты защищаемых сетей

`routes` принадлежит конкретному VPN-профилю и описывает защищаемые сети, направляемые
через его интерфейс.

Правила для набора управляемых профилей:

- только IPv4 CIDR;
- только канонические сетевые префиксы;
- `0.0.0.0/0` запрещён;
- `routes = []` для управляемого профиля запрещён;
- `routes` имеет семантику множества и не задаёт приоритет: точные дубликаты внутри
  одного профиля нормализуются, `--check-config` выдаёт предупреждение;
- любые **нетождественные** пересечения или вложения `routes` внутри одного управляемого
  профиля или между управляемыми профилями запрещены;
- один и тот же точный защищаемый префикс в разных управляемых профилях запрещён как
  конфликт ownership;
- любое пересечение управляемых `routes` с любой управляемой `vpn.network` запрещено
  (§16).

Конфликты `routes`, где хотя бы один профиль неуправляемый, обычным запуском не
анализируются и выдаются только `--check-config` как предупреждения о потенциальной
несовместимости при будущем выборе `managed_vpns`.

Например, недопустимо:

```text
primary:   10.0.0.0/8
backup:    10.20.0.0/16
```

и также:

```text
primary:   10.0.0.0/8
backup:    10.0.0.0/8
```

Хотя маршрутизация Linux умеет выбирать наиболее специфичный префикс, проект намеренно требует
непересекающегося защищаемого маршрутного пространства.

Каждый управляемый защищаемый префикс принадлежит ровно одному управляемому VPN-профилю.

Для каждого `profile.route` создаётся фиксированный набор маршрутов через все `peers`
профиля:

```text
peer[0] -> metric 10
peer[1] -> metric 20
peer[2] -> metric 30
...
```

Порядок `peers` в TOML тем самым определяет приоритет одновременно доступных путей.
`vpn-gatewayd` не отслеживает доступность удалённой стороны и не меняет метрики динамически.

Валидатор проверяет, что вычисленная метрика `(index + 1) * 10` помещается в беззнаковое
32-битное поле приоритета маршрута: `1..4294967295`. Искусственный более низкий лимит числа
`peers` не вводится.

## 19. Состояние VPN и сетевых правил

Структурная запрещающая политика и blackhole не зависят от связности VPN.

Ресурсы, зависящие от привязки, зависят только от разрешённого точного интерфейса и
ожидаемого локального IPv4, а не от рукопожатия VPN или доступности удалённой стороны:

- точные разрешающие правила `INPUT`/`FORWARD`;
- точный `MASQUERADE`;
- маршруты `UNICAST proto 202`.

Временная недоступность удалённой стороны при сохранении той же готовой жесткой привязки
не должна вызывать лишнее перестроение фильтрации/NAT/маршрутов.

Исчезновение или пересоздание точного интерфейса, изменение ifindex, изменение локального
IPv4 либо числа совпадений селектора является сменой привязки/готовности и инициирует
согласование.

При неготовом или неоднозначном состоянии остаются структурная запрещающая политика и
blackhole, а разрешающие правила/NAT/UNICAST, зависящие от привязки, отсутствуют.

## 20. Проверка конфигурации без запуска

Сервис обязан поддерживать режим:

```bash
vpn-gatewayd --check-config
```

Он:

- читает TOML;
- проверяет права и владельца конфигурационного файла;
- проверяет закрытую схему;
- выполняет ту же runtime-проверку для `managed_vpns`;
- отдельно проверяет схему, значения и семантику неуправляемых описаний, а также их
  потенциальные перекрёстные конфликты;
- агрегирует доступные `ERROR`, `WARNING` и `NOTE` за один прогон;
- не получает runtime-блокировку;
- не изменяет маршруты;
- не изменяет iptables;
- не изменяет `ip_forward`;
- не выполняет `cleanup()`;
- завершается с кодом 0, если нет `ERROR`; наличие только `WARNING` код не меняет.
  При `ERROR` код ненулевой.

`--check-config` читает файл без синхронизации с работающим сервисом. Для согласованного
административного обновления конфигурация должна публиковаться атомарной заменой готового
файла (`rename`/`mv` из временного файла).

Рекомендуемый административный порядок:

```bash
vpn-gatewayd --check-config &&
systemctl restart vpn-gateway.service
```

Настоящий запуск сервиса всё равно повторно проверяет конфигурацию.

CLI поддерживает:

```text
--config PATH
```

По умолчанию используется `/etc/vpn-gateway/vpn-gateway.toml`.

`--check-config` проверяет выбранный путь конфигурации и не затрагивает состояние ядра.

## 21. Административный интерфейс

Отдельный IPC может использоваться для простых локальных административных команд, например:

```text
status
shutdown
```

`reload-config` отсутствует по архитектурному решению.

IPC не должен позволять клиенту напрямую изменять состояние ядра; команды исполняет сам `vpn-gatewayd`.

## 22. Что сознательно исключено

На текущем этапе не реализуются:

- автоматическое переключение между VPN-профилями;
- изменение конфигурации без перезапуска;
- откат на старую конфигурацию;
- snapshot конфигурации runtime, сохраняемый между запусками;
- runtime-state, сохраняемое между запусками, как источник истины;
- проверка удалённой стороны VPN через ping;
- проверка рукопожатия WireGuard;
- пересылка IPv6;
- сторонние Python-библиотеки.

Неперсистентная runtime-инвентаризация `OWNED` не относится ни к runtime-state,
сохраняемому между запусками, ни к snapshot конфигурации runtime, сохраняемому между запусками.

## 23. Внутренняя модель реализации

Python-реализация больше не обязана помещаться в один исходный файл.

Допустим и предпочтителен небольшой пакет/каталог, если это улучшает аудит и снижает
связность кода. При развёртывании сохраняется одна точка входа daemon, например:

```text
vpn-gatewayd
vpn_gateway/
    config.py
    model.py
    kernel.py
    policy.py
    daemon.py
```

Точные имена и разбиение не являются архитектурным API. Не следует дробить код на
микромодули без смысловой границы.

Будущая реализация на Rust по-прежнему ориентируется на один исполняемый файл. Поэтому
границы предметных областей должны естественно переноситься в Rust `struct`/`enum` и модули
и не зависеть от динамической подмены методов (monkey-patching) или специфичной для Python
метапрограммной техники.

### 23.1. Модель конфигурации и предметной области

Неизменяемая runtime-конфигурация содержит только типизированные управляемые профили.

Поле TOML `interface` разбирается в типизированный селектор:

```text
InterfaceSelector:
    EXACT(name)
    PREFIX_FAMILY(prefix)
```

Исходная строка селектора `vpns+` не должна распространяться дальше границы модели
конфигурации/предметной области как аргумент разрешающего правила, NAT или маршрута. После
разрешения селектора ресурсы ядра используют только точное имя жесткой привязки.

Инвентаризация интерфейсов представлена типизированным snapshot, содержащим как минимум:

```text
InterfaceRecord:
    name: str
    ifindex: int
    ipv4: frozenset[IPv4Address]
```

Если одна инвентаризация содержит одно имя с несовместимыми значениями ifindex, адаптер не
объединяет записи молча и возвращает `KernelError`.

Результат разрешения селектора одного профиля имеет вид:

```text
InterfaceResolution:
    ABSENT
    BOUND(name, ifindex)
    AMBIGUOUS(matches...)
```

Готовность daemon вычисляет из результата разрешения и ожидаемого локального IPv4.

`VpnProfile` хранит неизменяемую конфигурацию и локальные для процесса OWNED-маршруты.
Он не читает и не изменяет состояние ядра и не выбирает runtime-интерфейс.

Старая идея `CONFIGURED routes` как полного набора готовых `RouteSpec` больше не
корректна: `BLACKHOLE` выводится только из конфигурации, а `UNICAST` требует жесткой
привязки.

Daemon создаёт один неизменяемый `ReconciliationSnapshot` на цикл согласования. Он
содержит как минимум инвентаризацию интерфейсов, результаты разрешения селекторов,
готовность, требуемые маршруты и полную требуемую политику. Snapshot строится один раз и
повторно используется на всех фазах построения, применения и проверки цикла.

### 23.2. Модель маршрутов

`RouteSpec` остаётся самодостаточным неизменяемым объектом-значением:

```python
@dataclass(slots=True, frozen=True)
class RouteSpec:
    destination: IPv4Network
    route_type: RouteType
    via: IPv4Address | None
    interface: str | None
    metric: int | None
    proto: int | None
    onlink: bool
```

Для `BLACKHOLE` `interface=None`.

Для `UNICAST` поле `interface` всегда содержит точное runtime-имя интерфейса жесткой
привязки. Специальное значение селектора в `RouteSpec` запрещено.

План уровня daemon:

```text
route_adds
route_deletes
route_replaces
```

сохраняет существующую определяющую семантику точного префикса.

### 23.3. Runtime-состояние OWNED

Локальное для процесса runtime-состояние daemon/профиля хранит:

- подтверждённые OWNED-маршруты;
- последнее подтверждённое состояние жесткой привязки и готовности;
- кэш диагностических пересечений.

OWNED-маршруты и подтверждённое состояние привязки/готовности принадлежат только текущему
процессу. Они не сохраняются на диск, не переживают перезапуск и в новом процессе
начинаются пустыми.

Подтверждённое состояние привязки/готовности не считается истиной о состоянии ядра.
Каждый цикл заново читает инвентаризацию интерфейсов и заново вычисляет разрешение
селекторов и готовность.

OWNED-маршруты и состояние привязки/готовности фиксируются только после успешной проверки
соответствующего требуемого snapshot.

### 23.4. Граница взаимодействия с ядром

`KernelInterface` остаётся узкой физической границей и не принимает решений политики.

Обычное согласование:

```text
list_routes() -> строгий полный snapshot основной IPv4-таблицы
list_interfaces() -> записи интерфейсов с name/ifindex/IPv4
add_route(RouteSpec)
delete_route(RouteSpec)
replace_route(RouteSpec)
read/write ip_forward
iptables-save / iptables-restore
```

Для очистки дополнительно используются выборочные по маркеру запросы маршрутов:

```text
list_routes_by_proto(201)
list_routes_by_proto(202)
```

Точное имя метода относится к деталям реализации. Семантический контракт: запрос с
фильтром не разбирает несвязанные сторонние маршруты.

Адаптер дочерних процессов для Debian использует:

```text
ip -j -N -4 route show table main
ip -j addr show
ip -j -N -4 route show table main proto <N>
```

Полная инвентаризация маршрутов по-прежнему считает ошибкой непредставимые формы
multipath/nexthop/nhid.

Выборочная инвентаризация при очистке получает идентичность протокола из контекста запроса,
потому что iproute2 может не печатать `protocol` в отфильтрованном выводе.

Инвентаризация по протоколу остаётся строгой **внутри зарезервированного пространства
маркеров**: непредставимый маршрут `proto 201/202` с multipath/nhid в структурированной форме не
пропускается молча и считается ошибкой очистки. Для `proto 201` ресурс очистки дополнительно
обязан соответствовать `type=BLACKHOLE metric=65536`; другая форма с зарезервированным
`proto 201` является конфликтом маркера, а не кандидатом на молчаливое удаление.

Разборщик адресов/интерфейсов учитывает только `addr_info[].family == "inet"` и поле
`local`; ifindex сохраняется в `InterfaceRecord`. Дублирующиеся записи одного имени
могут объединяться только при согласованном ifindex.

### 23.5. Модель политики фильтрации

Слой политики строит из неизменяемой конфигурации и snapshot текущего цикла две явные
формы:

```text
desired_full_policy(snapshot)
desired_isolation_filter(config)
```

Точные имена функций и классов относятся к деталям реализации.

Полная политика содержит структурные ресурсы и точные правила, зависящие от привязки.

Изолирующий фильтр:

- не зависит от инвентаризации интерфейсов;
- не содержит `ACCEPT`, зависящих от привязки;
- не содержит разрешающего сопоставления по префиксу;
- сохраняет защитные правила селекторов `INPUT`;
- сохраняет запрещающие правила входящего `FORWARD`-трафика селекторов;
- сохраняет `REJECT` транспортных сетей VPN, защищаемых назначений и окончательный
  `VPNG-FORWARD-DENY`.

Его профильные цепочки имеют однозначную структуру.

`VPNG-<PROFILE>-INPUT` в изолирующем фильтре:

```text
RETURN
```

`VPNG-<PROFILE>-FORWARD`:

```text
для каждого защищаемого назначения:
    -d route
        REJECT --reject-with icmp-host-prohibited

RETURN
```

`VPNG-INGRESS` не содержит точных блоков готовых жестких привязок. Он содержит только
запрещающие правила всех управляемых селекторов и завершающий `RETURN`.

При применении изолирующий фильтр является **полным требуемым daemon-owned состоянием
таблицы `filter`** для этой промежуточной стадии. Он не добавляется поверх текущего фильтра:
устаревшие daemon-owned правила `ACCEPT`, которых нет в требуемом состоянии изолирующей
стадии, должны быть удалены или заменены в той же операции применения.

Применение изолирующего фильтра не изменяет таблицу `nat`. Ранее применённый NAT может
временно оставаться за проверенным запрещающим барьером. Затем оркестрация применяет и
проверяет требуемый NAT текущего snapshot и только после этого применяет полную разрешающую
политику фильтрации.

Успешная проверка изолирующего фильтра означает только подтверждение защитного барьера и
никогда не эквивалентна состоянию `SAFE` полной требуемой политики фильтрации/NAT.

Только состояние `SAFE` полной требуемой политики фильтрации/NAT после проверки требуемого
NAT и полного фильтра может открыть путь к завершению согласования маршрутов и последующему
включению пересылки.

Обе формы выводятся из **одной модели политики**. Сравнение и восстановление не имеют
независимых источников истины; оркестрация не выполняет точечных правок отдельных правил.

Префиксный селектор никогда не применяется в разрешающем `ACCEPT` или правиле NAT; там
используется только точное имя жесткой привязки. Сопоставление `-i prefix+` допустимо
только в проверенных на целевой системе запрещающих защитных правилах `INPUT`/`FORWARD`.

### 23.6. Политика владения маршрутами

Daemon является определяющим владельцем маршрутов только для точных защищаемых префиксов
управляемых профилей.

Для каждого точного защищаемого префикса:

```text
требуемый OWNED RouteSpec              -> оставить
OWNED, но не требуемый                 -> удалить
сторонний нетребуемый точный маршрут   -> удалить
точный требуемый, но не OWNED          -> заменить/канонизировать, затем проверить
настроенный защитный BLACKHOLE          -> требуется всегда
```

Маршрут `proto kernel` никогда не удаляется и не заменяется. Совпадение точного
защищаемого префикса с connected-маршрутом ядра является фатальным при запуске.

Если такой конфликт с `proto kernel` появляется во время `RUN`, daemon также не имеет
права изменять этот маршрут. План маршрутизации завершается ошибкой для соответствующего
профиля; при уже проверенной безопасной политике фильтрации жизненный цикл сохраняет отказ
с запретом и переходит в `DEGRADED`, а маршрут ядра не принимается как OWNED.

Пересечения с более или менее специфичными маршрутами автоматически не удаляются и
остаются диагностическими.

Отказ с запретом обеспечивается тремя независимыми слоями:

1. `BLACKHOLE` для защищаемого префикса;
2. безусловный `REJECT` защищаемого назначения внутри профильной цепочки `FORWARD`;
3. глобальный окончательный `VPNG-FORWARD-DENY`.

### 23.7. Цикл обработки событий

Один `VpnGatewayDaemon` владеет:

- одним слушателем Netlink;
- периодическим таймером согласования;
- механизмом пробуждения по сигналу;
- событиями IPC и административными командами.

Все события сериализованы. Одновременно выполняется не более одного цикла согласования.

Netlink-событие используется как сигнал пробуждения и признак необходимости пересверки,
а не как достоверное описание изменения состояния. Согласование читает заново полный
snapshot интерфейсов.

События неизвестных интерфейсов могут быть проигнорированы только если имя не может
соответствовать ни одному управляемому селектору. Событие имени, которое **может**
соответствовать управляемому селектору, должно инициировать полную пересверку, даже если
жесткая привязка ещё не известна.

### 23.8. Диагностическая модель

Ожидаемые эксплуатационные ошибки имеют стабильную машинную идентичность причины,
независимую от человекочитаемого текста. Концептуальный контракт:

```text
DiagnosticFact:
    code   -> стабильный код причины
    detail -> необязательный человекочитаемый контекст
```

Точные имена Python-классов относятся к реализации. Архитектурным контрактом является
стабильная машинная идентичность причины; полный каталог конкретных кодов определяется
реализацией и тестами, а не выводится из свободного текста исключения.

После того как код причины опубликован через CLI/IPC/status или закреплён regression-тестом,
его изменение считается изменением совместимости и должно быть явным.

Поле `detail` предназначено только для диагностики человеком и не должно определять
идентичность или дедупликацию события.

Ожидаемые ошибки на границе взаимодействия ядра и пользовательского пространства
переводятся в известные диагностические причины на соответствующей границе оркестрации.
Исключения из-за ошибок программирования, нарушенные внутренние инварианты и иные
неожиданные ошибки не маскируются как штатные `UNKNOWN`/`DEGRADED`.

### 23.9. Результат профиля

Завершённый цикл согласования формирует для каждого управляемого профиля один результат:

```text
SUCCESS
FAIL
```

`SUCCESS` означает, что требуемое для текущего состояния профиля состояние ресурсов
успешно применено и проверено. Поэтому `ABSENT` или неготовый профиль может иметь
`SUCCESS`, если его fail-closed состояние — blackhole, запреты и отсутствие
разрешающих ресурсов — полностью проверено.

`FAIL` означает, что требуемое состояние конкретного профиля не удалось получить или
проверить. `AMBIGUOUS` всегда даёт `FAIL`; к `FAIL` также относятся, например,
неразрешимый конфликт точного защищаемого префикса с `proto kernel` и ошибка применения
или проверки ресурсов этого профиля.

Ошибка наблюдаемости или интерпретации, не позволяющая достоверно построить результаты
профилей вообще, не преобразуется искусственно в набор `FAIL`: это ошибка уровня всего
цикла и состояние `ISOLATED` (§8.4, §8.9).

- EXP-001 подтвердил каноническое представление `iptables-save` на проверенных Debian 13 /

  правил.
- Применение, восстановление и очистка фильтрации используют `iptables-save` stdout и

  маршрутов и сохранение интерфейсов без адресов.
- EXP-003 подтвердил успешный сценарий запуска RC2.5.1.

- EXP-004.2 подтвердил отказ с запретом при совместном существовании `proto 201`

- EXP-004.3 подтвердил, что ocserv создаёт семейство runtime-интерфейсов, а не

- EXP-005 подтвердил контракт префиксного сопоставления iptables на целевой системе:
  `-i vpns+` принимается и канонически сохраняется как `-i vpns+`; он совпадает с
  `vpns`, `vpns0`, `vpns1`, `vpnsX`, но не с `other0`; более ранний точный
  `-i vpns0` `ACCEPT` обходит последующее запрещающее `-i vpns+`.
- Поэтому префиксный селектор конфигурации использует тот же контракт завершающего `+`;
  разрешающие правила, NAT и маршруты ядра используют только разрешённое точное имя
  жесткой привязки.
- EXP-004.4 подтвердил транзакцию очистки отдельно для каждой таблицы:
  `-D -> -F -> -X -> COMMIT`.
- EXP-004.5 подтвердил выборочную по маркерам `proto 201/202` инвентаризацию маршрутов
  для очистки.
- Формы внешних CLI-команд, влияющие на контракт безопасности, должны вручную проверяться
  на целевой Debian до закрепления в адаптере дочерних процессов.
- Запрещающее сопоставление префиксного семейства для `INPUT` и `FORWARD` проверено
  EXP-005; префиксное сопоставление запрещено для разрешающих `ACCEPT`/NAT.
- `ip_forward` сначала читается, затем при необходимости изменяется; результат
  подтверждается повторным чтением.
- Вызовы дочерних процессов ограничены тайм-аутом и используют стабильные
  `LC_ALL=C`/`LANG=C`.
- Уведомления Netfilter остаются необязательным улучшением; корректность опирается на
  Netlink-события маршрутов и периодическое полное согласование.
- Переходы, меняющие политику (смена привязки или готовности), используют восстановление с
  первоначальным запретом: изолирующий фильтр -> проверка -> требуемый NAT -> проверка ->
  полный требуемый фильтр -> проверка -> маршруты -> проверка. Защитный барьер временно
  запрещает управляемую пересылку всех профилей, даже если изменился только один. Этот
  порядок сохраняется и при неудаче подтверждения выключенной пересылки.
- Ошибка инвентаризации интерфейсов относится к классу изоляции: слепое восстановление
  зависящей от привязки политики запрещено; изолирующий фильтр, выводимый только из
  конфигурации, может использоваться как безопасный барьер при читаемом состоянии
  фильтрации.
- Snapshots маршрутов, адресов и интерфейсов не являются атомарной транзакцией ядра.
  Архитектура требует один заново прочитанный snapshot каждого типа, последовательно
  используемый в пределах цикла, а не псевдоатомарную оболочку.
- Безопасность конфигурации: обычный файл, не символическая ссылка, принадлежит root;
  родительский каталог защищён от записи group/other.
- Безопасность runtime-каталога отдельно проверяет тип, символические ссылки, владельца и
  режим до открытия блокировки.
- При `Type=notify` `READY=1` отправляется только после успешного `APPLY`, последней
  контрольной точки и фактического перехода в `RUN`; watchdog не заменяет проверки
  состояния ядра и очистку.
- IPv6 forwarding является обязательным условием среды: перед `RUN` проверяются как минимум
  `net.ipv6.conf.all.forwarding=0` и `net.ipv6.conf.default.forwarding=0`, а доступные
  per-interface overrides не должны разрешать пересылку.
- Managed VPN `INPUT` не содержит общего `NEW ACCEPT`: удалённая сторона не получает
  право инициировать соединения с локальными сервисами gateway.
- Python-реализация может быть пакетом из нескольких файлов, но сохраняет одну точку входа
  daemon. Будущий Rust — один исполняемый файл.

### 24.1. Несовместимые изменения относительно реализации RC2.5.1

Следующий рефакторинг реализации обязан учитывать как минимум:

- типизированный `InterfaceSelector` для точной и префиксной форм;
- `InterfaceRecord` с `name`, `ifindex` и IPv4-адресами;
- `InterfaceResolution` с `ABSENT/BOUND/AMBIGUOUS`;
- замену `list_interface_ipv4()` на инвентаризацию интерфейсов с ifindex;
- отказ от идеи полного набора готовых `CONFIGURED RouteSpec` внутри `VpnProfile`;
- один неизменяемый `ReconciliationSnapshot` на цикл согласования;
- две производные формы одной модели политики: полную политику и изолирующий фильтр;
- локальное для процесса подтверждённое состояние привязки и готовности;
- `RouteSpec.interface` только с точным runtime-именем, никогда со специальным значением
  селектора;
- проверку обязательного отключения IPv6 forwarding до `RUN`;
- явный `ProfileResult` с семантикой `SUCCESS`/`FAIL`;
- отсутствие прежнего общего `NEW ACCEPT` в управляемой цепочке `INPUT`.

`ReconciliationPlan` может сохранить модель `adds/deletes/replaces`; архитектура не
требует менять её только ради RC3. Набор значений `DaemonState` также не обязан меняться,
если новые условия переходов выражаются существующими состояниями.

Регрессионная база реализации RC2 сохранена в:

## 25. Открытые решения

Следующие детали реализации и исследований требуют подтверждения:

1. Точный механизм сериализованного цикла обработки событий и подавления/объединения серий
   Netlink-событий.
2. Точный механизм постановки и объединения полной пересверки после Netlink `ENOBUFS`;
   само требование полной пересверки уже является нормативным.
3. Финальная модель привилегий systemd: root либо отдельный служебный пользователь с
   минимальными capabilities/permissions.
4. Точный минимальный набор IPC и административных команд.
5. Пограничный случай конфликта метрики/ключа стороннего точного маршрута, ранее отложенный
   до отдельного эксперимента на целевой системе.
6. Пороги «шторма восстановления» и защёлкивания состояния не вводятся без наблюдаемых
   данных.

## 26. Ключевые инварианты

Ниже используется компактная техническая запись. Именованные состояния, поля конфигурации,
имена цепочек, классов, методов и команд сохраняются без перевода; обычные понятия
формулируются по-русски.

```text
1. Один daemon-процесс владеет всеми ресурсами VPN-GATE в ядре.

2. Конфигурация читается один раз за время жизни процесса; изменения применяются только
   перезапуском.

3. Запуск: handlers -> runtime-dir/LOCK -> CLEANUP -> LOAD/VALIDATE -> APPLY -> RUN.

4. Ошибка запуска никогда не переводит сервис в DEGRADED; IPv4-пересылка не должна
   остаться включённой, а обязательное условие выключенной IPv6-пересылки проверяется до
   перехода в RUN.

5. Очистка не зависит от конфигурации и опирается на маркеры владения.

6. Маркер владения BLACKHOLE: proto 201 + type BLACKHOLE + metric 65536.

7. Маркер владения VPN UNICAST: proto 202.

8. При очистке маршруты читаются выборочными запросами по proto 201/202, а не полной
   инвентаризацией основной таблицы.

9. При обычном согласовании полная инвентаризация маршрутов остаётся строгой и не
   пропускает молча неподдерживаемые multipath/nhid формы.

10. ip_forward находится в exclusive ownership daemon'а, изменяется только по схеме
    «прочитать перед записью» и подтверждается повторным чтением; IPv6 forwarding daemon
    не управляет, но требует его отключения как условие запуска.

11. Эксклюзивное владение ip_forward архитектурно связано с эксклюзивной ответственностью
    daemon за окончательное решение для каждого IPv4-пакета FORWARD.

12. В проверенном состоянии сторонние правила FORWARD физически находятся после
    daemon-owned префикса и недостижимы из-за VPNG-FORWARD-DENY; правило, вставленное перед
    префиксом, является рассогласованием UNSAFE до следующего цикла согласования.

13. Сторонние правила INPUT сохраняют значение для трафика вне управляемых селекторов;
    OUTPUT не изменяется daemon и полностью остаётся политикой администратора хоста.
    Локальный OUTPUT не проходит ACL источников FORWARD.

14. Значение interface в конфигурации является селектором: точное имя либо префиксное
    семейство prefix+.

15. Завершающий + является оператором префиксного селектора и использует проверенную на
    целевой системе семантику префиксного сопоставления интерфейсов iptables.

16. Семейство prefix+ означает всё текстовое пространство ifname, начинающееся с prefix,
    включая имя prefix без суффикса.

17. Префиксный селектор никогда не используется в RouteSpec и разрешающих условиях
    интерфейса ACCEPT/NAT; там применяется только точное имя жесткой привязки.
    Сопоставление -i prefix+ допустимо только в проверенных запрещающих защитных правилах
    селектора.

18. Управляемые селекторы попарно не пересекаются по множеству возможных точных имён;
    пересечение является фатальной ошибкой конфигурации.

19. 0 совпадений селектора = ABSENT/не готов; 1 = жесткая привязка; >1 = AMBIGUOUS.

20. Неоднозначность при запуске фатальна; во время RUN состояние AMBIGUOUS означает
    FAIL профиля / DEGRADED с отказом с запретом.

21. Идентичность жесткой привязки включает точное имя + ifindex; пересоздание того же имени
    с новым ifindex считается сменой привязки.

22. Готовность = единственная жесткая привязка + ожидаемый локальный IPv4.

23. operstate/LOWER_UP, доступность peer, ping и handshake не входят в критерий готовности.

24. Разрешающие правила, NAT и UNICAST-маршруты, зависящие от привязки, существуют только
    для готовой жесткой привязки.

25. BLACKHOLE и REJECT защищаемого назначения не зависят от привязки/готовности.

26. Точная цепочка INPUT готового профиля разрешает только ESTABLISHED,RELATED и запрещает
    остальное; общего NEW ACCEPT с VPN-стороны нет. Незавершённый трафик селектора закрывает
    VPNG-INPUT-GUARD.

27. Сопоставление семейства по префиксу допустимо только как проверенное запрещающее
    защитное правило; префиксные ACCEPT/NAT запрещены.

28. Порядок FORWARD: VPNG-INGRESS -> VPNG-RESERVED -> цепочки профилей ->
    VPNG-FORWARD-DENY -> сторонние правила.

29. Динамический ACCEPT в цепочке FORWARD профиля требует источник + защищаемое назначение
    + точный выходной интерфейс жесткой привязки.

30. В каждом отдельном блоке защищаемого назначения после динамических ACCEPT всегда
    существует безусловный REJECT.

31. VPNG-FORWARD-DENY выдаёт окончательный DROP/REJECT для всего оставшегося IPv4-транзита.

32. FORWARD к управляемой транспортной vpn.network получает REJECT до ACL профиля.

33. VPNG-INGRESS для готового точного интерфейса: INVALID -> DROP,
    ESTABLISHED/RELATED -> ACCEPT, остальное -> REJECT; входящий трафик управляемого
    селектора, не завершённый точным блоком, получает REJECT до ACL профиля.

34. NAT-цепочка существует структурно для каждого управляемого профиля; MASQUERADE по
    точному выходному интерфейсу существует только при готовой привязке; сторонние правила
    POSTROUTING сохраняются и остаются достижимыми после RETURN профильной цепочки для
    неуправляемого исходящего трафика.

35. NAT проверяется раньше восстановления маршрутов proto 202 через новую привязку.

36. Смена привязки или готовности является переходом, меняющим политику: до изменения
    зависящих от неё ресурсов выполняется best-effort ip_forward=0.

37. Остаточное окно «событие ядра -> реакция daemon» существует и документировано;
    запрещающие правила селекторов закрывают входящий трафик нового непривязанного
    интерфейса семейства, но ограничение same-name/new-ifindex в iptables остаётся границей
    модели.

38. Netlink-событие является сигналом пробуждения/необходимости пересверки; достоверное
    состояние читается заново из snapshot.

39. Событие имени, потенциально соответствующего управляемому селектору, инициирует полную
    пересверку.

40. Периодическое согласование обязательно как страховка; reconcile_interval имеет диапазон
    [1.0, 60.0] и не может быть отключён значением 0.

41. Один неизменяемый snapshot привязки/готовности повторно используется на всех фазах
    построения, применения и проверки одного цикла.

42. Требуемый BLACKHOLE RouteSpec выводится только из конфигурации; требуемый UNICAST
    RouteSpec — из конфигурации и жесткой привязки.

43. RouteSpec.interface для UNICAST всегда содержит точное имя интерфейса жесткой привязки.

44. Отсутствующие BLACKHOLE добавляются раньше любых разрушительных операций с маршрутами.

45. Исполнитель маршрутов: добавить BLACKHOLE -> удалить конкурирующие точные маршруты ->
    выполнить замены -> добавить оставшиеся маршруты.

46. Daemon является определяющим владельцем маршрутов только для точных защищаемых
    префиксов profile.routes.

47. Конкурирующие сторонние точные маршруты могут удаляться; proto kernel никогда не
    удаляется и не заменяется.

48. Пересечения с более или менее специфичными маршрутами автоматически не удаляются.

49. Маршрут по умолчанию не считается ресурсом диагностики пересечений.

50. OWNED-маршруты и подтверждённое состояние привязки/готовности являются локальными для
    процесса, после перезапуска начинаются пустыми и меняются только после проверки.

51. Локальная для процесса фиксация OWNED/привязки выполняется до финального включения
    пересылки, а не после.

52. Само по себе фактическое состояние ядра не означает принятия ресурса в ownership.

53. desired_full_policy и desired_isolation_filter являются двумя производными формами
    одной модели политики; сравнение и восстановление не имеют независимых источников
    политики.

54. Состояние безопасности firewall = SAFE/UNSAFE/UNKNOWN; UNKNOWN не восстанавливается
    вслепую.

55. UNSAFE либо переход, меняющий политику, использует порядок с первоначальным запретом:
    изолирующий фильтр -> проверка -> требуемый NAT -> проверка -> полный требуемый фильтр
    -> проверка -> маршруты -> проверка.

56. Невозможность подтвердить ip_forward=0 не разрешает полный ACCEPT раньше проверенного
    NAT; защитный барьер с первоначальным запретом всё равно применяется.

57. Ошибка чтения/разбора инвентаризации интерфейсов либо невозможность завершить разрешение
    селекторов на уровне всего цикла -> ISOLATED; AMBIGUOUS одного профиля означает
    FAIL профиля / DEGRADED, а не эту ошибку.

58. При ошибке инвентаризации интерфейсов слепое восстановление политики, зависящей от
    привязки, запрещено; изолирующий фильтр, выводимый только из конфигурации, допустим как
    безопасный барьер при читаемом состоянии firewall.

59. После изоляции пересылка возвращается только после SAFE полной политики и завершённой
    новой проверки маршрутов.

60. Требуемая политика профиля AMBIGUOUS удаляет или не создаёт точные ACCEPT/NAT/UNICAST,
    сохраняя blackhole и запреты.

61. Профиль ABSENT/не готов сам по себе не является FAIL, если его требуемое состояние с
    отказом с запретом успешно применено и проверено.

62. Профиль AMBIGUOUS остаётся FAIL до восстановления однозначности.

63. ACTIVE = политика SAFE + результаты всех профилей SUCCESS + ip_forward=1; ACTIVE не
    означает доказанную связность VPN.

64. SAFE с FAIL профиля -> DEGRADED; состояние не SAFE или недостаточная наблюдаемость
    политики -> ISOLATED.

65. Очистка не переходит к разрушительным операциям, пока не подтверждено ip_forward=0;
    затем: proto 202 -> filter/NAT -> proto 201 blackhole -> проверка.

66. Blackhole снимается только после подтверждённой очистки остальных принадлежащих daemon
    ресурсов.

67. Очистка iptables точная; глобальная очистка таблиц запрещена.

68. Пространство имён VPNG-* полностью зарезервировано daemon'ом.

69. Атомарность iptables-restore в пределах одной таблицы не считается атомарностью между
    таблицами.

70. Последний компонент runtime-каталога: не символическая ссылка, каталог, режим 0700,
    ожидаемый владелец сервиса.

71. Отсутствующий runtime-каталог daemon может создать сам при достаточных правах.

72. Неправильные владелец/режим существующего runtime-каталога не исправляются молча.

73. Файл блокировки: O_NOFOLLOW + пожизненная неблокирующая flock.

74. Конфигурационный файл: обычный файл, не символическая ссылка, принадлежит root;
    родительский каталог защищён от записи group/other.

75. --check-config не получает runtime-блокировку и не меняет состояние ядра.

76. Неизвестные ключи конфигурации фатальны для runtime-проекции управляемых профилей.

77. Некорректные неуправляемые описания профилей не блокируют запуск; --check-config выдаёт
    WARNING.

78. Защищаемые маршруты управляемых профилей глобально не пересекаются и не пересекают
    управляемые vpn.network.

79. Порядок peers задаёт метрики 10,20,30...; peers=[] допустим; вычисленная метрика не
    превышает 4294967295.

80. common_allowed_sources объединяется с profile.allowed_sources; семантики deny/exclude нет.

81. Обратная доступность со стороны VPN не входит в текущий контракт: новый INPUT с
    управляемого VPN-интерфейса запрещён, а NEW FORWARD закрыт ingress-политикой. Локальный
    OUTPUT самого доверенного gateway регулируется отдельно администратором.

82. Python-реализация может быть пакетом из нескольких файлов, но имеет одну точку входа
    daemon.

83. Границы предметных областей должны переноситься в будущие Rust modules/structs/enums;
    развёртывание Rust ориентировано на один исполняемый файл.

92. Замена same-name/new-ifindex обнаруживается при согласовании snapshot, но существующее

93. Дублирующееся имя интерфейса с конфликтующими ifindex является некорректной

96. Применение изолирующего фильтра заменяет/канонизирует полное требуемое daemon-owned

98. SAFE полной политики требует проверки требуемого NAT и полного требуемого фильтра для
    одного и того же неизменяемого snapshot согласования.

99. Операционный статус сообщает селектор/привязку/готовность отдельно от состояния
```
