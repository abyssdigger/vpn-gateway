# NG3 — решения по рефакторингу дерева требований

**Дата:** 2026-11-20  
**Статус:** исследовательский документ  
**База:** snapshot 145 `623a688e4080de56e5ac14675ffca028c3865d18`

## 1/18 — различимость входящего VPN-трафика

Текущий Profile `+snat` не является самостоятельной ценностью, следующей из состава
`Profile`. Продуктовая ценность должна быть поднята на первый уровень под
`VPNG0001`.

### Новый первый уровень — условный `VPNG0001-R3`

**Зачем:** чтобы пользователь мог применять дополнительную сетевую политику к входящему
через VPN трафику не только по исходным адресам удалённых узлов.

**Требование:** VPN-GATE должен позволять пользователю делать входящий через VPN трафик
от разных источников различимым в обычной сети для последующего дополнительного управления.

Дальнейшая декомпозиция этого требования не нужна.

### Недостающее общее требование к ограничению трафика

Под `VPNG0002-R2.R1` требуется отдельный наследник, определяющий свойства трафика,
по которым пользователь может задавать ограничения.

**Зачем:** чтобы пользователь мог отличать трафик, к которому должна применяться заданная
политика VPN-GATE, по существенным свойствам самого трафика.

**Требование:** VPN-GATE должен позволять пользователю ограничивать трафик по его источнику,
получателю и типу независимо от разрешённого направления передачи и от преобразований
трафика внутри области, контролируемой VPN-GATE.

Направление передачи остаётся отдельным измерением политики в ветке `VPNG0002-R2.R3`.

### Судьба нынешних наследников Profile `+snat`

`VPNG0001-R1.R2.R4.R4.R4.R1` как самостоятельное продуктовое требование не нужен:
сохранение смысла ограничений по исходному трафику при его последующих преобразованиях уже
следует из нового общего требования под `VPNG0002-R2.R1`. Конкретный порядок проверки и
преобразования относится к архитектуре.

`VPNG0001-R1.R2.R4.R4.R4.C1` не является ограничением продуктовой способности различать
входящий трафик. Его содержательная часть относится к контракту конфигурации первого релиза:
`+snat`, `+snat>IPv4`, `default_snat_address` и их размещение должны быть рассмотрены
в ветке пользовательской конфигурации.

`VPNG0001-R1.R2.R4.R4.R4.C2` не нужен как самостоятельное продуктовое ограничение в
нынешнем виде. Требование различимости уже задаёт необходимый результат; конкретные правила
допустимых IPv4-адресов относятся к выбранному способу реализации и, если нужны нормативно,
должны быть оформлены как ограничение соответствующего нижнего контракта.

## 2/18 — NAT для сокрытия обычной сети при выходе через VPN

Нынешний `VPNG0001-R1.R2.R4.R6.R1` смешивает продуктовую способность скрывать обычную
сеть и конкретный параметр конфигурации первого релиза. Эти уровни нужно разделить.

### Продуктовая способность

**Зачем:** чтобы пользователь мог скрыть от удалённой стороны исходные адреса обычной сети
при передаче трафика через VPN-ресурс.

**Требование:** VPN-GATE должен позволять пользователю применять NAT для сокрытия исходных
адресов обычной сети в трафике, передаваемом через выбранный VPN-ресурс.

Эта способность относится к политике использования конкретного VPN-ресурса и должна
располагаться рядом с дополнительными ограничениями трафика для такого ресурса, а не
следовать из того, что Device является контейнером transport-specific параметров.

### Контракт конфигурации первого релиза

Отдельное требование к параметру конфигурации сохраняется, но его «Зачем» должно отвечать
на задачу явного управления уже определённой продуктовой способностью.

**Зачем:** чтобы пользователь мог однозначно включить или отключить NAT-сокрытие обычной
сети для конкретного VPN-ресурса и чтобы оно не возникало неявно.

**Требование:** для enabled Device, который в текущей enabled-конфигурации может
обслуживать трафик ordinary→VPN, конфигурация первого релиза должна явно задавать boolean
`use_outbound_nat`: `true` включает предусмотренное NAT-сокрытие, `false` оставляет
исходные адреса без такого преобразования. Для Device без ordinary→VPN роли параметр не
требуется.

Конкретная реализация через masquerade и выбор адреса трансляции относятся к
архитектуре/нижнему контракту реализации, а не к продуктовой формулировке.

Агрегирующий Release-1 grammar constraint может продолжать перечислять
`use_outbound_nat` как каноническое имя поля; это не заменяет отдельную семантику самого
параметра.

## 3/18 — дополнительные ограничения трафика по VPN-ресурсу

Нынешняя Device-firewall ветка должна быть перестроена от продуктовой способности, а не
от выбранной модели firewall.

### Дополнительные ограничения по VPN-ресурсу

**Зачем:** чтобы пользователь мог исключать из разрешённого трафика то, что недопустимо
при использовании конкретного VPN-ресурса.

**Требование:** VPN-GATE должен позволять пользователю задавать дополнительные ограничения
трафика в зависимости от VPN-ресурса, через который этот трафик передаётся; такие
ограничения могут только сужать разрешения, заданные общей политикой трафика.

Пример: общая политика разрешает DNS-трафик через несколько VPN-ресурсов, но пользователь
может запретить DNS через конкретный ресурс, если его DNS-сервис считается небезопасным.

Отсутствие дополнительных ограничений уже означает отсутствие дополнительного сужения
общей политики и отдельного требования не требует.

### Ограничения для отдельного VPN-пути

**Зачем:** чтобы ограничение, относящееся только к одному из путей VPN-ресурса, не
приходилось распространять на остальные его пути.

**Требование:** VPN-GATE должен позволять пользователю задавать дополнительные ограничения
трафика для отдельного различимого VPN-пути.

### Ограничение первого релиза

**Почему:** потому что надёжное связывание пользовательского ограничения с отдельным
VPN-путём требует достаточной идентификации его текущей конечной точки, а эта возможность
ещё не подтверждена для всех поддерживаемых VPN-интеграций первого релиза.

**Ограничение:** первый релиз может поддерживать дополнительные ограничения только на
уровне VPN-ресурса целиком и не обязан позволять задавать их для отдельного VPN-пути.

### Следствия для нынешней Device-firewall ветки

Способ описания правил через `firewall = [...]`, порядок правил, `allow/deny/reject`,
`IN/OUT` и конкретный результат отсутствия совпадения относятся к контракту
конфигурации и реализации, а не к самостоятельным верхнеуровневым продуктовым
требованиям.

Признаки трафика, по которым действуют дополнительные ограничения, должны опираться на
общее требование под `VPNG0002-R2.R1`: источник, получатель и тип трафика независимо от
разрешённого направления передачи и от преобразований трафика внутри области,
контролируемой VPN-GATE.

## 4/18 и 5/18 — сетевые условия для работы используемых VPN-каналов

Нынешние `VPNG0001-R1.R2.R4.R6.R3` (`publish_vpn_server`) и
`VPNG0001-R1.R2.R4.R6.R4` (`allow_vpn_client`) не относятся к дополнительной
политике payload-трафика и не должны находиться рядом с NAT/firewall только потому,
что их параметры записываются в Device.

Обе способности нужны для базовой работоспособности VPN-канала, который VPN-GATE принимает
в обслуживание, поэтому их следует перенести под `VPNG0001-R1.R3`.

### Общий родитель

**Зачем:** чтобы VPN-канал, принятый VPN-GATE в обслуживание, мог обмениваться необходимым
для своей работы транспортным и управляющим трафиком.

**Требование:** VPN-GATE должен обеспечивать необходимые сетевые условия для транспортного
и управляющего обмена поддерживаемого VPN-канала в пределах контролируемой им области.

### 4/18 — внешняя доступность VPN-сервера

**Зачем:** чтобы поддерживаемый VPN-сервер мог принимать необходимые внешние соединения.

**Требование:** VPN-GATE должен позволять обеспечивать внешнюю доступность транспортного
трафика поддерживаемого VPN-сервера, когда она требуется для работы используемого
VPN-канала.

Конкретный `publish_vpn_server`, выбор host address/interface, port mapping и строковая
грамматика относятся к контракту конфигурации первого релиза.

### 5/18 — транспортный и управляющий трафик VPN-клиента

**Зачем:** чтобы поддерживаемый VPN-клиент мог устанавливать и поддерживать VPN-соединение
при ограниченной локальной сетевой политике.

**Требование:** VPN-GATE должен позволять пропускать необходимый транспортный и управляющий
трафик поддерживаемого VPN-клиента без предоставления ему произвольного доступа к локальной
сети.

Конкретный `allow_vpn_client` и способ описания разрешаемых потоков относятся к контракту
конфигурации первого релиза.

Оба требования описывают обеспечение работоспособности используемого VPN, а не firewall
payload-трафика. Их размещение в Device-конфигурации остаётся допустимым способом выражения
этих возможностей и не определяет их место в продуктовом дереве требований.

## 6/18 — сведения о транспортной конечной точке VPN-пути

Нынешние `VPNG0001-R1.R3.R5`, `.C1` и `.C1.R1` не нужны как отдельная ветка
продуктовых требований.

Для пользовательской политики достаточно различимого VPN-пути. Если конкретная функция
требует связать этот путь с его текущей транспортной конечной точкой, способ получения и
проверки такой связи относится к архитектуре поддерживаемой VPN-интеграции.

Проверки доступности первого релиза не зависят от такого вывода: их цель задаётся явно.
Будущие дополнительные ограничения для отдельного VPN-пути также должны ссылаться на
различимый путь, а не вводить транспортную конечную точку как отдельную пользовательскую
сущность.

Подтверждённая транспортная конечная точка может оставаться внутренним наблюдаемым фактом
адаптера и использоваться там, где выбранная архитектура интеграции этого требует.
Отсутствие такого факта не создаёт отдельной продуктовой семантики и не требует
самостоятельного Requirement/Constraint subtree.

## 7/18 — общая пользовательская конфигурация

Нынешний `VPNG0001-R1.R2` ошибочно расположен внутри ветки управляемой маршрутизации.
Пользовательская конфигурация VPN-GATE управляет не только маршрутизацией выбранного
payload-трафика, поэтому общий конфигурационный контракт следует поднять непосредственно
под `VPNG0001`.

### Новый общий узел конфигурации

**Зачем:** чтобы пользователь мог задавать поддерживаемое поведение VPN-GATE через
устойчивый продуктовый интерфейс, не воспроизводя внутренние механизмы его реализации.

**Требование:** VPN-GATE должен предоставлять пользовательскую конфигурацию для задания
поддерживаемого настраиваемого поведения продукта; конфигурация должна выражать
пользовательское намерение и не требовать задания внутренних объектов и операций
реализации.

Под этой веткой должны оставаться общие свойства конфигурационного контракта: предметные
сущности `Device` и `Profile`, их идентичность и ссылки, `enabled`-состояние,
однозначная валидация, канонические формы значений и синтаксиса, отсутствие неявных aliases
и другие общие правила пользовательской конфигурации.

Функциональные способности продукта не должны становиться потомками этой ветки только
потому, что управляются полями конфигурации. NAT, дополнительные ограничения трафика,
обеспечение transport/control connectivity VPN-клиента и публикация VPN-сервера остаются
под своими функциональными родителями. В конфигурационной ветке сохраняются только
требования к тому, как пользователь выражает уже определённую способность, например
`use_outbound_nat`, `firewall`, `allow_vpn_client`, `publish_vpn_server` и
Profile `+snat`.

Управляющие операции жизненного цикла не следует автоматически объединять с
конфигурационной веткой: их продуктовая семантика остаётся в `VPNG0005`.

## 8/18 — aggressive host-routing helper

Aggressive host-routing helper является желаемой будущей продуктовой capability и не должен
удаляться из requirement tree только потому, что первый релиз может обходиться без него.

Его нужно перепривязать к положительному функциональному требованию о предоставлении
автоматизации host routing, а не оставлять потомком требования, которое лишь ограничивает
влияние host-side функций на несвязанное сетевое состояние хоста.

Ограничение первого релиза сохраняется: первый release не обязан предоставлять aggressive
helper и связанные с ним continuous-recovery / fail-closed guarantees.

## 9/18 — настраиваемый критерий проверки доступности

Нынешний смысл capability сохраняется, но причинность в «Зачем» должна быть исправлена.

**Зачем:** чтобы пользователь мог выбирать наиболее подходящий для его целей критерий
доступности удалённой сети через VPN-путь.

**Требование:** VPN-GATE должен позволять пользователю задавать на уровне Profile механизм
проверки доступности и, когда выбранный механизм этого требует, цель проверки.

Для Release 1 по-прежнему допустимо ограничить поддерживаемый механизм ICMP echo с одним
явным IPv4 target. Device-default/Profile-override относится к конфигурационному контракту
этой capability и не должен находиться под ICMP-only Constraint только из-за исторического
placement.

## 10/18 — независимость правил VPN-GATE от сетевого состояния хоста

Нынешнее требование о managed network domain содержит полезный продуктовый инвариант,
смешанный с выбранным способом реализации.

**Зачем:** чтобы внешнее сетевое состояние хоста не могло нарушать правила обработки
управляемого трафика VPN-GATE.

**Требование:** VPN-GATE должен обеспечивать выполнение своей действующей политики для
управляемого трафика независимо от несвязанного сетевого состояния хоста; такое состояние
не должно позволять обходить установленные VPN-GATE ограничения или изменять требуемый
результат обработки управляемого трафика.

Отдельный managed network domain не является самостоятельной продуктовой capability.
Managed network domain, network namespace, boundary endpoints, размещение VPN endpoints
внутри домена и конкретные Linux/nft default policies вроде
`INPUT=DROP`/`OUTPUT=DROP`/`FORWARD=DROP` относятся к архитектуре и evidence,
если именно эти механизмы выбраны для выполнения продуктового инварианта.

При нормативном рефакторинге нынешний `VPNG0004-R4.R6.R1.*` нужно пересмотреть:
сохранить только требования, которые выражают самостоятельное поведение или fail-safe
гарантию, а implementation-specific descendants перенести в architecture/evidence.

## 11/18 — защитный режим

Нынешний административный payload-containment не должен оставаться потомком общего
fail-closed требования. Возможность немедленно прекратить контролируемую передачу трафика,
сохранив состояние для диагностики и восстановления, является самостоятельной
безопасностной способностью продукта и должна находиться на первом уровне под
`VPNG0004`.

**Зачем:** чтобы при подозрении на опасное или некорректное сетевое состояние оператор или
автоматика могли немедленно прекратить прохождение IP-трафика через контролируемую
VPN-GATE область, сохранив возможность определить причину проблемы и безопасно
восстановить работу.

**Требование:** VPN-GATE должен предоставлять защитный режим полного запрета IP-трафика с
сохранением состояния продукта, необходимого для диагностики и последующего восстановления,
а именно запрещать передачу:
- из обычной сети в VPN-GATE;
- из VPN-GATE в обычную сеть;
- между VPN-путями внутри VPN-GATE.

Формулировка намеренно ограничивает гарантию только трафиком, который находится под
контролем VPN-GATE. Требование не должно обещать блокирование трафика вне этой области.

Отдельные потомки, повторяющие три направления передачи или сохранение диагностического
состояния, не нужны: эти свойства полностью определены самим требованием. Если дальнейшая
декомпозиция понадобится, она должна добавлять самостоятельную семантику управления
защитным режимом — например, условия его автоматического или операторского включения и
безопасного выхода, — а не детали реализации блокировки.

Первый релиз по-прежнему может не предоставлять этот режим целиком; соответствующее
ограничение следует сохранить как Release-1 Constraint под новой веткой.

## 12/18 — peaceful host-routing helper и общий родитель автоматизации маршрутизации хоста

Нынешний `VPNG0001-R2.R2` содержит принятую продуктовую capability, но его текущий parent
`VPNG0001-R2` лишь ограничивает влияние явно включённых host-side функций на несвязанное
сетевое состояние хоста и не создаёт обязанность предоставить сам helper.

Peaceful и aggressive host-routing helper должны происходить от общей положительной
функциональной ветки автоматизации маршрутизации хоста. Нынешний `VPNG0001-R2` при этом
остаётся отдельным ограничивающим требованием о невмешательстве, а не причинным родителем
helper'ов.

### Общий родитель автоматизации маршрутизации хоста

**Зачем:** чтобы пользователь мог использовать VPN-GATE для передачи выбранного трафика без
обязательного ручного сопровождения необходимой для этого маршрутизации на хосте.

**Требование:** VPN-GATE должен позволять пользователю явно включать автоматизацию
маршрутизации на хосте, необходимую для доставки выбранного трафика к VPN-GATE и обратно.

### Peaceful host-routing helper

**Зачем:** чтобы автоматизация маршрутизации могла использоваться без передачи VPN-GATE
постоянного управления маршрутизацией хоста.

**Требование:** VPN-GATE должен предоставлять простой режим автоматизации маршрутизации,
который изменяет только явно выбранную пользователем область маршрутизации и не поддерживает
внесённое состояние под непрерывным авторитетным управлением между операциями жизненного
цикла.

Нынешние более детальные свойства peaceful helper — явное включение, selector scope,
неразрушающее lifecycle-применение и cleanup, отсутствие continuous recovery между
lifecycle-операциями и невмешательство в невыбранную host routing policy — должны
декомпозировать или ограничивать эту capability, а не служить основанием её существования.

Ранее принятое решение по aggressive helper из раздела 8/18 уточняется тем же общим
родителем: aggressive режим является альтернативным более авторитетным вариантом той же
host-routing automation capability и по-прежнему может быть отложен за пределы Release 1.

## 13/18 — стабильность ответного трафика принятого VPN-обмена

Нынешний `VPNG0002-R2.R6` не относится к выбору пользовательской traffic/path policy как
отдельного пользовательского решения, но его смысл возникает именно при наличии нескольких
разрешённых VPN-путей: он определяет, какой из них должен использовать ответ уже принятого
обмена. Поэтому требование должно быть прямым ребёнком `VPNG0003`, параллельным ветке
baseline preference / availability adaptation.

### Новый draft-узел — `VPNG0003-R4`

**Зачем:** чтобы ответный трафик уже принятого обмена сохранял сетевые свойства и
работоспособность исходного пути и не оказывался произвольно перенесён на другой VPN-путь.

**Требование:** для управляемого трафика, принятого со стороны VPN через разрешённый
VPN-путь, VPN-GATE должен передавать относящийся к нему ответный трафик через тот же
VPN-путь; наличие других разрешённых VPN-путей для адреса отправителя не должно само по
себе менять путь такого ответа.

Само требование остаётся позитивной same-path forwarding-гарантией. Риск изменения NAT,
source identity или других сетевых свойств при произвольной смене пути является причиной
этой гарантии и относится к Purpose, а не заменяет Statement отрицательной формулировкой.

Это semantic reparenting существующей гарантии; оно не требует изменения уже доказанного
forwarding behavior само по себе. Размещение напрямую под `VPNG0003`, а не под
`VPNG0003-R3`, сохраняет различие между двумя основаниями выбора пути: baseline/availability
preference и стабильностью уже принятого обмена.

## 14/18 — второй VPN lifecycle evidence gate

`VPNG0007-R7.R7.R1.R1` удаляется из requirement tree.

Причина: узел не задаёт самостоятельное продуктовое обязательство и не уточняет
`VPNG0007-R7.R7.R1`; он предписывает конкретную последовательность evidence после PASS
базовой applicability-проверки. EXP-050 уже проведён и остаётся историческим evidence.

Актуальная применимость результата EXP-050 должна трассироваться на продуктовые обязательства,
которые он действительно проверяет:

- `VPNG0001-R1.R3.C1.R1.R2` — внешняя VPN-конфигурация не должна получать неявное право
  изменять сетевую политику VPN-GATE;
- `VPNG0001-R1.R3.C3.R1` — внешний lifecycle VPN runtime должен иметь воспроизводимый
  integration contract, согласованный с lifecycle VPN-GATE;
- `VPNG0004-R4.R6` — внешнее сетевое состояние не должно позволять обходить правила
  обработки управляемого трафика;
- `VPNG0005-R5.R4`, `VPNG0005-R5.R5`, `VPNG0005-R5.R6.R2`,
  `VPNG0005-R5.R6.R3` — cleanup, stop и restart должны приводить к требуемому безопасному
  результату без ручного устранения следов предыдущего состояния.

Исторический experiment dossier и старые review не переписываются задним числом:
`PROJECT-CONVENTIONS.md` требует сохранять исходную evidence/provenance запись. Текущая
architecture и experiment registry должны отражать новую актуальную трассировку.



## 15/18 — непрерывность при изменении эффективного порядка

Прежний `VPNG0004-R4.R3.R1` не является уточнением safety-transition parent:
безопасность допускает временно более ограничивающее состояние, тогда как здесь требуется
отсутствие искусственного разрыва только из-за перестановки уже разрешённых путей.

Требование переносится под `VPNG0003-R3` как новый `VPNG0003-R3.R9`.

**Зачем:** чтобы изменение эффективного порядка уже разрешённых VPN-путей само по себе не
приводило к потере работоспособного пути и разрыву передачи только из-за применения нового
порядка.

**Требование:** если изменяется только эффективный порядок неизменного набора разрешённых
VPN-путей, VPN-GATE должен применять это изменение без временного вывода какого-либо из
этих путей из доступных для передачи трафика.

Старая детализация про временную route-копию и «staging-жертву» удаляется из requirement:
это вариант реализации make-before-break, а не продуктовая семантика.

## 16/18 — обновление конфигурации и `reload`

Продуктовая потребность заключается не в обязательной операции `reload`, а в возможности
предсказуемо применить изменённую конфигурацию.

Расширение первичного `VPNG0005` имеет отдельное внешнее основание: уточнение project holder
в проектной сессии 2026-11-21, прямо включившее обновление конфигурации в это продуктовое
обязательство.

Поэтому:

- в `VPNG0005` добавляется возможность обновлять конфигурацию;
- `VPNG0005-R5` распространяется на применение изменённой конфигурации;
- `VPNG0005-R5.R6` требует поддерживаемый способ применения изменённой конфигурации наряду
  с операциями запуска, остановки и перезапуска; успешность определяется достижением
  безопасного итогового состояния;
- отдельный `VPNG0005-R5.R6.R4` удаляется;
- его `.C1` также удаляется: отдельное исключение «alpha может не иметь reload» больше не
  требуется, поскольку requirement изначально не обещает `reload`.

Применение новой конфигурации может требовать явного перезапуска. Если конкретный интерфейс
управления предоставляет операцию `reload`, её поведение и результат должны быть явно
определены, и она не должна неявно подменяться полным перезапуском экземпляра. Это правило
относится к архитектуре/контракту интерфейса, а не к самостоятельной product capability.
