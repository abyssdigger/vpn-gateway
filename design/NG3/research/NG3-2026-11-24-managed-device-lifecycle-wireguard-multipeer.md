# NG3 — исследование управляемого жизненного цикла Device и WireGuard с несколькими пирами

**Дата:** 2026-11-24
**Статус:** исследование / кандидат для последующей нормативной декомпозиции

Основание — решение владельца проекта начать проектирование управления VPN-конфигурацией и
жизненным циклом Device, сохранив работу с внешне подготовленными Devices, и начать
практическую проработку с WireGuard, где несколько пиров предоставляют одну удаленную сеть.

Документ не меняет требования, архитектуру или внешний формат конфигурации.

## 1. Исходные границы

Текущая NG3-модель уже разделяет обязанности:

- Device описывает транспортную возможность, которую могут использовать Profiles;
- VPNPathAdapter наблюдает уже существующий VPN-интерфейс и подтверждает binding, но не
  создает VPN-сеанс и не управляет конфигурацией VPN;
- LogicalPathId выводится из настроенной формы expected_interfaces, а PathBinding связывает
  логический путь с точным поколением интерфейса (ifname, ifindex);
- первый выпуск разрешает оставить подготовку VPN и жизненный цикл VPN-служб внешнему
  администратору или внешнему диспетчеру служб;
- Device участвует в обнаружении и привязке только когда он enabled и нужен хотя бы одному
  enabled Profile.

Последний пункт уже дает естественный сигнал структурной потребности в Device.

## 2. Обратная совместимость

Будущее управление VPN со стороны VPN-GATE должно быть явной дополнительной обязанностью,
а не новым смыслом enabled = true.

Если управление VPN для Device не включено, VPN-GATE:

- не создает и не переписывает VPN-конфигурацию;
- не запускает, не перезапускает и не останавливает VPN-службу;
- продолжает использовать существующие VPNPathAdapter и механизм привязки без изменения их смысла.

Если управление явно включено, VPN-GATE получает право владеть только заранее определенной
областью VPN-конфигурации и жизненного цикла этого Device. После появления интерфейса
VPNPathAdapter подтверждает его тем же способом, что и для внешне подготовленного Device.

Новый менеджер не должен поглощать VPNPathAdapter и не должен считать успешный запуск службы
доказательством существования пригодного пути.

## 3. Область владения будущего менеджера

Для явно управляемого Device кандидат на область владения включает:

- подготовку принадлежащей VPN-GATE конфигурации поддерживаемой VPN-реализации;
- запуск принадлежащей VPN-службы или эквивалентного экземпляра;
- остановку и подтверждение исчезновения принадлежащего экземпляра;
- перезапуск при изменении принадлежащей VPN-GATE части конфигурации;
- наблюдение результата собственных операций;
- состояние «запрошено / выполняется / подтверждено / ошибка»;
- координацию с обычным обнаружению и привязке после появления или замены интерфейса.

Не должны автоматически переходить к нему:

- процессы и конфигурации Device, для которого управление не включено;
- маршрутизация полезного трафика и firewall/NAT, уже принадлежащие текущим компонентам;
- решение о пригодности пути для конкретного Profile;
- внешняя инфраструктура и секреты, право владения которыми явно не передано продукту.

Для секретов до реализации нужен отдельный контракт источника, прав доступа и замены.

## 4. Что означает «подключать по потребности»

Первый безопасный смысл уже задан существующей моделью:

    Device.enabled
    AND Device referenced by >= 1 enabled Profile
        -> структурная потребность в Device

Для управляемого Device это естественный кандидат на желаемое наличие экземпляр VPN.

Появление структурной потребности означает подготовку принадлежащей конфигурации и запуск
экземпляр VPN. Исчезновение потребности означает сначала снятие зависимой сетевой политики
обычным текущим путем, затем остановку только принадлежащего экземпляр VPN.

Запуск по фактическому первому пакету и остановка после простоя — отдельная функция. Для нее
нужно определить судьбу первого пакета, критерий простоя, входящий трафик и совместное
использование Device несколькими Profiles. Ее нельзя незаметно включить в первый контракт.

## 5. Применение измененной конфигурации

Нужно различать желаемую конфигурацию и фактически запущенное поколение экземпляр VPN.

Без отдельного доказательства безопасной семантики операции reload конкретной VPN-реализации
предпочтителен простой контракт:

    существенное изменение принадлежащей конфигурации
        -> остановить старое поколение
        -> подтвердить его отсутствие
        -> атомарно подготовить новое содержимое
        -> запустить новое поколение
        -> передать его обычному обнаружению и привязке

Reload может появляться только для интеграций, где доказан его точный смысл.

## 6. WireGuard: пиры одного wg0 не являются отдельными LogicalPathId

EXP-086 подтвердил:

- одинаковый удаленный префикс внутри одного wg0 одновременно принадлежит только одному пиру
  через AllowedIPs;
- перестановка обычных Linux-маршрутов через тот же wg0 не выбирает пир.

EXP-087 подтвердил:

- у каждого пира можно постоянно оставить собственный внутритуннельный /32 для проверки;
- общий префикс полезного трафика можно переносить между пирами во время работы через wg set;
- для такого переключения не требуется переписывать файл конфигурации WireGuard.

Из этого не следует, что пир должен стать обычным LogicalPathId. Десять пиров одного wg0
имеют одно поколение Linux-интерфейса и не удовлетворяют существующему контракту десяти
PathBinding.

Кандидат:

    один управляемый WireGuard Device
        -> один wg0
        -> один обычный LogicalPathId / PathBinding
        -> N внутренних WireGuard пиров
             -> стабильная идентичность пира
             -> постоянный индивидуальный проверочный /32
             -> возможность временно владеть префикс полезного трафика

Пиры остаются деталями WireGuard-реализации Device, а не универсальными VPN-путями продукта.

## 7. Базовая конфигурация и изменяемые AllowedIPs

Базовая конфигурация управляемого WireGuard Device должна содержать долговечные свойства:

- ключ интерфейса или ссылку на его защищенный источник;
- адрес и параметры интерфейса;
- открытый ключ каждого пира;
- транспортную конечную точку каждого пира;
- при необходимости PersistentKeepalive;
- постоянный уникальный внутритуннельный probe /32 каждого пира.

Во время работы отдельный компонент должен отвечать за:

- тем, какой пир владеет общим префиксом полезного трафика;
- точным наблюдением текущих AllowedIPs;
- безопасным применением нового владельца;
- подтверждением результата и восстановлением после ошибки.

Общий префикс полезного трафика не должен одновременно быть постоянной частью базовой конфигурации
всех пиров. После полного перезапуска безопасное начальное состояние таково: wg0 и постоянные проверочные /32 существуют, но общий префикс полезного трафика еще не назначен ни одному пиру. Пир выбирается только по результатам нового наблюдения; после этого ему назначается общий префикс.

## 8. Жизненный цикл wg0 и переключение пира — разные обязанности

Перезапуск VPN-службы меняет поколение экземпляр VPN и обычно поколение интерфейса.

Перенос AllowedIPs между пирами меняет состояние уже работающей WireGuard-реализации.

Поэтому обычное переключение между пирами не должно перезапускать wg0 или службу.

Кандидатное разделение:

- менеджер жизненного цикла Device создает и удаляет базовую реализацию wg0 и набор пиров;
- отдельный владелец WireGuard владение префиксами между пирами при существующем wg0 наблюдает пиры, выбирает
  допустимого владельца префикс полезного трафикаа, изменяет AllowedIPs и подтверждает результат.

## 9. Доступность пира и доступность Profile различаются

Постоянный внутритуннельный /32 из EXP-087 доказывает, что конкретный пир отвечает через
WireGuard. Он не доказывает доступность каждой бизнес-сети за этим пиром.

Поэтому нужны два уровня:

1. пригодность пира для выбора внутри WireGuard — техническое свидетельство интеграции;
2. пригодность выбранного пути для конкретного Profile — существующая продуктовая
   семантика доступности.

После смены пира старое свидетельство Profile не должно считаться актуальным только потому,
что LogicalPathId и wg0 не изменились.

Кандидатное решение: каждому выбранному состоянию WireGuard соответствует отдельное поколение реализации. Контекст
сведения о доступности Profile учитывает его вместе с текущим PathBinding. Смена владельца
префикс полезного трафикаа делает старое свидетельство неактуальным, не превращая пир в новый
LogicalPathId.

## 10. Гранулярность выбора

AllowedIPs принадлежит префиксам. В общем случае один «текущий пир Device» слишком груб:
разные префиксы одного Device могут иметь разных владельцев.

Для первого практического шага достаточно узкого случая:

    один управляемый WireGuard Device
    один wg0
    десять пиров
    одна общая удаленная подсеть
    один набор префикс полезного трафикаов, переключаемый как единое целое

Обобщение до независимого выбора для нескольких наборов префиксов следует делать после
проверки этой формы.

## 11. Предварительная компонентная граница

Без принятия окончательных имен полезно разделить три обязанности.

В STACK нужен владелец желаемого наличия и поколения управляемых Devices. Он получает
нормализованное намерение и структурную потребность.

На границе VPN integration нужен нижний компонент конкретной VPN-реализации, который готовит
принадлежащую конфигурацию, запускает/останавливает принадлежащий runtime и наблюдает
результат.

Для управляемого WireGuard нужен отдельный владелец изменяемого владение префиксом полезного трафика в AllowedIPs.
Он не подменяет VPNPathAdapter и общую Profile policy.

Общая команда systemd сама по себе не является основанием вводить универсальный
SystemdDriver: переиспользуемой границей должен быть полный контракт управления конкретной
VPN-реализацией.

## 12. Требования, необходимые до реализации

Существующие VPNG-U001-R1.R3.C1 и VPNG-U001-R1.R3.C3 разрешают первому выпуску оставить
provisioning и lifecycle внешними. Они не запрещают будущий явно управляемый путь.

Перед реализацией новая нормативная ветвь должна как минимум определить:

1. явное включение управления VPN для Device;
2. сохранение прежнего внешнего режима при отсутствии такого включения;
3. область владения создаваемой конфигурацией и экземпляр VPN;
4. подтверждаемые проверяемые результаты запуска, остановки и перезапуска;
5. применение измененной конфигурации без зависимости от старого runtime-состояния;
6. семантику структурной потребности для запуска и остановки;
7. разделение успешного запуска VPN и подтвержденного PathBinding;
8. требования к секретам и правам доступа;
9. для WireGuard с несколькими пирами — отдельное владение изменяемыми AllowedIPs, peer-specific
   observation и недействительность старого свидетельство доступности после смены реализации.

## 13. Следующий эксперимент

Следующий эксперимент должен проверять границу будущего управляемого Device, а не повторять
двухпировую возможность EXP-087.

Стенд:

    один wg0
    10 peers
    10 постоянных probe /32
    один общий префикс полезного трафика
    сгенерированная базовая конфигурация без общего префикс полезного трафика

Проверить:

1. запуск из базовой конфигурации дает все десять проверочные адреса и ни одного владельца общего
   префикс полезного трафикаа;
2. все десять пиров различимы независимыми проверками;
3. выбранный пир получает общий префикс без перезапуска интерфейса;
4. последовательное выключение выбранных пиров переносит префикс по приоритету;
5. старое свидетельство доступности после каждого переноса становится недействительным при смену поколения
   WireGuard-реализации в модели эксперимента;
6. полный stop/start базовой реализации удаляет динамический payload ownership;
7. после restart система снова начинает без владельца и восстанавливает выбор из свежего
   наблюдения;
8. ошибка выполнения wg set не приводит к ложному подтверждению владельца;
9. отдельно проверить транзакционные свойства обновления AllowedIPs нескольких пиров и,
   если они недостаточны, определить временное ограничение полезного трафика на время переключения.

Эксперимент не должен содержать рабочую реализацию менеджера Device. Он проверяет нижний контракт,
который менеджер впоследствии сможет использовать.

## 14. Предварительный вывод

Совместимый путь существует без разрушения текущей модели внешне подготовленных Devices:

- управление VPN является явной дополнительной функцией и не меняет старый внешний режим;
- новый менеджер обеспечивает наличие VPN-реализации, но VPNPathAdapter остается источником
  истины о фактически появившемся интерфейсе;
- структурная потребность из существующей Device/Profile модели является первым безопасным
  смыслом «подключения по потребности»;
- десять пиров одного wg0 не становятся десятью LogicalPathId;
- базовый жизненный цикл wg0 и перенос AllowedIPs принадлежат разным обязанностям;
- индивидуальная проверка пира пригоден для внутреннего выбора пира, но не заменяет сведения о доступности Profile;
- смена выбранного пира должна менять поколение реализации, чтобы старое свидетельство Profile не
  переживало фактическую смену пути внутри того же интерфейса.

До реализации нужны два следующих шага: принять нормативную ветвь управляемого Device и
получить результаты проверки на десяти пирах по описанному эксперименту.
