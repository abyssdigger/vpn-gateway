# VPN-GATE NG3 — Requirements

**Status:** NG3 design-cycle draft  
**Cycle:** `ng3-design-cycle-20261115-40m`  
**Normative model:** `design/requirements-model.md`  
**Architecture status:** no NG2 architecture is inherited automatically

This document is the normative requirement tree for NG3.

The seven L1 requirements are accepted. Lower-level nodes remain subject to normal
requirement/constraint review.

Canonical compact form:

```text
**[ID]** Purpose | Statement   — for R
**[ID]** Reason  | Statement   — for C
```

The italicized part answers **зачем** for a requirement and **почему** for a constraint.
The part after `|` is the normative implementation-facing statement.

Section headings below are only human-readable grouping. They are not requirements and do
not participate in the requirement tree.

No NG2 component, state machine, event, Linux mechanism or configuration object becomes an
NG3 requirement merely because it existed before.

## VPN routing and VPN-channel service

**[VPNG-R1]** *Чтобы пользователь мог использовать VPN-GATE как управляемый сетевой узел для передачи выбранного IP-трафика через VPN, не собирая поведение продукта вручную из низкоуровневых сетевых команд.* | VPN-GATE должен предоставлять управляемую маршрутизацию выбранного IP-трафика между обычной сетью и настроенными VPN-путями.

 **[VPNG-R1.R1]** *Чтобы трафик, принятый продуктом в обслуживание, действительно мог проходить через предназначенный для него VPN-путь в требуемом направлении.* | Для принятого в обслуживание IP-трафика VPN-GATE должен обеспечивать необходимое forwarding поведение между обычной сетью и разрешенными VPN-путями.

 **[VPNG-R1.R2]** *Чтобы эксплуатация продукта не зависела от ручного воспроизведения его внутренней сетевой механики оператором.* | Пользователь должен задавать требуемое поведение через продуктовую конфигурацию и управляющие операции VPN-GATE; внутренние сетевые действия должны выполняться продуктом.

 **[VPNG-R1.R3]** *Чтобы VPN-GATE мог использовать подготовленные VPN-соединения как реальные пути передачи управляемого трафика.* | VPN-GATE должен уметь принимать в обслуживание поддерживаемые VPN-каналы, однозначно идентифицировать их и использовать как VPN-пути в соответствии с текущей политикой.

  **[VPNG-R1.R3.C1]** *В первом релизе развертывание и базовая настройка VPN-инфраструктуры остаются ответственностью администратора и внешней эксплуатационной среды.* | VPN-GATE первого релиза не обязан самостоятельно создавать и конфигурировать VPN-каналы; администратор должен заранее развернуть и настроить поддерживаемый VPN-канал так, чтобы VPN-GATE мог принять его в обслуживание.

   **[VPNG-R1.R3.C1.R1]** *Чтобы администратор мог выполнить возложенную на него часть без знания внутренних деталей реализации VPN-GATE.* | Для каждого поддерживаемого способа внешнего развертывания VPN-канала должны быть предоставлены инструкции и необходимый контракт, позволяющие сделать канал однозначно видимым и пригодным для управления и использования VPN-GATE.
   ↳ [decomp: VPNG-R4.R6 -> VPNG-R4.R6.R1]

  **[VPNG-R1.R3.C2]** *Для выполнения требования изоляции управляемой сетевой среды NG3 использует отдельный изолированный network domain, а не host network namespace как рабочее пространство маршрутизации.* | Поддерживаемый внешний VPN-канал может использоваться VPN-GATE только если его data-plane endpoint может быть представлен внутри изолированной управляемой сетевой среды; VPN-адаптер, остающийся только в обычном сетевом пространстве хоста, не считается полноценным управляемым VPN-путем NG3.

   **[VPNG-R1.R3.C2.R1]** *Чтобы администратор мог выполнить требование изоляции без знания внутренней сетевой механики VPN-GATE.* | Onboarding contract для поддерживаемого внешнего VPN-канала должен описывать требуемый результат размещения его data-plane endpoint внутри изолированной управляемой сетевой среды; конкретный механизм достижения этого результата уточняется только после выбора поддерживаемого способа интеграции.
   ↳ [decomp: VPNG-R4.R6 -> VPNG-R4.R6.R1]

## Explicit traffic policy

**[VPNG-R2]** *Чтобы использование VPN было следствием явного решения пользователя, а не побочным эффектом наличия работоспособного VPN-пути.* | Пользователь должен иметь возможность явно определить, какой трафик VPN-GATE обслуживает, через какие VPN-пути этот трафик разрешено передавать и в каком направлении.

 **[VPNG-R2.R1]** *Чтобы можно было однозначно отличить управляемый VPN-GATE трафик от остального трафика системы.* | Политика должна однозначно определять, какой трафик входит в область управления VPN-GATE.

 **[VPNG-R2.R2]** *Чтобы динамическое состояние системы не могло само расширять разрешенный пользователем набор VPN-путей.* | Для каждого управляемого класса трафика политика должна однозначно определять набор VPN-путей, через которые этот трафик разрешено передавать.

 **[VPNG-R2.R3]** *Чтобы разрешение одного направления передачи не становилось неявным разрешением другого.* | Политика должна однозначно определять разрешенное направление передачи управляемого трафика.

 **[VPNG-R2.R4]** *Чтобы наличие работающего VPN или автоматически обнаруженной пригодности пути не изменяло пользовательскую политику доступа.* | Трафик или VPN-путь, не разрешенные текущей политикой, не должны становиться разрешенными из-за доступности, автоматического failover, recovery или иного runtime-состояния.

 **[VPNG-R2.R5]** *Чтобы одинаковая конфигурация не приводила к различному поведению при неоднозначном совпадении нескольких правил.* | Если к одному трафику применимы несколько частей политики, VPN-GATE должен получать один детерминированный эффективный результат либо явно отклонять неоднозначную конфигурацию.

## Path preference and availability

**[VPNG-R3]** *Чтобы при наличии нескольких разрешенных VPN-путей трафик использовал их предсказуемо и сохранял практическую работоспособность при деградации предпочтительного пути.* | Если для одного трафика разрешено несколько VPN-путей, VPN-GATE должен использовать их в предсказуемом пользовательском порядке, автоматически понижать предпочтение действительно проблемных путей и после восстановления возвращаться к пользовательскому порядку.

 **[VPNG-R3.R1]** *Чтобы при нормальной работе выбор между несколькими разрешенными путями соответствовал намерению пользователя.* | Для нескольких разрешенных путей должен существовать детерминированный настроенный порядок предпочтения.

 **[VPNG-R3.R2]** *Чтобы availability-механизм не подменял собой пользовательскую политику.* | Автоматическая адаптация по состоянию пути может изменять только эффективное предпочтение среди уже разрешенных путей и не должна изменять их policy membership.

 **[VPNG-R3.R3]** *Чтобы новый трафик не продолжал предпочитать путь, для которого получены достаточные признаки практической непригодности, когда разрешена пригодная альтернатива.* | После достаточного подтверждения проблемы на предпочтительном пути VPN-GATE должен понизить его эффективное предпочтение относительно разрешенных путей без подтвержденной проблемы.

 **[VPNG-R3.R4]** *Чтобы временная деградация не превращалась в постоянное изменение пользовательской политики.* | После достаточного подтверждения восстановления пути VPN-GATE должен вернуть его к позиции, заданной настроенным порядком предпочтения.

 **[VPNG-R3.R5]** *Чтобы единичное, кратковременное или случайное наблюдение не вызывало ненужной перестройки маршрутизации.* | Переход между нормальным и пониженным предпочтением должен требовать достаточного подтверждения деградации и восстановления, чтобы единичное случайное наблюдение само по себе не вызывало переключение.

  **[VPNG-R3.R5.R1]** *Чтобы единичная потеря или отсутствие одного положительного наблюдения не понижали путь, который практически остается пригодным.* | Путь без установленной availability-проблемы должен переходить в пониженное предпочтение только после достижения конечного policy-defined порога подтверждения деградации по актуальным evidence/evaluation boundaries.

  **[VPNG-R3.R5.R2]** *Чтобы случайное единичное успешное наблюдение не возвращало проблемный путь в предпочтительное положение раньше устойчивого восстановления.* | Путь с установленной availability-проблемой должен возвращаться к настроенному предпочтению только после достижения конечного policy-defined порога актуальных положительных свидетельств восстановления.

 **[VPNG-R3.R6]** *Чтобы автоматическая адаптация опиралась на сведения, действительно относящиеся к текущей пригодности конкретного пути, а не на догадку о его состоянии.* | VPN-GATE должен получать достаточно актуальные сведения о пригодности каждого пути, для которого включена автоматическая availability-адаптация, используя механизм наблюдения, достаточный для поддерживаемого сценария.

  **[VPNG-R3.R6.R1]** *Чтобы сведения об одном пути не изменяли приоритет другого.* | Каждое availability-свидетельство, используемое для адаптации, должно быть однозначно связано с логическим путем, к состоянию которого оно относится.

  **[VPNG-R3.R6.R2]** *Чтобы старое наблюдение не изменяло решение после замены наблюдаемого экземпляра пути или существенного изменения контекста, к которому относилось это наблюдение.* | Availability-свидетельство, потерявшее актуальность для текущего экземпляра или контекста пути, не должно влиять на текущее effective preference.

  **[VPNG-R3.R6.R3]** *Чтобы формально успешное наблюдение локального объекта не скрывало отказ, который делает VPN-путь непригодным в реально поддерживаемом сценарии.* | Механизм получения availability evidence должен наблюдать свойство, достаточное для выявления тех видов непригодности пути, которые существенны для поддерживаемых продуктовых сценариев.

 **[VPNG-R3.R7]** *Чтобы само включение availability-функции не ухудшало или произвольно изменяло нормальное поведение маршрутизации.* | Пока для разрешенных путей нет достаточного подтверждения проблемы, effective order должен совпадать с настроенным пользовательским порядком.

## Safety under uncertainty and failure

**[VPNG-R4]** *Чтобы ошибка, неполная конфигурация или непроверенное состояние не приводили к передаче управляемого трафика способом, который пользователь не разрешал.* | VPN-GATE не должен передавать управляемый трафик способом, не разрешенным текущей политикой или безопасность которого продукт не может подтвердить; при существенной неопределенности предпочтителен отказ от передачи.

 **[VPNG-R4.R1]** *Чтобы отсутствие однозначного policy result не превращалось в неявное разрешение.* | Если VPN-GATE не может однозначно определить разрешенное поведение для управляемого трафика, такой трафик не должен получать неявный VPN forwarding.

 **[VPNG-R4.R2]** *Чтобы продукт не считал желаемое сетевое состояние фактически действующим без подтверждения.* | Если фактическое сетевое состояние, критичное для безопасной передачи, неизвестно или не может быть подтверждено, VPN-GATE должен сохранять или устанавливать безопасное ограничивающее поведение до получения достаточного подтверждения.

 **[VPNG-R4.R3]** *Чтобы корректная конечная конфигурация не достигалась через промежуточное состояние с неразрешенной передачей трафика.* | Изменение effective network policy должно выполняться так, чтобы промежуточные состояния не создавали передачу, запрещенную до или после изменения.

 **[VPNG-R4.R4]** *Чтобы запуск процесса не открывал трафик до построения и проверки требуемой политики.* | До подтверждения безопасной исходной сетевой границы VPN-GATE не должен считать payload forwarding готовым к использованию.

 **[VPNG-R4.R5]** *Чтобы ошибка посреди изменения сетевого состояния не оставляла продукт в неизвестном разрешающем режиме.* | После частично выполненного или неуспешного изменения network policy VPN-GATE должен повторно установить авторитетное фактическое состояние и либо безопасно довести его до требуемого результата, либо оставить соответствующий трафик закрытым.

 **[VPNG-R4.R6]** *Чтобы ошибки, восстановление и развитие VPN-GATE не изменяли несвязанные сетевые настройки хоста и не превращали host networking в неявную часть внутреннего состояния продукта.* | Сетевое состояние, которым VPN-GATE управляет для обслуживания трафика, должно быть изолировано от обычного сетевого пространства хоста и взаимодействовать с ним только через явно определенные границы; изменения внутри управляемой области не должны требовать владения или произвольного изменения несвязанного host network state.

  **[VPNG-R4.R6.R1]** *Чтобы изоляция была не декларацией, а проверяемой границей владения сетевым состоянием.* | VPN-GATE должен иметь отдельный управляемый сетевой домен, в котором локализованы принадлежащие продукту routing/policy/data-plane состояния; взаимодействие этого домена с внешней сетью и хостом должно происходить только через явно определенные граничные точки, а используемые VPN data-plane endpoints должны быть представлены внутри этого домена.

   **[VPNG-R4.R6.R1.R1]** *Чтобы внутренние изменения VPN-GATE не требовали знания или изменения несвязанных сетевых объектов хоста.* | Сетевые объекты и mutable state, необходимые для внутренней маршрутизации и policy VPN-GATE, должны принадлежать управляемому сетевому домену либо явно объявленной boundary-области; произвольные host routes/rules/firewall state не должны использоваться как скрытая часть внутренней модели VPN-GATE.

   **[VPNG-R4.R6.R1.R2]** *Чтобы весь обмен между управляемой сетью VPN-GATE и внешней средой был видим, проверяем и управляем.* | Вход и выход управляемого трафика из сетевого домена должны происходить через явно определенные boundary endpoints с известной ролью и направлением; наличие обычной host connectivity само по себе не должно создавать неявную границу передачи.

   **[VPNG-R4.R6.R1.R3]** *Чтобы VPN-путь подчинялся тем же routing, policy и safety правилам, что и остальная управляемая сеть.* | Data-plane endpoint каждого VPN-пути, используемого VPN-GATE для managed forwarding, должен быть доступен внутри управляемого сетевого домена как его внутренний path endpoint; endpoint, существующий только в обычном host network space, не должен использоваться напрямую как управляемый VPN-путь.

   **[VPNG-R4.R6.R1.R4]** *Чтобы продукт не считал внешнюю интеграцию корректной только потому, что администратор выполнил некоторую настройку.* | До использования внешнего boundary endpoint или VPN path endpoint VPN-GATE должен иметь возможность проверить, что требуемый endpoint присутствует в правильном управляемом домене, однозначно соответствует ожидаемой роли/идентичности и пригоден для дальнейшего применения policy; несоответствие должно оставаться безопасным и наблюдаемым.

## Lifecycle and recovery

**[VPNG-R5]** *Чтобы VPN-GATE можно было предсказуемо запускать, эксплуатировать, перезапускать и останавливать без ручной уборки или восстановления его внутренних сетевых объектов.* | VPN-GATE должен управлять жизненным циклом принадлежащего ему runtime-состояния, восстанавливать требуемое состояние после обычных восстановимых изменений среды и явно сообщать, когда безопасное восстановление невозможно.

 **[VPNG-R5.R1]** *Чтобы одинаковая допустимая конфигурация приводила к воспроизводимому рабочему состоянию.* | Startup должен из безопасной исходной границы построить и подтвердить необходимое runtime-состояние до объявления соответствующих функций готовыми.

 **[VPNG-R5.R2]** *Чтобы обычное изменение или потеря принадлежащего продукту runtime-состояния не требовали ручного пересоздания всей системы.* | Во время работы VPN-GATE должен уметь обнаруживать существенное расхождение между требуемым и фактическим принадлежащим ему состоянием и восстанавливать его, если это безопасно и возможно.

 **[VPNG-R5.R3]** *Чтобы временный технический отказ не становился постоянной потерей функции после исчезновения его причины.* | Операция, не выполненная из-за восстановимой ошибки, должна оставаться повторяемой из актуального подтвержденного состояния без необходимости перезапуска всего продукта, если этого не требует сама внешняя среда.

 **[VPNG-R5.R4]** *Чтобы остановленный или удаленный VPN-GATE не продолжал незаметно влиять на сетевое поведение системы.* | После успешного shutdown/cleanup не должны оставаться активные сетевые или процессные ресурсы, принадлежащие остановленному экземпляру VPN-GATE и продолжающие влиять на трафик.

 **[VPNG-R5.R5]** *Чтобы отказ одной независимой части cleanup не мешал попытке безопасно убрать другие принадлежащие продукту части состояния.* | Если несколько независимо управляемых областей требуют cleanup или recovery, ошибка одной области не должна сама по себе отменять попытку обработать остальные; все существенные ошибки должны оставаться наблюдаемыми.

## Observability

**[VPNG-R6]** *Чтобы оператор мог понять фактическое поведение VPN-GATE и причину невозможности выполнить требуемую политику, не восстанавливая внутреннее состояние по логам и kernel-командам.* | VPN-GATE должен предоставлять наблюдаемую текущую проекцию существенного настроенного, фактического и эффективного состояния, а также проблем, мешающих выполнить требуемую политику.

 **[VPNG-R6.R1]** *Чтобы оператор мог проверить, какое поведение продукт считает требуемым.* | Должно быть возможно определить существенную текущую конфигурацию и policy intent, используемые VPN-GATE.

 **[VPNG-R6.R2]** *Чтобы оператор мог понять, какие разрешенные VPN-пути фактически участвуют в текущем выборе и каков их effective order.* | Должно быть возможно определить текущий набор разрешенных для использования путей, существенное availability-состояние и effective preference, применяемые к управляемому трафику.

 **[VPNG-R6.R3]** *Чтобы невозможность выполнить требование не выглядела как молчаливое отсутствие функции.* | Существенные проблемы, из-за которых требуемая policy, lifecycle operation или safety postcondition не могут быть выполнены, должны быть доступны оператору.

 **[VPNG-R6.R4]** *Чтобы observability не сообщала желаемое состояние как фактическое.* | Текущая status-проекция должна различать требуемое, подтвержденное фактическое и неизвестное/неподтвержденное состояние там, где это различие влияет на пользовательское понимание поведения или safety.

## Implementation quality

**[VPNG-R7]** *Чтобы VPN-GATE можно было безопасно развивать и сопровождать живыми разработчиками и AI, не превращая продукт ни в универсальную систему из ненужных механизмов, ни в хрупкий монолит, изменение которого требует понимания всего кода сразу.* | Реализация VPN-GATE должна быть минимально достаточной для принятых требований, сопровождаемой и понятной, допускать локальное изменение и параллельную разработку через явные внутренние контракты и не содержать сложности, не оправданной требованиями или реальными целевыми сценариями.

 **[VPNG-R7.R1]** *Чтобы развитие продукта не создавало состояния, компоненты и универсальные механизмы, которые увеличивают стоимость сопровождения без продуктовой ценности.* | Каждый существенный механизм, состояние, очередь, lifecycle, retry policy, interaction и компонент должны быть необходимы для конкретного принятого требования или ограничения; неоправданная общность должна удаляться или не создаваться.

  **[VPNG-R7.R1.R1]** *Чтобы локальная задача не превращалась в систему хранения и воспроизведения истории без необходимости.* | Если требование может быть полностью выполнено текущим или ограниченным агрегированным состоянием, реализация не должна вводить неограниченную историю, журнал или replay-механику.

 **[VPNG-R7.R2]** *Чтобы сопровождение и review не зависели от знания неявной глобальной механики одним автором.* | Существенные обязанности, состояния, контракты и причины проектных решений должны быть локализованы и документированы настолько, чтобы разработчик или AI мог определить назначение блока, его границы и последствия изменения без реконструкции всей системы.

 **[VPNG-R7.R3]** *Чтобы изменения внутри одной области не распространялись на несвязанные части продукта через неявные зависимости.* | Внутренние области реализации должны взаимодействовать через явные контракты, скрывающие детали, которые не требуются соседней области.

  **[VPNG-R7.R3.R1]** *Чтобы зависимость между частями системы была видима для разработки, review и тестирования.* | Материальная межкомпонентная зависимость должна быть представлена явным контрактом, определяющим необходимые входы, выходы и семантику взаимодействия.

  **[VPNG-R7.R3.R2]** *Чтобы замена или изменение внутреннего механизма нижней области не требовали переделки верхней policy без продуктовой причины.* | Внутренние технические детали одной предметной области не должны пересекать ее контрактную границу, если они не нужны другой области для выполнения собственного принятого требования.

  **[VPNG-R7.R3.R3]** *Чтобы исправление или развитие одной ответственности можно было выполнять и проверять изолированно.* | Изменение реализации внутри стабильного внутреннего контракта не должно требовать изменения несвязанных потребителей этого контракта.

 **[VPNG-R7.R4]** *Чтобы независимые части продукта можно было проектировать, реализовывать и проверять параллельно без постоянной сериализации работы через общий внутренний код.* | Архитектура должна позволять выделять независимые review/development units с явными контрактными границами и достаточным локальным evidence, когда требования не создают неизбежной общей транзакционной ответственности.

 **[VPNG-R7.R5]** *Чтобы декомпозиция NG3 использовала единый проверяемый словарь обязанностей и взаимодействий вместо ad-hoc архитектурных ролей.* | Архитектура и реализация NG3 должны соответствовать `design/component-model.md`; существенное отклонение допускается только после явного изменения требования, ограничения или самой компонентной модели через review.

 **[VPNG-R7.R6]** *Чтобы архитектура оставалась отчетом о реализации принятых требований, а не становилась самостоятельным источником новых функций и сложности.* | Каждое существенное архитектурное решение NG3 должно явно ссылаться на наиболее конкретные requirement/constraint IDs, которые его требуют или ограничивают; решение без честной трассировки является finding.

  **[VPNG-R7.R6.R1]** *Чтобы можно было как найти реализацию требования, так и установить причину существования архитектурного элемента.* | Документация должна позволять пройти по связям `requirement -> architecture -> implementation/evidence` и обратно `architecture -> requirement/constraint`.

  **[VPNG-R7.R6.R2]** *Чтобы изменение смысла требования не оставляло архитектуру, формально ссылающуюся на уже другой contract.* | Изменение requirement/constraint требует повторной проверки архитектурных решений, ссылающихся на измененный узел или его затронутых потомков, до продолжения реализации.

## Initial acceptance/evidence expectations

This table adds no new requirement semantics.

| L1 | Minimum final evidence type |
| --- | --- |
| `VPNG-R1` | end-to-end VPN-path forwarding and externally provisioned channel onboarding scenario |
| `VPNG-R2` | policy acceptance/rejection scenarios |
| `VPNG-R3` | deterministic failover/failback scenarios with path-state changes |
| `VPNG-R4` | negative/failure scenarios proving no unintended forwarding |
| `VPNG-R5` | startup, drift, retry and shutdown lifecycle scenarios |
| `VPNG-R6` | status projection checked against authoritative runtime state |
| `VPNG-R7` | architecture/review traceability plus isolated-change evidence |

## Constraint policy for this NG3 pass

No NG2 implementation constraint is accepted into NG3 merely by inheritance.

`VPNG-R1.R3.C1` is accepted explicitly for the first product release: VPN-channel
provisioning/configuration remains an administrator responsibility, while VPN-GATE must
provide the instructions/contract required to consume those channels.

Other candidate constraints discovered while building the NG3 architecture must be added at
the requirement node whose promise they actually restrict and must pass normal constraint
lifting before they become accepted NG3 constraints.
