# VPN-GATE NG3 — Requirements

**Status:** NG3 design-cycle draft  
**Cycle:** `ng3-design-cycle-20261115-40m`  
**Normative model:** `design/requirements-model.md`  
**Architecture status:** no NG2 architecture is inherited automatically

This document is the normative requirement tree for NG3.

The seven L1 requirements are accepted. Lower-level nodes remain subject to normal
requirement/constraint review.

Canonical compact form:

```text
**[ID]** Purpose | Statement   — for R
**[ID]** Reason  | Statement   — for C
```

The italicized part answers **зачем** for a requirement and **почему** for a constraint.
The part after `|` is the normative implementation-facing statement.

Section headings below are only human-readable grouping. They are not requirements and do
not participate in the requirement tree.

No NG2 component, state machine, event, Linux mechanism or configuration object becomes an
NG3 requirement merely because it existed before.

## VPN routing and VPN-channel service

**[VPNG-R1]** *Чтобы пользователь мог использовать VPN-GATE как управляемый сетевой узел для передачи выбранного IP-трафика через VPN, не собирая поведение продукта вручную из низкоуровневых сетевых команд.* | VPN-GATE должен предоставлять управляемую маршрутизацию выбранного IP-трафика между обычной

 **[VPNG-R1.R1]** *Чтобы трафик, принятый продуктом в обслуживание, действительно мог проходить через предназначенный для него VPN-путь в требуемом направлении.* | Для принятого в обслуживание IP-трафика VPN-GATE должен обеспечивать необходимое forwarding

 **[VPNG-R1.R2]** *Чтобы эксплуатация продукта не зависела от ручного воспроизведения его внутренней сетевой механики оператором.* | Пользователь должен задавать требуемое поведение через продуктовую конфигурацию и

 **[VPNG-R1.R3]** *Чтобы VPN-GATE мог использовать подготовленные VPN-соединения как реальные пути передачи управляемого трафика.* | VPN-GATE должен уметь принимать в обслуживание поддерживаемые VPN-каналы, однозначно идентифицировать их и использовать как VPN-пути в соответствии с текущей политикой.

  **[VPNG-R1.R3.C1]** *В первом релизе развертывание и базовая настройка VPN-инфраструктуры остаются ответственностью администратора и внешней эксплуатационной среды.* | VPN-GATE первого релиза не обязан самостоятельно создавать и конфигурировать VPN-каналы; администратор должен заранее развернуть и настроить поддерживаемый VPN-канал так, чтобы VPN-GATE мог принять его в обслуживание.

   **[VPNG-R1.R3.C1.R1]** *Чтобы администратор мог выполнить возложенную на него часть без знания внутренних деталей реализации VPN-GATE.* | Для каждого поддерживаемого способа внешнего развертывания VPN-канала должны быть предоставлены инструкции и необходимый контракт, позволяющие сделать канал однозначно видимым и пригодным для управления и использования VPN-GATE.

## Constraint policy for this NG3 pass

No NG2 implementation constraint is accepted into NG3 merely by inheritance.

`VPNG-R1.R3.C1` is accepted explicitly for the first product release: VPN-channel
provisioning/configuration remains an administrator responsibility, while VPN-GATE must
provide the instructions/contract required to consume those channels.

Other candidate constraints discovered while building the NG3 architecture must be added at
the requirement node whose promise they actually restrict and must pass normal constraint
lifting before they become accepted NG3 constraints.
