# VPN-GATE NG3 — Requirements

**Status:** NG3 design-cycle draft  
**Cycle:** `ng3-design-cycle-20261116-config-intent-model-40m`  
**Normative model:** `design/requirements-model.md`  
**Architecture status:** no NG2 architecture is inherited automatically

This document is the normative requirement tree for NG3.

The seven L1 requirements are accepted. Lower-level nodes remain subject to normal
requirement/constraint review.

Canonical compact form:

```text
**[ID]** Purpose | Statement [pending_closure|closed|rejected_closure]   — for R
**[ID]** Reason  | Statement [pending_closure|closed|rejected_closure]   — for C
```

The italicized part answers **зачем** for a requirement and **почему** for a constraint.
The part after `|` is the normative implementation-facing statement.

The optional closure label records acceptance state only:
`[pending_closure]` means an architecture candidate exists but is not yet accepted;
`[closed]` means it has been accepted as sufficient for the current scope;
`[rejected_closure]` means the candidate failed acceptance. Requirements do not list the
architectural decisions themselves; those are found by searching architecture documents for
the requirement/constraint ID.

Section headings below are only human-readable grouping. They are not requirements and do
not participate in the requirement tree.

No NG2 component, state machine, event, Linux mechanism or configuration object becomes an
NG3 requirement merely because it existed before.

## VPN routing and VPN-channel service

**[VPNG-R1]** *Чтобы пользователь мог использовать VPN-GATE как управляемый сетевой узел для передачи выбранного IP-трафика через VPN, не собирая поведение продукта вручную из низкоуровневых сетевых команд.* | VPN-GATE должен предоставлять управляемую маршрутизацию выбранного IP-трафика между обычной сетью и настроенными VPN-путями.

 **[VPNG-R1.R1]** *Чтобы трафик, принятый продуктом в обслуживание, действительно мог проходить через предназначенный для него VPN-путь в требуемом направлении.* | Для принятого в обслуживание IP-трафика VPN-GATE должен обеспечивать необходимое forwarding поведение между обычной сетью и разрешенными VPN-путями. [closed]

 **[VPNG-R1.R2]** *Чтобы эксплуатация продукта не зависела от ручного воспроизведения его внутренней сетевой механики оператором.* | Пользователь должен задавать требуемое поведение через продуктовую конфигурацию и управляющие операции VPN-GATE; внутренние сетевые действия должны выполняться продуктом.
 ↳ [decomp: VPNG-R5 -> VPNG-R5.R6]

  **[VPNG-R1.R2.R1]** *Чтобы пользователь описывал намерение продукта, а не последовательность Linux/networking действий.* | Продуктовая конфигурация должна выражать логические сущности и связи, необходимые принятым требованиям, без обязанности пользователя задавать внутренние route/rule/firewall/process операции VPN-GATE.

  **[VPNG-R1.R2.R2]** *Чтобы администратор мог описать заранее подготовленные VPN resources без ручного именования каждого случайно появившегося runtime endpoint.* | Декларативный контракт конфигурации должен позволять задать Device identity и binding expectations, достаточные для детерминированного получения логических VPN-путей и их concrete data-plane endpoint bindings внутри управляемого сетевого домена.

  **[VPNG-R1.R2.R3]** *Чтобы ошибочная декларативная конфигурация не превращалась в частично примененное или случайное сетевое состояние.* | Конфигурация, из которой нельзя однозначно получить требуемые логические сущности, связи и обязательные binding/policy намерения, должна быть отклонена до применения зависящих от нее сетевых изменений; причина отказа должна оставаться наблюдаемой.

  **[VPNG-R1.R2.R4]** *Чтобы пользователь мог описывать ожидаемое сетевое поведение устойчивыми предметными сущностями, а не смешивать сетевую потребность с текущими runtime-интерфейсами.* | Пользовательская конфигурация должна предоставлять именованные сущности `Device` и `Profile`: Device описывает ожидаемый внешний VPN/network resource и его binding expectations, а Profile описывает пользовательскую сетевую потребность и связывает ее с разрешенными Devices.

   **[VPNG-R1.R2.R4.R1]** *Чтобы пользователь мог стабильно ссылаться на одну и ту же логическую сущность из других частей конфигурации, status и diagnostics.* | Каждый Device и Profile должен иметь стабильный уникальный user-visible ID; ссылки между сущностями должны использовать этот ID, а runtime interface name, metric или случайный object identity не должны подменять пользовательскую идентичность.

    **[VPNG-R1.R2.R4.R1.C1]** *Чтобы Device/Profile IDs оставались однозначными без quoting/escaping в human-facing configuration, CLI и diagnostics.* | В текущем human-facing contract Device/Profile ID ограничен формой `[a-z0-9][a-z0-9-]*`; dots, underscores, whitespace и uppercase не поддерживаются, leading digit допустим, а ID должен трактоваться как opaque string, не как число или системный identifier.

   **[VPNG-R1.R2.R4.R2]** *Чтобы пользователь мог заранее описать будущую или временно неиспользуемую часть конфигурации без ее фактической активации.* | Device и Profile должны иметь явное `enabled` состояние без неявного default; disabled объект может существовать как именованный placeholder и не должен сам по себе создавать active routing/binding behavior.

    **[VPNG-R1.R2.R4.R2.R1]** *Чтобы placeholder не требовал преждевременно заполнять еще не определенную будущую конфигурацию.* | Для `enabled = false` остальные поля Device/Profile могут отсутствовать и не должны проходить глубокую semantic validation, кроме корректности самой внешней структуры и идентичности объекта.

   **[VPNG-R1.R2.R4.R3]** *Чтобы один и тот же внешний VPN/network resource можно было переиспользовать в нескольких независимых пользовательских сетевых потребностях.* | Device должен быть отдельной от Profile сущностью; один Device может быть referenced несколькими Profiles, а Device-specific binding expectations не должны дублироваться внутри каждого Profile.

   **[VPNG-R1.R2.R4.R4]** *Чтобы Profile оставался описанием пользовательского намерения, а не снимком текущей Linux-реализации.* | Enabled Profile должен явно задавать direction, непустой набор remote destinations и непустой ordered список Device IDs; Profile не должен требовать от пользователя задания runtime interface names, Linux metrics или внутренних route/rule/firewall объектов.

    **[VPNG-R1.R2.R4.R4.R1]** *Чтобы availability определяла пригодность пути именно для конкретной пользовательской потребности.* | Availability-check configuration должна быть Profile-scoped: для каждого availability-enabled Profile проверка применяется к его использованию конкретных разрешенных путей, поэтому один и тот же Device/interface может иметь разные availability outcomes в разных Profiles.

   **[VPNG-R1.R2.R4.R5]** *Чтобы ссылки на конфигурационные сущности были предсказуемыми и не создавали скрытых объектов.* | Enabled Profile может ссылаться только на объявленные Device IDs; unknown Device reference должен отклонять конфигурацию, а ссылка на известный disabled Device допустима и означает, что такой Device временно не участвует operationally без изменения самого Profile intent.

 **[VPNG-R1.R3]** *Чтобы VPN-GATE мог использовать подготовленные VPN-соединения как реальные пути передачи управляемого трафика.* | VPN-GATE должен уметь принимать в обслуживание поддерживаемые VPN-каналы, однозначно идентифицировать их и использовать как VPN-пути в соответствии с текущей политикой.

  **[VPNG-R1.R3.R1]** *Чтобы normalized policy, availability и status могли различать VPN-пути независимо от случайной идентичности текущего runtime-объекта.* | Каждый VPN-путь, полученный из Device binding semantics и используемый продуктом, должен иметь однозначную логическую идентичность, стабильную для соответствующего Device/selector/slot binding lifecycle и отличимую от конкретного текущего data-plane endpoint.

  **[VPNG-R1.R3.R2]** *Чтобы конкретный внешний VPN endpoint мог безопасно использоваться как именно тот путь, который указан в политике.* | До использования VPN-пути VPN-GATE должен иметь однозначный текущий binding между логической идентичностью пути и конкретным data-plane endpoint; отсутствие, неоднозначность или несоответствие binding не должны приводить к использованию endpoint как этого VPN-пути. [closed]

  **[VPNG-R1.R3.R3]** *Чтобы замена или пересоздание внешнего VPN endpoint не оставляли старый runtime-объект неявно действующим представителем логического пути.* | При изменении текущего binding новый concrete endpoint может представлять тот же логический VPN-путь только после подтверждения нового binding; superseded endpoint после этого не должен считаться текущим endpoint этого пути. [closed]

  **[VPNG-R1.R3.R4]** *Чтобы пользователь мог описать ожидаемые runtime endpoints внешнего Device до их фактического появления и не зависеть от ручного назначения каждого обнаруженного интерфейса.* | Enabled Device должен задавать непустой ordered набор `expected_interfaces`, по которому VPN-GATE однозначно распознает допустимые runtime interface endpoints этого Device и допускает их к binding только в пределах заданных selector semantics.

   **[VPNG-R1.R3.R4.R1]** *Чтобы точный интерфейс и семейство динамически создаваемых интерфейсов можно было описать одной предсказуемой моделью.* | Expected-interface selector должен поддерживать exact interface identity с quota 1 и prefix-family selector с явной положительной quota; prefix selector без quota не должен молча получать неявную емкость.

   **[VPNG-R1.R3.R4.R2]** *Чтобы один runtime interface не мог одновременно и неоднозначно представлять несколько активных Devices.* | Expected-interface selectors должны быть не пересекающимися внутри одного Device и между Devices, одновременно активными в текущем configuration intent; неоднозначный binding должен отклоняться до использования endpoint.

   **[VPNG-R1.R3.R4.R3]** *Чтобы временное отсутствие или появление дополнительных runtime interfaces не меняло пользовательский смысл Device.* | Runtime binding должен отличать user-declared expected-interface capacity от фактически обнаруженных endpoints; отсутствие ожидаемого endpoint не создает другой Device, а endpoint сверх selector quota не должен неявно становиться управляемым путем.

    **[VPNG-R1.R3.R4.R3.R1]** *Чтобы replacement или появление соседнего endpoint не меняли идентичность уже известного пути и не ломали Profile preference/status.* | Каждый admitted selector slot должен соответствовать стабильной logical path identity, производной от Device identity, selector position и stable slot; concrete endpoint является текущим binding этой logical identity и может заменяться без изменения самой identity после подтверждения нового binding.

   **[VPNG-R1.R3.R4.R4]** *Чтобы объявление Device само по себе не запускало управление сетевым ресурсом, который пользователь пока ни для чего не использует.* | Device считается active для discovery/binding только если он enabled и referenced хотя бы одним enabled Profile; disabled или не referenced Device не должен создавать active binding/path behavior.

  **[VPNG-R1.R3.C1]** *В первом релизе развертывание и базовая настройка VPN-инфраструктуры остаются ответственностью администратора и внешней эксплуатационной среды.* | VPN-GATE первого релиза не обязан самостоятельно создавать и конфигурировать VPN-каналы; администратор должен заранее развернуть и настроить поддерживаемый VPN-канал так, чтобы VPN-GATE мог принять его в обслуживание. [closed]

   **[VPNG-R1.R3.C1.R1]** *Чтобы администратор мог выполнить возложенную на него часть без знания внутренних деталей реализации VPN-GATE.* | Для каждого поддерживаемого способа внешнего развертывания VPN-канала должны быть предоставлены инструкции и необходимый контракт, позволяющие сделать канал однозначно видимым и пригодным для управления и использования VPN-GATE. [closed]

## Explicit traffic policy

**[VPNG-R2]** *Чтобы использование VPN было следствием явного решения пользователя, а не побочным эффектом наличия работоспособного VPN-пути.* | Пользователь должен иметь возможность явно определить, какой трафик VPN-GATE обслуживает, через какие VPN-пути этот трафик разрешено передавать и в каком направлении.

 **[VPNG-R2.R1]** *Чтобы можно было однозначно отличить управляемый VPN-GATE трафик от остального трафика системы.* | Политика должна однозначно определять, какой трафик входит в область управления VPN-GATE.

  **[VPNG-R2.R1.R1]** *Чтобы Profile мог прямо выражать remote network need пользователя.* | Enabled Profile должен задавать непустой набор strict IPv4 CIDR `destinations`, определяющий его remote/VPN-side prefixes; list order не должен иметь routing semantics, а некорректные/нестрогие CIDR не должны молча canonicalize-иться.

  **[VPNG-R2.R1.R2]** *Чтобы одна Profile destination semantics одинаково определяла нужную remote сеть в обоих направлениях передачи.* | Для ordinary/host-to-VPN NEW traffic Profile выбирается по remote destination prefix; для VPN-to-ordinary/host NEW traffic — по remote source prefix только среди Profiles, разрешающих фактический ingress Device/path.

 **[VPNG-R2.R2]** *Чтобы динамическое состояние системы не могло само расширять разрешенный пользователем набор VPN-путей.* | Для каждого управляемого класса трафика политика должна однозначно определять набор VPN-путей, через которые этот трафик разрешено передавать.

  **[VPNG-R2.R2.R1]** *Чтобы Profile явно определял, какие пользовательски описанные VPN resources разрешено использовать для его трафика.* | `Profile.device_order` должен быть непустым ordered списком уникальных Device IDs; только enabled Devices из этого списка и их допустимо bound paths могут участвовать в forwarding данного Profile.

 **[VPNG-R2.R3]** *Чтобы разрешение одного направления передачи не становилось неявным разрешением другого.* | Политика должна однозначно определять разрешенное направление передачи управляемого трафика.

  **[VPNG-R2.R3.R3]** *Чтобы направление Profile было читаемым пользовательским policy decision, а не выводилось из topology.* | Enabled Profile должен явно задавать одно из `outbound`, `inbound`, `bidirectional`: outbound разрешает инициирование новых flows со стороны ordinary/host network к Profile destinations, inbound — со стороны разрешенного VPN path к ordinary/host network, bidirectional — оба направления; return traffic уже допустимых flows может обслуживаться statefully независимо от стороны инициатора.

  **[VPNG-R2.R3.R1]** *Чтобы разрешение отправки трафика из обычной сети через VPN не подразумевало обратный доступ.* | Политика должна позволять независимо определить, разрешена ли передача соответствующего управляемого трафика со стороны обычной сети в сторону выбранных VPN-путей. [closed]

  **[VPNG-R2.R3.R2]** *Чтобы разрешение передачи трафика из VPN в обычную сеть было отдельным явным решением пользователя.* | Политика должна позволять независимо определить, разрешена ли передача соответствующего управляемого трафика со стороны VPN-пути в сторону обычной сети. [closed]

 **[VPNG-R2.R4]** *Чтобы наличие работающего VPN или автоматически обнаруженной пригодности пути не изменяло пользовательскую политику доступа.* | Трафик или VPN-путь, не разрешенные текущей политикой, не должны становиться разрешенными из-за доступности, автоматического failover, recovery или иного runtime-состояния. [closed]

 **[VPNG-R2.R5]** *Чтобы одинаковая конфигурация не приводила к различному поведению при неоднозначном совпадении нескольких правил.* | Если к одному трафику применимы несколько частей политики, VPN-GATE должен получать один детерминированный эффективный результат либо явно отклонять неоднозначную конфигурацию.

  **[VPNG-R2.R5.R1]** *Чтобы несколько Profiles с пересекающимися remote prefixes не делали классификацию случайной.* | Одинаковый destination prefix не должен принадлежать более чем одному enabled Profile; overlap разных prefix lengths может быть допустим только при детерминированной most-specific классификации, а для VPN-to-host traffic классификация должна учитывать только Profiles, разрешающие фактический ingress Device/path, чтобы более специфичный prefix другого Device не затенял допустимый Profile.

## Path preference and availability

**[VPNG-R3]** *Чтобы при наличии нескольких разрешенных VPN-путей трафик использовал их предсказуемо и сохранял практическую работоспособность при деградации предпочтительного пути.* | Если для одного трафика разрешено несколько VPN-путей, VPN-GATE должен использовать их в предсказуемом пользовательском порядке, автоматически понижать предпочтение действительно проблемных путей и после восстановления возвращаться к пользовательскому порядку.

 **[VPNG-R3.R1]** *Чтобы при нормальной работе выбор между несколькими разрешенными путями соответствовал намерению пользователя.* | Для нескольких разрешенных путей должен существовать детерминированный настроенный порядок предпочтения.

  **[VPNG-R3.R1.R1]** *Чтобы пользовательский порядок Devices и ожиданий внутри Device сохранялся при появлении нескольких runtime endpoints.* | Для Profile настроенный baseline preference должен следовать иерархии `Profile.device_order -> Device.expected_interfaces order -> stable runtime slot внутри selector quota`; появление нового endpoint не должно произвольно переставлять уже bound survivors.

 **[VPNG-R3.R2]** *Чтобы availability-механизм не подменял собой пользовательскую политику.* | Автоматическая адаптация по состоянию пути может изменять только эффективное предпочтение среди уже разрешенных путей и не должна изменять их policy membership. [closed]

 **[VPNG-R3.R3]** *Чтобы новый трафик не продолжал предпочитать путь, для которого получены достаточные признаки практической непригодности, когда разрешена пригодная альтернатива.* | После достаточного подтверждения проблемы на предпочтительном пути VPN-GATE должен понизить его эффективное предпочтение относительно разрешенных путей без подтвержденной проблемы. ## Initial acceptance/evidence expectations

This table adds no new requirement semantics.

| L1 | Minimum final evidence type |
| --- | --- |
| `VPNG-R1` | end-to-end VPN-path forwarding and externally provisioned channel onboarding scenario |
| `VPNG-R2` | policy acceptance/rejection scenarios |
| `VPNG-R3` | deterministic failover/failback scenarios with path-state changes |
| `VPNG-R4` | negative/failure scenarios proving no unintended forwarding |
| `VPNG-R5` | startup, drift, retry and shutdown lifecycle scenarios |
| `VPNG-R6` | status projection checked against authoritative runtime state |
| `VPNG-R7` | architecture/review traceability plus isolated-change evidence |

## Constraint policy for this NG3 pass

No NG2 implementation constraint is accepted into NG3 merely by inheritance.

`VPNG-R1.R3.C1` is accepted explicitly for the first product release: VPN-channel
provisioning/configuration remains an administrator responsibility, while VPN-GATE must
provide the instructions/contract required to consume those channels.

Other candidate constraints discovered while building the NG3 architecture must be added at
the requirement node whose promise they actually restrict and must pass normal constraint
lifting before they become accepted NG3 constraints.
