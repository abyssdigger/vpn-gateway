# VPN-GATE NG3 — Requirements

**Status:** NG3 design-cycle draft  
**Cycle:** `ng3-design-cycle-20261115-40m`  
**Normative model:** `design/requirements-model.md`  
**Architecture status:** no NG2 architecture is inherited automatically

This document is the normative requirement tree for NG3.

The seven L1 requirements below are accepted for this cycle. Lower-level nodes are the
first decomposition produced from those promises and remain subject to requirement review.

Every `R` node contains the mandatory pair:

```text
Purpose   — зачем это нужно
Statement — что система обязана обеспечить
```

No NG2 component, state machine, event, Linux mechanism or configuration object becomes an
NG3 requirement merely because it existed before.

## Requirement tree

```text
VPNG-R1  Managed VPN router
VPNG-R2  Explicit allowed-traffic policy
VPNG-R3  Predictable path choice and adaptation
VPNG-R4  Safe behavior under uncertainty and failure
VPNG-R5  Managed lifecycle and recovery
VPNG-R6  Observability of effective state
VPNG-R7  Sufficient, maintainable and evolvable implementation
```

# VPNG-R1 — Managed VPN router

**Purpose:**  
Чтобы пользователь мог использовать VPN-GATE как управляемый сетевой узел для передачи
выбранного IP-трафика через VPN, не собирая поведение продукта вручную из низкоуровневых
сетевых команд.

**Statement:**  
VPN-GATE должен предоставлять управляемую маршрутизацию выбранного IP-трафика между обычной
сетью и настроенными VPN-путями.

## VPNG-R1.R1 — Managed forwarding

**Purpose:**  
Чтобы трафик, принятый продуктом в обслуживание, действительно мог проходить через
предназначенный для него VPN-путь в требуемом направлении.

**Statement:**  
Для принятого в обслуживание IP-трафика VPN-GATE должен обеспечивать необходимое forwarding
поведение между обычной сетью и разрешенными VPN-путями.

## VPNG-R1.R2 — Declarative operation

**Purpose:**  
Чтобы эксплуатация продукта не зависела от ручного воспроизведения его внутренней сетевой
механики оператором.

**Statement:**  
Пользователь должен задавать требуемое поведение через продуктовую конфигурацию и
управляющие операции VPN-GATE; внутренние сетевые действия должны выполняться продуктом.

# VPNG-R2 — Explicit allowed-traffic policy

**Purpose:**  
Чтобы использование VPN было следствием явного решения пользователя, а не побочным эффектом
наличия работоспособного VPN-пути.

**Statement:**  
Пользователь должен иметь возможность явно определить, какой трафик VPN-GATE обслуживает,
через какие VPN-пути этот трафик разрешено передавать и в каком направлении.

## VPNG-R2.R1 — Explicit traffic membership

**Purpose:**  
Чтобы можно было однозначно отличить управляемый VPN-GATE трафик от остального трафика
системы.

**Statement:**  
Политика должна однозначно определять, какой трафик входит в область управления VPN-GATE.

## VPNG-R2.R2 — Explicit path eligibility

**Purpose:**  
Чтобы динамическое состояние системы не могло само расширять разрешенный пользователем
набор VPN-путей.

**Statement:**  
Для каждого управляемого класса трафика политика должна однозначно определять набор
VPN-путей, через которые этот трафик разрешено передавать.

## VPNG-R2.R3 — Explicit direction

**Purpose:**  
Чтобы разрешение одного направления передачи не становилось неявным разрешением другого.

**Statement:**  
Политика должна однозначно определять разрешенное направление передачи управляемого
трафика.

## VPNG-R2.R4 — No implicit VPN admission

**Purpose:**  
Чтобы наличие работающего VPN или автоматически обнаруженной пригодности пути не изменяло
пользовательскую политику доступа.

**Statement:**  
Трафик или VPN-путь, не разрешенные текущей политикой, не должны становиться разрешенными
из-за доступности, автоматического failover, recovery или иного runtime-состояния.

## VPNG-R2.R5 — Deterministic policy resolution

**Purpose:**  
Чтобы одинаковая конфигурация не приводила к различному поведению при неоднозначном
совпадении нескольких правил.

**Statement:**  
Если к одному трафику применимы несколько частей политики, VPN-GATE должен получать один
детерминированный эффективный результат либо явно отклонять неоднозначную конфигурацию.

# VPNG-R3 — Predictable path choice and adaptation

**Purpose:**  
Чтобы при наличии нескольких разрешенных VPN-путей трафик использовал их предсказуемо и
сохранял практическую работоспособность при деградации предпочтительного пути.

**Statement:**  
Если для одного трафика разрешено несколько VPN-путей, VPN-GATE должен использовать их в
предсказуемом пользовательском порядке, автоматически понижать предпочтение действительно
проблемных путей и после восстановления возвращаться к пользовательскому порядку.

## VPNG-R3.R1 — Configured preference

**Purpose:**  
Чтобы при нормальной работе выбор между несколькими разрешенными путями соответствовал
намерению пользователя.

**Statement:**  
Для нескольких разрешенных путей должен существовать детерминированный настроенный порядок
предпочтения.

## VPNG-R3.R2 — Adaptation changes priority, not permission

**Purpose:**  
Чтобы availability-механизм не подменял собой пользовательскую политику.

**Statement:**  
Автоматическая адаптация по состоянию пути может изменять только эффективное предпочтение
среди уже разрешенных путей и не должна изменять их policy membership.

## VPNG-R3.R3 — Degradation demotion

**Purpose:**  
Чтобы новый трафик не продолжал предпочитать путь, для которого получены достаточные
признаки практической непригодности, когда разрешена пригодная альтернатива.

**Statement:**  
После достаточного подтверждения проблемы на предпочтительном пути VPN-GATE должен понизить
его эффективное предпочтение относительно разрешенных путей без подтвержденной проблемы.

## VPNG-R3.R4 — Recovery failback

**Purpose:**  
Чтобы временная деградация не превращалась в постоянное изменение пользовательской
политики.

**Statement:**  
После достаточного подтверждения восстановления пути VPN-GATE должен вернуть его к
позиции, заданной настроенным порядком предпочтения.

## VPNG-R3.R5 — Stable adaptation

**Purpose:**  
Чтобы единичное, кратковременное или случайное наблюдение не вызывало ненужной перестройки
маршрутизации.

**Statement:**  
Переход между нормальным и пониженным предпочтением должен использовать ограниченное
подтверждение деградации и восстановления, достаточное для подавления случайных единичных
наблюдений без создания неограниченной истории.

## VPNG-R3.R6 — Availability observation

**Purpose:**  
Чтобы автоматическая адаптация могла обнаруживать проблемы пути независимо от того,
случился ли уже пользовательский payload failure, когда такая проверка включена.

**Statement:**  
VPN-GATE должен уметь получать актуальные сведения о пригодности конкретного разрешенного
VPN-пути с помощью настроенного механизма проверки, не изменяя этим фактом policy membership.

### VPNG-R3.R6.R1 — Observation identity

**Purpose:**  
Чтобы результат проверки одного пути или экземпляра пути не изменял приоритет другого.

**Statement:**  
Каждое availability-наблюдение должно быть однозначно связано с тем логическим путем,
к состоянию которого оно относится.

### VPNG-R3.R6.R2 — Current checking cadence

**Purpose:**  
Чтобы сведения о пригодности обновлялись с частотой, достаточной для принятой политики
адаптации.

**Statement:**  
При включенной активной проверке VPN-GATE должен выполнять ее с явно определенной cadence,
необходимой для соответствующего availability-канала.

### VPNG-R3.R6.R3 — Stale observation rejection

**Purpose:**  
Чтобы поздний результат старой проверки не изменял решение после замены проверяемого
экземпляра пути или его существенной конфигурации.

**Statement:**  
Результат проверки, относящийся к уже неактуальному физическому экземпляру или поколению
проверяемого пути, не должен влиять на текущее effective preference.

## VPNG-R3.R7 — Availability-neutral baseline

**Purpose:**  
Чтобы само включение availability-функции не ухудшало или произвольно изменяло нормальное
поведение маршрутизации.

**Statement:**  
Пока для разрешенных путей нет достаточного подтверждения проблемы, effective order должен
совпадать с настроенным пользовательским порядком.

# VPNG-R4 — Safe behavior under uncertainty and failure

**Purpose:**  
Чтобы ошибка, неполная конфигурация или непроверенное состояние не приводили к передаче
управляемого трафика способом, который пользователь не разрешал.

**Statement:**  
VPN-GATE не должен передавать управляемый трафик способом, не разрешенным текущей политикой
или безопасность которого продукт не может подтвердить; при существенной неопределенности
предпочтителен отказ от передачи.

## VPNG-R4.R1 — Fail closed on missing policy certainty

**Purpose:**  
Чтобы отсутствие однозначного policy result не превращалось в неявное разрешение.

**Statement:**  
Если VPN-GATE не может однозначно определить разрешенное поведение для управляемого трафика,
такой трафик не должен получать неявный VPN forwarding.

## VPNG-R4.R2 — Fail closed on unverified effective state

**Purpose:**  
Чтобы продукт не считал желаемое сетевое состояние фактически действующим без подтверждения.

**Statement:**  
Если фактическое сетевое состояние, критичное для безопасной передачи, неизвестно или не
может быть подтверждено, VPN-GATE должен сохранять или устанавливать безопасное
ограничивающее поведение до получения достаточного подтверждения.

## VPNG-R4.R3 — Safe transition

**Purpose:**  
Чтобы корректная конечная конфигурация не достигалась через промежуточное состояние с
неразрешенной передачей трафика.

**Statement:**  
Изменение effective network policy должно выполняться так, чтобы промежуточные состояния не
создавали передачу, запрещенную до или после изменения.

## VPNG-R4.R4 — Protective startup boundary

**Purpose:**  
Чтобы запуск процесса не открывал трафик до построения и проверки требуемой политики.

**Statement:**  
До подтверждения безопасной исходной сетевой границы VPN-GATE не должен считать payload
forwarding готовым к использованию.

## VPNG-R4.R5 — Safe recovery after partial mutation

**Purpose:**  
Чтобы ошибка посреди изменения сетевого состояния не оставляла продукт в неизвестном
разрешающем режиме.

**Statement:**  
После частично выполненного или неуспешного изменения network policy VPN-GATE должен
повторно установить авторитетное фактическое состояние и либо безопасно довести его до
требуемого результата, либо оставить соответствующий трафик закрытым.

# VPNG-R5 — Managed lifecycle and recovery

**Purpose:**  
Чтобы VPN-GATE можно было предсказуемо запускать, эксплуатировать, перезапускать и
останавливать без ручной уборки или восстановления его внутренних сетевых объектов.

**Statement:**  
VPN-GATE должен управлять жизненным циклом принадлежащего ему runtime-состояния,
восстанавливать требуемое состояние после обычных восстановимых изменений среды и явно
сообщать, когда безопасное восстановление невозможно.

## VPNG-R5.R1 — Predictable startup

**Purpose:**  
Чтобы одинаковая допустимая конфигурация приводила к воспроизводимому рабочему состоянию.

**Statement:**  
Startup должен из безопасной исходной границы построить и подтвердить необходимое
runtime-состояние до объявления соответствующих функций готовыми.

## VPNG-R5.R2 — Drift recovery

**Purpose:**  
Чтобы обычное изменение или потеря принадлежащего продукту runtime-состояния не требовали
ручного пересоздания всей системы.

**Statement:**  
Во время работы VPN-GATE должен уметь обнаруживать существенное расхождение между
требуемым и фактическим принадлежащим ему состоянием и восстанавливать его, если это
безопасно и возможно.

## VPNG-R5.R3 — Retry after recoverable failure

**Purpose:**  
Чтобы временный технический отказ не становился постоянной потерей функции после исчезновения
его причины.

**Statement:**  
Операция, не выполненная из-за восстановимой ошибки, должна оставаться повторяемой из
актуального подтвержденного состояния без необходимости перезапуска всего продукта, если
этого не требует сама внешняя среда.

## VPNG-R5.R4 — Owned-state cleanup

**Purpose:**  
Чтобы остановленный или удаленный VPN-GATE не продолжал незаметно влиять на сетевое
поведение системы.

**Statement:**  
После успешного shutdown/cleanup не должны оставаться активные сетевые или процессные
ресурсы, принадлежащие остановленному экземпляру VPN-GATE и продолжающие влиять на трафик.

## VPNG-R5.R5 — Independent cleanup attempts

**Purpose:**  
Чтобы отказ одной независимой части cleanup не мешал попытке безопасно убрать другие
принадлежащие продукту части состояния.

**Statement:**  
Если несколько независимо управляемых областей требуют cleanup или recovery, ошибка одной
области не должна сама по себе отменять попытку обработать остальные; все существенные
ошибки должны оставаться наблюдаемыми.

# VPNG-R6 — Observability of effective state

**Purpose:**  
Чтобы оператор мог понять фактическое поведение VPN-GATE и причину невозможности выполнить
требуемую политику, не восстанавливая внутреннее состояние по логам и kernel-командам.

**Statement:**  
VPN-GATE должен предоставлять наблюдаемую текущую проекцию существенного настроенного,
фактического и эффективного состояния, а также проблем, мешающих выполнить требуемую
политику.

## VPNG-R6.R1 — Configured intent visibility

**Purpose:**  
Чтобы оператор мог проверить, какое поведение продукт считает требуемым.

**Statement:**  
Должно быть возможно определить существенную текущую конфигурацию и policy intent,
используемые VPN-GATE.

## VPNG-R6.R2 — Effective path visibility

**Purpose:**  
Чтобы оператор мог понять, какие разрешенные VPN-пути фактически участвуют в текущем
выборе и каков их effective order.

**Statement:**  
Должно быть возможно определить текущий набор разрешенных для использования путей,
существенное availability-состояние и effective preference, применяемые к управляемому
трафику.

## VPNG-R6.R3 — Failure visibility

**Purpose:**  
Чтобы невозможность выполнить требование не выглядела как молчаливое отсутствие функции.

**Statement:**  
Существенные проблемы, из-за которых требуемая policy, lifecycle operation или safety
postcondition не могут быть выполнены, должны быть доступны оператору.

## VPNG-R6.R4 — Effective-state truthfulness

**Purpose:**  
Чтобы observability не сообщала желаемое состояние как фактическое.

**Statement:**  
Текущая status-проекция должна различать требуемое, подтвержденное фактическое и
неизвестное/неподтвержденное состояние там, где это различие влияет на пользовательское
понимание поведения или safety.

# VPNG-R7 — Sufficient, maintainable and evolvable implementation

**Purpose:**  
Чтобы VPN-GATE можно было безопасно развивать и сопровождать живыми разработчиками и AI,
не превращая продукт ни в универсальную систему из ненужных механизмов, ни в хрупкий
монолит, изменение которого требует понимания всего кода сразу.

**Statement:**  
Реализация VPN-GATE должна быть минимально достаточной для принятых требований,
сопровождаемой и понятной, допускать локальное изменение и параллельную разработку через
явные внутренние контракты и не содержать сложности, не оправданной требованиями или
реальными целевыми сценариями.

## VPNG-R7.R1 — No unjustified machinery

**Purpose:**  
Чтобы развитие продукта не создавало состояния, компоненты и универсальные механизмы,
которые увеличивают стоимость сопровождения без продуктовой ценности.

**Statement:**  
Каждый существенный механизм, состояние, очередь, lifecycle, retry policy, interaction и
компонент должны быть необходимы для конкретного принятого требования или ограничения;
неоправданная общность должна удаляться или не создаваться.

### VPNG-R7.R1.R1 — Prefer bounded current state

**Purpose:**  
Чтобы локальная задача не превращалась в систему хранения и воспроизведения истории без
необходимости.

**Statement:**  
Если требование может быть полностью выполнено текущим или ограниченным агрегированным
состоянием, реализация не должна вводить неограниченную историю, журнал или replay-механику.

## VPNG-R7.R2 — Human and AI comprehensibility

**Purpose:**  
Чтобы сопровождение и review не зависели от знания неявной глобальной механики одним
автором.

**Statement:**  
Существенные обязанности, состояния, контракты и причины проектных решений должны быть
локализованы и документированы настолько, чтобы разработчик или AI мог определить
назначение блока, его границы и последствия изменения без реконструкции всей системы.

## VPNG-R7.R3 — Explicit internal contracts and isolation

**Purpose:**  
Чтобы изменения внутри одной области не распространялись на несвязанные части продукта
через неявные зависимости.

**Statement:**  
Внутренние области реализации должны взаимодействовать через явные контракты, скрывающие
детали, которые не требуются соседней области.

### VPNG-R7.R3.R1 — Contract-visible dependency

**Purpose:**  
Чтобы зависимость между частями системы была видима для разработки, review и тестирования.

**Statement:**  
Материальная межкомпонентная зависимость должна быть представлена явным контрактом,
определяющим необходимые входы, выходы и семантику взаимодействия.

### VPNG-R7.R3.R2 — Domain-detail containment

**Purpose:**  
Чтобы замена или изменение внутреннего механизма нижней области не требовали переделки
верхней policy без продуктовой причины.

**Statement:**  
Внутренние технические детали одной предметной области не должны пересекать ее контрактную
границу, если они не нужны другой области для выполнения собственного принятого требования.

### VPNG-R7.R3.R3 — Local change containment

**Purpose:**  
Чтобы исправление или развитие одной ответственности можно было выполнять и проверять
изолированно.

**Statement:**  
Изменение реализации внутри стабильного внутреннего контракта не должно требовать изменения
несвязанных потребителей этого контракта.

## VPNG-R7.R4 — Parallel development

**Purpose:**  
Чтобы независимые части продукта можно было проектировать, реализовывать и проверять
параллельно без постоянной сериализации работы через общий внутренний код.

**Statement:**  
Архитектура должна позволять выделять независимые review/development units с явными
контрактными границами и достаточным локальным evidence, когда требования не создают
неизбежной общей транзакционной ответственности.

## VPNG-R7.R5 — Project component model

**Purpose:**  
Чтобы декомпозиция NG3 использовала единый проверяемый словарь обязанностей и
взаимодействий вместо ad-hoc архитектурных ролей.

**Statement:**  
Архитектура и реализация NG3 должны соответствовать
`design/component-model.md`; существенное отклонение допускается только после явного
изменения требования, ограничения или самой компонентной модели через review.

## VPNG-R7.R6 — Requirement-traceable architecture

**Purpose:**  
Чтобы архитектура оставалась отчетом о реализации принятых требований, а не становилась
самостоятельным источником новых функций и сложности.

**Statement:**  
Каждое существенное архитектурное решение NG3 должно явно ссылаться на наиболее конкретные
requirement/constraint IDs, которые его требуют или ограничивают; решение без честной
трассировки является finding.

### VPNG-R7.R6.R1 — Bidirectional traceability

**Purpose:**  
Чтобы можно было как найти реализацию требования, так и установить причину существования
архитектурного элемента.

**Statement:**  
Документация должна позволять пройти по связям
`requirement -> architecture -> implementation/evidence` и обратно
`architecture -> requirement/constraint`.

### VPNG-R7.R6.R2 — Revalidation after requirement change

**Purpose:**  
Чтобы изменение смысла требования не оставляло архитектуру, формально ссылающуюся на уже
другой contract.

**Statement:**  
Изменение requirement/constraint требует повторной проверки архитектурных решений,
ссылающихся на измененный узел или его затронутых потомков, до продолжения реализации.

# Initial acceptance/evidence expectations

Эта таблица не добавляет новой семантики требованиям; она фиксирует ожидаемый уровень
доказательства для последующей декомпозиции.

| L1 | Минимальный тип итогового evidence |
| --- | --- |
| `VPNG-R1` | end-to-end forwarding scenario |
| `VPNG-R2` | policy acceptance/rejection scenarios |
| `VPNG-R3` | deterministic failover/failback scenarios with path-state changes |
| `VPNG-R4` | negative/failure scenarios proving no unintended forwarding |
| `VPNG-R5` | startup, drift, retry and shutdown lifecycle scenarios |
| `VPNG-R6` | status projection checked against authoritative runtime state |
| `VPNG-R7` | architecture/review traceability plus isolated-change evidence |

# Constraints in this first NG3 pass

No NG2 implementation constraint is accepted into NG3 merely by inheritance.

Candidate constraints discovered while building the NG3 architecture must be added at the
requirement node whose promise they actually restrict and must pass normal constraint
lifting before they become accepted NG3 constraints.
