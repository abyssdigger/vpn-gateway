## Differentiating evidence

The topology deliberately made the remote sender `10.0.0.2` match both:

- channel A / `10.0.0.0/16`, through which the inbound flow actually entered;
- channel B / `10.0.0.0/24`, which ordinary longest-prefix reply routing prefers.

The ordinary-host namespace had no main-table route to the remote network. Therefore the
reply had to cross the already-proven host-side stateful return boundary and re-enter the
managed stack before the decisive second routing choice.

The job emitted:

```text
EXP061_MORE_SPECIFIC_BASELINE=PASS
EXP061_HOST_NO_REMOTE_ROUTE=PASS
EXP061_WITHOUT_STACK_AFFINITY_FAILS=PASS
EXP061_STACK_AFFINITY_RETURN=PASS
EXP061_AFFINITY_REMOVAL_RESTORES_FAILURE=PASS
EXP061_RESULT=PASS
```

Interpretation:

1. without flow affinity, reply lookup in the managed stack selects channel B because `/24`
   is more specific than channel A's `/16`; the end-to-end flow fails;
2. marking the inbound connection on channel A, restoring that mark when the reply re-enters
   from the host boundary, and applying a higher-precedence fwmark RPDB rule to an A-specific
   routing table makes the same flow succeed;
3. removing only that stack-side affinity owner restores the failure.

## Proven boundary

EXP-061 proves that the Release-1 Linux implementation can preserve the original inbound VPN
routing domain across:

```text
VPN ingress
    -> managed stack
    -> ordinary host/LAN
    -> ordinary host
    -> managed stack
    -> original VPN routing domain
```

even when ordinary NEW-flow destination classification at the final stack lookup would choose
a different overlapping VPN network.

This is direct differentiating evidence for `VPNG0002-R2.R6`,
`VPNG0007-R7.R3.R4` and `VPNG0007-R7.R3.R4.R1`.

## Not proven

This result does **not** prove Release-2 multi-path inbound/bidirectional semantics. The tested
mark selects the original Profile routing domain; under the current Release-1 constraint that
domain has at most one eligible inbound logical path. Pinning one established flow to one of
several simultaneously eligible paths remains EXP-014 or equivalent future evidence.

The experiment also does not choose permanent Linux mark/rule numeric allocation or owner
inventory representation; those remain implementation work constrained by the accepted
platform resource model.
