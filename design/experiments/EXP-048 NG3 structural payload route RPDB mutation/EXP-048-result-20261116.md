## Proven behavior

1. A terminal blackhole default may be added to the payload table while no RPDB dispatch
   reaches that table; real host traffic continues through ambient/main routing.
2. A desired unicast path route may then be added to the same table; it also remains
   unreachable until dispatch exists.
3. Adding the exact host-boundary/destination RPDB rule switches real host traffic into the
   prepared payload table.
4. With dispatch active, deleting the ordinary path route leaves the terminal blackhole guard
   authoritative: traffic fails rather than falling through to the ambient main route.
5. Re-adding the path route restores the intended VPN path.
6. Deleting the exact dispatch rule restores ambient/main routing.
7. Exact managed route/rule cleanup preserves unrelated route/RPDB state.

```text
route add/del blackhole default
    table <payload-table>

route add/del unicast <destination>
    table <payload-table>
    proto <path-proto>
    metric <metric>
    via <gateway>
    dev <current-ifname>

rule add/del
    priority <priority>
    iif <current-host-boundary-ifname>
    to <destination>
    lookup <payload-table>
```

These are lower primitives only. Production RPDB activation remains coupled to a closed
ForwardingGate, prepared guarded routes, exact nft policy and fresh whole-scope verification.

The authoritative structural parser was corrected to normalize **only** this proven
bare-IPv4/no-`dstlen` form as `/32`. Prefix text without `dstlen` remains rejected.
