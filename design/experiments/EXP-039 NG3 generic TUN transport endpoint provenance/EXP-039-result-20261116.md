## Observed result

The privileged Linux runner created a real userspace-held TUN interface, configured an
inner point-to-point IPv4 peer, and separately connected a userspace UDP transport socket.

Observed facts:

```text
EXP039_INNER_LOCAL=10.39.0.1
EXP039_INNER_PEER=10.39.0.2
EXP039_TRANSPORT_A=198.51.100.39
EXP039_TRANSPORT_B=203.0.113.39
EXP039_GENERIC_INTERFACE_STATE_UNCHANGED=1
EXP-039 generic TUN transport endpoint provenance: PASS
```

The interface reported `POINTOPOINT`, and its inner/network-layer peer was visible in
normal address discovery.

Changing only the userspace transport socket peer from `198.51.100.39` to
`203.0.113.39` changed `getpeername()` as expected but produced byte-equivalent parsed
`ip -j -d link show` and `ip -j addr show` observations for the TUN interface.

Neither transport endpoint address appeared in the generic link/address inventory.

## Hypotheses

- H1 — generic TUN is observable as point-to-point: **PASS**.
- H2 — inner/network-layer peer is observable: **PASS**.
- H3 — userspace transport peer is absent from generic TUN link/address state: **PASS**.
- H4 — transport-peer replacement leaves generic TUN discovery unchanged: **PASS**.

## Interpretation

A Linux point-to-point TUN interface exposes its data-plane/interface and inner-address
properties. It does not generically expose which remote transport socket endpoint a
userspace VPN process uses to carry that TUN's traffic.

Therefore:

```text
point-to-point TUN interface discovery
    !=
transport endpoint provenance
```

For userspace VPNs such as the OpenConnect-shaped integration, a transport endpoint must be
obtained from an integration-specific authoritative fact: process/session metadata,
bootstrap/onboarding metadata, a protocol-specific control surface, or another separately
proved source.

This result does not say that every VPN integration lacks endpoint introspection. A
kernel/protocol-specific integration may expose transport peers through its own control
surface. Such data is still integration-specific provenance and must be correlated with the
exact current path binding.

## Architectural decision

Generic `VPNPathAdapter` interface discovery must not infer a transport endpoint from:

- `IFF_POINTOPOINT`;
- inner peer/address state;
- interface prefix/name;
- logical selector slot.

Transport provenance remains an optional enrichment of the exact current path binding and
is not a Release-1 prerequisite.

## Verdict

**PASS.** The negative generic-discovery hypothesis is confirmed. The endpoint-provenance
requirement is implementable only through accepted integration-specific provenance, not as
an organic property of generic point-to-point TUN discovery.
