## Question

Can an nft `meta mark` set after accepted managed Profile policy carry the selected Profile
through the common veth into the ordinary host namespace?

## Observed result

```text
managed Profile-A association rule counter = 1
managed Profile-B association rule counter = 1
host Profile-A mark counter                = 0
host Profile-B mark counter                = 0
```

The same real UDP flows reached the downstream LAN, so the failure was not ordinary forwarding
or routing. The metadata itself did not survive the managed->host namespace crossing.

The preceding unaccepted-source negative also passed, proving the later association chain was
not reached by traffic dropped at the priority-0 managed payload policy.

## Interpretation

Linux deliberately scrubs namespace-sensitive skb metadata at a cross-netns injection
boundary. In current Linux `skb_scrub_packet(..., xnet=true)`, `skb->mark` is explicitly
cleared.

That behavior exactly matches the experiment:

```text
managed nft:
    accepted Profile A -> meta mark set A   counter=1
    accepted Profile B -> meta mark set B   counter=1
                  |
                  | veth / network namespace boundary
                  v
host nft:
    meta mark A counter=0
    meta mark B counter=0
```

## Disposition

**Rejected carrier:** skb packet mark / nft `meta mark`.

Do not:

- allocate a production packet-mark range for this function;
- add host source-CIDR reclassification as a fallback;
- copy the mark into conntrack and assume host conntrack shares managed-netns state;
- weaken `VPNG0004-R4.R6.R1.R6.R1`.

The next evidence unit should test a metadata/resource carrier that actually survives the
explicit network-namespace boundary while remaining distinguishable from routing/probe/host
policy.
