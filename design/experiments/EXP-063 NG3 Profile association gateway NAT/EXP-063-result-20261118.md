# EXP-063 result — Profile-association packet-tag handoff

**Date:** 2026-11-18  
**Technical result:** **FAIL**

## Claim tested

The candidate mechanism attempted to carry an already-established Profile association from the
managed network namespace to the ordinary-host namespace as a transient packet mark, consume it
at host ingress, store host connection state, and clear the packet mark before ordinary host
routing.

## Distinguishing evidence

The final run established all facts needed to distinguish carrier loss from packet loss:

- the managed-stack export rule matched the attempted flow repeatedly;
- the ordinary-host boundary interface received packets from that flow;
- the host-side exact transient-tag consumer matched zero packets;
- gateway-NAT and return-state rules therefore also matched zero packets.

Final evidence run:

- workflow: `44296352509`;
- job: `134774346419`;
- source commit: `4c201e473efd5471af985f467348ef4916d8755f`.

Observed distinguishing counters:

```text
stack association-tag export: > 0
host boundary receive:         > 0
host exact-tag consume:        0
```

Therefore the packet crosses the managed/host boundary while the transient packet mark does
not remain available as the association carrier on the receiving side.

## Consequence

The tested transient-`skb`-mark handoff is not a valid Linux realization for the explicit
cross-netns VPN-GATE host boundary.

This result does **not** reject:

- Profile ordinary-side gateway NAT;
- Profile association continuity as a requirement;
- host-side conntrack/NAT after some other unambiguous boundary carrier.

A replacement mechanism must carry only the host-side behavior information actually required
after the boundary and must not rely on packet metadata scrubbed by the namespace transition.

Registry disposition remains `pending_decision` until the result is reviewed separately.
