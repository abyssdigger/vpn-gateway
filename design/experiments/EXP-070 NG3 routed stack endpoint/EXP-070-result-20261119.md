# EXP-070 result — routed managed-stack endpoint candidates

**Date:** 2026-11-19  
**Primary privileged run:** NG3 Python run `44572719678`, job `135732043861`  
**Kernel:** `7.0.0-1019-azure`  
**iproute2:** `6.19.0`

## Technical result

The experiment produced distinguishing evidence for three candidate shapes.

### IPvlan L3S

- external LAN -> stack IPvlan address: **PASS**;
- stack-side SNAT flow through the tested IPvlan L3S shape: **FAIL**;
- host-side sibling IPvlan as a route target: **FAIL**;
- host-side sibling IPvlan even with explicit `via <stack-ipvlan-IP>`: **FAIL**.

The failed SNAT case reached the stack NAT rule once, but the tested stack route shape did not produce a usable forward path. This negative result is local to the tested topology and is not a general rejection of IPvlan.

### netkit L3

- `route <remote> dev <host-netkit>` with no gateway IP: **PASS**;
- cross-netns `meta mark` with explicit `scrub none`: **PASS**;
- stack-side SNAT + reverse NAT through netkit: **PASS**;
- neighboring no-SNAT flow: **PASS**.

The NAT observer saw the stack-owned source `198.18.71.2`; the no-SNAT observer saw the original remote source `10.70.0.3`.

### routed veth

The decisive routed-veth matrix was:

| Shape | Result |
| --- | --- |
| unnumbered `route <remote> dev vpng0`, no Proxy ARP | **FAIL** |
| /32 peer addresses + `route <remote> dev vpng0`, no Proxy ARP | **FAIL** |
| /32 peer addresses + `via <peer-IP> dev vpng0` | **PASS** |
| unnumbered device-only routes + Proxy ARP on both ends | **PASS** |
| /32 peer addresses + device-only routes + Proxy ARP on both ends | **PASS** |

For the two device-only failures, the host neighbour state for the remote destination became
`INCOMPLETE`/`FAILED`, distinguishing the missing L2 resolution from an IP-routing failure.

For the Proxy-ARP cases, the host route remained device-only:

```text
remote-prefix dev vpng0
```

and the reverse stack route was likewise device-only. Neighbour resolution learned the opposite
veth MAC for the routed destination, while the end-to-end TCP observer on REMOTE saw the original
LAN source `192.0.2.2`.

Therefore Proxy ARP acted only as the Ethernet neighbour-resolution mechanism. The payload itself
was forwarded as ordinary IP traffic through HOST -> STACK -> REMOTE; no NAT or userspace proxy was
used in this phase.

## Debian 12 / Linux 6.1 portability confirmation

A separate QEMU guest booted the official Debian 12 (bookworm) cloud image and ran the
routed-veth subset on the guest's own kernel rather than sharing the hosted runner kernel.

Environment:

- Debian GNU/Linux 12 (bookworm);
- kernel `6.1.0-56-cloud-amd64`;
- iproute2 `6.1.0`.

Distinguishing result:

- device-only route without Proxy ARP: **EXPECTED FAIL**, host neighbour
  `10.70.0.2 INCOMPLETE`;
- unnumbered device-only routed veth with Proxy ARP: **PASS**;
- host route remained `10.70.0.2 dev vpng0 scope link`;
- stack reverse route remained `192.0.2.2 dev stack0 scope link`;
- learned neighbour entries resolved the routed destinations to the opposite veth MAC.

Privileged portability run: NG3 Python run `44574019867`,
job `linux-debian12-routed-veth` (`135736626574`).

This closes the specific Debian-12/kernel-6.1 portability uncertainty for the tested IPv4
routed-veth + Proxy-ARP mechanism.

## Narrow conclusion

A Debian-12-compatible design candidate exists in the ordinary veth feature set:

```text
HOST
    route <managed-prefix> dev vpng0
        |
      vpng0
        ||
      veth
        ||
    stack0
        |
STACK routing / Profile policy / VPN paths
```

To keep host routes free of a stack gateway IP, an Ethernet veth requires Proxy ARP/NDP or an
equivalent neighbour-resolution mechanism. Merely assigning /32 peer addresses does not make
`route ... dev vpng0` point-to-point.

This experiment does not yet select routed veth over netkit or IPvlan and does not prove the exact
same harness on Linux 6.1. The routed-veth/Proxy-ARP primitives themselves are longstanding Linux
mechanisms; an actual Debian 12 runtime confirmation remains a separate portability check if
required.
