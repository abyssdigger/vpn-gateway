# EXP-009 — RC3 failover semantics при нескольких peers

**Запуск:** 2026-11-10  
**Статус:** IN PROGRESS — EXP-009.1 COMPLETE/PASS; EXP-009.2 PENDING  
**Тип:** ручной live experiment без `vpn-gatewayd`

## EXP-009.1 — OpenConnect peer failure

**Статус:** COMPLETE — PASS

### Условия

Два независимых OpenConnect client одновременно подключены к одному ocserv server:

```text
pri -> 172.20.130.6
sec -> 172.20.130.5
```

Реальная защищаемая цель:

```text
172.21.201.19
```

### H1 — concurrent multi-interface discovery

Одновременное server state:

```text
=== ocserv users ===
      id     user    vhost             ip         vpn-ip device   since    dtls-cipher    status
   31612      sec  default 192.168.201.199   172.20.130.5 vpns01     6s  (AES-256-GCM) connected
   31214      pri  default 192.168.201.108   172.20.130.6 vpns00    45s  (AES-256-GCM) connected

=== vpns interfaces ===
vpns00           UNKNOWN        172.20.130.1 peer 172.20.130.6/32
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
```

**PASS:** concurrent peers используют разные runtime interfaces. Association evidence
видно непосредственно в kernel inventory: exact interface + local IPv4 + point-to-point
peer IPv4.

### H2 — failover after preferred interface disappearance

При двух sessions:

```text
172.21.201.19 via 172.20.130.6 dev vpns00 metric 10 onlink
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

Kernel выбирал primary route. LAN traceroute шел через `172.20.130.6`.

После остановки primary client `vpns00` исчез. Linux автоматически удалил route metric
10, оставив:

```text
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

LAN traffic продолжил работать через `172.20.130.5`.

**PASS:** удаление concrete interface удаляет зависимый preferred route, после чего backup
route становится выбранным.

### H3 — failback requires route rematerialization

После повторного запуска primary:

```text
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
vpns00           UNKNOWN        172.20.130.1 peer 172.20.130.6/32
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

Preferred route сам не восстановился.

После ручной materialization:

```text
172.21.201.19 via 172.20.130.6 dev vpns00 metric 10 onlink
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

kernel снова выбрал primary, а LAN traceroute вернулся через `172.20.130.6`.

**PASS:** interface reappearance требует reconciliation для восстановления desired
preferred route.

### H4 — preferred route remains, preferred path is dead

Цель H4 — отделить route preference от path-health detection.

Исходно OpenConnect sessions и оба server-side routes оставались на месте. На client
`pri` был выключен только forwarding:

```text
net.ipv4.ip_forward = 0
```

OpenConnect session не останавливалась. Server routing намеренно не изменялся; secondary
оставался доступным.

Результат на LAN Windows host:

```text
tracert 172.21.201.19

  1    <1 ms    <1 ms    <1 ms  192.168.201.107
  2     *        *        *     timeout
  3     *        *        *     timeout
```

Traffic на secondary route metric 20 не переключился.

**PASS как отрицательный контроль.**

Наблюдение:

```text
preferred route существует
preferred path за route не пересылает traffic
backup route существует
        ->
kernel продолжает выбирать preferred route
        ->
автоматического metric failover нет
```

Следовательно, route metric является механизмом выбора между routes, а не механизмом
end-to-end health detection.

> Ограничение evidence: после fault injection отдельный повторный snapshot server route
> table не снимался; условие сохраненного preferred route следует из последовательности
> эксперимента — OpenConnect session/interface не останавливались и server routing между
> контрольными действиями не изменялся.

## Итог EXP-009.1

**EXP-009.1 COMPLETE — PASS.**

Подтверждено:

1. concurrent OpenConnect peers создают отдельные point-to-point runtime interfaces;
2. peer association наблюдаема по `(local_address, peer)`;
3. interface disappearance удаляет dependent route;
4. route deletion дает kernel возможность выбрать backup route;
5. interface return сам route не восстанавливает;
6. failback требует rematerialization;
7. сохраненный preferred route продолжает выигрывать по metric даже при фактически
   неработающем path за ним.

Последний пункт важен для дальнейшей архитектуры: наличие secondary route не должно
интерпретироваться как автоматический health-aware failover.

## EXP-009.2 — WireGuard peer failure

**Статус:** PENDING

Проверяемый сценарий:

```text
stable exact interface wg0
preferred peer path + preferred route
secondary peer path + secondary route
preferred WG peer становится недоступен
wg0 остается существовать
```

Нужно наблюсти:

- меняется ли route table;
- появляется ли kernel-level признак непригодности preferred route;
- куда фактически идет traffic;
- происходит ли автоматический переход на secondary;
- что происходит при восстановлении preferred peer.

До завершения EXP-009.2 результат EXP-009.1 не распространяется на WireGuard peer failure.
