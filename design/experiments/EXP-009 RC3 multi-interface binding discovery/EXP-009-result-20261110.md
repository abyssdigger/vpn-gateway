# EXP-009 — RC3 multi-interface binding discovery and route failover

**Запуск:** 2026-11-10  
**Статус:** COMPLETE — PASS  
**Тип:** ручной live experiment без `vpn-gatewayd`

## Условия

Два независимых OpenConnect client одновременно подключены к одному ocserv server:

```text
pri -> 172.20.130.6
sec -> 172.20.130.5
```

## H1 — multi-interface discovery

Одновременное server state:

```text
=== ocserv users ===
      id     user    vhost             ip         vpn-ip device   since    dtls-cipher    status
   31612      sec  default 192.168.201.199   172.20.130.5 vpns01     6s  (AES-256-GCM) connected
   31214      pri  default 192.168.201.108   172.20.130.6 vpns00    45s  (AES-256-GCM) connected

=== vpns interfaces ===
vpns00           UNKNOWN        172.20.130.1 peer 172.20.130.6/32
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
```

**PASS:** healthy concurrent peers используют разные runtime interfaces. Association
evidence присутствует непосредственно в kernel inventory:
exact interface + local IPv4 + point-to-point peer IPv4.

## H2 — route failover

Оба clients независимо достигали `172.21.201.19`.

С двумя interfaces на server:

```text
172.21.201.19 via 172.20.130.6 dev vpns00 metric 10 onlink
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

Kernel выбирал primary route. LAN traceroute:

```text
192.168.201.107
172.20.130.6
192.168.201.1
172.21.201.19
```

После остановки primary:

```text
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

LAN traceroute без ручного изменения routing продолжил работать через
`172.20.130.5`.

## H3 — возврат primary и failback materialization

После повторного запуска primary:

```text
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
vpns00           UNKNOWN        172.20.130.1 peer 172.20.130.6/32
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

Primary route сам не восстановился.

После ручной materialization:

```text
172.21.201.19 via 172.20.130.6 dev vpns00 metric 10 onlink
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

kernel снова выбрал primary, а LAN traceroute вернулся через `172.20.130.6`.

**PASS:** interface disappearance автоматически удаляет зависимый route и открывает backup
path; interface reappearance требует reconciliation для восстановления desired primary
route.

## Итог

**EXP-009 COMPLETE — PASS.**

Эксперимент фиксирует наблюдаемый kernel/transport lifecycle. Общая модель селекторов и
binding cardinality является архитектурным выводом из результата, а не частью условий
эксперимента.
