# EXP-009 — RC3 interface-centric failover semantics

**Запуск:** 2026-11-10  
**Статус:** COMPLETE — PASS  
**Тип:** ручной live experiment без `vpn-gatewayd`

## Цель

Эксперимент начинался как проверка multi-interface association и failover по configured
transport peers. По ходу live-проверок выяснилось, что для VPN-GATE существенной
kernel-сущностью является concrete runtime interface, тогда как transport peer может
вообще не соответствовать Linux route next-hop.

Эксперимент поэтому разделен на:

- EXP-009.1 — OpenConnect: один logical transport profile, несколько concrete interfaces;
- EXP-009.2 — WireGuard: один стабильный concrete interface, несколько внутренних peers;
- H5 — контроль direct `dev` route без transport next-hop.

Реальная защищаемая цель во всех path-проверках:

```text
172.21.201.19
```

## EXP-009.1 — OpenConnect multi-interface lifecycle

**Статус:** COMPLETE — PASS

### Условия

Два независимых OpenConnect client одновременно подключены к одному ocserv server:

```text
pri -> VPN address 172.20.130.6
sec -> VPN address 172.20.130.5
```

Одновременное server state:

```text
=== ocserv users ===
      id     user    vhost             ip         vpn-ip device   since    dtls-cipher    status
   31612      sec  default 192.168.201.199   172.20.130.5 vpns01     6s  (AES-256-GCM) connected
   31214      pri  default 192.168.201.108   172.20.130.6 vpns00    45s  (AES-256-GCM) connected

=== vpns interfaces ===
vpns00           UNKNOWN        172.20.130.1 peer 172.20.130.6/32
vpns01           UNKNOWN        172.20.130.1 peer 172.20.130.5/32
```

### H1 — concurrent interfaces

**PASS.** Healthy concurrent sessions используют разные runtime-интерфейсы и один
server-side local IPv4 `172.20.130.1`.

Point-to-point remote endpoint присутствует в kernel inventory, но последующие фазы
показывают, что VPN-GATE не обязан использовать его как route association key.

### H2 — interface disappearance gives failover

Исходно:

```text
172.21.201.19 via 172.20.130.6 dev vpns00 metric 10 onlink
172.21.201.19 via 172.20.130.5 dev vpns01 metric 20 onlink
```

После остановки primary OpenConnect client `vpns00` исчез. Linux автоматически удалил
зависимый preferred route. Остался route через `vpns01`, и реальный LAN traffic
продолжил достигать target через secondary.

**H2: PASS.**

### H3 — interface return requires rematerialization

После возвращения primary interface `vpns00` preferred route автоматически не
восстановился. После ручного повторного добавления route kernel снова выбрал primary path.

**H3: PASS.** Возврат concrete interface требует reconciliation/rematerialization
desired route.

### H4 — route metric is not path-health detection

При сохраненных interfaces и server-side routes на client `pri` был выключен только:

```text
net.ipv4.ip_forward = 0
```

OpenConnect session не останавливалась, preferred route намеренно не удалялся.

LAN traceroute:

```text
1  192.168.201.107
2  timeout
3  timeout
```

Traffic не перешел на secondary route metric 20.

**H4: PASS как отрицательный контроль.**

Вывод: route metric задает preference между существующими routes, но не обнаруживает
end-to-end failure за preferred route.

> Ограничение evidence: отдельный route-table snapshot сразу после fault injection не
> снимался; сохранение preferred route следует из последовательности опыта — session и
> interface не останавливались и server routing не менялся.

## EXP-009.2 — WireGuard peer semantics

**Статус:** COMPLETE — PASS

### Условия

Gateway:

```text
wg0 = 172.20.126.1/29
pri = 172.20.126.2
sec = 172.20.126.3
```

Оба peers одновременно выполняли handshake с одним стабильным gateway interface `wg0`.

Linux FIB был подготовлен в peer-centric форме:

```text
172.21.201.19 via 172.20.126.2 dev wg0 metric 10 onlink
172.21.201.19 via 172.20.126.3 dev wg0 metric 20 onlink
```

`ip route get 172.21.201.19` выбирал next-hop `172.20.126.2`.

### H2.1 — Linux next-hop не выбирает WireGuard peer

Изначально gateway WireGuard config содержал только tunnel-address ownership:

```text
pri AllowedIPs = 172.20.126.2/32
sec AllowedIPs = 172.20.126.3/32
```

При наличии FIB route к target отправка с gateway дала:

```text
From 172.20.126.1 Destination Host Unreachable
ping: sendmsg: Required key not available
```

**PASS.** Linux next-hop `.2` не является WireGuard peer-selection key. WireGuard
отдельно ищет destination prefix в `AllowedIPs`.

### H2.2 — destination ownership принадлежит одному peer

После добавления:

```text
pri AllowedIPs = 172.20.126.2/32, 172.21.201.19/32
```

gateway успешно достиг target через pri.

Затем тот же `172.21.201.19/32` был назначен sec. Runtime state стал:

```text
pri AllowedIPs = 172.20.126.2/32
sec AllowedIPs = 172.20.126.3/32, 172.21.201.19/32
```

Target prefix исчез у pri и перешел к sec.

При этом Linux FIB по-прежнему предпочитал:

```text
172.21.201.19 via 172.20.126.2 dev wg0 metric 10
```

но фактический LAN traceroute показал hop:

```text
172.20.126.3
```

а локальный gateway ping через sec успешно достиг target.

**PASS.** WireGuard cryptokey routing выбирает peer по destination ownership, независимо
от Linux route next-hop внутри того же `wg0`.

### H2.3 — peer failure не вызывает ownership failover

После успешного sec path WireGuard на sec был выключен. На gateway:

- `wg0` остался существовать;
- peer sec остался в runtime config;
- `172.21.201.19/32` остался в `AllowedIPs` sec;
- latest handshake только устаревал;
- peer pri продолжал существовать;
- traffic к target не перешел на pri.

**PASS как отрицательный контроль.** Peer health/handshake не переводит destination
ownership на другой peer.

### H2.4 — duplicate static AllowedIPs: last-applied peer wins

Gateway static config был намеренно записан с одинаковым target prefix у обоих peers и
с `SaveConfig = false`, чтобы runtime state не переписывал исходный файл.

При порядке:

```text
pri
sec
```

после `wg-quick down/up` runtime state оставил target только у sec:

```text
pri -> 172.20.126.2/32
sec -> 172.20.126.3/32, 172.21.201.19/32
```

Наличие/отсутствие endpoint и handshake sec ownership не меняло.

После зеркальной перестановки peer-блоков:

```text
sec
pri
```

runtime state стал:

```text
sec -> 172.20.126.3/32
pri -> 172.20.126.2/32, 172.21.201.19/32
```

**PASS.** Duplicate target prefix не создает primary/secondary peer routes. Последний
примененный peer получает destination ownership.

## H5 — OpenConnect direct dev route без transport peer

После WG-проверок OpenConnect interfaces оставались:

```text
vpns01  UNKNOWN  172.20.130.1 peer 172.20.130.5/32
vpns00  UNKNOWN  172.20.130.1 peer 172.20.130.6/32
```

На gateway был добавлен route **без `via` и без `onlink`**:

```text
ip route add 172.21.201.19/32 dev vpns00 proto 202 metric 10
```

Результат:

```text
3 packets transmitted, 3 received, 0% packet loss
rtt min/avg/max/mdev = 2.629/2.675/2.730/0.041 ms
```

**H5: PASS.** Для проверенного OpenConnect point-to-point interface route к protected
destination не требует configured transport peer как Linux next-hop.

## Transient NAT/path observation

Во время подготовки WG baseline один LAN flow временно не проходил, несмотря на:

- `net.ipv4.ip_forward=1`;
- `FORWARD` policy ACCEPT;
- корректный FIB к `wg0`;
- `tcpdump`, показывающий `ens18 In` и `wg0 Out`.

В `POSTROUTING` оставались прежние OpenConnect MASQUERADE rules, а новое WG MASQUERADE
сначала имело нулевой счетчик. Userspace tool `conntrack` отсутствовал.

После удаления OC MASQUERADE rules path заработал. Последующее повторное добавление OC
MASQUERADE уже не ломало path; его counter оставался нулевым, а WG MASQUERADE counter
рос. Позднее ранее неработавший LAN ping также начал проходить без дополнительного
изменения конфигурации.

**Причина не установлена.** Возможный ранее существовавший conntrack/NAT state остается
гипотезой, а не доказанным объяснением. Наблюдение не используется как архитектурное
доказательство.

Если симптом повторится на live-test, до изменений следует сохранить как минимум:

- `iptables-save -t nat`;
- POSTROUTING counters;
- `ip route get <destination>`;
- simultaneous ingress/`wg0` packet capture;
- kernel conntrack state доступным на target host способом.

## Итог

**EXP-009 COMPLETE — PASS.**

Экспериментально подтверждено:

1. Один logical transport profile может иметь несколько одновременно пригодных concrete
   runtime interfaces.
2. Исчезновение concrete interface удаляет dependent route; возвращение interface требует
   rematerialization route.
3. Route metric не является end-to-end health-check.
4. Transport peer не является универсальным Linux route-next-hop abstraction.
5. WireGuard peer selection внутри одного `wg0` определяется transport-owned
   destination `AllowedIPs`, а не Linux next-hop.
6. Peer health WireGuard не создает автоматического failover между peers одного interface.
7. OpenConnect protected route может быть direct `dev <interface>` route без `via peer`.

Архитектурный вывод, который должен быть оформлен отдельно:

```text
VPN-GATE управляет concrete VPN interfaces и protected routes.
Transport peer selection остается внутри transport и не является частью route model.
```

Это позволяет удалить configured `peers`, `PeerBinding` и peer-specific next-hop из
нормативной модели VPN-GATE.
