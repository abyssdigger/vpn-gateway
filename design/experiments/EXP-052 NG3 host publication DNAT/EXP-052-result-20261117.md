## Findings

### F1 — publication matching must prove a host-local destination before DNAT

The first probe run (`44164513402`, job `134326882810`) proved positive TCP/UDP DNAT,
selector behavior and unrelated host-local traffic, but its initial interface/selector-less
rule shapes matched only ingress/port. Review found that such a shape could capture unrelated
transit traffic using the same destination port.

The final evidence therefore adds a same-port transit negative and requires a pre-DNAT
local-destination predicate:

```text
fib daddr type local
```

for publication rules that are not already restricted to one exact local host IPv4 address.
The final run proves both interface-selected and selector-less publication leave foreign
transit untouched.

This is an ownership/safety correction to the lower realization, not a new user-facing
selector.

### F2 — conntrack DNAT preserves the useful transport properties

For both TCP and UDP the internal listener observed the original external client source
address. The external client observed the reply from the originally addressed host
IP/host-port rather than the internal managed address/port.

Therefore the kernel connection-tracking path supplies both the forward translation and
reverse translation needed by the tested publication mapping without a userspace per-flow
relay.

### F3 — one Device intent has two distinct lower responsibilities

EXP-052 covers only the host-side external-to-internal mapping. Existing EXP-046/047 evidence
continues to cover the managed-domain `stack_input`/`stack_output` local admission for the
internal publication endpoint.

Neither result subsumes the other.

### F4 — host forwarding is a prerequisite, not newly acquired ownership

The disposable host namespace used `net.ipv4.ip_forward=1` to route DNATed packets toward
the managed boundary. EXP-052 deliberately does not write the real runner-host forwarding
state.

Current NG3 architecture already keeps ordinary external host forwarding outside the managed
ForwardingGate. This result therefore does **not** justify the publication implementation
silently changing the host-global forwarding sysctl. A runtime using this DNAT realization
may observe the required external forwarding prerequisite and report the publication unready
when it is absent; changing ownership of that prerequisite requires a separate accepted
requirement/design decision.

## Verdict

PASS for a narrow host-boundary nftables DNAT realization with all of these conditions:

- only explicitly owned publication objects may be created/removed;
- interface/selector-less rules prove pre-DNAT destination locality and cannot capture
  unrelated transit;
- exact IPv4 selectors remain exact;
- host/internal port mapping comes only from normalized canonical Device intent;
- host-side mapping and managed-domain local admission remain separate observed/converged
  postconditions;
- unrelated host nft/routing/sysctl state is not adopted;
- no new ownership of host-global forwarding follows from this experiment.
