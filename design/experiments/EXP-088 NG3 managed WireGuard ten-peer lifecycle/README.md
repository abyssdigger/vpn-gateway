# EXP-088 — WireGuard: десять пиров, одна сеть и граница управляемого Device

## Статус

PLANNED — постановка принята к проверке; исполняемый стенд и результат еще не созданы.

## Связь с требованиями

Эксперимент проверяет нижние предпосылки для:

- VPNG-U001-R1.R3.R7 — явно включаемая подготовка и жизненный цикл управляемого Device;
- VPNG-U001-R1.R3.R7.R2 — различение желаемой конфигурации и подтвержденного поколения
  VPN-экземпляра;
- VPNG-U001-R1.R3.R8 — несколько WireGuard-пиров для одного удаленного префикса с
  автоматическим переносом AllowedIPs.

Эксперимент не является реализацией будущего менеджера Device и не закрывает эти требования.

## Вопрос

Можно ли построить нижний WireGuard-контракт, в котором:

1. один wg0 содержит десять заранее настроенных пиров;
2. у каждого пира постоянно остается собственный внутритуннельный проверочный /32;
3. базовая конфигурация не назначает общий удаленный префикс ни одному пиру;
4. после свежего наблюдения общий префикс назначается выбранному пиру через wg set;
5. при отказе выбранного пира префикс последовательно переносится на следующий пригодный пир;
6. удаление и повторное создание wg0 из той же базовой конфигурации гарантированно удаляет
   динамическое владение общим префиксом;
7. каждое изменение выбранного пира получает новое поколение реализации, поэтому результат
   проверки доступности предыдущего поколения нельзя принять за актуальный?

## Граница проверки

Проверяется только WireGuard-механизм и минимальная модель поколения реализации.

Не проверяются:

- production-компоненты VPN-GATE;
- окончательный формат пользовательской конфигурации;
- systemd-реализация будущего менеджера;
- хранение секретов;
- запуск VPN по первому пакету или остановка по времени простоя;
- независимый выбор пира для нескольких разных наборов префиксов.

## Стенд

Один disposable client namespace:

- wg0;
- inner address 10.200.0.1/32;
- десять WireGuard-пиров A..J;
- десять независимых underlay-соединений.

Каждый пир:

- имеет отдельную пару ключей и UDP endpoint;
- постоянно владеет на стороне клиента одним проверочным адресом
  10.201.0.1/32 .. 10.201.0.10/32;
- независимо предоставляет одну и ту же удаленную payload identity 10.77.0.1;
- способен стать владельцем общего префикса 10.77.0.0/24.

Базовое состояние клиента после создания wg0:

    peer A AllowedIPs = 10.201.0.1/32
    ...
    peer J AllowedIPs = 10.201.0.10/32

    10.77.0.0/24 отсутствует у всех пиров

## Модель поколения

Стенд ведет только экспериментальный счетчик:

    realization_generation

Он увеличивается после каждого подтвержденного изменения владельца общего префикса и после
полного пересоздания wg0.

Любое сохраненное наблюдение доступности помечается поколением, в котором оно получено.
Проверка должна показать, что наблюдение с предыдущим поколением отвергается как устаревшее.

Это не выбор production-типа и не изменение LogicalPathId.

## Гипотезы

### H1 — безопасная базовая конфигурация представима

После применения базовой конфигурации все десять проверочных /32 одновременно видны в
wg show, каждый проверочный адрес достигает только своего пира, а 10.77.0.0/24 не принадлежит
ни одному пиру.

### H2 — общий префикс можно назначить без перезапуска wg0

Одна runtime-операция wg set назначает 10.77.0.0/24 выбранному пригодному пиру; ifindex wg0
не меняется, а реальный payload 10.77.0.1 проходит через выбранного пира.

### H3 — десять пиров переключаются в заданном порядке

При последовательном отказе текущих владельцев A..I стенд выбирает следующий пригодный пир,
переносит общий префикс и подтверждает фактический пир по WireGuard transfer counters.
Переход к J должен выполняться без пересоздания wg0.

### H4 — восстановление обратимо

После восстановления более предпочтительных пиров стенд может вернуть общий префикс на
заданного пира без пересоздания интерфейса. Эксперимент не вводит автоматически политику
failback продукта; он проверяет только обратимость нижней операции.

### H5 — перезапуск стирает динамическое владение

После удаления wg0 и его повторного создания из неизменной базовой конфигурации:

- все постоянные проверочные /32 восстановлены;
- 10.77.0.0/24 снова отсутствует у всех пиров;
- старое поколение реализации и его наблюдения не принимаются как текущие;
- новый выбор выполняется только после свежего наблюдения.

### H6 — подтверждение важнее команды

Стенд считает перенос успешным только после нового чтения wg show ... allowed-ips и проверки,
что общий префикс принадлежит ровно ожидаемому пиру. Ошибка команды, отсутствие интерфейса,
неожиданное владение или невозможность наблюдения дают отрицательный результат, а не
предполагаемый успех.

### H7 — свойства перехода должны быть измерены, а не придуманы

При переносе общего префикса между двумя живыми пирами стенд должен посылать параллельный
payload и отдельно фиксировать:

- были ли потеряны пакеты;
- был ли хотя бы один пакет передан через невыбранного пира;
- можно ли одной командой wg set задать полное состояние затронутых пиров;
- достаточно ли наблюдаемого поведения для обычного перехода либо будущей реализации нужен
  временный запрет payload-трафика на время переключения.

H7 не получает заранее назначенного желаемого результата. Наблюдение определяет последующее
архитектурное решение.

## Критерий PASS

PASS требует H1-H6.

H7 должен дать воспроизводимый результат, но обнаруженная потеря пакетов или отсутствие
доказанной транзакционности сами по себе не превращают нижний механизм в FAIL. В таком случае
review обязан явно определить дополнительную защиту, необходимую production-архитектуре.

Обязательные маркеры будущего стенда:

    EXP088_BASE_NO_OWNER=PASS
    EXP088_TEN_PEER_PROBES=PASS
    EXP088_INITIAL_SELECT=PASS
    EXP088_ORDERED_FAILOVER=PASS
    EXP088_RECOVERY=PASS
    EXP088_RESTART_RESETS_OWNER=PASS
    EXP088_GENERATION_REJECTS_STALE=PASS
    EXP088_CONFIRMED_APPLY=PASS
    EXP088_TRANSITION_OBSERVATION=<recorded-result>
    EXP088_RESULT=PASS

## Последующее решение

После результата нужно отдельно решить:

- достаточно ли одного поколения WireGuard-реализации для связи с текущим availability
  context;
- требуется ли защитное ограничение трафика на время переноса AllowedIPs;
- где проходит компонентная граница между менеджером жизненного цикла Device и владельцем
  динамических AllowedIPs;
- как выбранный нижний контракт обобщается с одной удаленной сети на несколько наборов
  префиксов.

До этого production-реализация не начинается.
