# EXP-086 result — WireGuard same-prefix multi-peer availability

**Date:** 2026-11-24  
**Status:** COMPLETE — PASS / NEGATIVE FEASIBILITY FINDING  
**Source commit:** `70d44af5388b7d0d2ad8d5b76dfbde5729ec59bf`  
**GitHub Actions run:** `45320595770`  
**Job:** `linux-wireguard-multipeer` (`138198006146`)

## Environment

The experiment ran on a privileged GitHub Actions Linux runner using real Linux network
namespaces, kernel WireGuard interfaces, `wireguard-tools`, `iproute2` and `ping`.

The topology had one client WireGuard interface, `wg0`, with two independent WireGuard peers.
Both peers represented the same remote payload identity `10.77.0.1`, and the candidate payload
prefix was `10.77.0.0/24`.

## Observations

### H1 — same-prefix peer ownership is exclusive

PASS.

The experiment first assigned `10.77.0.0/24` to peer A and then assigned the same prefix to
peer B on the same client `wg0`.

Observed state:

```text
EXP086_ALLOWEDIPS_STATE={
  'RBFs8C/x97loapHg+pEjfh+cAxSAOkGDC/8R2u/7T1A=': (),
  'vrpncDVJ1GTx9lngVDl1+vmWsRwFSvYmZgOeGv8ztUw=': ('10.77.0.0/24',)
}
EXP086_ALLOWEDIPS_EXCLUSIVE=PASS
```

The second assignment moved destination ownership to peer B. The same exact prefix was not
simultaneously retained by both peers.

### H2 — Linux route priority does not select the WireGuard peer

PASS.

Two Linux routes for the same payload prefix were installed through the same `wg0` with
different metrics. Payload was sent, the metric ordering was changed, and payload was sent
again without changing WireGuard peer configuration.

The selected peer remained unchanged. Linux route lookup only exposed the common egress
interface:

```text
EXP086_FIB_ROUTE=10.77.0.1 dev wg0 src 10.200.0.1 uid 0
EXP086_FIB_SELECTED_PEER=vrpncDVJ1GTx9lngVDl1+vmWsRwFSvYmZgOeGv8ztUw=
EXP086_FIB_PRIORITY_PEER_UNCHANGED=PASS
```

The selected peer was identified from actual per-peer WireGuard transfer-counter deltas, not
from configuration inference.

### H3 — cryptokey ownership changes the selected peer

PASS.

Without changing the Linux egress interface, the experiment reassigned
`10.77.0.0/24` to peer A.

Observed state and dataplane selection:

```text
EXP086_SWITCHED_ALLOWEDIPS_STATE={
  'RBFs8C/x97loapHg+pEjfh+cAxSAOkGDC/8R2u/7T1A=': ('10.77.0.0/24',),
  'vrpncDVJ1GTx9lngVDl1+vmWsRwFSvYmZgOeGv8ztUw=': ()
}
EXP086_SWITCHED_SELECTED_PEER=RBFs8C/x97loapHg+pEjfh+cAxSAOkGDC/8R2u/7T1A=
EXP086_ALLOWEDIPS_OWNER_SWITCH=PASS
EXP086_RESULT=PASS
```

The payload moved to peer A only when WireGuard destination ownership moved.

## Result

All H1-H3 passed.

A single WireGuard interface with two peers that are alternatives for the same remote prefix
cannot use the existing VPN-GATE Linux route-priority availability mechanism to choose between
those peers. The generic route layer can choose `wg0`; WireGuard still performs the subsequent
peer selection from its own cryptokey-routing / `AllowedIPs` state.

Therefore the proposed substitution

```text
WireGuard peer choice
    <- ordinary VPN-GATE route-priority availability
```

is not a valid realization.

## Architecture implications

This result confirms, rather than contradicts, the current NG3 boundary that treats WireGuard
destination ownership as an integration-specific cryptokey-routing concern.

Two distinct designs remain technically possible if the product later needs same-prefix
WireGuard redundancy:

1. use one WireGuard interface per alternative peer, giving the existing NG3 path/availability
   model distinct concrete endpoints to rank;
2. keep one WireGuard interface but introduce a WireGuard-specific lower owner that changes
   `AllowedIPs` ownership in response to availability.

The second design is not generic FIB route-priority reuse. It creates new managed WireGuard
peer state and therefore needs an explicit product/architecture decision before implementation.
