# EXP-083 result — single Private-network protective gate

**Date:** 2026-11-22  
**Technical result:** **PASS**  
**Workflow run:** `45038597280`  
**Job:** `linux-forwarding-barrier`

## Proven

A disposable ORD/HOST/STACK/VPN1/VPN2 topology established five distinct IPv4 paths:

- ordinary -> local Private-network endpoint;
- Private-network local -> ordinary;
- ordinary -> VPN;
- VPN -> ordinary;
- VPN -> VPN.

All five passed before containment.

The experiment then loaded one dedicated nftables `inet` table inside STACK/Private network
using one `nft -f -` ruleset transaction. The table contained:

- an INPUT drop for IPv4 arriving through the exact ordinary-side managed-boundary interface;
- an OUTPUT drop for IPv4 leaving through that boundary;
- a FORWARD drop for IPv4 transit.

With that single table active:

- all five representative paths were blocked: **PASS**;
- Private-network interfaces and routes were unchanged: **PASS**;
- `net.ipv4.ip_forward` remained enabled: **PASS**.

After deleting the dedicated table:

- all five paths were restored: **PASS**.

The same workflow job also reran EXP-030, EXP-082 and the production ForwardingGate integration
successfully.

## Architectural conclusion

The protective-mode traffic postcondition does not require a composite host-side gate plus
Private-network `ForwardingGate`. One independently owned Private-network nft gate can cover
the ordinary-boundary INPUT/OUTPUT and all Private-network IPv4 FORWARD classes together.

This is preferable as the current lower candidate because:

- all protective traffic classes share one ownership domain;
- activation can be loaded as one nftables ruleset transaction;
- removal is a single owned-table operation rather than an ordered release of two independent
  barriers;
- normal routing/link/runtime state is preserved for diagnosis and later recovery;
- the existing `ForwardingGate` can keep its current structural-transition responsibility
  instead of acquiring a second public-mode meaning.

The result does not close `VPNG-U004-R5` by itself. Long-lived mode ownership, fresh
observation/recovery, public control semantics and safe leave preconditions still require an
upper architecture.
