# EXP-087 result — WireGuard runtime AllowedIPs failover

**Date:** 2026-11-24  
**Status:** COMPLETE — PASS / FEASIBILITY CONFIRMED  
**Source commit:** `4ae88f67d3cd02f64f04f99e9a62cb3876abea76`  
**GitHub Actions run:** `45333802569`  
**Job:** `linux-wireguard-multipeer` (`138241133580`)

## Environment

The experiment ran on a privileged GitHub Actions Linux runner using real Linux network
namespaces, kernel WireGuard interfaces, `wireguard-tools`, `iproute2` and `ping`.

The client had one `wg0` with two peers on separate underlay paths. Peer A permanently owned
probe target `10.201.0.1/32`, peer B permanently owned `10.201.0.2/32`, and the shared
payload prefix `10.77.0.0/24` belonged to exactly one selected peer at a time.

No WireGuard configuration file was created or edited by the experiment. Runtime state changes
used `wg set wg0 peer ... allowed-ips ...`.

## Observations

### H1 — runtime mutation without config-file rewrite

PASS.

Initial state showed the permanent peer probe prefixes plus the shared payload prefix on A:

```text
EXP087_INITIAL_ALLOWEDIPS={
  peer-A: ('10.201.0.1/32', '10.77.0.0/24'),
  peer-B: ('10.201.0.2/32',)
}
EXP087_RUNTIME_ONLY_ALLOWEDIPS=PASS
```

The interface remained up while later `wg set` calls replaced the peers' `AllowedIPs`
sets.

### H2 — transport endpoint is unsuitable for the current in-interface ICMP probe shape

PASS.

The peer-A underlay address was first confirmed reachable on the ordinary underlay. The
experiment then reproduced the current probe shape by forcing an ICMP lookup and
`ping -I wg0` for that same transport address through `wg0`.

Because the transport address was not in any peer's `AllowedIPs`, it was not a usable
in-tunnel ICMP target:

```text
EXP087_TRANSPORT_ENDPOINT_PROBE_UNSUITABLE=PASS
```

This result is intentionally narrower than "the endpoint cannot be checked": it proves that
the existing VPN-interface-bound ICMP probe mechanism cannot simply use a WireGuard UDP
transport endpoint as its target.

### H3 — permanent peer-specific in-tunnel /32 targets discriminate peers

PASS.

`ping -I wg0 10.201.0.1` selected peer A, while
`ping -I wg0 10.201.0.2` selected peer B. Selection was verified from real per-peer
WireGuard transfer-counter deltas.

```text
EXP087_PEER_PROBE_DISCRIMINATION=PASS
```

Thus one `wg0` can retain independently probeable peer identities when each peer owns a
distinct permanent in-tunnel target prefix.

### H4 — runtime desired state can move the shared payload prefix on failure

PASS.

After peer A's underlay was made unavailable, A's permanent probe target stopped replying
while B's permanent target remained reachable.

One runtime desired-state apply removed `10.77.0.0/24` from A and added it to B while
preserving both probe prefixes:

```text
EXP087_FAILOVER_ALLOWEDIPS={
  peer-A: ('10.201.0.1/32',),
  peer-B: ('10.201.0.2/32', '10.77.0.0/24')
}
EXP087_FAILOVER_TO_B=PASS
```

Real payload to `10.77.0.1` then used peer B.

### H5 — recovery is reversible

PASS.

After A's underlay was restored, A's permanent probe target became reachable again. A
runtime desired-state apply moved the shared payload prefix back to A:

```text
EXP087_RECOVERY_ALLOWEDIPS={
  peer-A: ('10.201.0.1/32', '10.77.0.0/24'),
  peer-B: ('10.201.0.2/32',)
}
EXP087_RECOVERY_TO_A=PASS
EXP087_RESULT=PASS
```

Real payload then used peer A again.

## Result

The single-interface candidate is technically feasible with a WireGuard-specific runtime
ownership layer:

```text
one wg0
  peer A: permanent probe target A + shared payload prefixes iff selected
  peer B: permanent probe target B + shared payload prefixes iff selected

peer availability evidence
  -> desired peer ownership
  -> runtime wg set ... allowed-ips ...
  -> fresh observation / verification
```

This avoids one WireGuard interface/listen port per alternative peer. It does **not** reuse
ordinary Linux route-priority selection: the selected shared prefixes still move inside
WireGuard cryptokey-routing state.

## Current architecture boundary

The existing Release-1 availability implementation is keyed by
`ProbePolicyOwner(profile_id, LogicalPathId)` and a concrete interface endpoint. Two peers
inside one `wg0` are therefore not two current generic logical paths.

The experiment proves the lower mechanism and probe target shape, not production integration.
A future implementation would need an explicit WireGuard peer-observation/desired-state
boundary rather than pretending each peer is an existing `LogicalPathId`.

The permanent peer-specific probe target is itself part of WireGuard desired `AllowedIPs`
state. The shared payload prefixes are the availability-controlled part.

## Limits

The experiment does not prove transactional zero-loss switching under concurrent payload,
does not prove that a peer-specific probe target implies reachability of every payload
destination behind the peer, and does not define user-facing configuration or service-manager
ownership.
