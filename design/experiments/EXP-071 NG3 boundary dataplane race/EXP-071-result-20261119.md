# EXP-071 result — managed-boundary dataplane race

**Date:** 2026-11-19

## Result

**PASS.**

Two independent hosted-runner executions found no stable material throughput or endpoint-CPU
advantage for plain `netkit L3` over the Debian-12-compatible
`routed veth + Proxy ARP` boundary.

The explicit-next-hop veth control also matched the Proxy-ARP veth shape, showing no measurable
steady-state Proxy-ARP tax in this workload.

## Run A

Workflow run `44582397400`, job `135766214137`.

Environment:

- kernel `7.0.0-1019-azure`;
- iproute2 `6.19.0`;
- iperf3 `3.20`.

| 4 streams reverse | 61.126 | 61.445 | 61.558 |

Ratios `netkit / veth+proxy`:

- 1 stream forward: `0.977`;

The 4-stream workloads saturated measured system CPU (~99.8%), so they are throughput saturation
points rather than fine CPU-efficiency measurements.

## Interpretation

For the tested managed-boundary shape, the difference between plain `netkit L3` and ordinary
routed veth is below the resolution/noise floor of this CI microbenchmark.

Proxy ARP is neighbour-plane machinery. After neighbour resolution, its veth dataplane is
indistinguishable here from the same veth pair using an explicit peer IP next-hop.

Therefore there is currently no performance evidence requiring a netkit-only design or justifying
dropping Linux 6.1 / Debian 12 support.

A product realization may treat both as implementations of one managed-L3-endpoint contract and
select the backend from platform capability without changing Profile/Device semantics.

## Scope

This is a relative local forwarding microbenchmark. It does not claim absolute production
throughput, latency-tail equivalence, or equivalence under real VPN crypto.

IPvlan L3 is not ranked in this matrix: it is not a peer primitive and cannot realize the same
HOST-visible `vpng0 <-> STACK` topology without changing the packet path. A separate direct-attach
IPvlan baseline would answer a different performance question.
