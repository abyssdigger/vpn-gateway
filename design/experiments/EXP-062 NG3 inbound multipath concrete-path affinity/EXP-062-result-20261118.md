## Scope

EXP-062 supersedes historical unexecuted EXP-014 as the active evidence vehicle for
remote-initiated multi-path concrete-path affinity.

The ordinary host is intentionally out of scope. EXP-053/EXP-061 already prove that a related
reply can cross the host boundary and re-enter the managed stack. EXP-062 starts from the
narrower question inside that stack:

```text
one Profile
  -> multiple simultaneously eligible inbound paths
  -> flow entered concrete path A2
  -> can established return traffic remain on A2
     even after ordinary Profile preference changes to A1?
```

## Topology

```text
sink A1
  172.16.1.2/30
      |
      | A1
      |
managed stack
      |
      | A2
      |
remote A2
  172.16.2.2/30
  10.0.0.2/32

managed stack
      |
ordinary-side peer
  192.0.2.2/30
```

A1 is a deliberate sink. Both A1 and A2 are present and eligible in the Profile-equivalent
routing table.

The test uses an established TCP flow. Control and affinity phases use separate server ports,
and dedicated nft counters observe only remote-bound A1 packets belonging to the corresponding
phase. This prevents stale packets from a previous control connection from contaminating the
loss result.

## Mechanism tested

The successful mechanism class is:

```text
NEW inbound on A2
    -> save concrete-path identity in conntrack mark

established return packet from ordinary side
    -> restore ct mark to packet fwmark

higher-precedence marked RPDB lookup
    -> A2-specific routing table
    -> A2 path

if marked path-specific lookup cannot route:
    -> terminal marked fail-closed RPDB rule
    -> do not fall through to ordinary Profile preference
```

The path-specific table also contains a terminal unreachable route for the tested remote
prefix. EXP-062 proves the tested combined guarded mechanism; it does not separately establish
which of the two terminal guards is minimal.

## Final evidence

The final privileged run emitted:

```text
EXP062_INITIAL_A2_FLOW=PASS
EXP062_CONTROL_PREFERENCE_SWITCH_BREAKS_FLOW=PASS
EXP062_MARKED_LOOKUP_SELECTS_A2=PASS
EXP062_AFFINITY_SURVIVES_PREFERENCE_SWITCH=PASS
EXP062_PINNED_PATH_LOSS_FAILS_CLOSED=PASS
EXP062_RESULT=PASS
```

Interpretation:

1. **Initial flow through A2 works.**
   With A2 initially preferred, a remote-A2 TCP flow reaches the ordinary-side peer and
   receives its first response.

2. **Ordinary preference change breaks the unpinned control flow through A1.**
   After the same established control flow is created, ordinary Profile preference changes
   to A1. Its next server response is observed on A1 and the client does not receive it.

3. **Concrete-path affinity survives that preference change.**
   A fresh flow established through A2 receives a concrete-path connection mark. After A1
   becomes the preferred Profile path, the next response still reaches the client through A2,
   while the A1 observer counter for that flow remains unchanged.

4. **Pinned-path loss can fail closed.**
   After the affinity-marked flow is established and survives the preference change, A2 is
   made unusable. The ordinary-side server then generates a new packet on the already
   established TCP connection; no new ingress packet from A2 is required. The client does not
   receive the packet, and the A1 observer counter remains unchanged. Therefore the marked
   flow does not silently migrate to the alternate eligible A1 path.

## Iteration notes

Earlier harness iterations are useful negative evidence about the test itself:

- a simple client request issued only after bringing A2 down mixed ingress-path loss with
  return-path loss and was rejected as an invalid discriminator;
- a broad A1 interface counter could be contaminated by packets from the prior control TCP
  connection and was rejected;
- the final harness separates control/affinity TCP ports and uses per-flow nft egress counters.

These iterations do not change the final technical Result; they document why the final
discriminator is stronger.

## Proven technical fact

For the tested Linux namespace/RPDB/nft/conntrack data plane, concrete-path affinity for a
remote-initiated established flow across multiple simultaneously eligible paths is technically
feasible.

The tested mechanism can also prevent an established marked flow from silently falling back to
another eligible path when the pinned path becomes unusable.

## Not decided by this result

Disposition therefore remains `pending_decision` until discussion.
