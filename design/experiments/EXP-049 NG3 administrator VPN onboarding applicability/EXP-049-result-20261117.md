
The Debian 13 container ran on the normal GitHub Actions Ubuntu host, but all experiment

the privileged Debian 13 environment.

## Tested integration

Candidate integration:

```text
external OpenVPN server
    -> UDP underlay
managed NG3 network namespace
    -> OpenVPN client process started inside namespace
    -> client creates named TUN endpoint vpn0 inside namespace
```

This deliberately avoids WireGuard-specific network-namespace behavior and does not move a
pre-created VPN interface from another network namespace.

The administrator-supplied VPN-specific configuration contains only OpenVPN transport/TLS/TUN
configuration. It does not inject NG3-owned routes, RPDB rules or nft policy.

## Reproducible procedure

For each clean cycle the probe:

1. creates the NG3 managed domain with production `ensure_managed_network_domain(...)`;
2. confirms `vpn0` is absent;
3. creates an isolated external OpenVPN server endpoint;
4. starts the OpenVPN client process using `ip netns exec <managed> openvpn ...`;
5. proves the OpenVPN tunnel works before NG3 policy activation;
6. reads fresh `ip -j link` inventory through production `parse_ip_link_inventory(...)`;
7. projects the configured exact `vpn0` selector with production
   `project_device_bindings(...)`;
8. invokes production `start_controller_once(...)`, whose pure policy builder uses the
   observed binding and the normal NG3 structural policy pipeline;
9. installs a host route only to inject the controlled ordinary-side payload into the existing
   managed-domain host boundary;
10. sends controlled ICMP payload to the remote tunnel address;
11. stops the external OpenVPN client;
12. runs normal NG3 stop/domain cleanup and verifies namespace + host boundary absence;
13. repeats from clean state.

The complete executable procedure is:

`design/experiments/EXP-049 NG3 administrator VPN onboarding applicability/exp049_openvpn_onboarding.py`.

## Finding

The real VPN placement hypothesis is **partially confirmed**:

```text
real userspace VPN process inside managed namespace       PASS
real TUN endpoint created there                          PASS
fresh production endpoint observation                   PASS
exact logical-path binding                              PASS
NG3 structural activation using that binding            PASS
controlled payload after accepted NG3 activation        FAIL
```

The failure is caused by NG3's own terminal local-system policy:

```text
OpenVPN process
    -> needs locally generated/received UDP underlay traffic
    -> stack_output / stack_input terminal DROP
    -> no concrete supported-integration allow contribution exists
    -> encrypted VPN transport cannot carry admitted payload
```

This is **not**:

- an OpenVPN inability to run inside the managed namespace;
- an endpoint-placement failure;
- a binding ambiguity;
- stale host state;
- an environmental Debian/TUN failure.

It is a **supported-integration local/system policy gap** in the current executable NG3
closure.

## Relation to existing architecture

The architecture already anticipated that supported integrations may require source-owned
local/system exceptions under the terminal INPUT/OUTPUT DROP boundary.

However, no concrete OpenVPN integration contribution is currently materialized by the
production desired-state/activation pipeline.

Therefore EXP-049 does not justify adding an ad-hoc nft exception inside the experiment.
Doing so would violate the experiment criterion forbidding manual injection of network policy
owned by VPN-GATE.
