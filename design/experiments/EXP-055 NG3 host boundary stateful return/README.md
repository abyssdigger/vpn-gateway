# EXP-055 — host-boundary stateful return steering

## Purpose

Test whether the ordinary host can return replies to the managed network domain without
publishing every remote Profile prefix into host routing state.

This experiment is scoped to the explicit managed/host boundary. It does not carry Profile
identity across namespaces and does not reuse the rejected EXP-053/054 packet-metadata idea.

## Hypothesis

When a tracked connection first enters the host from the managed boundary, the host can record
one host-local conntrack mark on that connection without marking the packet used for the
initial route lookup.

On the reverse direction only, the host restores that conntrack mark to the packet mark.
One owned RPDB rule then selects one owned table whose default route points to the managed
boundary.

Conceptually:

```text
managed -> host
    remember connection came from managed boundary
    DO NOT steer this packet back

reply -> host
    restore host-local connection mark
    policy route marked reply -> managed boundary
```

No remote prefix is required in the host main table or in the owned return table.

## Cases

The disposable topology proves in one run:

1. routed inbound: original remote source is preserved to the ordinary LAN and its reply
   returns through the managed boundary with no host route for that remote prefix;
2. host-side SNAT: ordinary LAN sees the host address; reverse NAT restores the remote
   destination and the same stateful steering returns it through the managed boundary;
3. host-local termination: a reply generated by the host itself is rerouted through the
   managed boundary from an nft route/output chain;
4. unrelated host->LAN traffic remains unmarked and uses ordinary host routing;
5. arbitrary managed-originated traffic equivalent to a `0.0.0.0/0` destination set exits
   the host instead of being recursively routed back into the managed boundary.

## Owned experimental state

Only inside disposable namespaces:

- one host nft table;
- one conntrack mark value;
- one packet mark value used only on reverse packets;
- one RPDB fwmark rule;
- one dedicated return table containing only a default route to the managed boundary.

The numeric mark/table/priorities are disposable evidence values, not production allocation.

## Acceptance

PASS requires all five cases plus proof that the host has no route entries for the three
remote test prefixes.

A PASS establishes technical viability only. Production acceptance still requires ownership,
collision, lifecycle, observation and recovery review.
