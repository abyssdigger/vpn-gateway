# NG3 2026-11-24 — ревью нормализации управляемого WireGuard

**Единица ревью:** разбор `managed_vpn` и выпуск нормализованных намерений без управления VPN  
**Рабочая версия кода:** `d115d86b6a4f0cbb97c1be74acec0db26b6e6831`  
**Архитектурное отражение:** `e5b0b35d5fb08af42c406ee980392f96fa801b9a`  
**Компонент:** A.002 ConfigurationAdapter

## Вердикт

**PASS — НОРМАЛИЗАЦИЯ РЕАЛИЗОВАНА; ВКЛАД A.002 ПО R7/R8 ОСТАЕТСЯ PARTIAL ДО ПОДКЛЮЧЕНИЯ К РАБОЧЕМУ ПУТИ ЗАГРУЗКИ.**

## Findings и решения

### F1 — исторический Release-1 parser не должен расширяться задним числом

**Решение:** принято.

`parse_release1_config` сохраняет прежнюю грамматику и прежнее поведение. Новый
`parse_current_config` разбирает текущую конфигурацию, удаляет из внутренней копии
`managed_vpn` после его собственной проверки, выводит совместимые структурные факты и затем
использует существующую Release-1 нормализацию для общей части контракта.

Тест внешне подготовленного Device сравнивает результат обоих путей и подтверждает
неизменность старой семантики.

### F2 — нормализация не выполняет действий с VPN

**Решение:** принято.

Новый код не читает файлы секретов, не вызывает `wg`, не обращается к systemd и не создает
сетевые интерфейсы. Результатом являются только типизированные значения:

- точный интерфейс управляемого Device;
- базовый адрес WireGuard;
- ссылки на файлы секретов;
- упорядоченный набор пиров;
- транспортные точки UDP;
- индивидуальные проверочные адреса;
- выведенные общие префиксы.

Тем самым граница A.002 не захватывает обязанности A.012/D.001/D.002/D.003.

### F3 — один источник истины действительно обеспечен кодом

**Решение:** принято.

Для управляемого Device разбор отвергает одновременно заданные:

- `managed_vpn` и `expected_interfaces`;
- `managed_vpn` и `allow_vpn_client`.

Точный structural selector выводится из `managed_vpn.interface`. Разрешения транспорта UDP
выводятся из `managed_vpn.peers[].endpoint`; при заданном `listen_port` он становится
точным локальным портом существующего нормализованного транспортного контракта.

### F4 — порядок и идентичность пиров сохраняются

**Решение:** принято.

Порядок массива пиров сохраняется. Внутри одного Device проверяется уникальность
`id`, канонического публичного ключа и `probe_target`. Публичный ключ принимается только
в каноническом base64-представлении 32 байт.

### F5 — общие сети выводятся после общей структурной нормализации

**Решение:** принято.

Набор общих префиксов строится из `destinations` всех включенных Profiles, которые
используют данный Device. Пользовательский порядок set-like `destinations` не становится
политикой; итоговый набор имеет детерминированный порядок.

Полный туннель `0.0.0.0/0` совместим с постоянными `probe_target/32`. Запрещена только
точная бизнес-цель `/32`, совпадающая с зарезервированным проверочным адресом.

### F6 — ссылки на секреты проверяются только синтаксически

**Решение:** принято.

A.002 требует канонический абсолютный путь и отвергает относительные пути, `..`, корень как
сам файл и неканоническое написание. Содержимое, тип файла, владелец и права доступа здесь не
наблюдаются: это остается обязанностью D.001 непосредственно перед воздействием.

### F7 — disabled placeholder сохраняет прежнюю поверхностную проверку

**Решение:** принято.

`enabled = false` не заставляет разбирать внутренности будущего `managed_vpn`, как и
прочие поля выключенного placeholder. Это сохраняет действующий контракт конфигурации.

### F8 — A.002 пока не full

**Решение:** принято.

Сам разбор реализован, но рабочий alpha/runtime configuration-load path по-прежнему вызывает
`parse_release1_config`. Поэтому текущая реализация продукта еще не передает нормализованное
управляемое намерение A.012/D.001/D.002.

В архитектуре вклад A.002 по `VPNG-U001-R1.R3.R7`,
`VPNG-U001-R1.R3.R7.R1` и `VPNG-U001-R1.R3.R8` изменен с [`none`] на
[`partial`] с явным описанием остатка.
