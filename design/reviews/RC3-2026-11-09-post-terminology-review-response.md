# Разбор review RC3 после терминологической правки

**Дата:** 2026-11-09  
**Статус:** проектное решение по внешнему review

## 1. Общая оценка

Review подтверждает, что предыдущие semantic- и terminology-исправления RC3 в основном
согласованы и не внесли регрессии. Новых причин пересматривать архитектурную модель нет.

Принимаются четыре терминологических/редакционных замечания C1–C4, одно операционное
уточнение D3 и необходимость сделать контракт IPv6-пересылки в D2 точнее. D1, D4 и D5
подтверждают уже сознательно принятый baseline и не требуют изменения политики.

Дополнительно при повторном поиске найдено несколько голых употреблений `runtime`,
вернувшихся в архитектуру после последующих semantic-правок. Они исправляются по уже
принятому правилу `PROJECT-CONVENTIONS`: самостоятельные технические сущности сохраняют
форму `runtime-*`, временной контекст работы daemon формулируется через «исполнение».

## 2. C1 — «среда выполнения»

Принимается. Более того, в архитектуре осталось два вхождения: §4.3 и startup sequence
§8.2. Оба заменяются на «среда исполнения».

## 3. C2 — IPv6-пересылка

Терминологическая часть принимается: в обычной русской прозе используется
«IPv6-пересылка».

Техническую предпосылку review уточняем. Целевой Debian 13 использует Linux 6.12 LTS.
В Linux 6.12 `net.ipv6.conf.<interface>.forwarding` задаёт Host/Router-поведение
интерфейса, но не позволяет независимо включить фактическую IPv6-пересылку при
`net.ipv6.conf.all.forwarding=0`. Поэтому для baseline обязательны проверки:

```text
net.ipv6.conf.all.forwarding     = 0
net.ipv6.conf.default.forwarding = 0
```

Перебирать `<interface>.forwarding` на Linux 6.12 как отдельный bypass не требуется.

При этом будущие kernels могут иметь независимый per-interface механизм фактической
пересылки. Для такого kernel daemon должен обнаружить этот механизм и подтвердить, что
соответствующие overrides выключены для существующих интерфейсов и, если предусмотрено,
для создаваемых позднее интерфейсов. Этот контракт фиксируется явно.

## 4. C3 — `peers = []`

Принимается как точная правка таблицы именованных параметров:

```text
profile.peers = [] -> разрешено
```

В остальном тексте `peers` остаётся корректным именем поля в контексте конкретного
профиля; механически добавлять `profile.` ко всем употреблениям не требуется.

## 5. C4 — проекция конфигурации

Принимается. Первая фраза §7.1 переписывается так, чтобы модификатор однозначно относился к
составу проекции:

```text
...строит проекцию конфигурации для исполнения,
содержащую только профили из managed_vpns.
```

## 6. D1 — отсутствие общего NEW ACCEPT в INPUT

Это сознательное изменение политики RC3 и остаётся без изменений. Управляемая VPN-сторона
не получает право инициировать новые соединения к локальным сервисам gateway.

Операционное следствие действительно нужно учитывать при deployment: сервис, который
предполагается публиковать удалённой VPN-стороне на tunnel IP, потребовал бы отдельного
явного расширения политики. Текущий baseline такого исключения не вводит.

## 7. D2 — IPv6 prerequisites

Содержательное замечание принимается в уточнённой форме, описанной в §3 настоящего ответа.
Архитектура теперь различает фактический baseline Linux 6.12 и возможный будущий
per-interface override, вместо расплывчатого «если ядро предоставляет отдельные механизмы».

## 8. D3 — административная сессия через управляемый VPN

Принимается как операционное следствие deny-first barrier.

Изолирующий фильтр временно убирает точные разрешающие блоки и оставляет selector guards.
Следовательно, `ESTABLISHED,RELATED`-пакеты, входящие с управляемого VPN-интерфейса, в
этот период также запрещаются. Административная SSH-сессия через такой путь теряет
прохождение пакетов и может оборваться либо пережить короткий барьер в зависимости от
тайм-аутов; архитектура не должна обещать непрерывность этой сессии.

Это не меняет fail-closed policy: сохранение ESTABLISHED для «незатронутого» профиля на
стадии изоляции осталось бы запрещённой оптимизацией.

## 9. D4 и D5

Оба пункта подтверждают сознательные изменения RC3:

- deny-only selector guards в `VPNG-INGRESS`;
- проверяемое положение daemon-owned prefix в `INPUT`, `FORWARD` и `POSTROUTING`.

Дополнительных изменений не требуется.

## 10. PROJECT-CONVENTIONS §3

Предложение убрать «по возможности» не принимается. Правило намеренно оставляет возможность
атомарного коммита, когда source review, project response и непосредственно вызванные им
нормативные правки образуют одну логическую единицу. Текущая обработка review является
именно таким случаем.

## 11. Дополнительный runtime-аудит

В review правильно отмечена общая терминологическая политика, но после последующих
semantic-правок в архитектуре снова появились голые формы `runtime`. Исправляются:

- «во время runtime» -> «во время исполнения»;
- «Запуск и runtime» -> «Запуск и исполнение»;
- «ошибка runtime» -> «ошибка во время исполнения»;
- `Runtime-проекция` -> «Проекция конфигурации для исполнения»;
- persisted `runtime-state` -> «состояние daemon»;
- `snapshot конфигурации runtime` -> «snapshot конфигурации».

Формы `runtime-интерфейс` и `runtime-каталог` остаются без изменений как имена
самостоятельных технических сущностей.

## 12. Итог

После этих правок review не содержит открытых блокирующих замечаний к архитектуре.
Изменения не требуют перестройки модели RC3 и совместимы с уже начатой реализацией.
