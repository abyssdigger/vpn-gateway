# Аудит русскоязычной терминологии RC3

**Дата:** 2026-11-09  
**Объект:** `design/RC3/vpn-gateway-architecture-rc3.md`  
**Базовая версия для сравнения:** архитектура после закрытия RC3 review findings  
**Тип изменения:** терминологический/редакторский, без изменения архитектурной семантики

## Цель

Проверить применение правила russian-preferred:

- обычный русский текст должен использовать естественную русскую терминологию;
- английский сохраняется для реальных технических идентификаторов, команд, имён состояний,
  API и исключений, прямо разрешённых нормативным словарём;
- привычный технический pidgin сам по себе не является основанием оставлять английские
  существительные и прилагательные.

Особое внимание уделялось конструкциям вида:

```text
managed profile
binding-specific rule
desired policy
foreign rule
route plan
cleanup payload
target-validated deny-only selector guard
interface operand
```

Такие конструкции должны переводиться, если английская форма не является идентификатором.

## Методика

Для первичного поиска использовалась механическая эвристика:

1. анализировать повествовательный текст вне inline-code;
2. не считать именованные состояния, команды, классы, поля конфигурации и явные технические
   идентификаторы;
3. отдельно просматривать fenced-блоки, потому что часть из них является не кодом, а
   компактной нормативной прозой;
4. после автоматического поиска вручную проверять контекст, чтобы перевод не менял
   технический смысл.

Эвристика не является нормативным линтером и намеренно завышает остаток: например,
`runtime-интерфейс`, `Netlink-событие`, названия технологий и Linux-сущностей всё ещё
содержат латиницу, хотя это допустимо по правилам проекта.

## Результат

Для повествовательного текста вне fenced-блоков и inline-code одной и той же эвристикой:

```text
до прохода:    1864 обычных English-like token
после прохода:  164
снижение:       ~91.2 %
```

При этом §26 в эту цифру не входит, потому что он оформлен fenced-блоком. Он был проверен
вручную и переписан целиком: английская грамматика заменена русской, а технические
идентификаторы сохранены.

## Основные исправленные классы

### 1. Архитектурные понятия

Переведены в обычном тексте:

- startup -> запуск;
- cleanup -> очистка;
- reconciliation -> согласование;
- binding/readiness -> привязка/готовность;
- managed/unmanaged profile -> управляемый/неуправляемый профиль;
- desired policy -> требуемая политика;
- foreign rules -> сторонние правила;
- isolation barrier -> защитный барьер;
- route plan -> план маршрутов;
- validation/lint -> проверка.

### 2. Фильтрация и маршрутизация

Убраны конструкции вроде:

```text
profile FORWARD chain
exact concrete interface
foreign POSTROUTING rules
full desired filter
route inventory
```

В обычном тексте они заменены русскими формулировками. Имена цепочек, таблиц,
`ACCEPT`/`REJECT`/`DROP`, `RouteSpec`, `proto 201/202` и другие реальные идентификаторы
сохранены.

### 3. Внутренняя модель реализации

Раздел §23 переведён с технического pidgin на русскую предметную лексику:

- «модель конфигурации и предметной области»;
- «граница взаимодействия с ядром»;
- «инвентаризация интерфейсов»;
- «результат разрешения селектора»;
- «локальное для процесса состояние»;
- «политика владения маршрутами».

Имена классов, методов и полей оставлены без перевода.

### 4. Инварианты

§26 был отдельной проблемой: fenced-блок визуально выглядел как код, хотя фактически
содержал нормативную прозу. Все 99 инвариантов приведены к русской грамматике без
изменения нумерации и смысла.

## Что намеренно осталось на английском

Сохраняются:

- технические идентификаторы и именованные состояния:
  `SAFE`, `UNSAFE`, `ACTIVE`, `RouteSpec`, `KernelError`, `ifindex` и т. п.;
- команды и ключи:
  `iptables-save`, `ip_forward`, `--check-config`, `reconcile_interval`;
- имена цепочек и таблиц:
  `INPUT`, `FORWARD`, `POSTROUTING`, `VPNG-*`;
- технологии и kernel/Linux-сущности:
  Netlink, systemd, iptables, multipath/nhid, capabilities;
- нормативные английские исключения из `terms-and-definitions.md`, в частности
  runtime, daemon, snapshot, ownership, daemon-owned, fallback, failover и CLI.

Допустимы русские словообразовательные формы вокруг таких технических основ:
`runtime-интерфейс`, `Netlink-событие`, `Python-реализация`.

## Проверка границы семантики

Проход не должен был менять:

- порядок bootstrap/runtime операций;
- семантику отказа с запретом;
- структуру фильтрации/NAT;
- модель селекторов и привязки;
- набор состояний жизненного цикла;
- конфигурационный контракт;
- владение маршрутами;
- инварианты по существу.

Изменения ограничены языком, заголовками, поясняющими формулировками и русификацией
нормативной прозы внутри технических блоков.
