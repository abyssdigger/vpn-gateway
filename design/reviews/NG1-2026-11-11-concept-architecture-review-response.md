# NG1 — response to concept and architecture review

Date: **2026-11-11**

Review: `design/reviews/NG1-2026-11-11-concept-architecture-review.md`

This response covers both the original review and the follow-up clarification dialogue.

## Summary

The review identified real production gaps around host-ingress fail-closed behavior,
Profile direction, Device firewall ownership, lifecycle, sysctls, bootstrap addressing and
production test/migration guidance.

The architecture is updated to **Draft 3**.

Two reviewer proposals are intentionally refined rather than copied literally:

1. the RPDB terminal action is scoped to **forwarded payload entering on host0**, not a
   global catch-all that would also break legitimate Device -> host/main-table traffic;
2. `Profile.direction` is not reduced to “routing/RPDB only”. It is ROU-generated
   **stateful transit policy**. The administrator firewall is the separate
   `Device.traffic_envelope`.

## B1 — unmatched host0 payload / RPDB catch-all

**ACCEPTED WITH REFINEMENT.**

Problem confirmed: forwarded traffic entering from host0 and matching no enabled Profile
must never fall through to main `default -> host0`.

Draft 3 now defines:

```text
iif host0, to <remote-prefix> -> Profile table
...
final iif host0 -> blackhole/unreachable
```

or a kernel-equivalent action.

The guard is intentionally **iif host0 scoped**. A global RPDB blackhole would also catch
Device -> host traffic and locally generated underlay traffic, which must retain access to
the namespace main table.

This closes the loop/fail-open gap without requiring conntrack marks merely for return
routing.

## B2/B3 — shared Device, Profile direction and firewall semantics

**ORIGINAL FINDING PARTLY ACCEPTED; FOLLOW-UP MODEL REFINED.**

The owner's clarification is accepted: the administrator's “today this tunnel may only
carry X / block port Y” policy is Device-scoped, not Profile-scoped.

The follow-up review then moved too far by defining `direction` as RPDB/routing semantics
only. That would make INBOUND/BIDIRECTIONAL ambiguous and would lose the already intended
NEW/ESTABLISHED meaning.

Draft 3 makes the separation explicit:

### Profile-direction guard

Generated by ROU, stateful:

- INVALID -> reject;
- ESTABLISHED,RELATED -> allow for an admitted flow;
- NEW -> allowed only from side(s) permitted by Profile direction.

Profile classification:

- host -> Device: remote **destination** prefix;
- Device -> host: remote **source** prefix + Device membership.

Therefore a shared Device can carry Profiles with different directions without an
interface-only ambiguity.

### Device traffic envelope

Administrator-authored firewall of the tunnel itself:

- from-device / to-device;
- source/destination IPv4 prefixes;
- TCP/UDP/ICMP;
- source/destination ports where applicable;
- allow/drop and terminal policy.

It applies uniformly to the Device and all Profiles sharing it.

The two layers are cumulative. Device envelope can restrict Profile traffic further but
cannot widen the generated direction guard.

## BIDIRECTIONAL semantics

**CLOSED.**

`destinations[]` is explicitly the set of remote/VPN-side prefixes.

The same prefix set is used:

- as destination classification host -> Device;
- as source classification Device -> host.

Thus BIDIRECTIONAL means either side may initiate a NEW flow involving that remote prefix;
it is not “dispatch without iif”.

Example on shared `oc-main`:

```text
corp     10.0.0.0/8       OUTBOUND
support  192.168.50.0/24  BIDIRECTIONAL
```

Host -> 10/8 NEW is allowed; 10/8 -> host NEW is rejected.
Both host -> 192.168.50/24 NEW and 192.168.50/24 -> host NEW are allowed, subject to the
same Device envelope.

## Return path

**CLOSED WITHOUT MANDATORY CONNMARK.**

Main table may retain `default -> host0`.

- Device -> host reply/INBOUND traffic uses main after stateful admission.
- host -> Device traffic to a remote prefix uses Profile dispatch/table.
- unmatched host0 forwarded traffic is caught by the terminal host0 action.

Conntrack marks remain an implementation option, not an architecture requirement.

## B4 — Device process lifecycle

**ACCEPTED.**

Draft 3 now states the production sequence:

1. `rou up` creates and verifies the fail-closed appliance;
2. VPN transports start independently inside that existing namespace;
3. DeviceEngine observes actual interfaces;
4. only verified bindings reach TrafficEngine.

Missing Device processes/interfaces are valid fail-closed operational state.

Normal Device lifecycle remains external to DeviceEngine. Namespace teardown remains
ROU-owned containment and must not leave residual processes/resources indefinitely.

## B5 — publication supervision

**ACCEPTED.**

Publication workers/sockets are explicitly supervised ROU-owned lifecycle state. A relay
may be in-process or a child, but unexpected loss must be observable and cannot silently
leave healthy status.

## B6 — namespace sysctls

**ACCEPTED.**

Draft 3 explicitly requires:

- forwarding off during fail-closed construction/repair;
- forwarding on only after verification;
- safe reverse-path filtering for ROU payload interfaces (strict rp_filter is forbidden;
  disabled is the default architecture policy);
- per-interface prerequisite verification before Device admission;
- IPv4-only payload contract / IPv6 forwarding disabled.

## B7 — link addressing

**ACCEPTED.**

`rouvpn0 <-> host0` addressing belongs to bootstrap/instance configuration, is stable
across ordinary restarts and changes only through explicit bootstrap configuration change.

## C1 — RPDB ordering

**CLARIFIED.**

The architecture now explicitly describes Profile dispatch as host0-scoped RPDB-style
rules ordered longest-prefix first, followed by terminal host0 fail-closed action.

## C3 — over-quota promotion order

**ACCEPTED, BUT NOT WITH ASCII SORTING.**

The suggested bytewise-ifname sort would reintroduce the ordering churn deliberately
removed earlier.

Draft 3 keeps survivor/creation semantics:

- committed first-observed candidate order is preserved;
- fresh candidates append in kernel snapshot order;
- ifindex is only a tie-break for candidates first observed in the same logical event;
- existing survivors are never reordered.

After restart, the current observation set starts a fresh process-local ordering.

## C4 — leading-digit IDs

**NO CHANGE; INTENTIONAL.**

The agreed grammar `[a-z0-9][a-z0-9-]*` remains.

Draft 3/config docs now explicitly state that IDs are opaque strings and must not be
reinterpreted as numbers, shell identifiers or raw systemd fragments.

## C7 — arbitrary publication translation

**UNCHANGED / STILL DEFERRED.**

EXP-011 proves same-port real protocol publication. Protocols that advertise endpoints may
need protocol-specific handling for arbitrary external/internal translation.

Human-facing publication grammar remains open.

## C8 — Device traffic envelope

**PROMOTED FROM ABSTRACT TO CAPABILITY CONTRACT.**

Exact TOML grammar remains open, but the architecture now fixes the minimum expressible
policy surface listed above.

The parser must continue rejecting invented envelope syntax until that grammar is agreed.

## C9 — over-quota traffic

**ACCEPTED.**

Matching but unbound/over-quota interfaces receive no payload routes and no payload ACCEPT
state. Inbound payload from them is rejected by owned transit policy.

## C10 — reverse-path / VPN->VPN loop concern

**RESOLVED BY DRAFT 3 ROUTING MODEL.**

Profile destination RPDB dispatch is scoped to `iif host0`; Device-originated payload is
not blindly re-dispatched by destination into the same VPN route.

Device-originated NEW traffic is first classified by remote source prefix + Device
membership and Profile direction, then routes toward host0 through main if admitted.

## C11 — publication INPUT

**ACCEPTED.**

Local INPUT policy must explicitly admit configured internal publication endpoints; there
is no blanket INPUT allow.

## C12 — disabled Device references

**CLARIFIED.**

A disabled Device may remain in `device_order` and consumes no metric range. If no
enabled/bound Device remains usable, the Profile is valid but operationally fail-closed.

## C13 — host source trust

**UNCHANGED.**

ROU intentionally does not decide which host/LAN sources may use it. BOU/manual host
policy owns source admission. ROU still enforces its own generated transit guard and Device
envelopes after traffic enters the appliance.

## D1 — v0 -> production migration

**ACCEPTED.**

Draft 3 now lists explicitly what is reusable evidence and what is rewritten/generalized.

## D2 — production testing strategy

**ACCEPTED.**

Four layers are documented:

1. rootless unit tests;
2. disposable-netns integration;
3. target-kernel experiments;
4. real-VPN live gates.

EXP-013 remains the current mandatory kernel/live gate for unavailable common-metric
materialization.

## D3 — scale limits

**ACCEPTED WITH REPRESENTABILITY MODEL.**

No arbitrary small N/M/K constants are invented.

Configuration must fit finite metric/RPDB/table/selector/publication/firewall resource
spaces and is rejected before mutation if not representable. Performance limits beyond
that are evidence-driven stress-test results, not guessed architecture constants.

## D4 — coexistence with host VPNs

**ACCEPTED.**

Host routing decides whether ROU outer transport itself traverses another host VPN and
whether payload enters ROU. ROU does not seize unrelated host VPN state.

## Result

The review does not invalidate NG1's topology or Device/Profile split. It exposed missing
production semantics around the boundary between routing, stateful flow direction and the
administrator's tunnel firewall.

Those semantics are now explicit in Architecture Draft 3.

**Remaining implementation gate:** EXP-013 must still close unavailable common-metric
kernel behavior before that TrafficEngine projector is implemented.
