# Ревью RC3 после терминологической правки

Проверил все заявленные в CHANGELOG терминологические правки и сверил с `PROJECT-CONVENTIONS.md`, `terms-and-definitions.md`, архитектурой и §26. Ниже — что действительно закрыто, что осталось несогласованным, и что нового появилось.

## A. Все заявленные терминологические правки подтверждены

### A1. `flock` — «без ожидания» вместо «non-blocking»

§5.2:
> Файл блокировки открывается с `O_NOFOLLOW`, режимом `0600`; daemon удерживает эксклюзивную блокировку `flock` в течение всего времени жизни процесса, а попытка её получения выполняется без ожидания.

Invariant 73:
> попытка её получения выполняется без ожидания.

✔ Это устраняет неоднозначность «exclusive non-blocking lock» — теперь явно, что **операция получения** не ждёт, а сама блокировка остаётся эксклюзивной на всё время жизни.

### A2. `runtime` разделён

- compound forms (`runtime-интерфейс`, `runtime-каталог`) — везде в документе корректно;
- «во время исполнения» — §4, §4.4, §7.1;
- «среда исполнения» — заявлена в CHANGELOG и в glossary как предпочтительная.

✔ Голых `runtime` в повествовательной прозе не осталось; всё, что осталось, — compound.

### A3. `firewall` восстановлен как термин

§2.3: `daemon-owned firewall`. §8.6, §23.5, §24.1: `firewall/NAT`. Glossary: `firewall = набор и политика установленных правил фильтрации пакетов; NAT — отдельная сущность; совокупное состояние — firewall/NAT`. ✔

При этом документ сохраняет «фильтрация» там, где речь о действии (§9 заголовок «Фильтрация и blackhole», §9.2 «Семантика INPUT»). Это **корректно** — glossary именно так разделяет.

### A4. `daemon-owned` восстановлен

§2.3, §4.4, §9.1, §23.5, invariant 12, 28, 68, 96. Glossary: формальный термин с обоснованием. ✔

### A5. `profile.routes` в §14

```text
managed_vpns = []               -> запрещено
profile.routes = []              -> запрещено
common_allowed_sources = []     -> разрешено
profile.allowed_sources = []    -> разрешено
peers = []                      -> разрешено
```

`profile.routes` теперь есть. ✔

Но есть небольшая непоследовательность: `profile.allowed_sources` с префиксом, а `peers` без. В контексте «для набора управляемых профилей принято» это читается как «per-profile default», но префикс `profile.` ставится не везде. Косметика.

## C. Оставшиеся терминологические несогласованности

### C1. «среда выполнения» vs «среда исполнения» (§4.3)

§4.3:
> при запуске это фатальный конфликт **среды выполнения**; сервис не включает пересылку;

Glossary явно говорит:
> `runtime` ... для временного смысла работы `vpn-gatewayd` предпочтительны «во время исполнения» и «**среда исполнения**».

И CHANGELOG:
> "среда исполнения" is preferred over "среда выполнения".

Но §4.3 использует «среда выполнения». Единственное вхождение в документе, но именно то, что CHANGELOG обещал исправить.

Правка: «конфликт среды исполнения».

### C2. «IPv6-пересылка» vs «IPv6 forwarding» (§2.6)

§2.6:
> Поэтому включённая **IPv6-пересылка** на хосте является неподдерживаемым обходным путём...

И через два абзаца в том же §2.6:
> ...способные разрешить **IPv6 forwarding** вопреки глобальному значению...

Invariant 10:
> ...**IPv6 forwarding** daemon не управляет...

Одна и та же сущность — «IPv6-пересылка» и «IPv6 forwarding». Glossary `forwarding` не содержит отдельной строки, но раздел §2.6 использует «IPv6-пересылка» как предпочтительную форму в заголовке. Стоит унифицировать на «IPv6-пересылка» (или на «IPv6 forwarding» везде, но первое звучит естественнее в русском тексте).

### C3. `peers = []` без префикса в §14 (уже отмечено)

Мелочь, но если хочется строгой консистентности с `profile.routes` и `profile.allowed_sources`, то `peers` тоже должен быть `profile.peers`.

### C4. «проекция конфигурации для исполнения» читается тяжело

§7.1:
> После успешной `cleanup()` daemon разбирает TOML-документ и строит проекцию конфигурации для исполнения
> только для профилей из `managed_vpns`.

«строит проекцию конфигурации для исполнения только для профилей» — читается как «только для профилей». Смысл — «проекция содержит только профили из managed_vpns». Альтернатива: «строит проекцию конфигурации для исполнения, содержащую только профили из `managed_vpns`». Мелочь.

## D. Новое поведение, которого не было в RC2.4.1 (не терминология, но появилось в этой версии)

Это не огрехи терминологической правки — это семантические изменения, часть baseline RC3 (см. `CHANGELOG RC3 semantic baseline`). Отмечаю, потому что для code-refactor они важны.

### D1. §9.2: INPUT без NEW ACCEPT для local_address

**Было в RC2.4.1 §9.1:**
```
-i profile.interface
-s profile.network
-d profile.local_address
ctstate NEW
    ACCEPT
```

**Стало в RC3 §9.2:**
```
-i <точный-интерфейс>
ctstate INVALID
    DROP

-i <точный-интерфейс>
ctstate ESTABLISHED,RELATED
    ACCEPT

-i <точный-интерфейс>
    REJECT --reject-with icmp-host-prohibited

RETURN
```

**NEW ACCEPT отсутствует.** Разрешён только ответный `ESTABLISHED,RELATED`.

§9.2 обосновывает:
> Таким образом, удалённая сторона VPN не может инициировать новое соединение с самим gateway через управляемый VPN-интерфейс. Разрешён только ответный `ESTABLISHED,RELATED`-трафик на соединения, инициированные локально самим хостом.

**Последствия, которые стоит явно осознать:**
- VPN peer не может пинговать `local_address` (ICMP NEW);
- VPN peer не может использовать gateway как DNS/NTP (UDP NEW);
- VPN peer не может подключиться к сервису, слушающему **на tunnel IP** (нестандартная, но возможная конфигурация — например, ocserv с `listen-host=172.20.130.1`).

Если сервисы VPN действительно слушают на физическом интерфейсе — всё работает. Если какой-то сервис слушает на tunnel IP — он будет недоступен. Это **сознательное изменение политики**, зафиксировано в `§24.1` «отсутствие прежнего общего NEW ACCEPT».

Стоит убедиться, что в целевом deployment ни один сервис не слушает на tunnel IP. Если слушает — добавить его в документированные исключения.

### D2. §2.6: IPv6 forwarding должен быть отключён

Новое требование. Логично (IPv4-only daemon не может фильтровать IPv6 transit). Но проверка «как минимум» включает только:

```
net.ipv6.conf.all.forwarding     = 0
net.ipv6.conf.default.forwarding = 0
```

Не проверяются `net.ipv6.conf.<iface>.forwarding` для существующих интерфейсов. А per-interface override в Linux переопределяет `all` для конкретного интерфейса.

§2.6 говорит:
> Если ядро предоставляет отдельные механизмы уровня отдельных интерфейсов, способные разрешить IPv6
> forwarding вопреки глобальному значению, они также должны быть выключены для всех
> существующих интерфейсов.

«должны быть выключены» — но кто и как это проверяет? Следующее предложение:
> Daemon не изменяет эти IPv6 sysctl ... Несоответствие при запуске является фатальной ошибкой.

Означает ли это, что **daemon проверяет per-interface**? Или что admin обязан это обеспечить, но daemon не проверяет?

Если daemon проверяет — надо явно сказать, и это окажется **не** «как минимум» из двух значений, а полная проверка per-interface (что потенциально дорого: чтение `net.ipv6.conf.<N>.forwarding` для каждого из N интерфейсов).

Если не проверяет — тогда per-interface override остаётся дырой в описанной политике, и §2.6 фактически требует от admin'а больше, чем daemon может проверить.

Стоит одну фразу добавить: проверяет ли daemon per-interface или ограничивается global+default, а per-interface — admin responsibility без runtime enforcement.

### D3. §8.6: isolation filter разрывает VPN-connected admin SSH

§23.5 явно подтверждает: в isolation filter `VPNG-<PROFILE>-INPUT` содержит только `RETURN`, а `VPNG-INPUT-GUARD` затем запрещает всё с managed селекторов.

Это значит: во время deny-first repair (шаги 2–7) **весь трафик с managed VPN interfaces блокируется, включая ESTABLISHED**. Если admin подключён через VPN (SSH на `local_address`), его сессия оборвётся на время repair-окна.

§8.6 подчёркивает:
> На время защитного барьера разрешающие правила всех управляемых профилей временно отсутствуют
> и вся управляемая пересылка запрещена, включая профили, чья привязка не менялась.

Это правильный fail-closed, но операционное последствие для VPN-connected admin'а нигде не задокументировано. Стоит добавить одну строку в §8.6 или §24: «isolation filter also blocks ESTABLISHED traffic from managed VPN interfaces; administrators connecting via VPN will lose SSH during the repair window».

### D4. §4.4: VPNG-INGRESS получил per-selector deny guards

Новое по сравнению с RC2.4.1 — теперь `VPNG-INGRESS` содержит не только exact blocks для ready bindings, но и **per-selector deny guards** в конце:

```
точный селектор:
    -i <точное-имя>
        REJECT --reject-with icmp-host-prohibited

префиксный селектор:
    -i prefix+
        REJECT --reject-with icmp-host-prohibited

RETURN
```

Это закрывает сценарий «новый непривязанный интерфейс семейства приходит в FORWARD и проваливается в foreign FORWARD ACCEPT» (§9.3 обоснование). Логически правильно, и в §24.1 отмечено:
> Отсутствие прежнего общего `NEW ACCEPT` в управляемой цепочке `INPUT`.

Хорошо.

Но: `VPNG-INGRESS` в **isolation filter** (§23.5) не содержит exact blocks, но содержит deny guards. Уточнено.

### D5. §9.1: prefix placement INPUT/FORWARD/POSTROUTING verified

Новое требование: daemon-owned prefix должен быть физически на позиции 1 во всех трёх встроенных цепочках. Если foreign rule вставлен перед — UNSAFE.

Это расширение по сравнению с RC2.4.1 (где проверялся только FORWARD). Логично, но раньше INPUT/POSTROUTING не проверялись. Стоит помнить при реализации compare.

### D6. §24.1: migration checklist

Отличное добавление. Полный список breaking changes для code-refactor. Ничего не пропущено из того, что я вижу. Хорошо, что явно указано: `ReconciliationPlan` и `DaemonState` **не обязаны** меняться.

## E. PROJECT-CONVENTIONS — быстрое ревью

Новый документ хорошо структурирован. Раздел 9 (приоритет источников) корректно ставит architecture выше review-response, а тот выше исторических review. §4 (терминологический проход не меняет архитектуру) — прямой ответ на риск, что правка языка случайно изменит семантику. §5 (исторический baseline экспериментов) — правильно, что experimental references не renumber'ятся. §6 (закрытый RC — только архив) — правильно.

Одна маленькая деталь: §3 говорит «по возможности оформлять отдельными коммитами» — «по возможности» смягчает правило. Если хотите строгости — «оформляются отдельными коммитами, кроме случаев, когда изменение атомарно требует обоих». Мелочь.
