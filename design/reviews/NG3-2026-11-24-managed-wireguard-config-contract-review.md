# NG3 2026-11-24 — ревью конфигурационного контракта управляемого WireGuard

**Единица ревью:** пользовательская конфигурация явно управляемого Device и граница секретов

**Требования:** `VPNG-U001-R1.R3.R7*`, `VPNG-U001-R1.R3.R8`  
**Архитектура:** A.002, A.012, D.001, D.002, D.003

## Вердикт

**PASS — КАНОНИЧЕСКИЙ КОНФИГУРАЦИОННЫЙ КОНТРАКТ ВЫБРАН; РАБОЧАЯ РЕАЛИЗАЦИЯ ЕЩЕ ОТСУТСТВУЕТ.**

## Findings и решения

### F1 — явное управление не требует отдельного флага

**Решение:** принято.

Наличие `[device.<id>.managed_vpn]` само является явной передачей управления VPN-GATE.
Отсутствие этой таблицы полностью сохраняет прежний внешний режим: VPN-GATE не создает,
не перезапускает и не останавливает такой VPN.

### F2 — у управляемого интерфейса один пользовательский источник истины

**Решение:** принято.

Для управляемого WireGuard точное имя интерфейса задается как
`managed_vpn.interface`. Поле `expected_interfaces` выводится из него как один точный
селектор и поэтому одновременно задаваться не может.

Это сохраняет прежнюю семантику привязки, но не заставляет пользователя повторять имя
создаваемого самим продуктом интерфейса.

### F3 — транспортные точки пиров также не дублируются

**Решение:** принято.

Для управляемого WireGuard разрешения UDP выводятся из `managed_vpn.peers[].endpoint`.
Поле `allow_vpn_client` для того же Device запрещено, поскольку иначе одна транспортная
точка имела бы два независимых пользовательских источника.

### F4 — порядок пиров является политикой пользователя

**Решение:** принято.

`managed_vpn.peers` — упорядоченный массив. Каждый пир имеет устойчивый `id`, публичный
ключ, точную транспортную точку и собственный `probe_target`. Отдельное числовое поле
приоритета не вводится.

### F5 — общие сети выводятся из уже существующей политики Profile

**Решение:** принято.

Общие изменяемые `AllowedIPs` не повторяются в каждом пире. Они выводятся из
`destinations` включенных Profiles, использующих этот Device. Тем самым пользователь не
задает одну и ту же удаленную сеть одновременно как политику Profile и как внутреннее
состояние WireGuard.

Все пиры одного текущего набора считаются альтернативами для полного выведенного набора
сетей. Различные наборы сетей для разных пиров требуют отдельного будущего расширения.

### F6 — проверочный /32 может находиться внутри широкого Profile

**Решение:** принято после исправления finding.

Первый вариант ошибочно запрещал пересечение `probe_target` с общим префиксом, что делало
невозможным `0.0.0.0/0`.

Исправленный контракт резервирует точный `probe_target/32` для технического наблюдения
конкретного пира. Такой /32 может быть более специфичным, чем общий префикс, включая полный
туннель. Пользователь не должен одновременно использовать этот точный адрес как отдельную
бизнес-цель Profile.

### F7 — секреты остаются вне основного TOML

**Решение:** принято.

Основная конфигурация содержит только абсолютные `private_key_file` и при необходимости
`preshared_key_file`. Значение секрета не входит в нормализованный контракт, отчет о
состоянии, диагностику или журнал.

Нижняя интеграция перед изменением VPN-экземпляра проверяет обычный файл без символической
ссылки, владельца читающего процесса и отсутствие доступа группы/остальных пользователей.
Изменение содержимого по прежнему пути образует новое желаемое поколение; для сравнения
допустим только необратимый криптографический хэш.

### F8 — конфигурационный контракт не выбирает диспетчер служб

**Решение:** принято.

Пользовательская грамматика не содержит systemd unit, команд запуска или путей создаваемых
служебных файлов. Эти детали остаются ниже D.001 и могут различаться между поддерживаемыми
VPN-интеграциями.

### F9 — действующие требования достаточны для этого выбора

**Решение:** принято.

Новых пользовательских обещаний сверх R7/R8 не потребовалось. Выбранная грамматика является
способом выразить уже принятое явное управление, набор альтернативных WireGuard-пиров и
существующие правила канонической конфигурации. Поэтому дерево требований в этом блоке не
расширяется.
