# Независимое ревью архитектуры RC2.6.3 по результатам EXP-004 и EXP-005

**Дата:** 2026-11-08  
**Архитектура:** RC2.6.3  
**Проверенный commit:** `352846369a6d6120b8e03720e640d92da12b5e96`  
**Основание:** `vpn-gateway-architecture-rc2.wip.md`, результаты EXP-004 и EXP-005

## Итоговый вердикт

**APPROVE WITH MINOR CORRECTIONS.**

RC2.6.3 в целом внутренне согласована и корректно учитывает фактические результаты EXP-004 и EXP-005.

Особенно удачно после EXP-005 устранена прежняя искусственная граница между:

```text
discovery selector
```

и

```text
iptables deny guard
```

Теперь `prefix+` описывает одно и то же пространство имён и для обнаружения интерфейса, и для предварительно установленной deny-only защиты. Это существенно упрощает модель, проверку пересечений селекторов и реализацию.

Архитектурных блокеров по результатам ревью не обнаружено.

## Соответствие экспериментам

| Эксперимент | Что фактически установлено | Отражение в RC2.6.3 | Оценка |
|---|---|---|---|
| EXP-004.1 | При `ip_forward=1` unmanaged FORWARD мог провалиться в базовый `FORWARD ACCEPT` | Введено полное владение IPv4 FORWARD и terminal `VPNG-FORWARD-DENY` | Полностью соответствует |
| EXP-004.2 | При исчезновении VPN dependent `proto 202` исчезает, blackhole `proto 201` остаётся и не допускает fallback через default route | Blackhole остаётся всегда desired; добавлены также независимые filter-level deny layers | Соответствует, архитектура осознанно усиливает защиту |
| EXP-004.3 | `ocserv device` задаёт семейство runtime-интерфейсов, а не стабильное точное имя | Введён runtime selector → concrete binding; RC2.6.3 использует `prefix+` | Соответствует; синтаксис `%` из EXP-004 позднее обоснованно superseded EXP-005 |
| EXP-004.4 | `iptables-restore --noflush` даёт атомарность в пределах одной таблицы при cleanup | Cleanup использует per-table transaction и явно не считает её cross-table atomic | Полностью соответствует |
| EXP-004.5 | Селективные `proto 201/202` queries изолируют cleanup от чужих сложных routes; поле protocol при этом может отсутствовать | Введён отдельный selective cleanup inventory с protocol из query context; обычный reconciliation остаётся strict | Полностью соответствует |
| EXP-005.1 | `-i vpns+` принимается и стабильно сохраняется `iptables-save` | `prefix+` закреплён как поддерживаемый deny-only interface-prefix contract | Полностью соответствует |
| EXP-005.2 | `vpns+` матчится на `vpns`, `vpns0`, `vpns1`, `vpnsX`, но не `other0` | Prefix selector резервирует весь textual namespace, включая bare prefix | Полностью соответствует |
| EXP-005.3 | Более ранний exact `vpns0 ACCEPT` имеет приоритет над последующим `vpns+ REJECT` | Exact binding-specific policy располагается перед deny-only family guard | Полностью соответствует |

## Найденные замечания

### 1. Устаревшая формулировка в §4.4 — исправить

В §4.4 всё ещё сказано, что:

> точная iptables encoding family guard должна быть подтверждена отдельным target experiment до реализации

После EXP-005 это уже неверно.

В других частях RC2.6.3 документ правильно говорит, что EXP-005 данный контракт подтвердил, а соответствующий пункт удалён из «Открытых решений».

Это единственное найденное прямое внутреннее противоречие.

Рекомендуемая формулировка:

> Для local INPUT используется заранее установленный deny-only selector guard `-i prefix+`, чей match scope и canonical `iptables-save` representation подтверждены EXP-005. Prefix/wildcard matching не используется для ACCEPT или NAT.

### 2. `iptables -i/-o` в §4.1 шире экспериментальных данных

RC2.6.3 говорит, что trailing `+` использует semantics interface operand `iptables -i/-o`.

EXP-005 непосредственно проверял `-i prefix+`, но не `-o prefix+`.

Практической проблемы здесь нет: wildcard `-o` архитектурой всё равно запрещён для ACCEPT/NAT, поэтому его поведение не используется как safety contract.

Для строгого соответствия экспериментальным данным лучше написать просто:

> совпадает с подтверждённой EXP-005 semantics `iptables -i prefix+`

и не заявлять проверенность `-o`, которая проекту всё равно не нужна.

### 3. Exact-selector grammar запрещает любой `+`, а обоснован только trailing `+`

Regex exact selector:

```text
[A-Za-z][A-Za-z0-9_.-]{0,14}
```

запрещает `+` вообще в любой позиции.

При этом текстовое обоснование говорит только о literal interface name, **заканчивающемся** на `+`: именно trailing `+` iptables воспринимает как prefix wildcard.

Это не safety defect, но контракт сейчас немного шире доказательства.

Есть два корректных варианта. Для простоты архитектуры предпочтителен первый:

**Вариант A:** явно зарезервировать символ `+` целиком для selector grammar и написать, что exact selectors с `+` в любой позиции vpn-gateway не поддерживает; trailing `+` дополнительно имеет специальную iptables-семантику.

**Вариант B:** разрешить `+` внутри exact имени, но не в конце. Это потребует отдельной target-проверки и практически ничего проекту не даёт.

Рекомендация: **вариант A**.

### 4. Исторический `%` в EXP-004 лучше оставить, но пометить как superseded

EXP-004.3 и overall decision совершенно правильно сохраняют первоначальное решение:

```text
vpns% -> ^vpns[0-9]+$
```

Переписывать эксперимент задним числом не следует: это исторический результат и принятое тогда архитектурное решение.

Но для читателя полезно после исходного текста добавить отдельное примечание:

> **Subsequent architecture note:** selector grammar, предложенная после EXP-004.3, superseded результатами EXP-005 и RC2.6.3. Фактический вывод EXP-004.3 — необходимость family selector; текущий синтаксис и match scope определены EXP-005.

Это сохранит историю без создания впечатления, что `%` всё ещё актуален.

## Что архитектура добавляет сверх непосредственных результатов экспериментов

Следующие решения не следует представлять как непосредственно «доказанные EXP-004/005»; это архитектурные меры, принятые на основании наблюдений:

- ambiguity (`>1` matching interface) трактуется как fail-closed;
- concrete identity включает `name + ifindex`;
- same-name recreation считается binding transition;
- selector namespace резервируется целиком за managed profile;
- runtime event/reaction window принимается в рамках trusted-host threat model;
- deny-first sequence `isolation -> NAT -> full filter -> routes` является архитектурным следствием динамического binding, а не экспериментальным результатом EXP-004/005;
- blackhole дополняется двумя независимыми filter-level deny layers.

Все эти решения согласуются с экспериментальными данными и друг с другом. Архитектура здесь корректно идёт дальше минимально доказанного поведения, а не противоречит ему.

## Термины, которые лучше оставить как идентификаторы

Имена kernel/API состояний и команд лучше не переводить внутри технических утверждений: `INPUT`, `FORWARD`, `ACCEPT`, `REJECT`, `DROP`, `MASQUERADE`, `SAFE`, `UNSAFE`, `UNKNOWN`, `ACTIVE`, `DEGRADED`, `ISOLATED`, `RouteSpec`, `ifindex`, `Netlink`, `iptables`, `systemd`.

В обычном русском тексте рядом с ними можно использовать перевод, например:

```text
состояние ISOLATED (изолирован)
фактическое состояние (ACTUAL)
требуемое состояние (DESIRED)
точная привязка (concrete binding)
цикл сверки (reconciliation pass)
```

Это уменьшит количество смешанных русско-английских конструкций, не теряя однозначной связи с именами enum/API.
