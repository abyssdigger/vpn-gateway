# Разбор ревью RC3 и аудита §26

**Дата:** 2026-11-09  
**Статус:** проектное решение по двум внешним ревью

## 1. Общая оценка

Оба документа полезны и должны храниться как самостоятельные review-артефакты без
редактирования исходных выводов.

Первое ревью хорошо проверяет, действительно ли RC3 закрывает проблемы RC2.4.1/RC2.5.1 и
следует ли новая архитектура из EXP-004/005. Второй документ полезен уже как чистовой аудит
нормативного блока §26 и ловит несколько мест, где краткий инвариант формально слабее либо
двусмысленнее основного текста.

При этом принимать замечания механически целиком не следует: есть один новый реальный
дефект политики, несколько точных уточнений, один неверный вывод про NAT на стадии
изоляции и несколько «пробелов», которые архитектура уже фактически закрывает.

## 2. FORWARD ACCEPT без `-i`: замечание принимается сильнее, чем предложено в ревью

Сценарий из первого ревью реален:

```text
vpns1 (новый, daemon ещё не увидел)
    ↓ spoofed allowed source
protected destination
    ↓ kernel route
vpns0 (старый BOUND)
```

Текущий `VPNG-INGRESS` знает только точную готовую привязку `vpns0`. Новый `vpns1`
возвращается из этой цепочки. Далее разрешающее правило профиля:

```text
-s source -d route -o vpns0 -> ACCEPT
```

может принять пакет, потому что входной интерфейс в нём не ограничен.

Оставлять это как просто документированное окно реакции не стоит. У архитектуры уже есть
проверенный EXP-005 примитив, которым это можно закрыть: запрещающее сопоставление по
селектору после точных правил готовой привязки.

`VPNG-INGRESS` должен стать аналогом INPUT-модели:

```text
для каждого ready concrete binding:
    -i concrete INVALID                 -> DROP
    -i concrete ESTABLISHED,RELATED     -> ACCEPT
    -i concrete                         -> REJECT

после exact blocks:
    -i <managed exact selector>         -> REJECT
    -i <managed prefix+ selector>       -> REJECT

RETURN
```

Точный готовый интерфейс завершается раньше соответствующего семейного запрета, а новый
`vpns1` будет остановлен до попадания в профильную FORWARD-цепочку.

Свойства архитектуры при этом сохраняются:

- сопоставление по префиксу остаётся только запрещающим;
- `ACCEPT`, NAT и маршруты используют только точное имя жесткой привязки;
- поведение exact-before-prefix уже подтверждено EXP-005.

Отдельный эксперимент до рефакторинга кода здесь не требуется; негативный сценарий нужно
включить в будущую end-to-end проверку восстановления.

Неустранимым остаётся same-name/new-ifindex race: iptables сопоставляет интерфейс по имени
и не способен задним числом отличить старый `vpns0` от пересозданного `vpns0`. Это уже
честно заявленная граница модели угроз.

## 3. Стороннее FORWARD-правило перед daemon-owned префиксом

Замечание принимается.

Нормативный текст должен различать:

1. **проверенное требуемое состояние** — daemon-owned префикс физически начинается с
   позиции 1, `VPNG-FORWARD-DENY` завершает его, сторонние правила расположены после него
   и недостижимы;
2. **окно рассогласования** — внешний менеджер может вставить правило перед префиксом, и до
   следующего цикла согласования оно временно получает влияние.

Второе состояние является `UNSAFE`.

Восстановление с первоначальным запретом должно заново материализовать daemon-owned
префикс с позиции 1. Стороннее правило при этом не удаляется: оно физически сдвигается за
`VPNG-FORWARD-DENY`.

Так формулировка не создаёт ложного впечатления, будто daemon имеет абсолютную власть над
цепочкой в любой наносекунде, и одновременно сохраняет поддерживаемую модель coexistence.

Постоянное конкурентное переписывание префикса внешним менеджером остаётся unsupported.

## 4. Изолирующий фильтр и глобальный краткий outage

Замечание о полном кратком outage принимается полностью.

Изолирующий фильтр — не точечный ремонт одного профиля, а полная промежуточная
daemon-owned политика таблицы filter. Следовательно, при его применении временно
исчезают разрешающие правила **всех** профилей, зависящие от привязки.

Это надо описать как намеренную цену общего fail-closed barrier:

- весь управляемый forwarding на короткое время запрещён;
- это касается и профилей, чья привязка не менялась;
- реализация не должна пытаться «оптимизировать» barrier сохранением разрешающих правил
  незатронутых профилей без отдельного изменения архитектуры.

Такое уточнение важно и оператору, и реализатору.

## 5. Точная структура profile chains на стадии изоляции

Для filter замечание принимается.

Профильная INPUT-цепочка в изолирующем фильтре:

```text
VPNG-<PROFILE>-INPUT:
    RETURN
```

Все точные правила, зависящие от привязки, отсутствуют. Входящий трафик управляемых
селекторов закрывается `VPNG-INPUT-GUARD`.

Профильная FORWARD-цепочка:

```text
VPNG-<PROFILE>-FORWARD:
    для каждого protected destination:
        -d route -> REJECT

    RETURN
```

Там нет разрешающих и иных правил, зависящих от жесткой привязки.

А вот предложение первого ревью:

```text
profile NAT chains contain only RETURN
```

не должно становиться частью определения isolation filter.

`desired_isolation_filter(config)` — именно **filter-only barrier**. Последовательность
§8.6 намеренно такова:

```text
isolation filter
verify
desired NAT
verify
full filter
verify
routes
verify
```

На стадии изоляции ранее применённый NAT может ещё физически существовать в ядре. Это
безопасно, потому что уже проверенный filter barrier не пропускает управляемый forwarding.
Следующим шагом NAT приводится к требуемому состоянию текущего snapshot и проверяется.

Поэтому нормативное уточнение должно быть обратным:

> применение изолирующего фильтра не изменяет NAT; ранее применённый NAT может временно
> оставаться за проверенным запрещающим барьером до применения и проверки требуемого NAT.

Это важно, чтобы реализация случайно не превратила filter barrier в дополнительную
независимую NAT-cleanup транзакцию.

## 6. Readiness transition — настоящее недоопределение RC3

Здесь ревью попало в существенное место.

Сейчас явно описаны смены привязки:

```text
BOUND -> ABSENT
ABSENT -> BOUND
BOUND(A) -> BOUND(B)
to/from AMBIGUOUS
```

Но переход:

```text
BOUND + expected local IPv4 present
        ↓
BOUND + expected local IPv4 absent
```

не является сменой привязки. При этом он меняет требуемую политику:

```text
INPUT/FORWARD ACCEPT  исчезают
MASQUERADE            исчезает
proto 202 UNICAST     исчезают
```

На предположение, что старые правила в таком окне обязательно inert, полагаться не стоит.

Поэтому вводится более общее понятие:

```text
переход, меняющий политику =
    смена привязки
    ИЛИ
    смена готовности
```

Оба случая должны идти через одинаковый fail-closed порядок:

```text
best-effort ip_forward=0
-> isolation filter
-> verify barrier
-> desired NAT
-> verify
-> full filter
-> verify
-> routes
-> verify
-> restore forwarding
```

Process-local committed state логично расширить с «последней подтверждённой привязки» до
«последней подтверждённой привязки и готовности», чтобы изменение обнаруживалось явно до
изменения policy.

Это одно из обязательных изменений до начала code-refactor.

## 7. Окно реакции и периодический цикл согласования

Замечание принимается, но формулировка должна быть аккуратной.

Нельзя писать, что окно реакции **гарантированно** ограничено 60 секундами. Если event loop
завис, периодический timer также не выполнится.

Корректное утверждение:

- Netlink остаётся основным wakeup;
- если своевременный Netlink wakeup потерян или не обработан, периодический цикл
  согласования является fallback detection mechanism;
- при работающем цикле обработки событий следующая полная пересверка наступает не позже
  следующего `reconcile_interval`;
- `reconcile_interval` имеет диапазон 1–60 секунд.

## 8. Исторические номера инвариантов в EXP-001

Замечание принимается, но историческую запись нельзя переписывать под RC3.

Правильнее добавить общее правило в шапку журнала экспериментов:

> номера разделов и инвариантов внутри исторической experiment record относятся к
> `Architecture baseline`, указанному в самой записи, и не перенумеровываются задним числом
> при выпуске следующих RC.

Это решает проблему не только EXP-001, но и будущего чтения всего журнала.

## 9. Breaking changes к code-refactor

Нужен явный migration checklist, но не все сущности из первого ревью обязаны менять
публичный контракт.

Точно меняются или вводятся:

```text
InterfaceSelector
InterfaceRecord / ifindex
InterfaceResolution
KernelInterface.list_interface_ipv4 -> list_interfaces
VpnProfile: больше нет полного CONFIGURED RouteSpec set
ReconciliationSnapshot
full/isolation policy builder
committed binding/readiness state
RouteSpec.interface: только exact runtime name
```

`ReconciliationPlan` вполне может сохранить нынешнюю модель `adds/deletes/replaces`.

`DaemonState` также не обязан менять enum; может измениться только семантика переходов.

После архивирования RC2 regression tests находятся уже в:

```text
design/RC2/code/python/tests/
```

и именно на этот путь должен ссылаться migration checklist RC3.

## 10. Selector overlap и interface validation

Эти части ревью подтверждают текущую архитектуру, а не требуют её изменения.

Пересечение селекторов задаётся пересечением множеств возможных concrete names:

```text
vpns0 + vpns0+ -> overlap
a     + ab+    -> disjoint
```

Это корректная модель.

Для префиксного селектора ограничение длины 1..14 также согласовано с общим пределом
Linux ifname: плюс является оператором грамматики и доводит общую длину selector string до
максимальных 15 символов.

В реализации стоит только обеспечить явное сообщение `--check-config`, называющее оба
конфликтующих профиля и оба селектора.

## 11. Runtime exact `proto kernel` collision

На старте это уже fatal.

Для RUN семантика тоже должна быть явно fail-closed:

- `proto kernel` никогда не удаляется и не заменяется;
- exact collision на protected prefix делает route plan неприемлемым;
- профиль не получает desired owned route;
- если firewall policy при этом проверена как безопасная, lifecycle переходит в
  `DEGRADED`, сохраняя deny/blackhole semantics настолько, насколько это возможно;
- kernel route не принимается как OWNED.

Это полезно явно записать в §23.6.

## 12. Аудит §26: A1–A6

### A1 / invariant 17

Формально текущий текст уже говорит:

```text
RouteSpec / iptables ACCEPT / NAT kernel operand
```

а не «любой kernel operand», поэтому прямое логическое противоречие с deny-only
`-i prefix+ -j REJECT` слабее, чем утверждает аудит.

Но формулировка действительно позволяет неверное прочтение и должна стать однозначной:

- префиксный селектор запрещён в `RouteSpec`;
- запрещён в **разрешающих** interface conditions `ACCEPT` и NAT;
- `-i prefix+` допускается только в проверенных deny-only guards.

Замечание принимается по смыслу.

### A2 / invariant 11

Полностью принимается.

Владение `ip_forward` и владение terminal FORWARD verdict — два разных свойства.
Архитектура сознательно связывает их обязательством, а не выводит одно из другого.

### A3 / invariant 12

Полностью принимается.

Инвариант должен различать verified state и drift window с foreign rule перед prefix.

### A4 / invariant 57

Полностью принимается.

Нужно различать:

- pass-level inability to read/parse/resolve policy-critical interface inventory ->
  `ISOLATED`;
- штатный per-profile result `AMBIGUOUS` -> profile FAIL / `DEGRADED`.

### A5 / invariants 88–89

Это один из лучших catches аудита.

RC3 сохранил требования:

```text
programming errors are not masked
machine reason identity is stable
```

но из внутренней модели исчезла сущность, которая эти требования объясняла.

Диагностическую модель следует вернуть в §23 как абстрактный архитектурный контракт:

```text
DiagnosticFact:
    code   -> стабильный машинный идентификатор причины
    detail -> необязательный человекочитаемый контекст
```

Точное Python-имя класса не нормативно. Нормативно:

- стабильный enum-like reason code;
- `detail` не участвует в identity/dedup;
- expected operational failures переводятся в известные codes на orchestration boundary;
- programming exceptions и нарушения внутренних контрактов не превращаются в обычный
  `UNKNOWN`/`DEGRADED`.

Это хорошо переносится в Rust.

### A6 / invariant 93

Принимается.

Duplicate name с conflicting ifindex должен явно означать `KernelError` адаптера, а не
«invalid state» без указанного результата.

## 13. Аудит §26: пробелы B

### B1 — readiness transition

Принимается через общее понятие policy-changing transition. Это существенное изменение.

### B2 — OUTPUT untouched

Принимается.

Нужна явная гарантия:

```text
vpn-gatewayd не создаёт, не изменяет, не переставляет и не удаляет OUTPUT rules.
```

OUTPUT остаётся политикой администратора хоста.

### B3 — единая модель full/isolation

Как отдельный пробел не принимается: §23.5 уже буквально говорит, что обе формы выводятся
из одной модели policy, а invariant 53 фиксирует единый источник.

Но invariant 53 стоит сделать явнее, назвав обе формы:

```text
desired_full_policy
desired_isolation_filter
```

### B4 — foreign POSTROUTING preservation

Принимается.

Это третий тип coexistence, отличающийся от INPUT и FORWARD:

- daemon profile NAT chains возвращают управление через `RETURN` на non-match;
- сторонние POSTROUTING rules физически сохраняются;
- они остаются достижимыми для неуправляемого egress;
- daemon не получает terminal ownership над произвольным NAT хоста.

### B5 — OWNED/binding process-local

Основной текст уже это описывает, поэтому отдельный новый invariant не обязателен.

Лучше расширить invariant 50:

- OWNED и committed binding/readiness state process-local;
- не переживают restart;
- новый процесс начинает с пустого process-local ownership;
- изменяются только после verify.

### B6 — reconcile_interval range

Принимается как расширение invariant 40:

```text
reconcile_interval range [1.0, 60.0], zero forbidden
```

## 14. Дубли и косметика C

### 42/43

Оставить оба.

42 описывает происхождение desired RouteSpec, 43 отдельно запрещает некорректное значение
`RouteSpec.interface`. Это полезная избыточность.

### 44/45

Оставить оба.

44 выделяет safety-critical property «BLACKHOLE first», 45 фиксирует полный порядок
исполнителя маршрутов.

### 30

Стоит уточнить «для каждого отдельного protected-destination block», чтобы текст нельзя
было прочитать как один общий REJECT в конце цепочки.

### 63/64

Оставить: это не дубли, а определение ACTIVE и классификация остальных состояний.

### Structural chain enumeration

Не добавлять отдельный invariant со вторым полным списком chains. Нормативным местом
топологии должен оставаться §9.1, иначе появятся два списка, способные разойтись.

## 15. Итоговый набор обязательных изменений до code-refactor

До начала реальных работ по RC3 следует закрыть:

1. deny-only selector guard для входящего FORWARD-трафика в `VPNG-INGRESS`;
2. readiness transition как policy-changing transition наравне с binding transition;
3. точную структуру profile INPUT/FORWARD chains в isolation filter;
4. явную глобальную краткую потерю managed forwarding на стадии isolation barrier;
5. verified FORWARD ownership vs foreign pre-prefix drift window;
6. стабильную machine-readable diagnostic reason model;
7. уточнения invariants 11, 12, 17, 30, 40, 50, 53, 57, 93;
8. явную untouched semantics для OUTPUT;
9. preservation semantics для foreign POSTROUTING;
10. historical-baseline note в журнале экспериментов;
11. RC2.5.1 -> RC3 implementation migration checklist;
12. явный runtime fail-closed результат exact collision с `proto kernel`.

После этих правок ещё один полный общий архитектурный review не нужен. Имеет смысл
попросить короткий re-review по закрытию конкретных замечаний и повторный чистовой аудит
§26. После этого архитектуру можно замораживать и переходить к реализации.
